# Changelog

All notable changes to Tenko DDI are recorded here, one section per release, in the format of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) 1.1.0 with Semantic Versioning 2.0.0. One addition: a `### Action required` subsection under a release lists what an administrator must do before or after upgrading to it. Every change to `crates/**` or `ui/src/**` adds an entry under Unreleased; CI checks this with `scripts/changelog.mjs`.

## [Unreleased]

## [0.0.7] - 2026-10-25

### Added

- Prefix delegation in the API, the web UI and the Kea export (Phase 3, DHCP-09, DHCP-10): the IPAM range form makes a delegation pool on an IPv6 network with its delegated length, and the pools tab of a DHCPv6 scope lists and adds delegation pools with their prefixes and bound prefixes (`role`, `delegated_len` and sizes in prefixes on `GET /api/v1/dhcp/pools`, a `pd` block on the scope's utilization); the lease list shows a delegated prefix as `prefix/length` with the router's address lease (`address_lease`), filters by what a lease holds (`kind=na|pd`, `--kind` on `tenko dhcp lease list`) and finds leases by an IPv6 prefix; the history's MAC filter finds DHCPv6 clients behind an RFC 6939 relay whatever their DUID; `GET /api/v1/nodes/{id}/dhcp` reports the router advertisement check (`ra`) and the server DUID, which the leases page and the Nodes page show with the `dhcp.ra.*` findings in words; the Kea export writes `pd-pools` and the delegated prefixes in `kea-leases6.csv`, and `server-id` from the role's DUID when the role runs in the process.
- The columns of the lists can be resized: every data grid (addresses, hosts, a network's addresses, DNS zones and records, DHCP scopes, leases and history, the audit log, nodes, proposals and the rest) and the DNS query log have a handle on the trailing edge of each column header that is dragged with the mouse, a pen or a finger, fitted to the content in view with a double click or a double tap, or moved in steps with the arrow keys once it has the focus (Shift for larger steps, Enter or Escape to return). The other columns keep their widths, the last one takes the remaining space and a wider set of columns scrolls sideways. The widths are kept per list and per user in the browser and come back on the next visit; "Reset column widths" in the list's column menu, or under a list that has none, drops them, and the phone layout ignores them.
- DHCPv6 prefix delegation and the router advertisement check (Phase 3, DHCP-09, DHCP-10): an IPAM range of the new role `dhcp_pd_pool` with a `delegated_len` (longer than its network's length, at most 64, on that length's boundaries) is a delegation pool of the scope on its network and of the scopes of that scope's shared network; a requesting router's `IA_PD` gets a prefix of that length (its own bound prefix, a free hinted one, else one of the pool; `NoPrefixAvail` when none is free), committed as a lease of kind `pd` before the REPLY, renewed, rebound, released and expired like an address, shown in IPAM as a `network` fact of the prefix and never given a DNS name. With the probe role in the process the dhcp role hears the router advertisements of its links (a raw ICMPv6 socket, `CAP_NET_RAW` of `deploy/systemd/probe.conf`) and the health view says when a link with a DHCPv6 scope gets advertisements without the M or O flag (`dhcp.ra.flags_off`), with O but not M (`dhcp.ra.other_only`), when M is set on a link without a scope (`dhcp.ra.managed_without_scope`), and when the check cannot run (`dhcp.ra.unchecked`); DHCPv6 never sets a default route, which stays with the advertisements. The data format goes to 5 (an empty migration at the first start): a binary of format 4 refuses the data directory afterwards, since it cannot read the new range role.
- The Kea export covers DHCPv6 (MIG-16): `tenko dhcp export --format kea --out <dir>` also writes `kea-dhcp6.json` for Kea 2.6's `kea-dhcp6` when a scope is on an IPv6 prefix, and with `--leases` the DHCPv6 lease file `kea-leases6.csv`, so a DHCPv6 server can move to Kea with its leases. The scopes become `subnet6` and `shared-networks` with their pools, reservations by DUID or MAC address, options at every level (23, 24 and 56 as the server sends them), the lifetimes, rapid commit and the relay Interface-Id; the MAC filters, the server DUID and the DDNS settings carry over, and the loss report names what Kea does not express the same way (classes and policies apply to DHCPv4 only, delegated prefixes are not exported yet). `GET /api/v1/dhcp/export` answers with `dhcp6` and `leases6_csv` beside the DHCPv4 parts.
- DHCPv6 in the API, the command line and the web UI (DHCP-09, DHCP-11): the lease list and the history show both families with a family and a DUID filter (`family` and `duid` on `GET /api/v1/dhcp/leases` and `/dhcp/history`, `--family` and `--duid` on `tenko dhcp lease list` and `tenko dhcp history`), each lease with its MAC address where it is known, a DHCPv6 lease with its DUID and IAID, and a link to the client's lease of the other family with the same MAC address (`peer`); a DHCPv6 lease is shown and released by its IPv6 address; the history merges both tables newest first. A DHCPv6 scope's utilization counts its DHCPv6 leases (`family`, and `pool_bits` for a pool too large to count), its page has a DHCPv6 tab for the preferred lifetime, Rapid Commit and the relay Interface-Id and leaves out the DHCPv4-only parts with a line saying why, and its options tab edits `dhcp6` options with the DHCPv6 catalog, which `GET /api/v1/dhcp/option-catalog` now serves beside the DHCPv4 one (`space` keeps one). The host page lists a reserved host's DHCPv6 reservations, keyed by the interface's DUID or MAC address, with their leases; `GET /api/v1/nodes/{id}/dhcp` reports `listeners6`, `scopes6` and `leases6`; the start page's DHCP tiles count both families. Lease and history items replace the flattened DHCPv4 lease row with one shape for both families: `client` is present on DHCPv4 items only, and a lease or history cursor of an earlier release is refused. See `docs/dhcp.md` sections 7 and 19.8.

### Changed

- The Connect panel of the host page offers RDP, SSH and the web interface from the ports the probe saw open (the `services` fact of each address): the RDP and SSH buttons are enabled for a port seen open and disabled, with the time of the last scan in the tooltip, for one that was not; an address no scan has reached shows no button, and a host none of whose addresses has a fact says so in one line with a link to the nodes page. The port fields start with the open ports found (2222 for SSH when 22 is closed and 2222 open), and the open ports with their TLS mark and the time of the last scan are listed under the buttons. A "Web interface" link opens HTTPS (the address whose 443 answered TLS first) or HTTP in a new tab, by the DNS name where the address has one, with 8080, 8443, 8006, 8123 and 9443 under "More" when the fact holds them. See `docs/secrets.md` section 5.

### Fixed

- The 5-second bars of the start page's Cache hit ratio and Answers tiles keep their place: the buckets were counted back from the newest sample, so each new second moved every edge by one sample and every bar was recomputed from other samples. A bar is now the bucket `floor(t / 5 s)` of the samples' own times, the chart shows six completed buckets and the one in progress (lighter), and it shifts one step only when a bucket completes. The percentage and the RCODE rates beside the bars are taken over the same completed buckets (a mean per second, with two decimals below one), so a quiet tile no longer reads 0/s beside bars of answers.
- The Kea export of a configuration without classes, filters or boot options starts Kea: it wrote an empty `client-classes` list, which `kea-dhcp4` 2.6 refuses as a syntax error; the list is now left out when it is empty.
- The row menu of an address has its final items the first time it opens: the address lists and a network's address grid show their rows once the DHCP scopes that decide "Reserve in DHCP" have been read (or have failed to read), instead of adding or leaving out the item when the answer arrives; the tests wait for that state instead of assuming it.

### Action required

- This release raises the data format from 4 to 5 (a delegation pool is an IPAM range of a new role). The update migrates the data directory on the first start and a binary of 0.0.6 or earlier then refuses it, so take a backup of the data directory before the update (`tenko backup`, or the node's own backup page) if you may want to go back; the restore path of `docs/upgrades.md` brings a 0.0.6 binary back on that backup.

## [0.0.6] - 2026-10-25

### Added

- A node says per role whether the machine is prepared for it (OPS-01): the installer records what it prepared in `prepared-roles` beside `tenko.toml` (the roles, the systemd drop-ins, the ports, the host firewall), the server reads it at start and reports it in `GET /api/v1/system/status` (`node.prepared`) and `GET /api/v1/nodes/{id}/roles` (`prepared`, with what is missing and the installer command that prepares it), and `tenko node roles show` prints it. At start the server checks that `CAP_NET_RAW` is in its bounding and effective sets when the probe role or the dhcp role's direct mode runs; the health row `node.roles.privileges` names the role, the capability and the installer command, and `node.roles.unprepared` names a running role the installer did not prepare. The roles editor on the Nodes page tags each role of this controller Prepared or Not prepared; an administrator may still switch on an unprepared role, and the editor and its confirmation name what is missing and the exact installer command that prepares it. The page shows both health rows.

- An address is reserved in DHCP from where you stand (DHCP-01, IPAM-18, IPAM-23): Reserve in DHCP on the IPAM address page and in the row menus of the address list and of a network's addresses, and Reserve this address in the lease list's row menu, for an address in a network with a DHCP scope and a principal who may write IPAM there and DHCP. The dialog prefills the host (the address's, the lease client's, or a new one named after the DNS name or the lease's host name), the interface, the MAC address (from the interface, the lease or discovery) and the client identifier, says in sentences what the save changes and whether the scope serves it, refuses an address inside a DHCP pool and offers, from a lease, the next free address outside the pools, and afterwards shows the reservation with links to the scope and the host; the address page of a reserved host shows its reservation, and a lease that is its client's reservation says Reserved with a link to the host. `POST /api/v1/addresses/{id}/reserve` and `POST /api/v1/addresses/reserve` (by value, creating the address) write the host, the interface and the address in one batch with one audit record `ipam.address.reserve`, refuse a network without a scope (`dhcp.scope.not_found`), an interface without identity (`dhcp.reservation.no_identity`) and an address or client another reserved host holds (`dhcp.reservation.conflict`) without writing anything, and ask for exactly the IPAM writes they make; `tenko ipam address reserve` calls them. See `docs/dhcp.md` section 12.1.

- DHCPv6 in the dhcp role (Phase 3, DHCP-09, DHCP-11, DHCP-13): a `[dhcp] listen` entry with an IPv6 address answers on UDP 547 (`relay` on the unicast address for relay agents, `direct` on an interface with the multicast group `ff02::1:2`), and a scope on an IPv6 prefix hands out addresses of its IPAM `dhcp_pool` ranges in `IA_NA` (RFC 8415): SOLICIT, ADVERTISE, REQUEST, RENEW, REBIND, CONFIRM, RELEASE, DECLINE and INFORMATION-REQUEST, Rapid Commit where the scope allows it (`v6.rapid_commit`), relay chains up to eight deep with the scope chosen by the relay's Interface-Id (`v6.interface_id`) or the link address of the innermost relay that has one (RFC 6221), the DNS servers and search list of RFC 3646 and the NTP servers of RFC 5908 from the `dhcp6` option sets, and reservations of IPAM hosts of mode `reserved` by the interface's DUID or MAC address. Every binding is a row of `dhcp.leases6` committed before the REPLY, with its history in `dhcp.history6` and its expiry by `dhcp.expiry6`; the client's link-layer address of RFC 6939 (or its DUID-LLT or DUID-LL) goes on the lease and on the IPAM address fact, so a device's DHCPv4 and DHCPv6 addresses show under one MAC, and the name of RFC 4704 gets its AAAA, DHCID and `ip6.arpa` PTR records in Tenko's zones. `[dhcp.v6]` sets the ports and the server's DUID, scope items say their `family`, and `tenko_dhcp_packets_total` counts `family="v6"`. The lease and history routes and the UI show DHCPv6 leases in a later release. See `docs/dhcp.md` section 19.

### Changed

- The Linux installer asks for the security profile first and for the roles only under the Hardened profile: outside Hardened it prepares the machine for every role (the drop-ins `probe.conf` and `dhcp-direct.conf`, the roles' ports on firewalld or ufw when one is active, systemd-resolved's stub listener off for the dns role on every address) and the node starts with every role, which the operator trims on the Nodes page; `--roles` still names the starting set, and a port another program holds leaves a defaulted role out of it with a warning instead of stopping. Under Hardened only the chosen roles are prepared. A dependency check lists what the prepared roles miss and asks once whether to set it up (yes by default, `--yes` answers yes); `install.sh --check` only reports (exit 11 when something is missing) and `install.sh --prepare` sets up what is missing and nothing else. `--keep-resolved-stub` is remembered for later runs, and `--uninstall` closes the ports the installer opened. The Windows MSI adds the DNS and DHCP firewall rules (now with UDP 547 for DHCPv6) for every role outside Hardened and records `prepared-roles` too.

### Fixed

- The scan configuration of the controller's own probe role is reachable without typing its address: `GET /api/v1/system/status` lists the `probe` role when the controller runs it (it listed only `controller`, `dns` and `dhcp`, so the link in the section "This controller" of the Nodes page never showed), and that section links to **Scan configuration** whenever the stored role set or the running set has the probe role, with a line saying to switch the role on otherwise. Every row of the Probes table on the Scans page, the controller's own included, has a **Scan configuration** link, the "no probe covers this target" error of Scan now links to each probe instead of the Nodes page when there are several, and the page of the controller's own probe leads back to the Nodes page. See `docs/scanning.md` section 7.5.

### Action required

- A rerun of `install.sh` on a node installed before 0.0.6 now prepares the machine for every role unless its profile is Hardened: it adds the drop-ins `probe.conf` and `dhcp-direct.conf`, opens ports 53, 67 and 547 on firewalld or ufw when one is active, and turns systemd-resolved's stub listener off for the dns role. The dependency check asks once before it changes anything; answer no, or run `install.sh --check` first, to see what it would do. The running role set is not changed by a rerun; a fresh install outside Hardened starts every role, which the Nodes page trims.

## [0.0.5] - 2026-10-24

### Added

- The VLANs of a network controller arrive in IPAM: every network of a controller becomes a `network` fact (name, subnet, VLAN id, DHCP mode, management flag), and the reconciler opens "VLAN discovered" proposals for a tagged network whose VLAN IPAM does not have and "Prefix VLAN differs" proposals for a prefix whose range equals the network's subnet but is not linked to that VLAN, each approved or rejected on the Discovery page with its own kind filter (the two approve in either order); the topology lists the controllers' networks with VLAN, subnet, DHCP and management under the controller lines and in the panel of a controller's gateway; and the UniFi connector with only an API key reads the networks of Network 10.0 and later through the Integration API, placing each client in the network whose subnet holds its address. See `docs/reconciliation.md` section 4.10 and `docs/connectors-unifi.md` section 2.3.
- An administrator or operator approves or rejects many proposals at once: the proposal inbox has the grid's check box column, select all and an action bar with "Approve N" and "Reject N" (one confirmation naming the count and the kinds, one reason dialog, one toast with the counts and a panel of the skipped proposals with their reasons and a button to keep them selected), and `POST /api/v1/proposals/approve` and `POST /api/v1/proposals/reject` take up to 500 identifiers and decide each as the single route does, independently, answering the outcome of every one (`approved`, `rejected` or `skipped` with the single route's code and message) and the counts, with the audit records of the single decisions and none for the batch.
- The Certificates page under Settings (`/settings/certificates`) and `GET /api/v1/system/tls` show the TLS mode, the certificate the listener serves (subject, names, issuer, validity, days left, chain length, SHA-256 fingerprint, when it was loaded), the imported files, the internal CA root with its download, or the trusted proxies, and the status warning `sys.tls.certificate_pending`; `[tls] accept_external_replacement` decides per security profile whether a certificate replaced in the imported files is loaded while the node runs (on under Lab and Home, off under Standard unless set, refused under Hardened), and where it is off the newer certificate is pending until the next restart; `docs/certificates.md` has the runbook for an OPNsense ACME client that uploads renewed certificates over SFTP to a chrooted, shell-less account.
- The recursive resolver asks each server only for the labels it needs and answers names it can prove absent from its cache (DNS-34): QNAME minimisation of RFC 9156 in the relaxed mode (`[dns.recursion] qname_minimisation`: `relaxed` by default, `strict` or `off`; a server that answers NXDOMAIN or fails on a shorter name is asked the full name, and its zone is asked full names for the infrastructure TTL), and a denial cache of RFC 8198 and RFC 8020 (`aggressive_nsec`, `denial_entries`): the validated NSEC and NSEC3 records answer NXDOMAIN, NODATA and wildcard names on the query path without a query to an authority, with the proofs and AD for clients that ask with DO, and a name below a cached NXDOMAIN of an unsigned zone is NXDOMAIN. The failure cache of RFC 9520 is bounded, answers on the query path and holds bogus answers with the doubling hold; `dns.cache.flush` empties all three. The query log shows a synthesised answer as `resolution = denial`, and `tenko_dns_denial_total{kind}` counts them.
- The recursive resolver's operator surface (DNS-02, DNS-03, DNS-13): a forwarding rule of mode `recurse` and a view's `resolution` are written by `POST`/`PATCH /api/v1/dns/forwarders` and `/dns/views` (they answered 501 before; a recurse rule with upstreams, a transport, a TLS name or `validate: false` is refused with `dns.forwarder.invalid`, and a view's answer carries `profile_resolution`); the forwarders page has the rule editor's Recurse mode with the Validate switch, the Default resolution of each view and the preset Forward everything to a DoT resolver with the privacy sentence beside it; the Recursion page lists the trust anchors with their RFC 5011 states and the refresh, add and remove actions (the root under the Lab profile only), the validation counters, and the negative trust anchors with their form, expiry and delete action, live through the `dns` topic; the DNS settings page browses and flushes the infrastructure cache per zone cut; the query log page shows the validation state and the extended error and narrows a page to one state; the start page has the Sub-queries and Validation tiles from the new `recursion` part of the `metrics` samples; the first-run wizard's DNS step asks whether to resolve names yourself or forward them to a resolver of your choice and writes the root rule only for the second; `tenko dns forwarder list` shows a recurse rule and `tenko dns view list` the resolution. See `docs/dns-resolver.md` sections 2.1 and 10.12.
- The start page, the status and the metrics show the host the node runs on (OPS-20): CPU, memory and the free space of the data directory's file system, read by the node itself every five seconds (CPU and memory on Linux, the disk on every platform; no history on the node, the time series is Prometheus'), as three tiles on the start page, the `host` object of `GET /api/v1/system/status` and the gauges `tenko_host_cpu_busy_ratio`, `tenko_host_memory_bytes{kind}` and `tenko_host_disk_bytes{kind}`. The status warns `node.disk.low` while less than 10 percent or less than 1 GiB of the file system is available, whichever is more, and the disk tile turns to the warning style. See `docs/observability.md` section 4.

### Changed

- The cache of a DNS node is a tab of the DNS page, the rightmost one beside the query log, instead of a section of Settings → DNS: `/dns/cache` has its own page, shares the node choice with the query log (switching between the two keeps the node) and still reads only when you press Show the entries. The cache section is gone from the DNS settings page, whose infrastructure cache section stays. See `docs/dns-resolver.md` section 3.7.
- The cache view of a DNS node shows the cache as a tree of names in the style of the Windows DNS manager's cache view: folders from (root) down in the left pane, the records of the folder selected in the right pane with its own records as "(same as parent folder)", and each RRSIG as a row of its own with the type covered, the signer and the expiry instead of joined into the data of the entry it signs. A press of Show the entries or Read again reads up to 10,000 entries at once (1,000 a page) and says when the cap cut it short; expanding and selecting folders never reads, and the previous and next page buttons are gone. The data of a row is clamped to three lines, with a Show all button on a value that does not fit, so one long value cannot take over the page. See `docs/dns-resolver.md` section 3.7.
- A client command on a node whose configuration it can read (`/etc/tenko/tenko.toml` or `TENKO_CONFIG`) and that has no `--url`, `TENKO_URL` or sign-in reaches the node's own API (`https://localhost:8443` with the default listener) and trusts its internal CA root (`<data_dir>/tls/ca-root.pem`), so `tenko login -u admin` is enough on the node; a sign-in to another node still wins, credentials are never taken from the node, and `not signed in` names the full sign-in command for the node, with its address and CA file. See `tenko login --help` and `docs/QUICKSTART.md`.

### Fixed

- Running the installer again no longer undoes the operator's configuration or hides what it cannot change: `install.sh --reconfigure` changes `tenko.toml` by the answers given and carries every other value over (a hand-set `[dns] listen`, `[dhcp]`, `[server]`, `[tls]`, `[kek]`, `[dns.recursion]`, the profile), saying so per section, instead of writing the defaults, which put the dns role on every address and failed to start where systemd-resolved's stub holds 127.0.0.53:53; it refuses that with exit 4 under `--keep-resolved-stub`, before the file is written; `--roles` on a node that has started before says that the stored set does not follow the file and names the three ways to change it (the nodes page, `tenko node roles set`, `PUT /api/v1/nodes/{id}/roles`) while still putting the drop-ins of the new roles in place (`dhcp-direct.conf` joins `probe.conf`); and the processes the service starts (the update check of a new binary, the scan tools, `systemd-creds`, the connector plugins) no longer get `NOTIFY_SOCKET`, so systemd has nothing to refuse and log.
- The scan configuration of the controller's own probe role is reachable from the UI: the section "This controller" of the Nodes page links to it while the probe role runs, and the Scan now error "no probe covers this target" links to the scan configuration of the one probe, or to the Nodes page when there are several or none.
- The OpenAPI document (`GET /api/v1/openapi.json`, `docs/api/openapi.json`) declares the security requirement of every operation: a session cookie or a bearer token by default, a session only on the 66 operations a personal token can never call (account changes, the administration of users, access, settings and the system, secrets, DNS keys, trust anchors, language packs and updates), and none on the 14 public ones (setup, the sign-in ceremonies, node enrolment, liveness and readiness, the CA root, the languages of the sign-in page and the document itself). Before, 326 operations said nothing about authentication although the server answers them 401 without credentials, and three said the opposite of what the server does: `DELETE /auth/sessions/{id}` and `GET /access/service-accounts/{id}/tokens` refuse a token, and `GET /access/subjects` accepts one. See `docs/api/README.md`.

### Action required

- A node in the Standard profile with `[tls] mode = "imported"` no longer loads a certificate file that changed on disk by itself: `[tls] accept_external_replacement` is off there by default (on in Home and Lab, never in Hardened). Set it to `true` to keep the automatic reload, or restart the node after a renewal; the status warning `sys.tls.certificate_pending` says when a newer file waits on disk. Nothing changes for the internal CA or a reverse proxy.

## [0.0.4] - 2026-10-23

### Added

- A node's roles can be changed from the web UI, the API and the command line (OPS-01): the nodes page has a roles editor in each node's panel and for the controller that serves the page, `GET`/`PUT /api/v1/nodes/{id}/roles` read and store the node's role set (audited as `nodes.roles`, with `If-Match`), and `tenko node roles show|set <id> --roles a,b,c` does the same from a shell. The stored set (`nodes.roles`, seeded from `roles` of `tenko.toml` at a controller's first start and synced to every node) decides at the next start unless `--roles` on the command line pins the roles; a node under a service manager restarts itself with exit status 12 to apply a change, otherwise `GET /system/status` warns `node.roles.restart_required`. The controller role follows the cluster membership and is never taken from the last controller; a role whose raw methods need a drop-in the node lacks (`probe.conf`, `dhcp-direct.conf`) is the finding `node.roles.privileges`, and the dns role leaving a host whose resolver the installer pointed at the node (`--use-self`) is `node.roles.dns_resolver`. See `docs/cluster.md` section 13.
- The installer offers the `probe` role, so an installed node can run the dhcp role's conflict detection: `deploy/install.sh --roles` takes any combination of `controller` with `dns`, `dhcp` and `probe`, the questions ask for the role, and with it the installer puts the drop-in `deploy/systemd/probe.conf` (`CAP_NET_RAW`, for ARP and the raw scan methods) next to the unit and removes it when `--reconfigure --roles` drops the role; a rerun reads the roles of a kept `tenko.toml`, so adding `probe` there by hand and running the installer again installs the drop-in too (`docs/dhcp.md` section 14.5).
- The Kea export of the DHCPv4 configuration and its leases (Phase 3, MIG-16): `tenko dhcp export --format kea [--leases] [--out <dir>]` and `GET /api/v1/dhcp/export?format=kea` write the `kea-dhcp4` configuration of Kea 2.6 (subnets, shared networks, pools without their exclusions, reservations, options at every level with their definitions, classes and policies as client classes with `test` expressions, the MAC filters, the boot settings, the DDNS settings as `ddns-*` parameters and a `kea-dhcp-ddns` skeleton, the listeners), the leases as Kea's memfile lease file, and a loss report of what Kea does not express as Tenko does; every export is audited.
- The rest of the DHCP web UI, the DHCP tiles of the start page and the home cut-over runbook (Phase 3, DHCP-02, DHCP-05, DHCP-13, DHCP-16, IPAM-18, OPS-20): the scope page has a DDNS tab (every field of the scope's DDNS settings with the server's settings and what the security profile does) and a network boot tab (the next server, TFTP server name, boot file and PXELINUX options of the scope, its boot policies per client type, and a dialog that adds a boot file for BIOS, UEFI, UEFI HTTP boot or iPXE as a class, a policy and its option 67); the policy editor sets all four actions (options, address range, lease time, DDNS) and picks option 93 architectures by name; the options tab shows why a client gets each value for its MAC address, client identifier, vendor class, user class, architecture and host name (`GET /api/v1/dhcp/scopes/{prefix}/effective-options` now also takes `architecture` and `host_name`), with the classes and policies that matched; the lease list shows how full the chosen scope's pools are, or a bar per scope, and how many leases were granted since the page was opened; a reserved host's page shows its DHCP reservations, the scope each address falls in, whether the role serves it and its lease; the first-run wizard has a DHCP step for the first scope and how the role listens (relay from the gateway or direct on an interface), writes the scope after setup and shows the `[dhcp]` section for `tenko.toml`. While a controller runs the `dhcp` role, the samples of the `metrics` topic carry a `dhcp` part and the start page shows six DHCP tiles: leases granted per second with the minute's sparkline, the REQUEST to ACK p99, the active leases, the three fullest scopes, NAKs and DECLINEs, and DDNS outcomes. `docs/dhcp.md` section 17 is the runbook of the home cut-over (E23): the scopes and reservations in IPAM, the old server's lease time shortened days before, its scopes deactivated before each network's relay is switched to the node, the check from one client per network, the first hour on the tiles, the rollback and the verification rows to tick.

### Fixed

- The dependency `tokio` is 1.54.1: earlier versions let `AsyncFd::new` take a descriptor without owning it, which the I/O safety rules forbid (RUSTSEC-2026-0386).
- A dialog of the web UI never reaches past the window: the panel is capped to the viewport's height, scrolls as a whole and keeps its title pinned at the top and its buttons at the bottom, so Cancel and the primary button of a tall form (a connector's configuration, a DHCP scope, a scoped personal token) stay in reach on a laptop screen; before, a tall dialog grew past the bottom edge and its buttons could only be reached by tabbing blind.
- The dependency `ctutils` (constant-time helpers under the Argon2 password hashing) is 0.4.5: versions before 0.4.4 could generate a branch on a secret value in their mask generation (RUSTSEC-2026-0385).
- A live view that reads again after its own write no longer loads a second time when the event of that write arrives a moment later: the rows were rebuilt once more about 150 ms after the change, which lost a drag started in between (the order of the DNS views).

- The IPAM reconciler writes its proposals in batches under the store's batch limit (read from the store, three quarters of 16 MiB each by default), in subject-key order and each fenced with the leader's epoch, so a run that opens tens of thousands of discovered-host proposals, as a DHCP server's unknown clients make it, no longer fails as a whole with `sys.store.batch_too_large` and loses them all. A batch the store refuses is tried again as two halves, what still fails is reported on the run (`unwritten`, `failure`) and written by the next run, the report says how many `batches` the write took, and the run's audit record `ipam.reconcile.run` counts them (see `docs/reconciliation.md` section 3.2).
- DNSSEC validation in the resolver (Phase 3, Slice 10, DNS-13, OPS-09, TGL-12): every answer, recursed or forwarded, is validated with Tenko's own validator from the trust anchors (the root's anchors shipped from the IANA file and kept current by RFC 5011 on the leader, or an operator's anchor for a private zone) through DS and DNSKEY, with NSEC and NSEC3 proofs (opt-out, wildcards, the RFC 9276 iteration cap) and the cost caps of the KeyTrap class; a secure answer carries AD, an insecure one does not, a bogus one is SERVFAIL with the extended error that names the fault unless the client set CD, and a name no anchor covers is indeterminate. The validator verifies RSA (5, 7, 8, 10), ECDSA P-256 and P-384 (13, 14) and Ed25519 (15) with the DS digests SHA-1, SHA-256 and SHA-384; the signer keeps signing with 13 and 15. `GET|POST /api/v1/dns/trust-anchors`, `GET|DELETE /dns/trust-anchors/{zone}`, `POST .../refresh`, `GET|POST /dns/ntas` and `DELETE /dns/ntas/{id}` are real (`tenko dns trust-anchor ...`, `tenko dns nta ...`): negative trust anchors live at most seven days (an expiry is required under Hardened), are audited and show in the warnings of `GET /system/status`; the root's anchor is replaced only under the Lab profile (`--replace-root`). RFC 8509's sentinel names are answered, RFC 8145's signalling query is sent once a day (off under Hardened), a wrong clock is the finding `dns.validation.clock`, an upstream that strips the DNSSEC records is `dns.forwarder.strips_dnssec` per rule and a rule's `validate = false` is its escape; `[dns.recursion] validate = false` switches validation off under Lab only. The node status shows the trust anchor keys with their RFC 5011 states, the validation outcomes and the validator's key sets beside the infrastructure cache; the query log gains `validation` and `ede` (the DNSSEC state and the extended error of each answer). See `docs/dnssec.md` section 12.

### Action required

- Validation is on after the upgrade in every profile but Lab. A forwarding rule whose upstream strips the DNSSEC records (a resolver that answers without signatures, or a non-validating upstream behind a stripping middlebox) makes the names under it bogus, which `GET /api/v1/system/status` names as `dns.forwarder.strips_dnssec` with the rule; set `validate = false` on that rule or point it at an upstream that relays the signatures. - The DNS engine (Phase 2): an authoritative server for the zones in the replicated store, answering over UDP and TCP on IPv4 and IPv6 from an in-memory index that follows every change without stopping answers. - The DNS resolver side (Phase 2): names outside the zones go through a cache to upstream resolvers chosen by forwarding rules (`/api/v1/dns/forwarders`, `tenko dns forwarder`), by longest suffix and view, with a root rule as the default forwarder, and to the name servers of stub zones, learnt from their source servers. ### Changed

- A move completes its observation step by itself when the device is seen at its new address from its own MAC address; a person can still confirm the step by hand.

- `tenko serve` starts in eleven steps: a new `cluster` step after the store, and the step of the node transport is now called `nodes`.
- The data-directory format is 3. The first start of this version migrates the data directory (after the usual copy), and earlier versions refuse it afterwards; to go back, restore the copy taken before the migration.
- `tenko kek rotate` refuses to run on a member of a cluster.
- A user may hold no global role at all: grants within a scope can be their only access.
- The prune of the node registry runs on the leader only (`cluster.prune`).
- The web UI shows inventory actions only to those who may take them: viewers and the auditor no longer see the write actions of the IPAM, host and job views, and a person with scoped grants sees them only on objects inside the scope. The server still decides every request.

- In right-to-left languages the arrow keys of the grids and of the prefix tree follow the reading direction.

### Security

- The cluster port accepts only node certificates of the installation's internal CA that are not revoked, and a node accepts only a controller of its own CA. Enrolment tokens are kept only as a digest, work once and expire after an hour by default; every enrolment, and every refused one, is written to the audit log. On Windows a node's private key is sealed with DPAPI.
- A PIN session never reveals a secret, and personal API tokens never do. The vault takes no operator secret while an account that may reveal secrets signs in with a PIN alone.
- Reveals are limited to ten a minute per person, counted across all controllers of a cluster.
- A plain, unprotected key generation placed beside generations sealed with DPAPI or systemd-creds is not loaded unless `[kek] allow_plain = true`; the refusal raises an alarm and an audit record.
- A controller that starts with a weaker key protection than it had before raises the alarm `vault.kek.downgrade` and keeps a warning in the system status.
- Connectors can be given a secret only by people who may change secrets, so the reveal policy cannot be bypassed through a connector.
- Repeated requests with an idempotency key are recognised by a fingerprint keyed with a random secret that exists only in memory and changes at every start, so the stored fingerprints reveal nothing about the requests; sign-in, setup and password requests are never fingerprinted. A retry after a restart of a request sent before it is answered as already performed instead of being run again.
- Before a rollback undoes a write through a network controller (a VLAN network or the network change of a move), the undo steps are checked against the guardrails on a fresh read of the controller, so an undo never changes an uplink or the path through which Tenko or the controller is reached.
- The one-time setup token of a first start no longer appears in the log or in the output of a service. It is kept in `setup-token` in the data directory, readable only by the service account, until setup is complete; `tenko setup token` prints it, and a start in a terminal still shows it on the console.
- A token for the role `controller` needs an interactive sign-in within the last five minutes and lives at most an hour; the installation's key encryption keys reach a joining controller only sealed to a one-time key of that host, once per token, audited as `vault.kek.transfer`.
- The controller services of the cluster port accept only controller certificates of the installation, and a data directory refuses to start under another node id.
- A scoped token never exceeds its owner: its grants must lie inside the owner's when it is created, and every request is checked against the token's and the owner's grants as they are then, so revoking an owner's grant or role takes the right from the token at once. The token lifetime cap (TGL-05) is checked again at every use, so lowering it shortens existing tokens.
- Grants and scoped tokens are kept in tables that earlier versions do not read, so going back to an earlier version refuses them instead of widening them into global access.
- Routes refuse a scoped principal unless they decide how the object is scoped, and a scoped write is checked before it is planned and again object by object on its plan, so neither an answer, an event nor an error names an object outside the principal's scope.
