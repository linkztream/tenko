# Changelog

All notable changes to Tenko DDI are recorded here, one section per release, in the format of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) 1.1.0 with Semantic Versioning 2.0.0. One addition: a `### Action required` subsection under a release lists what an administrator must do before or after upgrading to it. Every change to `crates/**` or `ui/src/**` adds an entry under Unreleased; CI checks this with `scripts/changelog.mjs`.

## [Unreleased]

### Added

- One binary, `tenko`: `tenko serve` runs the server with the web UI, and `setup`, `login`, `prefix`, `import`, `export`, `audit verify` and `ca-root` are the command-line client of its API.
- Configuration from built-in defaults, `tenko.toml`, `TENKO_*` environment variables and command-line flags, checked with `tenko config check`.
- The replicated store: an embedded key-value engine under a Raft log, with snapshots and crash-safe commits.
- The vault: secrets encrypted at rest under a key-encryption key held by the platform (DPAPI on Windows) or in a key file, rotated with `tenko kek rotate`.
- The internal certificate authority and three TLS modes: a certificate from the internal CA, an imported certificate reloaded on change, and plain HTTP behind a trusted reverse proxy.
- Sign-in with a password or a PIN as the security profile allows, with a breached-password check, TOTP, passkeys, recovery codes and personal API tokens.
- Four security profiles (Home, Standard, Hardened, Lab) and the toggles behind them, with insecure modes marked in the UI and in the log.
- The job engine: every change runs as a job with steps, timeouts, manual steps and rollback.
- IPAM objects: VRFs, tenants, sites, VLANs, prefixes, address ranges, addresses, hosts and their interfaces.
- The prefix tree with utilization per prefix and alarms at the configured levels.
- Tags and custom fields on IPAM objects.
- History of every IPAM object, with restore of an earlier revision.
- Bulk changes with a preview before anything is applied.
- Import of spreadsheets and CSV files with column mapping and a preview, and export of prefixes, addresses and hosts as CSV.
- Moving hosts to another network: a dry-run preview, then a job per device with manual steps for DHCP and DNS, the network change, the observation of the device at its new address, and rollback.
- The audit log, protected by a hash chain that `tenko audit verify` and the UI check.
- Server-sent events, so the UI follows changes made elsewhere without reloading.
- The web UI, embedded in the binary, in English and Swedish, with a first-run setup wizard.
- The Windows service (`tenko service`) and a hardened systemd unit.
- The container image, with a health check and Compose examples.
- A data-directory format version with migrations at start-up, and `tenko upgrade check`, a dry run against a copy of the data directory (exit codes 0, 10 and 11).
- An in-app update notice with release notes, a what's-new page after an upgrade, and installation from the UI on single native nodes with an automatic switch back (security profile toggle TGL-23).
- A module switch: `modules` in `tenko.toml` and a first-run choice of what the installation is for.
- The release manifest `releases.json` with SHA-256 checksums, and this changelog checked in CI.
- A version layout under `<data_dir>/updates` with a `current` link: the systemd unit and `tenko service install` run the version it points at, `tenko upgrade layout` sets it up, and a restart requested with exit status 12 is restarted by both. A server counts as supervised only when the Windows service runs it or `TENKO_SUPERVISED=1` says so (the systemd unit sets it); variables that systemd passes to every process are not taken as a sign.
- The Phase 1 exit document (`docs/plans/phase-1-exit.md`) and a requirement trace (`docs/plans/phase-1-trace.md`, written by `node scripts/requirement-trace.mjs`) that lists, for every Phase 1 requirement, the tests, measurements and documents that cover it, with acceptance tests of the Slice 3 areas and browser specs of their pages behind it.
- Observations: what connectors report about devices (MAC and IP addresses, names, operating system, platform, hypervisor node, the switch port or wireless network a client uses) is kept per source, apart from the intended state, with first and last sighting, and can be viewed per device across all sources. Observations not seen for 30 days are removed.
- Proposals: Tenko compares the intended state with what it observes, every five minutes and shortly after every change, and proposes discovered hosts, the deprecation of addresses no source has seen for seven days, a host's address when the device is seen elsewhere, networks for addresses outside every known prefix, and conflicts (two devices on one address, one device in several networks, an address used by another device). A proposal shows its evidence and the changes it would make, and can be previewed, approved or rejected; a rejected proposal stays closed until its evidence changes. A locked host never gets a proposal that would change it, and an unmanaged host gets none.
- Adoption policies per prefix, inherited by the prefixes inside it, that approve discovered hosts without a person: optionally only inside DHCP pools, only for listed vendor prefixes of the MAC address, or only after a number of sightings.
- Operator secrets: passwords, API keys, SSH keys and tokens with a name, purpose tags, a user name and notes, kept encrypted in the vault, each under a key of its own. Administrators create, change, replace and delete them; operators see them and may reveal them. A secret that a host or a connector still uses cannot be deleted, and its references are listed.
- Revealing a secret shows it once and copies it to the clipboard, which is cleared again after 30 seconds; every reveal, and every refused one, is written to the audit log with the person, the host and the reason, never the value.
- Credentials of a host: secrets bound to a host as its administration, remote desktop, SSH or web login, with "Copy password" on the host page.
- Remote access from the host page: a Remote Desktop file or an SSH link for each address of a host, with the user name of its credential and no password in either.
- The security profile toggle TGL-24 decides what a reveal takes: the signed-in session (Home, Lab), a sign-in within the last five minutes (Standard), or a passkey sign-in within the last five minutes and only from the page of a host the secret is bound to (Hardened).
- Probe nodes: `tenko node enrol` enrols a node with a controller using a single-use enrolment token, which an administrator creates in the API or with `tenko node enrol-token`. The node checks the controller's CA fingerprint, keeps its key to itself and receives a certificate with its node id and roles; `tenko serve --roles probe` then runs it. The node connects to the controller over mutual TLS on the cluster port (8444 by default, opened once a node or a token exists), sends heartbeats, renews its certificate before it expires, and keeps its observations in a buffer on disk while no controller is reachable, sending them in order once one is. `tenko node status` shows the node and its connection, `tenko node renew` renews at once.
- The node registry: `GET /api/v1/nodes` lists the enrolled nodes with their roles, certificate, version and live connection, enrolment tokens can be listed and deleted, and revoking a node closes its connections and refuses its certificate from then on. `GET /api/v1/system/status` reports enrolled and connected nodes and their versions.
- Controllers and nodes agree on the protocol version, so they can be upgraded one at a time; a node that shares no version with its controller is refused with a clear error and shown as a warning in the system status.
- A `[cluster]` section in `tenko.toml`: the addresses of the cluster port, the endpoints nodes are told, the heartbeat interval, the token lifetime and the size of a node's buffer.
- The probe scanner: a probe node discovers devices in the prefixes of the `[scan]` section of its `tenko.toml` and sends what it sees to the controller, each method on its own schedule. Without raw sockets it reads the ARP and IPv6 neighbour tables of its host, sends ICMP echo, scans a list of TCP ports and notes which answer with TLS, looks up the names of the discovered addresses in reverse DNS, asks mDNS and LLMNR for names, services and operating system hints, and polls switches over SNMPv3 (SHA-1 or SHA-2 authentication, AES-128 privacy) for their ARP, bridge and LLDP tables, so clients appear with their switch port and VLAN and switches with their links. Vendors of MAC addresses come from a built-in OUI table. ARP sweeps, SYN scans, OS fingerprinting and LLDP listening need raw sockets; they are listed with whether the host could run them and stay off until a later release.
- The vendor table of the scanner holds the whole IEEE MA-L registry (40,316 blocks as of 2026-10-10), so every MAC address with a registered manufacturer gets a vendor.
- Scan safety: scans never leave the configured prefixes and their exclusions, run within a rate limit per probe (TGL-19: 100, 50 or 10 probes a second, or unlimited) and a spacing per address, stay out of blackout windows such as `mon-fri 08:00-17:00` in a chosen time zone, and active probing can be switched off (TGL-18). `tenko node scan stop` is a kill switch that stops every running scan at once until `tenko node scan resume`.
- Probe configuration from the controller: each probe's scan configuration is kept by the controllers (`GET`, `PUT /api/v1/nodes/{id}/scan-config`) and synced to the probe as deltas, or as a compressed snapshot after a long absence, within a bandwidth cap per stream (`[cluster] sync_kbps`); the probe applies it atomically, keeps it across outages and reports its sync state and scope. A probe without one offers its own `[scan]` section as the initial configuration; once synced, the controller's configuration wins.
- Scans on demand: `POST /api/v1/scans` scans a prefix, a host or an address with the probes that cover it (passive refresh, port scan, SNMP poll) as a job with progress, and stores the diff against the facts before it (new, changed and gone per fact type).
- The kill switch per probe and installation-wide from the API (`POST /api/v1/nodes/{id}/scan/stop`, `/resume`, `POST /api/v1/scans/stop`, `/resume`): it stops running scans within seconds, reaches an offline probe when it connects again and shows when the probe confirmed it.
- SNMP credentials of probes are named as operator secrets and fetched over mutual TLS when a probe needs them, with an audit record each time; they are kept in memory and never stored on the probe.
- `tenko node scan status` shows the methods with their schedules, state, last run and what the host allows; `tenko node scan run <method>` runs one method at once, for a single address or prefix if wanted, and `--dry-run` prints what it saw instead of sending it.
- Observations name the address a device has a name for (reverse DNS, mDNS, LLMNR, SNMP) and the vendor of a MAC address, and open TCP ports note which answer with TLS; the observation view lists names, vendors and TLS ports per device.
- Discovery in the web UI: an inbox of the proposals, filtered by state, kind, severity, network and device and updated live, with the evidence behind each proposal and a preview of the changes it would make; approve it, reject it with a reason, dismiss a conflict once its cause is resolved, or run the reconciler at once. The observations of every source can be browsed and looked up per MAC address, IP address or name, with what each source reports, the matching hosts and addresses, and the proposals about the device.
- The host page shows what the sources report about the host: the facts per source, its open TCP ports, its operating system, when it was last seen, and the open proposals about it.
- The adoption policy of a prefix in the web UI, on the prefix's Adoption tab: the policy in force and the prefix it comes from, set for the prefix or cleared so that it inherits again.
- Connectors in the web UI: the installed plugins with their capabilities and platforms, and the connector instances with their health, plugin process and last run. A form built from the plugin's own settings creates and changes an instance, with secrets chosen by purpose (never shown) and writes off unless switched on; instances can be run or checked at once, enabled, disabled and deleted.
- Nodes in the web UI: the enrolled nodes with their roles, connection, versions and certificate expiry, revocation, and enrolment tokens that are shown once together with the command to run on the node. A node that shares no protocol version with the controller is pointed out.
- The start page shows the open proposals, the healthy connectors and the connected nodes.
- VLANs with their networks: creating a VLAN, optionally with a network prefix, first previews the IPAM changes and the network controller's read-back of the network; the job then creates the VLAN and prefix, writes the network through the controller after a dry run, checks it by reading it back, and rolls everything back when a step fails. Without a network controller, with writes switched off for it (TGL-20) or on request, the network becomes a manual step of the job. The management VLAN is never written. An existing VLAN can be put onto the controller the same way, and the prefixes of a VLAN are listed (`POST /api/v1/vlans/provision`, `GET /api/v1/vlans/{id}/prefixes`).
- The topology map: routers, switches, access points, hypervisors, virtual machines, containers and hosts with their wired ports, wireless associations, LLDP links, uplinks and virtual machine placement, computed from network controllers, SNMP probes, inventories and the IPAM data and filtered by site, VLAN, network, kind and text; each device shows its ports and what is connected to each port, the path to the gateway, and links to its host and observation pages (`GET /api/v1/topology`, `GET /api/v1/topology/nodes/{id}`).
- The Proxmox VE connector (plugin `proxmox`, bundled): it reads a cluster read-only through an API token (the role PVEAuditor on `/` is enough): the nodes as hypervisors, and the virtual machines and containers with their node, MAC addresses, IP addresses from the QEMU guest agent or the running container (else the static addresses of the configuration and of cloud-init), operating system, status, pool, tags, bridge or SDN vnet and VLAN, so they appear as discovered hosts and on the topology map under their node. Filters by node and pool, stopped guests and templates on request, large clusters read in pages.
- The Home Assistant connector (plugin `hass`, bundled): it reads the device registry read-only through a long-lived access token over the REST and WebSocket API: devices with their MAC addresses and the IP addresses their entities show, the manufacturer as the vendor of each MAC address, the model, the integration and the area, and device trackers that belong to no device. Devices without a network address, Bluetooth and Zigbee identifiers, the stale address of a tracker that is away and public IPv4 addresses (unless asked for) are left out; integrations can be included or excluded.
- Both connectors check the server certificate against the system's certificate authorities, a pinned CA or a pinned fingerprint, can connect to a fixed address while checking the certificate against the host name of the URL, name the cause when TLS fails and show the fingerprint the server presents; turning the check off is loud in every health check and log line.
- For plugin authors: inventory sources can report the vendor of a MAC address (vendor facts, field `vendors` of the inventory protocol), and the Rust SDK has a client for web APIs with the certificate checks above, error mapping and bounded reads (`tenko_connect::sdk::http`).
- For plugin authors: the Rust SDK has an anonymiser for recording the answers of a real system as fixtures (`tenko_connect::sdk::anonymise`): addresses become documentation addresses with networks and relations kept, identifiers keep their format, names become placeholders, credentials and locations are dropped. It splits the property strings of a Proxmox VE guest configuration so that their MAC address, bridge and VLAN tag stay readable, and narrows a private network to the blocks seen in it when the documentation and benchmarking ranges cannot hold it at its real width, and writes a bare prefix length (`netmask`, `prefix`) as the width of the anonymised network of the address next to it. The UniFi, Home Assistant and Proxmox VE plugins ship such recordings of a real controller, instance and node next to their documented fixtures, with a recorder in their live tests.
- The UniFi Network connector (plugin `unifi`, bundled): it reads a self-hosted Network Application or a UniFi OS console through the classic API with a local account: switches, access points and gateways with their ports, port profiles, uplinks and LLDP neighbours, the connected clients with their switch port or access point, wireless network and VLAN, the networks with their VLANs and DHCP mode, the port profiles, and the wireless networks with their VLANs and the access points that broadcast them. Devices and clients also arrive as inventory hosts with names and vendors, so they appear on the topology map and as discovered hosts. Without a local account, a local Integration API key gives a reduced read-only view of devices, uplinks and clients. The controller's certificate is checked against the system's certificate authorities, a pinned CA or a pinned fingerprint (the health check shows the fingerprint a self-signed controller presents).
- UniFi writes through the connector, each read back and diffed first, previewed as a dry run, verified by reading back afterwards and off unless the connector's writes are switched on (TGL-20): a VLAN-only network for a VLAN, or a new name or DHCP mode for the network that has it; a port profile on a switch port; a per-client VLAN override. Each write carries the steps that undo it. Uplinks, the switch port and the client through which Tenko or the controller is reached, and the management networks are never written.
- The observation views of the web UI filter and show the name and vendor facts, and the picture of a device lists its vendors and the TCP ports that answered with TLS.
- Moves change the network of each device through the network controller: the switch port of a wired device gets a port profile that carries the target VLAN untagged, and a wireless device gets a per-client VLAN override. Each change is read from the controller again when the job reaches it, refused when the device or its port changed since the move started, written after a dry run and verified by reading back. When the device is not seen at its new address in time, the change is undone with the controller's undo steps. A device the controller cannot move gets a manual step that says exactly what to do and why: no controller, not seen by it, writes off (TGL-20), a port shared with other devices, no port profile for the VLAN, an access point that does not carry the VLAN (join the named wireless network instead), or a guardrail.
- The move preview shows the network change of every device: the port profile on which switch port, the VLAN override on which access point, or the manual step and its reason, with the change on the controller, its side effects and the wireless networks that carry the target VLAN. A device on an uplink, on the port through which Tenko or the controller is reached, or that is the controller itself is refused by a guardrail, shown with the rule and left to a person after an acknowledgement; the other devices of the move are not held up. A move starts only the plan that was previewed, and asks for a new look at the preview when the network changed in between.
- The jobs view shows the network step of a move with the change the controller read back, when it was written and verified, the undo steps kept for a rollback, and the rollback itself.
- The role `auditor`, for people who check the installation without working in it: it reads the audit log, the state of the audit export and the system status, and nothing else.
- The security profile toggle TGL-21, the audit export: the local audit log only (Home, Lab), export optional (Standard), export required (Hardened). The export itself arrives in a later release.
- `tenko setup token` prints the one-time setup token of a first start from the data directory.
- New settings in `tenko.toml`, checked by `tenko config check`, for features of later releases: in `[cluster]` the isolation timeout, the catch-up timeout, the automatic promotion of new controllers and its lag limit, and a bandwidth cap for node configuration; `[metrics]` with an optional metrics listener on a loopback address; `[backup]` with the directory for backup files.
- Right-to-left layout: the interface mirrors itself for languages written right to left.
- Language packs: administrators upload a translation of the interface as an XLIFF 2.0 file, see a validation report with the share of translated texts and every problem, preview it in their own browser tab, and activate it for everyone. English and Swedish stay built in; an upload can override them and be reverted. Texts a pack lacks show in English. Packs placed in `<data_dir>/i18n/` are imported at start.
- The languages settings page (Settings, Languages) lists the languages with their packs and offers the upload, the report, preview, activation, discard, removal and revert.
- Template download: an XLIFF file with every text of the interface, in English or with the current texts of a language, for translators to start from.
- New fuzz target `xliff_pack` with a seed corpus.
- The key-encryption key can be handed to another controller sealed to a one-time key of the receiver, so every controller of a cluster opens the same envelopes; the cluster join that uses it arrives with the controller cluster.
- Controller cluster: more controllers join with `tenko cluster join` and a controller enrolment token. They copy the data over the cluster port (mutual TLS), become voters once caught up, and only ever to an odd number of voters, and forward writes to the leader; a write is readable at once on the controller that served it.
- `tenko cluster status`, `members`, `join`, `promote`, `remove`, `step-down` and `verify`, and the API `GET /cluster/members`, `POST /cluster/members/{id}/promote`, `DELETE /cluster/members/{id}`, `POST /cluster/step-down` and `GET /cluster/digests`.
- `[cluster] peer_address_map` lets a controller reach a peer through another address than the one the peer advertises (split-horizon setups and labs).
- `/system/status` shows whether the controller reaches a quorum (`store.quorum`: single, healthy, electing or isolated).
- Controllers of a cluster share the installation's key-encryption key: a joining controller receives every key generation from a member over the cluster port, sealed to a one-time key only it holds, and seals them with its own key store; a controller that was stopped during a key rotation fetches the new generation when it starts.
- `tenko kek rotate` rotates the `file` key provider too, keeping new generations in the data directory, wrapped under the key file.
- Online rotation of the key-encryption key (`POST /api/v1/system/kek/rotate`, administrators with a sign-in within the last five minutes): the new key reaches every running controller before it is used, then every secret is re-wrapped under it. `GET /api/v1/system/kek` and `GET /api/v1/system/status` (`kek`) show the key's provider, protection, generations and the rotation.
- The systemd credential key provider (`[kek] provider = "systemd_credential"`): the key comes from `LoadCredentialEncrypted=` in the unit and is reported as protected by systemd-creds instead of a plain file.
- API tokens can carry grants and scopes (`POST /auth/tokens`): a scoped token reaches only the metrics or the audit log, or the objects within the grants of its owner. The scoped views of the API follow.
- The installation's default language is set with `PUT /settings/default-language`.
- Controllers of a cluster apply a revocation made on any of them within a second, look up nodes enrolled through another controller via the leader, and show the same connected view of the nodes (`connection.controller`) everywhere.
- `Hello` answers with the cluster ports of every controller (`endpoints`).
- Every change of a controller's quorum state is a `cluster.quorum` event.
- A member renews its cluster certificate under `<data_dir>/node/` by the rule nodes use.
- Promoting or removing a controller is an inline job `cluster.edit` (step `cluster.member`), and the answer carries `job_id`.
- New fuzz target `raft_payloads` with a seed corpus.
- One job runner per cluster of controllers: the leader drives every job, and when leadership moves another controller takes the running jobs over at once, re-running a step only when it is idempotent and otherwise rolling the job back. Group limits and the worker count hold for the whole cluster, and the install of a release runs on the controller that downloaded it.
- Sign-in ceremonies (second factor, passkey sign-in and registration, TOTP enrolment) that finish on any controller, without sticky sessions; a used challenge is refused on every controller.
- Retried requests served by any controller: a retry with the same idempotency key that reaches another controller replays the first answer. Import uploads are staged in the replicated store, so preview, apply and discard work on every controller too.
- The leader services in `/system/status`: whether the controller leads, its leader epoch, the state of every leader-only service with its restarts and last error, the warning `cluster.leader.service_failing`, and the clock difference to the leader with the warning `cluster.clock_skew` above five seconds.
- Partition behaviour (OPS-26): a controller cut off from the quorum of its cluster marks every answer with `Tenko-Staleness` (since when, and the revision of its copy), keeps serving reads, and refuses writes with 503 `cluster.no_quorum`, `Retry-After` and whether the change can be queued; dry runs still work, and the command-line client prints a warning. IPAM changes (creates, changes, deletes, restores and bulk changes of tenants, VRFs, sites, VLANs, prefixes, ranges, addresses, hosts and interfaces) can be queued on that controller with `POST /api/v1/queue` for up to 7 days. Once the controller is back, each queued change is planned again with its author's current rights: an unchanged plan applies on the author's behalf, with the queue time and controller in the audit log, and any other one waits as a conflict that the author re-applies or discards (`/api/v1/queue/conflicts`). Every settled change is listed to its author; nothing applies silently.

- Grants within a scope (IAM-01): a person or a service account can hold the operator or viewer role over a VRF, a site or a prefix, with or without what lies below it, and then sees and changes only the objects inside: lists, searches, the prefix tree (which shows the ancestors of a granted prefix as context rows with the network only), exports, observations, proposals, jobs, the topology, the audit log and the event stream are filtered, and anything else answers 403 `auth.out_of_scope`. A delegable grant lets its holder grant a role no higher over a scope inside it; revoking it revokes what was granted under it. Grants are managed under `/api/v1/access/grants` and every change is audited.
- Service accounts (IAM-10): accounts for automation without a password, passkey or session, created by an administrator, holding roles or grants and acting only through scoped API tokens (`/api/v1/access/service-accounts`).
- Scoped API tokens (IAM-10): a token with grants that lie inside its owner's, and optionally the scopes `metrics` and `audit:read`, created with `POST /api/v1/auth/tokens` or for a service account; it acts with what both the token and its owner hold at the time of the request.
- The sign-in requirement per role (IAM-06): each role can require a second factor or a passkey (`/api/v1/access/role-policies`); a person must meet the strictest requirement of every role held, globally or through a grant, and the profile's requirement stays the floor.
- The auditor role: reads the audit log, the audit export status and the system status, and nothing else.
- An account that must change its password can use nothing else until it has: every other request answers 403 `auth.password_change_required`.
- Audit export (IAM-18): the audit log goes to syslog receivers over UDP, TCP or TLS and to rotated files, as RFC 5424 with the sequence number and hash in structured data, as CEF or as JSON lines that carry the bytes each hash covers. Checkpoints in the stream make gaps and truncation visible, delivery resumes from a stored position after a restart or a leader change (records may repeat, none is skipped), and a sink that fails for five minutes raises the alarm `audit.export.failing` in the system status. Sinks are managed under `/api/v1/settings/audit-export` with a test message; the Hardened profile (TGL-21) requires at least one.
- `tenko audit export` writes the audit log as a file in any of the three formats, and `tenko audit verify --file` checks a JSON export offline.
- Backups: `tenko backup create` writes one encrypted file with the whole store, the key-encryption keys, the imported TLS files and the configuration, online through the API (`POST /api/v1/system/backups`, administrators with a sign-in within the last five minutes) or from a stopped node; a backup opens with a passphrase or with a key file from `tenko backup keygen`, whose public recipient the server keeps so that it can write backups it cannot read. `tenko backup verify` checks a backup completely, and `tenko backup restore` (with `--dry-run`) restores it into a new data directory on any host, also after the loss of a cluster: the restored controller starts alone and the others rejoin it. Scheduled backups on the leader, off by default, with a keep count (`PUT /api/v1/system/backups/settings`); `GET /api/v1/system/backups` and `/system/status` (`backup`) show the last good backup, and the Standard and Hardened profiles warn after 7 days without one. See `docs/backup.md`.
- The cluster page in the web UI: every controller with its role, voter or learner, lag, last contact, version and the leader marker; promoting a learner, removing a member and handing leadership over, each with a preview of how many failures the cluster survives before and after; a digest check that compares the data of every member; and a single-use token for adding a controller, shown once with the `tenko cluster join` command.
- Partition awareness in the web UI: a banner while the controller has lost contact with the cluster or is electing a leader, with how long it has been so; the age of the local copy in the status bar; and, when a change is refused for want of a quorum, a dialog that queues an IPAM change on that controller and a view of the queued changes and of those that wait for a decision after the cluster heals.
- Scans in the web UI: "Scan now" on a prefix and on a host, the list of scans with their progress per probe and what each found (new, changed and gone facts), the probes with their applied scope, and the kill switch for every probe at once or for one.
- The scan configuration of a probe in the web UI (Nodes, then the probe): every method with its schedule and settings, the prefixes and exclusions, the rate profile and the SNMP devices with their vault secrets, the state of the sync to the probe, and the kill switch of that probe.
- The number of open proposals in the status bar, as a link to the proposal inbox.
- The access page under Settings: the four roles with the sign-in each requires, every scoped grant with a picker for the VRF, site or prefix it covers, and service accounts with their scoped tokens. The page of a user lists that account's grants, and of a service account its tokens; your own API tokens can be scoped too.
- The vault page under Settings: the key-encryption key of each controller, how it is protected, its generations, and the online rotation, followed phase by phase.
- The audit export page under Settings: syslog sinks over UDP, TCP or TLS (with the server name, CA and client certificate) and file sinks with their rotation, each with its format, delivery state, backlog, last error and checkpoint; a test record before a sink is saved; and how long a sink may fail before the alarm.
- The backup page under Settings: the last good and the last failed backup with a warning after seven days without a good one, the recent backups, "Back up now" with an optional passphrase next to the recipient key, the schedule in hours between backups with how many are kept, and the command that restores a backup on a new host.
- The page of a job group lists the jobs that ended without their change, with the reason, and its checklist shows which setting to put back on the network controller when undoing a layer 2 change needs a person.
- Connector settings take a pinned certificate authority in a multi-line field.
- The Windows service writes to the Application Event Log under its service name: `tenko service install` registers the source and `tenko service uninstall` removes it, `[log] event_log` chooses the level (default `warn`), the start and stop of the service are always written, and a configuration that cannot be used is reported there before the file log opens.
- The log file is rotated by size: `[log] max_file_mb` (default 64) and `keep_files` (default 5) keep `tenko.log` and `tenko.log.1` to `tenko.log.5`.
- `tenko cluster upgrade-check` lists every controller's version, protocol majors, Raft wire version and the data formats it knows, says whether the new binary can replace them, and prints the order of a rolling upgrade.
- In a controller cluster a newer data format waits until every voter runs a binary that knows it; the leader migrates then. `/system/status` shows the format of the data and, while a migration waits, the controllers that block it.
- A start that migrates the data directory first checks that the disk has room for the copy of the store, and `tenko upgrade check` checks it too (`upgrade.no_space`).
- The systemd smoke test (`deploy/systemd/smoke.sh`), the Windows service smoke test (`deploy/windows/smoke.ps1`) and a smoke test of the macvlan Compose example, run weekly in CI.
- A drop-in for the systemd unit that lets the probe role open raw sockets, a Compose example with host networking, a probe service in the macvlan example, and notes on LXC containers.
- The reconciler settings (interval, debounce, orphan age, retention, refresh, purge interval and adoption) are the same on every controller and change without a restart, through the API (`GET` and `PUT /api/v1/settings/reconciler`, administrators only, audited); the settings page follows in a later release.
- The guardrails of network-controller writes, protected ports, networks, VLANs and clients and the number of layer-2 writes a controller takes at once, are set through the API (`GET` and `PUT /api/v1/settings/guardrails`, administrators only, audited) and apply to moves, VLAN changes and their undo; the settings page follows in a later release.
- In a controller cluster the reconciler and its purge run on the leader only and move with the leadership; an observation that reaches any controller starts a run on the leader shortly after.
- With probe scopes, an address no probe scans is no longer proposed as orphaned: only an address inside a scope a probe applies counts as gone when it goes unseen.
- The vendor entries of adoption policies match the vendor names that probes, network controllers and Home Assistant report, not only MAC address prefixes.
- Undoing a layer-2 change checks the guardrails again, so a path protected since the change is never written back.
- A reconciler settings page (Settings, Reconciler): how often the reconciler runs, how long it waits after a change, how long facts and unseen addresses are kept and whether adoption policies apply, in seconds, minutes, hours and days, with the limits under each field and a notice when someone else saved first.
- A guardrails page (Settings, Guardrails): the most parallel layer 2 writes and the list of protected ports, networks, VLANs and clients that connector writes and moves never touch, added in a dialog and removed in the list.
- The cluster page shows the compatibility of every member (protocol versions, Raft wire version and the data formats it can open) and a data format panel that names the controllers blocking a pending migration, with the warning to update them first.
- `GET /api/v1/metrics` reports request latency histograms per area and gauges for the store, the cluster, the jobs, the connectors, the nodes, the keys, the audit export and the backup, computed on a timer; a token with the `metrics` scope reads it, and `[metrics] listen` serves the same text on loopback without authentication.
- The start page shows live metrics for administrators: API requests per second with p50 and p99, store size, Raft role and lag per controller, commit latency, jobs, ingest rate, event-stream clients and node buffers, with a sixty-second sparkline per tile, updated once per second while the page is open.
- Controllers exchange their metrics snapshots, so the start page of any controller shows the whole cluster.
- Traces over OpenTelemetry (OPS-05): with `[telemetry] otlp_endpoint` set, every API request, store write, job step, connector call and controller-to-controller call is exported as a span to an OTLP collector over gRPC, sampled by `sampling_ratio`, with the trace context carried between controllers and to plugins; off by default and free when off.
- The contracts of the DNS module (Phase 2): the model of zones, records, views, forwarders, access lists, TSIG and DNSSEC keys and block lists in the replicated store, with record validation and TXT strings split at 255 octets; the DNS engine's wire codec, zone feed and index; the DNS routes of the API in the OpenAPI document, answering 501 until each is built, with the scopes `dns.read`, `dns.write` and `dns.keys` and the event topic `dns`; a DNS page in the web UI that says the module is coming; ADR 0017 and `docs/dns-contracts.md`; and `node scripts/requirement-trace.mjs --phase 2`, which writes the Phase 2 requirement trace (`docs/plans/phase-2-trace.md`).
- The DNS engine (Phase 2): an authoritative server for the zones in the replicated store, answering over UDP and TCP on IPv4 and IPv6 from an in-memory index that follows every change without stopping answers. It answers with wildcards, CNAME chains, DNAME, referrals with glue and negative answers with the SOA, selects views by client subnet, transport, address, type, time and name, hands names outside its zones to a forwarder or refuses them, and supports EDNS (UDP size 1232), DNS cookies (RFC 7873, RFC 9018) and extended errors (RFC 8914). UDP runs on one worker thread per core (one socket per worker on Linux, a shared socket on Windows); TCP pipelines queries with an idle timeout and caps per node and per client. The query path allocates no memory, and `docs/dns-engine.md` describes it.
- DNS zones and records in the replicated store (`/api/v1/dns/zones`, `tenko dns`): primary, secondary, stub, forward and RPZ zones; batch changes of RRsets that apply together, with a dry run and a diff, the record rules checked, RRsets of IPAM or other origins kept unless a change takes them over; SOA serials by unixtime, counter or date counter and a bounded journal per zone scope for zone transfers (`GET /dns/zones/{id}/journal`); zone file import with a preview and losses (`$ORIGIN`, `$TTL`, `$GENERATE`; `$INCLUDE` refused) as a background job in chunks, and byte-stable export (MIG-15); access lists; TSIG keys generated or imported with the secret in the vault, shown once. See `docs/dns.md`.

### Changed

- Switching to the Hardened profile, or setting the audit export to `required`, is refused with 409 `audit.export.required` until at least one export sink is enabled; the refusal is audited like the PIN coupling rule.
- The API rate limiter and the login throttle count per controller: behind a load balancer over several controllers a client gets that many times the configured rate and free sign-in attempts before the replicated account lock takes over.
- The API names the health of a connector's remote system `RemoteHealth`, apart from the liveness answer of the health route, so generated clients see the three health values.
- Credentials taken over by an import are operator secrets bound to their host; the login becomes the user name of the secret. Credentials imported earlier are taken over at the first start of this version.
- Operators may reveal operator secrets, so the PIN rule applies to operator accounts too: once the vault holds a secret, an operator signs in with a password, a second factor or a passkey.
- A move completes its observation step by itself when the device is seen at its new address from its own MAC address; a person can still confirm the step by hand.
- The operator secrets page moved under Settings, to `/settings/secrets`, as a tab beside Security, Users and Updates; the former `/secrets` address and the links to one secret keep working and redirect there.
- A bulk move runs four devices at a time by default, instead of two; the preview still offers 1, 2, 4 and 8.
- `GET /api/v1/openapi.json` answers the committed OpenAPI document byte for byte, in the same pretty-printed form that `tenko openapi` prints, instead of compact JSON.
- `tenko serve` starts in eleven steps: a new `cluster` step after the store, and the step of the node transport is now called `nodes`.
- The data-directory format is 3. The first start of this version migrates the data directory (after the usual copy), and earlier versions refuse it afterwards; to go back, restore the copy taken before the migration.
- `tenko kek rotate` refuses to run on a member of a cluster.
- A user may hold no global role at all: grants within a scope can be their only access.
- The prune of the node registry runs on the leader only (`cluster.prune`).
- The web UI shows inventory actions only to those who may take them: viewers and the auditor no longer see the write actions of the IPAM, host and job views, and a person with scoped grants sees them only on objects inside the scope. The server still decides every request.
- A cancelled job whose cancellation undid the steps that had run shows as "Rolled back (cancelled)".
- A step that has to be undone by hand names the step in words instead of its internal kind.
- In right-to-left languages the arrow keys of the grids and of the prefix tree follow the reading direction.
- The systemd unit reads the key-encryption key with the `systemd_credential` provider instead of as a plain key file, so the warnings about a plain key file are gone, and it creates `/var/log/tenko` for the log file.
- While a start migrates the data directory, `tenko serve` asks systemd for more time, so a long migration no longer hits the start timeout of the unit.
- The Linux release binary is statically linked (musl) and runs on any distribution; every release is started once in Debian 12 and in a RHEL 9 compatible container before it is published.
- The container image and the Compose examples publish the cluster port 8444.
- `tls = insecure` on a connector is accepted under the Lab profile only: elsewhere it is refused (`connect.tls.insecure_refused`), and an instance stored with it before the profile changed is shown degraded and is not called until its TLS settings change.
- In a controller cluster the connectors are polled on schedule by the leader only; every controller still runs the plugins, their health checks and the runs a person asks for.
- An import with credential columns is refused, like storing a secret by hand, while another account that may reveal secrets signs in with a PIN alone; the preview names the accounts.
- The monospace font is served with a content-hashed name and cached for a year, like the other build output; it was revalidated on every page load before.

### Fixed

- The dialog that creates a scoped personal token on the account page scrolls when it is taller than the window, so its Create button can be reached with the mouse on a small screen.
- On a single controller, `GET /cluster/members` and `tenko cluster upgrade-check` report its version, protocol majors, Raft wire version and data formats; they were empty before the first join, and the check showed `-`.
- The page of a connector, the connectors list and the connectors tile of the start page follow the plugin process from starting to running, and every change of its health, without a reload.
- The nodes tile of the start page and the cluster summary of the nodes page count a node as soon as it enrols, connects, disconnects or is revoked, instead of keeping the old numbers until a reload.
- With an operator secret in the vault, the security settings of the Home and Lab profiles can be changed again, for example the reveal policy (TGL-24). Only a change of the password policy or of the MFA requirement that would let a PIN be the only factor is refused, and the settings page says so before anything is sent.
- After an update installed from the web UI, the health check and the start-up line name the version that runs, so the update page sees the restart into the new version.
- Revoking a node no longer fails with a conflict when the node's heartbeat changes its record at the same moment, for example right after it connects: the controller plans the revocation again, and does the same for a certificate renewal.
- A re-import no longer deletes a replaced credential that a connector instance still references.
- The API's metrics tests no longer assume they run alone in the process, so `cargo test` passes on Linux as `cargo nextest` does on Windows.
- The UniFi connector reads the LLDP port id `local Port 7`, which a UniFi switch reports for its own port, as the port index 7, so a link to a managed neighbour names the port instead of carrying the text.
- A node refuses a configuration message whose bytes declare a length far beyond what the message holds with `node.config.payload`, instead of trying to reserve that much memory and stopping; the same holds for every byte value Tenko reads from CBOR, such as keys, MAC addresses and DUIDs.

### Security

- The cluster port accepts only node certificates of the installation's internal CA that are not revoked, and a node accepts only a controller of its own CA. Enrolment tokens are kept only as a digest, work once and expire after an hour by default; every enrolment, and every refused one, is written to the audit log. On Windows a node's private key is sealed with DPAPI.
- A PIN session never reveals a secret, and personal API tokens never do. The vault takes no operator secret while an account that may reveal secrets signs in with a PIN alone.
- Reveals are limited to ten a minute per person, counted across all controllers of a cluster.
- A plain, unprotected key generation placed beside generations sealed with DPAPI or systemd-creds is not loaded unless `[kek] allow_plain = true`; the refusal raises an alarm and an audit record.
- A controller that starts with a weaker key protection than it had before raises the alarm `vault.kek.downgrade` and keeps a warning in the system status.
- Connectors can be given a secret only by people who may change secrets, so the reveal policy cannot be bypassed through a connector.
- Repeated requests with an idempotency key are recognised by a fingerprint keyed with a random secret that exists only in memory and changes at every start, so the stored fingerprints reveal nothing about the requests; sign-in, setup and password requests are never fingerprinted. A retry after a restart of a request sent before it is answered as already performed instead of being run again.
- Before a rollback undoes a write through a network controller (a VLAN network or the network change of a move), the undo steps are checked against the guardrails on a fresh read of the controller, so an undo never changes an uplink or the path through which Tenko or the controller is reached.
- The one-time setup token of a first start no longer appears in the log or in the output of a service. It is kept in `setup-token` in the data directory, readable only by the service account, until setup is complete; `tenko setup token` prints it, and a start in a terminal still shows it on the console.
- A token for the role `controller` needs an interactive sign-in within the last five minutes and lives at most an hour; the installation's key encryption keys reach a joining controller only sealed to a one-time key of that host, once per token, audited as `vault.kek.transfer`.
- The controller services of the cluster port accept only controller certificates of the installation, and a data directory refuses to start under another node id.
- A scoped token never exceeds its owner: its grants must lie inside the owner's when it is created, and every request is checked against the token's and the owner's grants as they are then, so revoking an owner's grant or role takes the right from the token at once. The token lifetime cap (TGL-05) is checked again at every use, so lowering it shortens existing tokens.
- Grants and scoped tokens are kept in tables that earlier versions do not read, so going back to an earlier version refuses them instead of widening them into global access.
- Routes refuse a scoped principal unless they decide how the object is scoped, and a scoped write is checked before it is planned and again object by object on its plan, so neither an answer, an event nor an error names an object outside the principal's scope.
