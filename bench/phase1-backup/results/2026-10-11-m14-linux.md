# M14 backup, verify and restore: 2026-10-11 (Linux)

Measurement M14 of the slice 3 plan (section 5): 1 M records, create below 2 min, restore and verify below 5 min (proposed). Data set: M6 (1,000,000 RRset-like records, 22 byte keys, 128 byte values). Harness: `bench/phase1-backup` (WP3.4b). Windows was not measured.

## Summary

Three runs, each on a freshly loaded store. Times are wall seconds.

| Threshold | Result (median / max of 3 runs) | Verdict |
|---|---|---|
| Create below 120 s: live store, `create::from_live` | recipient lock 9.6 s / 10.0 s; passphrase lock (Argon2id `HARDENED`) 9.5 s / 9.7 s | **PASS**, 12 times under the limit |
| Create below 120 s: stopped store, `create::from_closed` | 4.4 s / 4.7 s | **PASS** |
| Verify below 300 s: `restore::check` (`tenko backup verify`) | 6.1 s / 6.1 s | **PASS** |
| Restore below 300 s: `restore::restore`, no dry run | 5.4 s / 5.9 s | **PASS** |
| Restore and verify below 5 min, strict reading: verify plus restore, run one after the other | sum 11.5 s median, 12.0 s max (11.5, 10.5, 12.0 per run) | **PASS**, 25 times under the limit |

Reading applied: "restore and verify below 5 min" is read strictly, as the sum of a `verify` and a `restore` of the same file (what an operator does who checks first and then restores), against 300 s. Each of the two also passes against 300 s alone. `restore` runs the same checks as `verify` before it installs the store (it unpacks, installs the snapshot into a store, then runs the same `verify_store` as verify: digest, data format, CA fingerprint, envelopes; opening the store verifies the audit chain), so the restore figure on its own already includes the verification; under that reading the restore time (5.9 s max) is the figure.

The margins are large: the whole cycle for 1 M records takes about 21 s for a live backup, a verify and a restore together. The numbers are for a warm page cache on a virtual machine with 16 GiB RAM (the working set of about 2 GB stays in memory); cold-cache reads and a slow disk are not measured and would move all steps.

## Build and commands

```
cd bench/phase1-backup
export CARGO_INCREMENTAL=0
export TENKO_UI_DIST=<dir with an index.html>      # see the note below
cargo run --release -- --records 1000000 --runs 3 --out-name m14
```

Note on the build: the command from the plan, `TENKO_UI_STUB=1 cargo run --release`, does not compile here: `tenko-api` refuses a stubbed UI in release builds (`compile_error!` in `crates/tenko-api/src/ui/mod.rs`). The runs used `TENKO_UI_DIST` pointing at a directory outside the repository with a one-line `index.html` instead. The UI is not on the measured path (the backup code does not touch it), and the repository was not changed for this.

Checks: `cargo fmt`, `cargo clippy --release -- -D warnings` clean.

Data: synthetic only, documentation values (`192.0.2.1`, `ns1.example.test` in one marker row). No network access of any kind; the only I/O is the scratch directory.

## Method

- Load: 1,000,000 records into a fresh `RaftStore` in 100 batches of 10,000 with one audit draft each, four proposals in flight (as M6). Copy of the record shape and batch builder of `bench/phase1-store/src/data.rs` in `src/data.rs`. Then five operator secrets in the vault (`put_operator`, as in the end-to-end test of the backup library) and one small marker row, so that the envelope checks of verify have work to do. The snapshot holds 1,000,181 rows in all (the data set plus the vault, audit and system tables).
- Steps, in this order per run, each timed with `Instant` around the library call (the library's own duration is the same within noise):
  1. `create::from_live` with a recipient lock (`KeyLock::Recipient`).
  2. `create::from_live` with a passphrase lock and `KdfParams::HARDENED` (64 MiB, 3 passes, 1 lane). The file is deleted afterwards.
  3. `RaftStore::copy_state_to` alone (the store-copy part of step 1, for the breakdown). The copy is deleted afterwards.
  4. The store is shut down, then `create::from_closed` (offline) with a recipient lock. The file is deleted afterwards, and so is the source store.
  5. `restore::check` on the file of step 1 (`tenko backup verify`).
  6. `restore::restore` of the same file into an empty data directory, plain-file KEK provider (`provider = systemd_creds` with a missing tool, as in the test), `dry_run = false`. The reopen of the restored store by the caller is not part of the measurement.
- Per step the harness also samples the resident set of the process and the allocated size (`st_blocks`) of the whole run directory every 100 ms and keeps the peaks. The run directory holds the source store, the backups and work directories, and the restored store together, so the scratch peak is a total, not the step's own write.
- Before the three runs, a create of a store without records measures the fixed cost of each lock.
- The first complete execution (before the `copy_state_to` step was added) gave the same picture: create live 10.6 to 12.3 s, closed 5.1 to 5.2 s, verify 6.5 to 7.9 s, restore 6.1 to 6.4 s. It is kept in `results/raw/m14-first.{txt,json}`; the numbers here are from the second execution. Both executions ran on a machine with a load average of about 2 to 3.

Fixed cost of the locks (create of a store without records, 27 rows, 7.9 kB file): recipient 0.04 s, passphrase with `HARDENED` Argon2id 0.23 s. The Argon2 cost of a passphrase slot is therefore about 0.19 s, and it is not visible at 1 M records: passphrase and recipient creates differ by less than the run-to-run spread (9.50 against 9.61 s median). The reader pays one Argon2 derivation too when it opens a passphrase backup (not measured separately; the same order, 0.2 s).

Verification outcomes: every `check` and `restore` reported `digest_matches` true with 1,000,181 rows and 5 envelopes opened.

## Where the time goes

- A live create takes about twice as long as an offline create (9.6 s against 4.4 s). `RaftStore::copy_state_to` alone takes 4.4 s (4.4 to 4.8), which is about the whole offline create; the remaining 5.2 s of a live create are the same writer code that the offline create runs (snapshot read, digest, encrypt, write). The two do not add up cleanly: the offline create does the same writer work in less than 4.4 s in total, so the writer step is slower after a live copy than after a closed one. The harness cannot say why (the running store, with its caches and background tasks, shares the four cores and the page cache; the live copy is also written through redb rather than file-copied); no profile was taken.
- The create does not depend on the lock: a passphrase adds the 0.19 s of Argon2, a recipient adds nothing measurable.
- Verify costs 0.7 s more than restore (6.1 against 5.4 s median). Both unpack the file (read, decrypt, hash 190 MiB), install the snapshot into a store and run the same store check; verify then removes the scratch store, restore keeps it and also seals the key generations with the host provider. The difference is within one to two spreads and its cause was not isolated.
- The CPU did the work, not the disk: with warm caches the throughput is about 20 MiB/s of backup file for a live create, 44 MiB/s offline, 31 MiB/s verify and 35 MiB/s restore. That is slow for AES-GCM and SHA-256 alone on this CPU (both hardware accelerated), so the time is in the store side (reading and writing 1 M rows through redb), not in the cipher. This is an inference from the throughput; the step costs inside the library were not instrumented.
- Memory stays flat: the peak of the process grows by less than 100 MiB over the idle store for a 190 MiB backup, so create, verify and restore stream the data (chunks of 1 MiB) and do not hold the snapshot in memory.

## Caveats

- One machine, a 4-core virtual machine shared with other builds (load average 1.6 to 3.5 at the start of the runs). Three runs; medians and maxima are given, spread within a step is up to 20 percent (create live 9.0 to 10.0 s), which does not touch any verdict.
- Warm page cache: the source store was just written and the backup file just created, so reads come from memory. A restore from a backup that sits on a cold disk or a network share reads 190 MiB at the speed of that medium; even at 10 MiB/s that is 19 s.
- Scratch and source on the same device; the target of a real backup is usually another device. `fsync_probe_samples = 0`, so the store does not adapt its durability to a measured fsync cost; the device's fsync cost is not measured here (M10 does that).
- Restore is measured without the reopen of the restored store by `tenko serve` (a Raft start and the vault check), which the plan's wording does not include either.
- Single voter. A restore of a member of a cluster is the same snapshot; the three-controller case is covered by the end-to-end test, not measured.
- The data set is the M6 one: one table with 1 M small rows. A real installation with many tables, large values and a long audit chain has a different row count and byte size; the audit chain check in verify walks the chain (here: 100 audit entries from the load) and would grow with it.
- Windows was not measured.
