# M8 metrics cost on the UDP responder: 2026-10-14 (Windows)

Verdict: PASS

Measurement M8 of the slice 3 plan (WP3.5 item 7): the Spike B responder with the counters and a histogram of `tenko_core::metrics` on its hot path, on and off, in paired runs. Acceptance: the metrics cost below 2 percent of QPS and p99 unchanged within noise; a million updates allocate nothing. The Linux pair (WSL2) is run at the merge.

## Summary

| Workers | Pairs | Median QPS change (on against off) | Median p99 change | Server CPU per query, off / on (median) | Result |
|---|---|---|---|---|---|
| 1 | 5 | -0.68 % | +1.2 % | 6.090 / 6.142 µs (+52 ns, +0.9 %) | PASS |
| 4 | 20 (three sets) | -0.99 % | +2.2 % | 7.49 to 8.16 / 7.69 to 8.20 µs per set | PASS, within noise |

- QPS: below the 2 percent limit at both worker counts; at one worker, where the machine noise is smallest, every pair is within -2.14 % and the median is -0.68 %.
- p99: +1.2 % at one worker (pairs from -0.6 % to +1.5 %); at four workers the pair-to-pair spread of the p99 of the runs without metrics alone is 558 to 803 µs, and the median change over 20 pairs is +2.2 %. Unchanged within noise.
- The cost per packet is about 50 ns of server CPU (one worker: 6.090 against 6.142 µs per query), which matches two clock reads, one counter update and one histogram observation (three uncontended `lock xadd` on the thread's own cache lines).
- Allocations: `cargo test --release` (and the debug build) passes `tests/zero_alloc.rs`: a million `inc`, `add` and `observe` calls on sealed families on one thread, then 4 x 250,000 on four threads at once, made zero allocations on the updating threads.

## Method

- Source: `tenko-core` of branch `wp35a` as committed in `5723dc9` (the update path is unchanged in the later commits of the branch); the package `bench/phase1-metrics` as committed with this file, except that the binary that ran the sets predates the `report` grouping by set. The responder is the blocking-threads mode of Spike B (one shared socket, 8 MiB buffers), the `domain` codec, the 100,000-name zone `example.test`; see the README for what is copied and why.
- On: per packet `bench_dns_queries_total{outcome}` (`CounterVec`, 4 series) plus one and `bench_dns_query_duration_seconds` (`Histogram`, 11 bounds in nanoseconds) records the time of `respond`. Off: no instrumentation (a separate monomorphization of the worker).
- Load: the closed-loop generator of Spike B in process, 8 clients x 32 queries in flight, 5 % NXDOMAIN, EDNS, 2 s warm-up, 20 s measured (10 s in the set `m8-ten`). Every run starts a fresh server; a pair runs off and on back to back, the order alternating from pair to pair.
- Commands, from `bench/phase1-metrics` (Git Bash):

```
cargo test --release
cargo build --release
target/release/phase1-metrics pairs --listen 127.0.0.1:5399 --workers 1 --out results/raw/m8-windows.jsonl
target/release/phase1-metrics pairs --listen 127.0.0.1:5399 --workers 4 --out results/raw/m8-windows.jsonl
target/release/phase1-metrics pairs --listen 127.0.0.1:5399 --workers 4 --label m8-rerun --out results/raw/m8-windows.jsonl
target/release/phase1-metrics pairs --listen 127.0.0.1:5399 --workers 4 --pairs 10 --duration 10s --label m8-ten --out results/raw/m8-windows.jsonl
target/release/phase1-metrics report --input results/raw/m8-windows.jsonl
```

The sets ran from 12:06 to 12:27 UTC. No run had a timeout or an invalid response.

## Observations

- Four workers on this hybrid desktop are noisy: within one set the runs without metrics alone vary by 6 to 14 percent in QPS and by up to 40 percent in p99 (the scheduler places the eight client and four server threads on P-cores or E-cores differently from run to run, and the desktop load varies). The single pair at -11.7 % (`m8-rerun-w4`, pair 3) falls in a stretch where the following runs without metrics also dropped by 6 to 8 %. The one-worker set is the clean measurement of the cost; the four-worker sets show that sharding keeps it at that level with four updating threads (each thread updates its own stripe; no line is shared).
- At one worker the cost is about 52 ns of server CPU per packet. The responder spends about 6 µs per packet, almost all of it in the two system calls, so the counters and the histogram would weigh more on a responder with a cheaper I/O path (batched `recvmmsg`, io_uring); the Linux pair at the merge shows the second platform.

## Conclusion

PASS on Windows: the metrics cost below 2 percent of QPS (median -0.68 % at one worker, -0.99 % over 20 pairs at four workers), the p99 latency unchanged within the noise of the machine, and zero allocations on the update path.
