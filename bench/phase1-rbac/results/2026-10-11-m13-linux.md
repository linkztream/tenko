# M13 scope filtering cost: 2026-10-11 (Linux)

Measurement M13 of the slice 3 plan (section 5): a list of 10,000 hosts for a scoped principal within 1.5 times the unscoped time, and server-sent event fan-out of 100 events/s to 1,000 scoped subscribers below one core (proposed). Synthetic tree with 50 scoped grants. Harness: `bench/phase1-rbac` (WP3.2). Windows was not measured.

## Summary

| Threshold | Result | Verdict |
|---|---|---|
| List of 10,000 hosts, scoped at most 1.5 times unscoped | worst case (grants cover all 10,000 hosts): ratio of medians 1.36 on `MemStore`, 1.38 on `RaftStore`; p95 ratio 1.34 and 1.27. At 50% coverage 0.68 and 0.70, at 10% 0.13 and 0.12 | **PASS**, thin margin at 100% coverage |
| SSE, filter alone: `select` for 1,000 subscribers at 100 events/s, below one core | before the anchor cache 0.29 cores (0.289, 0.288); with it (commit `eadbd3d`) 0.17 and 0.18 cores | **PASS** |
| SSE, end to end: 1,000 scoped streams through the router and hub, 100 events/s, below one core | before the anchor cache 1.04 and 0.94 cores; with it 0.88 and 0.95 cores (administrator streams 0.70 and 0.69) | **PASS** in both runs with the cache, thin margin; most of it is the fan-out and the in-process readers, which unscoped streams pay too |

The list threshold holds, but only because the filter costs about 10 passes over the table (see Profile). The end-to-end SSE figure is at the limit on this 4-core virtual machine, and the in-process drain tasks are a large part of it; the filter's own share is 0.26 to 0.63 cores (scoped streams minus administrator streams). After these runs the scoped event filter got an anchor cache shared by all subscribers (commit `eadbd3d`, section "SSE: with the anchor cache"), which brought both end-to-end runs below one core.

Because of that load, every listing was measured **interleaved**: in each iteration the administrator and the scoped principal list one after the other (the order alternates), so both see the same load. The ratios below are ratios of medians of those interleaved series. The SSE numbers are process CPU time, which load does not add to directly (it can still inflate it through cache and hyper-thread contention).

## Build and commands

```
export CARGO_INCREMENTAL=0
cd bench/phase1-rbac
cargo build --release
./target/release/phase1-rbac list --store mem  --out results/raw/m13-list-mem.json
./target/release/phase1-rbac list --store raft --data-dir <scratch> --out results/raw/m13-list-raft.json
./target/release/phase1-rbac sse  --store mem  --out results/raw/m13-sse-mem.json       (run 1)
./target/release/phase1-rbac sse  --store mem  --out results/raw/m13-sse-mem-run2.json  (run 2)
```

Defaults: 100 /56 prefixes, 5 /64 leaves under each (500 leaves), 20 hosts per leaf (10,000 hosts, each with one interface and one address), 50 grants per scoped principal, 3 warm-up and 30 timed full listings, page size 1,000, 30 s per SSE run, 100 events/s, 1,000 subscribers, 50 principals. `cargo clippy --release --all-targets -- -D warnings` is clean and `cargo fmt` applied (the debug profile was not built: disk space).

Data: documentation values only (`2001:db8:100::/48`, names `hNNN-NNN.example.test`). No network except in-process calls.

## Method

- Path measured: `tenko_api::api(state)` with the auth, IPAM and anchors-index extensions, called with `tower::ServiceExt::oneshot`, session cookie per principal. Request: `GET /api/v1/hosts?limit=1000&cursor=...` repeated until `next_cursor` is null; the response body is read and the page parsed for `next_cursor` only. Same for `GET /api/v1/addresses`.
- Principals: the administrator (global role), and three scoped users with no global role and 50 grants each, `subtree: true`:
  - 10%: operator on 50 leaf /64 prefixes (1,000 hosts)
  - 50%: viewer on 50 of the 100 /56 prefixes (5,000 hosts)
  - 100%: operator on the /48 supernet plus 49 leaves (10,000 hosts, the worst case: all rows pass, and the filter still decides on each)
- Setup uses the Home profile (PIN passwords): the Standard profile asks administrators for a second-factor step-up that a benchmark cannot supply.
- Public APIs only. `EventHub::spawn_tasks` is crate-private, so the harness feeds the hub with the same loop (`Store::watch` from `hub.newest()` into `publish_change_set`). Everything else (`ScopedEvents`, `ScopeIndex`, `AuthService`, router) is the real code.

## List: where the time goes

Profile pass, outside the router, one pass over the 10,000 host references of the full-coverage principal (`MemStore`; `RaftStore` is within 10 percent):

| Step | Cost |
|---|---|
| `Authorizer::scope(principal, Read, Host)` | 0.8 to 1.0 µs per call (once per request) |
| `ScopeIndex::anchors(host)` | 2.3 to 2.8 µs per host, 23 to 28 ms per pass |
| `ScopeFilter::admits(anchors, Any)` with 50 rules | 0.09 µs per host at 100% (passes at the first rule or two), 0.24 to 0.28 µs at 10% and 50% (more rules tried), about 1 to 3 ms per pass |

One pass costs about 27 ms. A full listing costs about 10 times that, because of how paging is built: `tenko_ipam::query::list_where` scans the whole table (`scan_typed(.., usize::MAX, ..)`) and calls the scope condition `keep` on every row of every page, and only then drops the rows before the cursor (`.filter(|(key, _)| after...)` comes after `keep`). A listing of 10 pages therefore evaluates the filter 100,000 times, about 250 ms. That matches the measured difference between scoped and unscoped at 100% coverage (897 minus 658 = 239 ms; 880 minus 639 = 241 ms). The unscoped listing also scans and decodes the full table for each page (about 65 ms per page), so the base cost is itself quadratic in the number of pages.

Two cheap changes follow from this, for the author to weigh against a per-principal scope cache: apply the cursor test before `keep` (the average listing then evaluates the filter on about half the rows), and resolve anchors once per object instead of per call. A per-principal cache of the granted prefix set would not remove the per-object anchor resolution (`anchors_with` in `crates/tenko-ipam/src/scope.rs`, 2.3 to 2.8 µs), which is 90 percent of the cost.

## SSE: results

30 s per run at 100 events/s (3,000 events), one process (the harness) running the publisher, the hub, the 1,000 stream readers and the CPU meter; CPU time from `sysinfo` over the publishing window; cores = CPU seconds / wall seconds. One event is one `UpdateHost` command by the administrator on a random host; it publishes 3 frames to the hub (9,000 frames per run), of which the `ipam` topic subscribers receive the host's. 1,000 subscribers share 50 scoped principals round robin (50 grants each, on a random 50 of the 100 /56 prefixes, so about half of the events concern a host the principal may read); 50 sessions are shared by the 1,000 streams.

Filter alone, `ScopedEvents::select(principal, Topic::Ipam, &[host])` called 1,000 times per event, no router and no hub:

| Run | Principals | CPU s / wall s | Cores | Events delivered (of 3,000,000) | Slowest event (1,000 calls) |
|---|---|---|---|---|---|
| 1 | administrator | 1.16 / 29.99 | 0.039 | 3,000,000 | 9.0 ms |
| 1 | 50 scoped | 8.68 / 30.00 | **0.289** | 1,503,900 | 21.3 ms |
| 2 | administrator | 1.37 / 29.99 | 0.046 | 3,000,000 | 4.2 ms |
| 2 | 50 scoped | 8.63 / 30.00 | **0.288** | 1,503,900 | 16.9 ms |

That is 2.9 µs per call (3 µs times 100,000 calls/s), 90 percent of it anchor resolution, because `select` resolves the anchors of the event's object again for each subscriber even though the object is the same. Verdict: **PASS**, 0.29 cores for one object reference per event. The hub receives 3 frames per `UpdateHost` (only one reaches a subscriber of the `ipam` topic: administrators received exactly 1 event per command); whether the hub calls the filter for the other two frames before it drops them by topic was not checked.

End to end, 1,000 `GET /api/v1/events?topics=ipam` streams through the router and `EventHub`, fed from the store journal:

| Run | Streams | Cores | Events delivered | Dropped (`reset` frames) | Streams ended | Frames published | Achieved events/s |
|---|---|---|---|---|---|---|---|
| 1, no subscribers (publisher and feeder) | 0 | 0.103 | 0 | 0 | 0 | 9,000 | 100.03 |
| 1, administrator streams (no filtering) | 1,000 | 0.407 | 3,000,000 | 0 | 0 | 9,000 | 100.03 |
| 1, scoped streams | 1,000 | **1.039** | 1,499,340 | 0 | 0 | 9,000 | 100.03 |
| 2, no subscribers | 0 | 0.121 | 0 | 0 | 0 | 9,000 | 100.03 |
| 2, administrator streams | 1,000 | 0.672 | 3,000,000 | 0 | 0 | 9,000 | 99.90 |
| 2, scoped streams | 1,000 | **0.936** | 1,499,340 | 0 | 0 | 9,000 | 100.03 |

CPU seconds: run 1 scoped 31.17 over 29.99 s, run 2 scoped 28.06 over 29.99 s. Nothing was dropped and no stream ended. Delivered events are exact: all 3,000,000 for administrators, 1,499,340 (50.0 percent) for the scoped principals.

Verdict before the anchor cache: **not demonstrated below one core.** The scoped end-to-end figure is 1.04 and 0.94 cores. The difference between the two runs is about the same as the difference between the two administrator runs (0.41 and 0.67), so the noise on this shared 4-core machine is about 0.3 cores and the measurement cannot separate 0.94 from 1.04. What is clear: the filter adds 0.26 (run 2) to 0.63 (run 1) cores over unfiltered streams, the fan-out itself (administrator streams, including the readers in the harness) takes 0.4 to 0.7, and the two together sit at the limit. The proposed threshold ("below one core") is at best met with 6 percent to spare, which is not a margin to rely on; the 1,000-subscriber case needs the per-event anchor cache (below) or a measurement on the target hardware.

Notes on what the hub does per subscriber (crates read, not profiled): `Subscriber::render` is called per subscriber and frame; with `Admission::Only` the hub re-encodes the event per subscriber. For a frame with one object reference, `select` calls `Authorizer::scope` (about 1 µs) and `ScopeIndex::anchors` (about 2.5 µs) per subscriber, although the anchors depend on the object alone: with 1,000 subscribers one frame resolves the same anchors 1,000 times. Resolving them once per frame and handing them to the subscribers (or caching `Authorizer::scope` per principal and kind with a revision) removes about 90 percent of the filter's own cost (0.26 to 0.63 cores to well under 0.1).

## SSE: with the anchor cache

After the runs above, `ScopedEvents` (`crates/tenko-api/src/sse/filter.rs`) keeps the anchors of every reference per index revision in a bounded map shared by all subscribers (commit `eadbd3d`), so an event resolves each reference once instead of once per subscriber. Same harness, same command (`./target/release/phase1-rbac sse --store mem --out results/raw/m13-sse-mem-cached.json`, then `...-cached-run2.json`), load average 3.07 and 1.01 at the start:

| Run | Filter alone, administrator | Filter alone, 50 scoped | Hub, no subscribers | Hub, administrator streams | Hub, scoped streams |
|---|---|---|---|---|---|
| 1 | 0.047 | **0.175** | 0.115 | 0.698 | **0.876** |
| 2 | 0.045 | **0.183** | 0.120 | 0.693 | **0.955** |

Delivered events unchanged (3,000,000 and 1,499,340), no resets, no ended streams. The filter's own cost fell from 0.29 to 0.18 cores; what remains is `Authorizer::scope` per subscriber and the narrowed re-encoding. End to end the scoped streams now cost 0.18 to 0.26 cores more than unfiltered ones and stay below one core in both runs; the margin is thin because the unfiltered fan-out with in-process readers already takes 0.7 cores on this machine. A cache of `Authorizer::scope` per principal and kind was not added: it would save at most about 0.1 cores here.

## Caveats

- One machine: a 4-core virtual machine, shared with other builds during the runs (load average 1 to 6.5). Medians of interleaved series are robust to that; the SSE CPU figures are less so. There is no repeat of the 30-iteration list runs; the two SSE runs differ by 0.1 cores.
- The harness reads the frames in the same process (1,000 tasks counting `event: ` fields in each chunk), so the end-to-end figures include the client side, which a real deployment does not pay. The administrator streams (0.41 to 0.67 cores) measure that plus the hub's fan-out.
- The router is called in process (`oneshot`): no TCP, TLS or HTTP parsing, so the list time is route and store time only. A real client pays more, which makes the filter's share smaller.
- Data: all hosts are in a tree of two levels under one supernet; deeper trees or more VRFs raise the anchor cost (`prefix_anchors` walks the chain). 50 grants all on prefixes (no tenant, site or VRF grants).
- Home profile (not Standard): the scope code path is the same; password hashing only matters at sign-in.
- Events are `UpdateHost` commands. Events that touch many objects (imports, a prefix with many addresses) carry up to `max_objects_per_event` (500) references, and each reference costs one anchor resolution per subscriber: such an event would be up to 500 times the cost of the event measured here.
- Windows was not measured.
