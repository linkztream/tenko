# M9 idle RSS of `tenko serve --roles controller`: 2026-10-09 (Windows and Linux)

Verdict: PASS

Measurement M9 of the Phase 1 plan (section 8): idle RSS below 100 MB (OPS-15), 10 minutes idle after import, on Windows and on Linux. Both sets of numbers below come from the driver scripts in `bench/phase1-server/` (`m9-idle-rss.ps1`, `m9-idle-rss.sh`), run against the same release build of the same source.

Two deviations from the wording of M9 are explained under Caveats: the data set was created with `tenko prefix create` because the import command is not available yet, and only the controller role exists in Phase 1, so "all Phase 1 roles" is the controller role alone.

## Method

Both platforms ran at the same time, on different ports (18443 and 18444), next to the other builders' compile and test jobs. The measured process is the server only.

Configuration file (Windows). The Linux one differs in `data_dir` and the port only. Everything else is the shipped default: `internal_ca` TLS, profile `home`, `[kek] provider = "platform"`, 2 API and 2 core worker threads, store caches of 4 and 32 MiB.

```toml
data_dir = 'C:\Users\plm\AppData\Local\Temp\tenko-m9-20261009-195904\data'
roles = "controller"

[server]
listen = ["127.0.0.1:18443"]

[hibp]
online = false
```

Linux: `data_dir = "/tmp/tenko-m9-<random>/data"`, `listen = ["127.0.0.1:18444"]`.

Commands, in order. `<ca>` is `<data_dir>/tls/ca-root.pem`; `TENKO_CREDENTIALS` points into the work directory; the setup token travels in `TENKO_SETUP_TOKEN`; the administrator password is a six-digit PIN generated for each run and passed on standard input. Neither is recorded.

```
pwsh -NoProfile -File bench\phase1-server\m9-idle-rss.ps1 -Binary %TEMP%\tenko-m9-bin\m9-bench-server.exe -Port 18443
bash bench/phase1-server/m9-idle-rss.sh --binary /home/plm/m9-bin/tenko --port 18444     (inside WSL, as user plm)

tenko serve --roles controller --config <file>                     (Windows: plus --stop-on-eof)
tenko setup --url https://localhost:<port> --ca-file <ca> --admin admin --host-name localhost --password-stdin
tenko login --url https://localhost:<port> --ca-file <ca> --user admin --password-stdin
tenko prefix create 10.0.0.0/8 --role supernet
tenko prefix create 10.<a>.0.0/16 --role supernet                  a = 1..4
tenko prefix create 10.<a>.<b>.0/24 --role network                 195 networks, a = 1 + n mod 4, b = n div 4
tenko prefix list --all --json                                     check: the server lists all 200
```

Then 600 s idle with one sample every 30 s (21 samples, the first at the start of the idle phase), then a graceful stop: Windows closes the server's standard input (`--stop-on-eof`), Linux sends `SIGTERM`. No client connection is open while the server is sampled. Counters: on Windows `WorkingSet64` and `PrivateMemorySize64` with the kernel's `PeakWorkingSet64` and `PeakPagedMemorySize64`; on Linux `VmRSS`, `VmHWM`, `RssAnon` and `RssFile` from `/proc/<pid>/status`.

## Verdict

M9 is met on both platforms for this data set: idle RSS after 10 minutes is 47.6 MiB (49.9 MB) on Windows and 75.1 MiB (78.7 MB) on Linux, with peaks of 61.9 MB and 80.4 MB, all below 100 MB and below 95.37 MiB. Linux has the smaller margin: 18.7 MiB under 95.37 MiB at 200 prefixes, 8.7 MiB at 1,000 prefixes.

## Caveats

- Import: M9 says "after import". `tenko import` was not available (WP1.5), so the data set is 200 prefixes (one /8, four /16, 195 /24) created with `tenko prefix create`. There are no addresses, ranges, DHCP data or users beyond the administrator. A real import of a different size will move the number; the 1,000 prefix runs show the slope.
- Roles: "all Phase 1 roles" is only the controller role today (`dns`, `dhcp` and `probe` are reported as not implemented). OPS-15 is stated for all roles in one process, so M9 has to be measured again when they land.
- Profile: only the Home profile was measured. The Hardened profile hashes with 64 MiB of Argon2 memory instead of 19 MiB (`HashStrength::Hardened`); its effect on the resident set was not measured.
- Linux was measured inside a WSL2 VM, not on bare metal. VmRSS is the guest's accounting, and the allocator is glibc malloc; a distribution or container image with another allocator will differ (see Observations). This run is a glibc host build, not the shipped musl binary; the two are compared in [2026-10-16-m9-linux-memory.md](2026-10-16-m9-linux-memory.md).
- Windows working set and Linux VmRSS are the closest pair of counters but not identical. Both include the resident part of the executable image (about 28 to 30 MiB on Linux as RssFile); Windows can trim the working set; Windows private bytes (committed private memory) matches Linux RssAnon only roughly. The verdict uses working set and VmRSS, the larger numbers.
- Each run was done once, on a workstation that was busy compiling and running tests. The idle readings were flat (spread 0.11 MiB on Windows; 1.59 MiB on Linux, all of it in the first 4 minutes, as file pages left the resident set), so the load is unlikely to matter for idle memory, but there is no repeat of the 10-minute run.
- The verdict line that the scripts printed for these runs compared with 100 MiB. The scripts were changed afterwards to compare with 100,000,000 bytes (95.37 MiB) and to print both units; nothing else in them changed after the runs. This file applies the stricter limit.

## Observations

1. **The first Windows run ended early, probably killed from outside.** The first full Windows run (kept as `results/raw/m9-windows-20261009-194747-*-aborted.*`) lost the server between 150 s and 180 s into the idle phase (about 3.5 minutes after the start): exit status 1, no log line at all after start-up (no shutdown message, no panic text), memory flat until then. The graceful stop and the error paths of `tenko serve` all log, so this looks like `TerminateProcess` from outside, probably a name-based cleanup of `tenko.exe` by another session (other builders were running `nextest` for the `tenko` crate at the time; no test in the repository kills by name). The repetition used a copy named `m9-bench-server.exe` and ran to the end. This is a hypothesis: the cause was not proven, and if a server ever dies like this without a log line, that is a bug to chase. The Linux run next to it was not affected.
2. **Linux keeps about 19 MiB after the first password hash.** In a separate probe (not part of the results; Linux, same binary), RssAnon was 21.4 MiB when ready, 21.7 MiB after `tenko setup` (VmHWM reached 66.4 MiB during it, so that memory was released), 40.8 MiB after the first `tenko login`, and it stayed there (41.1 MiB after eleven logins). The size matches one Argon2id hash at the baseline cost (19,456 KiB). This is the usual glibc behaviour: after a large block has been freed once the dynamic mmap threshold rises, the next large allocation comes from an arena, and the arena keeps it. On Windows private bytes fall back to 12.5 MiB after setup and login (peak 32.55 MiB). Setting `MALLOC_MMAP_THRESHOLD_` (which switches the dynamic threshold off), calling `malloc_trim` after hashing, or another allocator would probably give most of these 19 MiB back on Linux; none of that was tried.
3. **Windows CLI calls are slow.** Each `tenko prefix create` takes 0.36 s on Windows against 0.027 s on Linux for the same server work (71 s against 5.4 s for 200 prefixes; 371 s against 46 s for 1,000). The cause was not investigated (process start, certificate chain validation against the system store and endpoint protection are candidates).
4. **Slow disk.** The repository drive D: is an SMR disk. Everything the server wrote went to the NVMe `%TEMP%` (Windows) and to ext4 `/tmp` (Linux), as the brief said; nothing was run with the data directory on D:.
