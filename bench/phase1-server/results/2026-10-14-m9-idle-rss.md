# M9 idle RSS of `tenko serve --roles controller`: `main` against WP3.5a, 2026-10-14 (Windows)

Measurement M9 (OPS-15, idle resident set below 100 MB), each time run with the same script on two builds at the same time: a release build of `main` at `14c1cf6` and a release build of branch `wp35a` (WP3.5a: the metrics core, the request metrics, the gauge timer). The slice 3 rule: no merge may raise the idle RSS by more than 3 MiB without the lead's consent. The first pair measured the branch with its request series on 32 shards; after the lead's decision to seal the two request families with at most eight shards, the second pair measured the branch again. The second pair is the result.

## Where the difference comes from

The counter and histogram families keep one stripe of cache lines per shard, and every stripe is written with zeros when the family is sealed at start, so all of it is resident. Since `9905a68` the shard count is a parameter of the seal: the request families pass `min(available parallelism, 8)` (8 on this machine), the process counters keep the default (32 here).

| Family | Series | Cells per stripe | Shards | Bytes |
|---|---|---|---|---|
| `tenko_http_requests_total` | 6,164: 268 route and method rows (252 documented operations, `ui` and `other` for 8 method labels) x 23 status labels | 6,164 (771 lines) | 8 | 394,752 |
| `tenko_http_request_duration_seconds` | 40 route classes, 17 cells each (15 bounds, `+Inf`, the sum) | 680 (85 lines) | 8 | 43,520 |
| `tenko_http_refused`, `_idempotent_replays`, `_connections` | 3 + 1 + 5 | one line each | 32 | 6,144 |
| Total | | | | 444,416 (0.42 MiB) |

The estimate series x shards x 8 bytes: (6,164 + 680) x 8 x 8 + 9 x 32 x 8 = 440,320 bytes (the table rounds each stripe up to whole cache lines). With 32 shards for all families, as in the first attempt, the same tables took 1,759,232 bytes (1.68 MiB). The gauges (one value per series, not striped, 679 series and slots) take about 5 KiB, the interned label values of the request series about 40 KiB.

The rest of the difference, about 0.5 MiB, is code and heap of the new start-up work: the route table and the label interning at start, and the rounds of the gauge timer (store status, job lists, the connector list, the KEK status, the audit export cursors and the backup summary, code that `main` does not run while idle).

Before both pairs, a build that built the route table from the cached OpenAPI document of the whole API measured +27 MiB at start, because that document stayed in memory; since `8b428ed` the table comes from the document the router assembly builds and drops anyway.

## Method

`bench/phase1-server/m9-idle-rss.ps1` as committed on the branch: the defaults (200 prefixes, 600 s idle, a sample every 30 s, the platform key provider), the two runs of a pair at the same time on ports 18443 (`main`) and 18445 (`wp35a`). The second pair started at 14:53:35 local time (+02:00) with nothing else running; the first at 14:03:44, with the paired M8 runs of the same day from about 40 s into its idle phase until 2 minutes before its end (the idle samples do not move with them).

```
pwsh -NoProfile -File bench\phase1-server\m9-idle-rss.ps1 -Binary F:\wp35a-m9\m9-main-server.exe -Port 18443 -WorkDir %TEMP%\tenko-m9-wp35a-main-3 -OutDir bench\phase1-server\results\raw\wp35a-main
pwsh -NoProfile -File bench\phase1-server\m9-idle-rss.ps1 -Binary F:\wp35a-m9\m9-branch-server.exe -Port 18445 -WorkDir %TEMP%\tenko-m9-wp35a-branch-3 -OutDir bench\phase1-server\results\raw\wp35a-branch
```

The first attempt used the work directories `...-main-2` and `...-branch-2`. The script needed one fix before it (commit `9a36649`): since the setup token file, the server's console names the file instead of printing the token when its standard output is not a terminal, so both M9 scripts read `<data_dir>/setup-token` now. An earlier try failed at `tenko setup` on both builds for that reason.

## WP3.5b: `main` `a89bafe` against `wp35b` `d54a5b9`

The same measurement for WP3.5b (the `metrics` topic of the event stream, `Metrics.Snapshot` between controllers, the live metrics of the start page), run with the same script on two release builds at the same time: `main` at `a89bafe` (WP3.5a merged) and branch `wp35b` at `d54a5b9`. Nobody subscribes to the `metrics` topic during the run, so the branch's publisher sleeps; the difference is what the package costs at rest.

WP3.5b raises the idle working set by 1.20 MiB, inside the 3 MiB budget of the slice 3 rule. Private bytes move by up to 3 MiB from run to run with the same binary (see the WP3.5a pairs above), so the working set is the figure to compare. Both builds idle about 13 MiB higher than the builds of the WP3.5a pairs (`main` `14c1cf6` 59.66 MiB, `wp35a` `e859606` 60.59 MiB), with the same working set when ready (46.1 against 45.4 MiB) and a higher peak during the data creation (81.6 against 69.3 MiB): the rise lies between `e859606` and `a89bafe` (the squash of WP3.5a, the rustls update `194ebae`), both builds of this pair carry it, and it is not measured further here; only the difference within the pair counts.

### Where the difference comes from

The new static families are small: `tenko_store_commit_duration_seconds` (one histogram series of 18 cells, three cache lines per stripe on 32 shards: 6 KiB) and the counters `tenko_ipam_ingest_batches_total` and `tenko_ipam_ingest_facts_total` (one cache line per stripe on 32 shards each: 4 KiB together). The event hub keeps one counter per topic and a `Notify`; the sleeping publisher and the sampler hold no snapshot. The rest is code: the release binary grows by 754,176 bytes (the publisher, the sample builder, the `Metrics` service and client, the larger embedded web UI), and the pages touched at start and by the gauge timer count in the working set.
