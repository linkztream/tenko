# M9 idle RSS of `tenko serve --roles controller`: the Slice 3 build, 2026-10-16 (Linux)

Verdict: FAIL (idle VmRSS 120.9 MiB against 95.37 MiB)

This is the glibc build, which does not ship. The static musl binary of the same source passes ([2026-10-16-m9-linux-memory.md](2026-10-16-m9-linux-memory.md)), and since 2026-10-17 the procedure builds the musl binary ([2026-10-17-m9-idle-rss.md](2026-10-17-m9-idle-rss.md)).

Measurement M9 of the Phase 1 plan (section 8): idle RSS below 100 MB (OPS-15), 10 minutes idle after the data creation. This is the first Linux run since [2026-10-09](2026-10-09-m9-idle-rss.md), which measured a build from before Slice 3 (deviation 70 of [phase-1-exit.md](../../../docs/plans/phase-1-exit.md)). It ran twice, with the same binary and the same script, `m9-idle-rss.sh`, by the procedure of [../README.md](../README.md), inside WSL2. Both runs fail by about 25 MiB.

## Method

As in [../README.md](../README.md): a fresh data directory, the shipped defaults (`internal_ca` TLS, profile `home`, `[kek] provider = "platform"`, which falls back to a plain key file for a non-root user in WSL), `hibp.online = false`, first-run setup and login with the CLI, 200 prefixes (one /8, four /16, 195 /24) with `tenko prefix create`, 600 s idle with a sample every 30 s, then `SIGTERM`.

```
bash bench/phase1-server/m9-idle-rss.sh --binary /home/plm/m9-bin/tenko-64e337d --port 18444     (inside WSL, as user plm)
```

Both runs ran on a workstation that was also running builds and tests on Windows. The idle readings rose by 1.7 MiB (run 1) and 1.3 MiB (run 2) in the first 60 s and were flat after that, within 0.4 MiB.

## Verdict

M9 is not met on Linux for this build: idle VmRSS after 10 minutes is 120.5 and 120.7 MiB, 25 MiB over 95.37 MiB, in two runs. Phase 1 exit criterion E11 (OPS-15) on Linux is therefore not met. The Windows result of [2026-10-15](2026-10-15-m9-idle-rss.md) (working set 73.70 MiB) is still a pass.

## Caveats and leads

- Not measured: where the anonymous 13 MiB come from, and how much of the file-backed 32 MiB a stripped binary or the static musl release binary would save. A stripped binary sheds symbol tables, which are not loaded; the resident file pages are code and read-only data that ran, so most of the file-backed rise is the larger program itself. Deviation 24 of the exit document (the bisect of the Windows rise from about 60 to about 73 MiB) is the related open item.
- Linux was measured inside a WSL2 VM, not on bare metal; the allocator is glibc malloc. The release binary for Linux is the static musl build (deviation 30), which this procedure did not build at the time; it does since 2026-10-17.
- The data set is CLI-created prefixes, not an import, and only the controller role exists, as in every M9 run so far.
