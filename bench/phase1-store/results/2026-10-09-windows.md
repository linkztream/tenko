## M1: index swap on snapshot install

**Method.** A leader (node 1) and a learner (node 2) run in one process over `InProcessNetwork`, each with its own data directory. The learner holds a test `DerivedIndex` modelled on Spike A's serving index: 64 shards of `RwLock<HashMap<Bytes, Bytes>>` behind an `ArcSwap`; `apply` updates the live image in place, `build` scans the table in pages of 20,000 rows into a new image, `install` swaps it in. N records of 150 bytes (22-byte key, 128-byte value) are loaded into the leader in batches of 10,000 records, the leader snapshots and purges its log, and the learner catches up from that snapshot (its first install builds the index). The learner is then cut off. Each round updates a random 10 percent of the records on the leader, snapshots, and pushes the snapshot to the learner through `RaftStore::receive_snapshot()` + `write_chunk` + `install(vote, meta)`. Four reader threads look up random keys that exist throughout, at a fixed 50,000 lookups/s in total (paced per millisecond, each lookup timed on its own with `Instant`), once for a baseline window without an install and once from the first streamed byte until the learner has applied the snapshot (the install window). A lookup that returns nothing is an empty read; a lookup that returns the value of another record is a mismatch. After the last round the learner is reconnected and must follow the leader by log again.

**Configuration.** 3 rounds per size; 4 reader threads; 50,000 lookups/s in total; baseline window 8 s (after 1 s of warm-up); 10 percent of the records updated per round; batches of 10,000 records; `sm_cache_bytes` 32 MiB, `log_cache_bytes` 4 MiB (store defaults); durability: Deferred, 1 s checkpoint interval (the default); snapshots: manual: snapshots on request only, keep_entries 0; index: 64 shards of RwLock<HashMap<Bytes, Bytes>> behind ArcSwap; apply in place, build by paged scan, install by swap.

Memory available at the start: 38.50 GiB.

### Observations

- No reader of the learner's index ever saw an empty or a wrong value during any of the six measured installs: the store builds the new image from the installed state while the old image keeps serving, then swaps it in (ADR 0002 condition). The install p99 stayed within 0.65x to 1.06x of the baseline p99.
- Single lookups in the millisecond range occurred in baseline windows as well as in install windows (12.9 ms in a 6,000,000-record baseline window), so the maxima reflect the shared machine rather than the install.
- At 6,000,000 records an install takes about 27 s end to end; the index rebuild is 5.0 to 6.7 s of it, the rest is writing the new state into redb. During that time the process holds both index images: the resident set rose by about 1.5 GiB (for example 1785 to 3308 MiB) for a learner and a leader in one process. Capacity planning for large zones should count one extra index image during an install.
- The second and third rounds of each size install over a populated index, which is the case the condition is about; the first install of a fresh learner replaces an empty one.

## M2: crash and restart

**Method.** The benchmark binary starts itself in a hidden child mode that opens a store in a data directory and writes batches under `bulk` or `steady` load. Every batch writes `m` rows, one manifest row that states `m`, bumps a counter and carries one audit draft. After `propose` returns, the child appends the batch id, the revision and `m` to `acks.log`. The parent kills the child at a random point with `Child::kill` (`TerminateProcess`), reopens the store with `verify_full_audit_chain: true`, times the open, verifies the invariants below over the whole store (not only the last run), shuts the store down cleanly and starts the next child. Each sequence reuses one data directory, so the store grows over its kills.

Invariants checked after every restart:

- every acknowledged batch exists at the acknowledged revision with all rows
- every manifest has exactly m contiguous rows at its revision with the right content; no rows without a manifest
- manifests = counter = audit head = revision
- verify_chain over sys.audit ends at the status head; audit record seq = revision
- the journal is contiguous from journal_oldest to the revision with journal_len change sets

**Configuration.** Bulk: 2 writers, 1000 rows + manifest per batch, 5 ms pause, at most 60 batches per run. Steady: 24 concurrent writers, 1 to 4 rows + manifest per batch, 0 to 3 ms pause. Kills: 90 percent of kills 300 to 1500 ms after the child reported the store open; 10 percent 20 to 400 ms after the process started, whatever it was doing (often opening the store) Snapshot policy: every 60 entries or 12 MiB of log, 10 entries kept. Journal retention: 20,000 change sets. Parent: RaftStore::open with verify_full_audit_chain: true, then verification, then a clean shutdown. Deferred durability uses a 1 s checkpoint interval.

### Observations

- 160 abrupt kills over five sequences (3 of them before the child had finished opening the store) left no partial batch, no lost acknowledged commit and an audit chain that verified in full every time.
- "Committed but never acknowledged" counts batches that the store committed while the child was killed before it could write the acknowledgement line: the client never learned the outcome, which is what idempotency keys are for (API-04). The opposite case, an acknowledged batch missing after the restart, never occurred.
- Most restarts happened after a log purge (152 of 160), so the start-up path through the snapshot plus the remaining log was exercised throughout, both with deferred durability (state made durable by checkpoints and recovered from the log) and with immediate durability.
- Restart time grows with the size of the store. In the bulk sequence with deferred durability the open took 85 ms at 60,000 rows and 755 ms at 2,024,000 rows; the "Verification" column is the benchmark's own invariant check after the open, not part of it. After an abrupt stop redb rebuilds its allocator state on the next open, which a clean shutdown avoids; restarts after a clean shutdown were not separated out here.

## M5: coalescer ceiling

**Method.** A single-voter store is preloaded with 1,000,000 records. Open-loop writers offer single-record updates at 1,000, 2,000 and 5,000 per second for 30 s each. A dedicated thread issues, every millisecond, the number of proposals that are due, each as its own task, so a late timer tick delays proposals but never lowers the offered rate. An update is a `WriteBatch` with one `put` of a 128-byte value under a 22-byte key (150 bytes) of a random existing record and one audit draft, as a DNS update would be. Latency is measured from just before `propose` to its return and includes queueing in the coalescer. Achieved updates/s counts proposals that returned before the end of the 30 s window. After the open-loop windows, 256 writers each propose in a closed loop for 20 s (the maximum). Entries, batches and log commits are `engine_stats()` deltas over each window including the drain. The whole sequence runs once with `SmDurability::Deferred` (the default) and once with `SmDurability::Immediate`. PASS when the 1,000/s level is sustained (at least 99 percent of the offered rate returned within the window) with zero errors.

**Configuration.** Coalescer: at most 1,000 batches and 8 MiB per entry, 4 entries in flight; `sm_cache_bytes` 32 MiB, `log_cache_bytes` 4 MiB; snapshots: default (10,000 entries or 64 MiB of log, 1,000 entries kept); deferred checkpoint interval 1000 ms; update: one put of 128 bytes under a 22-byte key plus one audit draft; a random existing record.

### Observations

- The coalescer does what ADR 0002 decision 4 needs: on the leader every Raft entry costs one fsynced log commit (log commits equal the Raft entries, within 2, in every window, because openraft 0.9 waits for each flush), and the store answers by putting more batches into each entry as the load rises, from 5.1 batches per entry at 1,000/s to 32.2 at 5,000/s and 45.3 in the closed loop (deferred durability).

ADR 0002 expects dynamic-update latency of 50 to 200 ms under heavy load.

## M6: disk growth after re-seed

**Method.** A leader is loaded with N records in batches of 10,000, then runs a compressed week: seven rounds, each updating a random 10 percent of the records, deleting 1 percent and inserting 1 percent new ones, in batches of 10,000 mutations. After the load and after every round the sizes are recorded. Raw is defined two ways: *all tables* is `status().data_bytes`, the live keys plus values of every table including the journal, audit records, counters and idempotency records; *user table* is the keys plus values of the data table itself, counted by a full scan. After the last round the leader takes a final snapshot. A fresh learner is then added; the leader's log has been purged past the start, so the learner catches up by snapshot install, which writes `sm.redb` in key order in one transaction. The learner's `sm.redb` is compared with raw. File sizes are the lengths of `sm.redb` and `log.redb` and the total size of the `snapshots` directory while the stores run; sizes after a clean shutdown, and redb's own accounting of the closed files (read with redb 4.3.0), follow. The measurement ran 4 times; each heading names the record count and the journal retention. ### Observations

**At the store's default configuration M6 fails: the snapshot-installed (re-seeded) `sm.redb` is 2.05x raw at 1,000,000 records and 2.74x at 1,500,000.** The figures are taken after a re-seed: the learner was seeded by a snapshot install that openraft chose because the leader had purged its log, the comparison Spike A made when it measured 1.19x. Three components explain the file, all read from redb's own accounting of the closed files above.

1. **The user data itself is compact after a re-seed.** The record table of the re-seeded learner takes 166.5 MiB of pages for 143.1 MiB of keys and values (1.16x; the stored 150.7 MiB include the store's 8-byte revision per value, and 9.7 MiB are B-tree branch pages). That is Spike A's 1.19x. The table written incrementally on the leader during the week takes 178.2 MiB, so most of the leader's growth is not in the live pages but in free pages (760.3 MiB "fragmented" in a 1028.0 MiB file).
2. **The journal is as large as the data under bulk writes.** `sys.journal` lists every changed key of every batch. With batches of 10,000 records, each change set is about 0.6 MiB, and the default retention of 100,000 change sets never trims during this week: 177 change sets hold 107.1 MiB, and redb stores each of these large values in a power-of-two run of pages, which leaves another 76.9 MiB unused inside them. The journal therefore occupies about 184 MiB, more than the record table. With a retention of 20 change sets the journal shrinks to 12.8 MiB stored plus 9.2 MiB unused, and the re-seeded file at 1,000,000 records drops from 514.0 MiB to 257.0 MiB (1.65x all tables, 1.80x user table: below 2x).
3. **redb grows a file below 4 GiB by doubling it** (redb 4.3.0, `TransactionalMemory::grow`) and shrinks it at commit only when at least half of the last region is free. A file written in one transaction therefore ends between 1x and 2x of its allocated pages, depending on where the allocation falls: the re-seeded 1,000,000-record file allocates 350.7 MiB in a 514.0 MiB file, the 1,500,000-record file 526.1 MiB in a 1028.0 MiB file. This is why the smaller journal passes at 1,000,000 records (188.7 MiB allocated, file 257.0 MiB) and still fails at 1,500,000 (272.0 MiB allocated, file 514.0 MiB, 2.26x). The ratio after a re-seed is decided by a power-of-two boundary, not by the data.

An offline `redb::Database::compact()` of the closed, re-seeded file removes that slack in under a second: 514.0 to 351.0 MiB (0.4 s, 1.40x all tables) and 1028.0 to 526.0 MiB (0.5 s) at the default retention; 257.0 to 188.7 MiB (0.8 s, 1.21x all tables, 1.32x user table) and 514.0 to 272.0 MiB (0.7 s, 1.20x all tables, 1.27x user table) with a retention of 20. Compaction does not repair the incrementally written leader file (1028.0 to 534.0 MiB, still 2.13x all tables at 1,000,000 records), which matches Spike A: re-seeding, not compaction, is what makes a file dense.

**Recommendation for the lead (policy that meets the condition; not implemented in WP1.1).**

- *Layout change: re-seed into a fresh file and compact it.* A snapshot install writes the new state into a new `sm` file, compacts it while it is still private (no reader holds it), and switches to it atomically through a small pointer file; the old file is removed once its last reader is gone. This also means a crash during an install leaves the previous state untouched. Measured effect: 1.20x to 1.40x of all tables after the re-seed at both sizes, from 0.4 to 0.8 s of compaction.
- *Journal retention bounded by bytes as well as by count.* The count bound is unbounded in bytes when batches are large; a byte budget for the journal (for example 16 to 32 MiB in the home profile, carried in each Raft entry so every replica trims the same) keeps a bulk import from doubling the store. Measured effect: with a journal of 20 change sets (12.8 MiB) the re-seeded file is 1.80x the user table before compaction and 1.32x after it, at 1,000,000 records.
- *Re-seed cadence as ADR 0002 states it:* re-seed a node when `sm.redb` exceeds about 2x raw. During this week the incrementally written leader file doubled from 514.0 to 1028.0 MiB (after round 6 in the run shown, after round 4 in the first pass with the same settings) and ended the week at 4.11x of all tables at 1,000,000 records.

With both changes every re-seeded file measured here is between 1.20x and 1.32x raw. The threshold itself is unchanged. The first two recommendations were then implemented (WP1.1b); the section "After WP1.1b" below repeats M6 and M1 with the changed store.

### M1: index swap on snapshot install

**Method.** A leader (node 1) and a learner (node 2) run in one process over `InProcessNetwork`, each with its own data directory. The learner holds a test `DerivedIndex` modelled on Spike A's serving index: 64 shards of `RwLock<HashMap<Bytes, Bytes>>` behind an `ArcSwap`; `apply` updates the live image in place, `build` scans the table in pages of 20,000 rows into a new image, `install` swaps it in. N records of 150 bytes (22-byte key, 128-byte value) are loaded into the leader in batches of 10,000 records, the leader snapshots and purges its log, and the learner catches up from that snapshot (its first install builds the index). The learner is then cut off. Each round updates a random 10 percent of the records on the leader, snapshots, and pushes the snapshot to the learner through `RaftStore::receive_snapshot()` + `write_chunk` + `install(vote, meta)`. Four reader threads look up random keys that exist throughout, at a fixed 50,000 lookups/s in total (paced per millisecond, each lookup timed on its own with `Instant`), once for a baseline window without an install and once from the first streamed byte until the learner has applied the snapshot (the install window). A lookup that returns nothing is an empty read; a lookup that returns the value of another record is a mismatch. After the last round the learner is reconnected and must follow the leader by log again.

**Configuration.** 3 rounds per size; 4 reader threads; 50,000 lookups/s in total; baseline window 8 s (after 1 s of warm-up); 10 percent of the records updated per round; batches of 10,000 records; `sm_cache_bytes` 32 MiB, `log_cache_bytes` 4 MiB (store defaults); durability: Deferred, 1 s checkpoint interval (the default); snapshots: manual: snapshots on request only, keep_entries 0; index: 64 shards of RwLock<HashMap<Bytes, Bytes>> behind ArcSwap; apply in place, build by paged scan, install by swap.

Raw data over all tables is 174.5 MiB at 1,000,000 records (250.2 MiB before) and 246.1 MiB at 1,500,000 (375.2 MiB before); the user table is unchanged.
- **The running file length still carries redb's growth slack.** Right after its re-seed the 1,000,000-record learner's file measured 441.2 MiB (2.53x all tables, so M6 fails on the running figure), twice the 220.7 MiB it has at rest: the compacted file holds no free pages, so the first commit after the install that needed pages doubled it, and redb trimmed it again when it closed. The 1,500,000-record learner had not grown when it was measured (1.24x). Below 4 GiB redb grows a file by doubling, so while the store runs the file can hold up to as much free space again as it has pages in use. The re-seed rule in the store's documentation is therefore stated on the size at start-up (`DiskUsage::state_ratio_at_open`, about 2.0) or, on the running figure, at about 4.0; the incrementally written leaders ran at 2.95x and 4.18x before their re-seed.
- **Installs take longer by the compaction.** M1 shows no empty read in any round and the lookup p99 within 1.22x of the baseline. Compacting the new file took 1.8 to 2.6 s of a 4.6 s median install window at 1,000,000 records (5.7 s before) and 2.7 to 5.4 s of a 34.8 s median window at 6,000,000 records (27.2 s before); the index rebuild varied between 5.4 and 10.4 s on the shared machine.
