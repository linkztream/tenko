# M16: QPS per core on loopback, the WP4.1 engine (Windows and WSL2)

Verdict: PASS (UDP above 100,000 QPS per server core in every row but Windows with 8 workers, 87,906, where the Spike B baseline is also below, at 88,776, with the load generator on the same cores; TCP documented)

M16 of the Phase 2 plan (section 6) asks for more than 100,000 queries per second per core over UDP on loopback with a 100,000-name zone, and for TCP to be documented. This run measures the WP4.1 engine through its example server (`crates/tenko-dns/examples/authoritative.rs`: the production index, the authoritative resolver, cookies and metrics on, the UDP workers and TCP of the engine), which stands in for `tenko serve --roles dns` until WP4.3 starts the role, with the `bench/phase2-dns` load generator, workers 1, 4 and 8, UDP and TCP, two runs of 30 s per row, on Windows and in WSL2 with the static musl binary. Every figure is a single-node figure (plan section 2.10) and a loopback figure: an upper bound. The comparison is with the Spike B baseline of the same harness (`2026-10-17-baseline-spike-b.md`), row by row on the same platform.

Reading:

- **At 4 and 8 workers on Windows** the engine matches the baseline within one percent in QPS and in CPU per query, although it does more per query than the spike's responder: the view check, the catalog swap load, the index walk with its cut and wildcard rules, cookies when asked, two clock reads and the metrics.
- **At 8 workers on WSL2** the engine with the shared socket reaches 1.78 M QPS against the baseline's 1.72 M at slightly less CPU per query (4.49 against 4.60 us). With `SO_REUSEPORT` it reaches 1.11 M because only about five of the eight server cores were busy: the load generator's eight sockets hash onto the eight worker sockets unevenly, the effect Spike B recorded (ADR 0009) and the reason the worker layout reports the datagrams per worker. A run with 64 client sockets (below) spreads evenly but loads the host differently, so it is not a like-for-like row.
- **At one worker, and at 4 workers on WSL2**, the engine spends 1 to 1.7 us more CPU per query than the spike (7.99 against 6.78 on Windows, 7.71 against 6.05 and 5.35 against 4.37 on WSL2). The second runs of the 1-worker rows (97,563 and 106,641) fell during host load from other work and are not counted. Two candidates were tried in a short A/B on Windows at one worker (20 s per run, two rounds: the default build with metrics on, the same with metrics off, and a build with fat LTO, one codegen unit and `panic = "abort"`, the profile of the Spike B responder): 109,819 and 91,950 QPS, 97,878 and 107,837, and 114,938 and 134,774. Another session's build ran on the host at the same time, so the spread between rounds (up to 20 percent) is larger than any difference between the variants; the LTO build was fastest in both rounds, which suggests the build profile accounts for part of the gap, and the metrics did not show a cost above the noise. M22 measures the metrics cost properly in Slice 6. The binary measured here is built with the workspace's default release profile, the one `tenko` ships with.

TCP has no baseline (the Spike B responder has no TCP). Pipelined TCP with 32 queries in flight per connection answers more queries per core than UDP, because a connection's queries are read and their answers written in batches (one read and one write system call for many queries); on Windows TCP stops scaling past 4 runtime threads, as loopback TCP does there.

### `SO_REUSEPORT` with 64 client sockets (WSL2)

The same 256 queries in flight as 64 sockets with 4 each reach every worker (the busiest worker received 8 to 15 percent more datagrams than the least busy one, from the server's counters; with the shared socket the spread is under 1 percent), but 64 client threads on 32 vCPUs change the host's load and the server's cost per query (10.31 and 14.66 us): 388,306 QPS at 4 workers (97,020 per server core) and 527,231 at 8 (68,191). These rows are recorded for the layout question only; they are not M16 rows. The two-host measurement (M17) is the place to compare the socket layouts with a load generator that does not share the CPUs.

## Method

`scripts/run-loopback.sh` starts the server for every worker count and transport, waits until it answers, runs the load generator for 2 s of warm-up and a 30 s measured window with the server sampled by pid (CPU time at both ends of the window, RSS every 100 ms), and stops it. The load layout is the baseline's: 8 clients x 32 in flight (256 outstanding queries), closed loop, EDNS on (OPT, UDP size 1232), `--require-aa`. For TCP each client is one connection with 32 pipelined queries. `--workers` sets the UDP workers and the tokio threads that serve TCP. Metrics are on (the production setting). Windows ran first, then WSL2, then the two extra WSL2 sets.

Windows (Git Bash, from `bench/phase2-dns`):

```
scripts/run-loopback.sh --harness <phase2-dns.exe> --server-binary <authoritative.exe> \
    --server-cmd "<authoritative.exe> --workers {workers} --metrics {metrics} --listen {listen}" \
    --label tenko-wp41-windows --names data/100000/queries.txt --workers "1 4 8" \
    --transports "udp tcp" --metrics on --require-aa --duration 30s --runs 2 \
    --out results/raw/m16-windows.jsonl
```

WSL2 (from a copy of the source in the VM's file system, through `wsl -d Ubuntu-24.04`):

```
scripts/run-loopback.sh --harness <phase2-dns> --server-binary <authoritative> \
    --server-cmd "<authoritative> --workers {workers} --metrics {metrics} --listen {listen}" \
    --listen 127.0.0.2:5399 --label tenko-wp41-wsl2-musl --names data/100000/queries.txt \
    --workers "1 4 8" --transports "udp tcp" --metrics on --require-aa --duration 30s --runs 2 \
    --out results/raw/m16-wsl2.jsonl
```

The shared-socket set adds `--mode shared` to the server command and runs `--workers "4 8" --transports udp`; the 64-client set adds `--mode reuseport` and `--clients 64 --inflight 4`. `phase2-dns report --input <file>` renders the tables (raw records and logs are in `results/raw/`, git-ignored).

## Caveats

- **Loopback.** Client and server share one host and one network stack: upper bounds, nothing about NIC, driver or switch behaviour. M17 measures the real link.
- **Other load on the machine.** Other sessions built and tested on the same host. Host CPU (Windows `Win32_Processor.LoadPercentage`, the whole machine including the server and the generator, sampled every 3 s) averaged per run: Windows UDP 3 and 60 percent (1 worker, runs 1 and 2), 34 and 49 (4), 40 and 36 (8); Windows TCP 52 and 71 (1), 99 and 37 (4), 18 and 55 (8); WSL2 UDP 25 and 53 (1), 78 and 85 (4), 82 and 76 (8); WSL2 TCP 40 and 49 (1), 4 and 85 (4), 87 and 90 (8). The server and the generator themselves account for at most about 7 percent (1 worker) to 50 percent (8 workers) of the 32 logical processors, so the rest is other work or the VM's own overhead; the numbers are if anything lower bounds for an idle machine, and the two runs of a row differ by up to 21 percent (Windows UDP, 1 worker), more than in the baseline.
- **WSL2 is a VM**, not bare-metal Linux; its rows are compared only with the baseline's WSL2 rows.
- **The example server, not `tenko serve`.** The query path is the engine's; the process around it is not the role of WP4.3 (no store, no API). Its RSS (77 to 80 MiB, against 8 to 17 MiB for the Spike B responder) holds the rows of the zone twice: `MemFeed` keeps its own image of the 100,000 RRsets as the stand-in for the store, beside the index built from them; the per-worker query buffers (192 KiB answer arena and two 64 KiB message buffers per worker) and the tokio threads add a few MiB. M18 and M23 measure the index and the role's memory.
- **Hybrid CPU, no pinning.** Threads may land on P- or E-cores.
- **Closed-loop latency** is queueing delay at a fixed 256 outstanding queries (Little's law), as in the baseline; compare latencies only between runs with the same load layout.
- **One zone size, one query mix**: 100,000 names, 95 percent hits and 5 percent NXDOMAIN, A only, no cookies in the queries; answers never need truncation.
- **Metrics on only.** The M22 comparison with metrics off (the example's `--metrics off`) is Slice 6; the short A/B above is not that measurement.
