# M16: QPS per core on loopback, the dns role of tenko serve (Windows and WSL2)

Verdict: PASS (UDP above 100,000 QPS per server core in every row but Windows with 8 workers, 87,999, where the engine's example (87,906) and the Spike B baseline (88,776) are also below, with the load generator on the same cores; TCP documented)

M16 of the Phase 2 plan (section 6) asks for more than 100,000 queries per second per core over UDP on loopback with a 100,000-name zone, and for TCP to be documented, measured against `tenko serve --roles dns`. This run measures the `dns` role of WP4.3 in the real process: `tenko serve --roles controller,dns` with the DNS module on, the 100,000-name `zonegen` zone imported through the command line (`tenko dns import`) into the store and served through the in-process feed, the `bench/phase2-dns` load generator, workers 1, 4 and 8, UDP and TCP, two runs of 30 s per row, on Windows with the release build and in WSL2 with the static musl binary. Every figure is a single-node figure (plan section 2.10) and a loopback figure: an upper bound. The comparison is with the engine's own example server (`2026-10-17-m16-loopback.md`, WP4.1) and the Spike B baseline (`2026-10-17-baseline-spike-b.md`), row by row on the same platform.

## Against the engine's example and the Spike B baseline

UDP, the same rows of `2026-10-17-m16-loopback.md` (the engine's example server, WP4.1) and of `2026-10-17-baseline-spike-b.md`:

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Windows 11 | 1 | 147,441 | 125,217 | 132,583 | 7.99 | 7.54 |
| Windows 11 | 4 | 113,606 | 112,966 | 112,582 | 8.85 | 8.88 |
| Windows 11 | 8 | 88,776 | 87,906 | 87,999 | 11.38 | 11.36 |
| WSL2, reuseport | 1 | 165,299 | 129,722 | 123,188 | 7.71 | 8.12 |
| WSL2, reuseport | 4 | 228,764 | 186,972 | 178,847 | 5.35 | 5.59 |

Reading:

- **The role costs what the engine costs.** On Windows the role's CPU per query is within half a microsecond of the example's at every worker count (7.54 against 7.99, 8.88 against 8.85, 11.36 against 11.38): the process around it (the store, the API, the job runner, the leader services, all idle during the run) adds nothing measurable to the query path. In WSL2 the role is 0.2 to 0.4 us per query above the example at 1 and 4 workers, within the run-to-run spread of these loopback runs on a host that other sessions also used (the load average was 2 to 6 before the WSL2 runs, from another session's test run).
- **Eight workers on WSL2** reached 1.53 M QPS against the example's 1.11 M because the eight client sockets hashed onto more of the eight `SO_REUSEPORT` worker sockets in this run (six cores busy against five); the second run (1.16 M) is the example's figure. This is the flow-hash effect of ADR 0009; `GET /api/v1/nodes/{id}/dns` now shows the datagrams per worker (`udp_workers`), so an operator sees it.
- **Eight workers on Windows** stay below 100,000 per core as the example and the baseline do: the eight load generator threads share the cores with the eight workers. M17 (another host) is the place for that row.
- **TCP** runs on the controller's core runtime in the role, whose thread count was set to the worker count (`[runtime] workers`, at least 2): `tenko serve` has no separate runtime for DNS over TCP. With 2 threads for the 1-worker row, TCP reaches 566 k QPS on Windows and 946 k in WSL2; Windows stops scaling past 4 threads as loopback TCP does there, WSL2 reaches 2.17 M at 8.

### A run on a loaded host

A first Windows run of the same configuration (commit `69f46fa`) fell during another session's workspace test run on the same machine: 127,318 / 382,612 / 565,628 QPS at 1 / 4 / 8 UDP workers, 7.82 / 10.27 / 12.83 us per query. The one-worker row matched; the multi-worker rows lost 15 to 20 percent to the competing load. The table above is the run on a quiet host (no other build or test process, load average 0 in WSL2), and the one this verdict uses.

## Method

| Item | Value |
| --- | --- |
| Machine | Intel Core i9-13900K (24 cores, 32 threads), 64 GiB RAM; Windows 11 Enterprise 10.0.26300; WSL2 Ubuntu 24.04.3, kernel 6.18.33.2-microsoft-standard-WSL2, 32 logical CPUs and 51 GiB RAM visible |
| Toolchain | Rust 1.99.0 (stable); the workspace release profile |
| Binaries | Windows: `cargo build -p tenko --release --locked` with the web UI embedded (`ui/dist` built), at `843e1ec`. WSL2: `cargo build -p tenko --release --locked --target x86_64-unknown-linux-musl`, static-pie, at `56d735c`. The commits between them change the feed's decoding and the status, not the query path |
| Harness | `bench/phase2-dns` (`phase2-dns` 0.1.0), built the same way per platform |
| Address | Windows `127.0.0.1:5399`; WSL2 `127.0.0.2:5399` (WSL2 does not deliver 127.0.0.1 traffic to local sockets) |
| Node | One node: `roles = "controller,dns"`, the TLS mode `reverse_proxy` on loopback, a key file, `[runtime] workers` = max(workers, 2), `[dns] listen` the address above, `[dns] workers` 1, 4 or 8, every other `[dns]` key at its default (cookies on, `udp.socket = "auto"`, no forwarder, no query log) |
| Zone | `phase2-dns zonegen --records 100000`: `example.test.zone` imported once with `tenko dns import example.test example.test.zone --replace` into a zone created with `tenko dns zone create` (100,003 RRsets: 100,000 A records, the SOA, the NS and the glue); the import took 2.1 s on Windows and 5.3 s in WSL2 |
| Load | `run-loopback.sh --workers "1 4 8" --transports "udp tcp" --require-aa --duration 30s --warmup 2s --runs 2 --settle 2`: 8 client sockets (connections) with 32 queries in flight each, the `queries.txt` of the same zonegen run (5 percent NXDOMAIN), the server's CPU and RSS sampled by pid |
| Server start | The script starts `tenko serve --config cfg-{workers}.toml` for each run on the same data directory, waits until the role answers and stops it after the run; the role builds its index from the store at each start (0.7 s for this zone) |

The scripts and the raw records (`results/raw/`, not committed) are kept by the run; the driver that set up the node, imported the zone and called `run-loopback.sh` is described in this table.
