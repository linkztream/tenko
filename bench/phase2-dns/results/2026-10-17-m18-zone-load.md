# M18: zone load and index memory at 1 M and 6 M RRsets (WSL2 musl and Windows)

Verdict: FAIL (load: a zone file import of 7.2 M RRsets is served 822 s after it starts on the musl binary and 198 s on Windows, above 60 s, and the import alone without the dns role takes 443 s and 125 s; the role's own load, the index built from the store at start, takes 51 s and 35 s, under 60 s. Index memory PASS: the index holds 926 MiB at 7.2 M RRsets, under 1.5 GiB, so the compact layout is not needed; the process RSS after a start is 2.32 GiB and 1.68 GiB above an empty node, because the start-up image is held while the index is built)

M18 of the Phase 2 plan (section 6) loads the Spike A data set at 1 M and 6 M RRsets through the zone file import and the feed, and asks for a load under 60 s and an index memory under 1.5 GiB at 6 M, else the compact index layout is scheduled. This run uses the `zonegen` data set of `bench/phase2-dns` (the Spike A data set record for record: `--records 1000000` and `--records 6000000` give the forward zone `example.test` with that many `host-{n}` A records and three reverse zones with a PTR record for every fifth host, 1,200,009 and 7,200,009 RRsets in four zones). Each run starts one node (`tenko serve --roles controller,dns`, four UDP workers), creates the four zones and imports the four zone files with `tenko dns import --replace` (the import job of WP4.2: one store write per 5,000 RRsets), waits until the role answers the last host name, restarts the node and reads the start step of the role, then starts an empty node for the baseline RSS. A second run imports the same files into a node without the dns role, to separate the import from the feed. Linux figures come from the static musl binary, the one that ships; the Windows figures from the release build beside them. Every figure is a single-node figure.

Reading:

- **The load threshold fails on the import path, not on the feed.** Most of the time is the import job itself: without the dns role it takes 443 s (musl) and 125 s (Windows) for 7.2 M RRsets, the time WP4.2 measured for 1 M (16.6 s on Windows) scaled up and slower on musl. The role is answering the last name about one second after the last job ends, so the feed keeps up with the import; what it costs is CPU and allocation beside the import (below). The role's own load, from the store into the index when a node starts, is 51 s and 35 s at 7.2 M RRsets, under 60 s.
- **What the role adds to an import.** With the role on, the same import takes 14 percent longer on Windows at 1 M (23.2 against 20.3 s) and 49 percent at 6 M (185.8 against 124.8 s), and 54 percent (1 M) and 85 percent (6 M) on musl. Two changes of this package halved the cost at 1 M on Windows (28 percent before them): the store's apply path only queues the stored bytes of the changed rows and the feed decodes them aside (`843e1ec`), and change sets that queue up behind a busy writer reach the index as one delta (`ee93f3e`, which made no difference here because the writer kept up). What remains is the index writer working beside the import: each delta of 5,000 RRsets copies the overlay of the zone it touches, and the overlay is folded into a new base each time it passes an eighth of the base (the limit `docs/dns.md` section 12.11 records), which on a zone that grows from nothing to 6 M names means copying and rebuilding a large structure many times. On musl, whose allocator serialises the threads more than the Windows heap does, that work slows the import threads as well. The way out is in the index (an incremental base, or a bulk path that builds a zone's base once when an import replaces it), not in the feed; until then an operator who imports millions of records into a serving node waits longer, and a node that starts with them loads in under a minute.
- **Index memory passes.** The index holds 926 MiB for 7,200,009 RRsets, 135 octets per RRset, counted by the instrumented allocator (`crates/tenko-dns/tests/index_memory.rs`: the bytes allocated and not freed after the image is dropped, so the allocator's own overhead and what it keeps after a free are not counted). The figure is the same on both platforms because it counts requested bytes. The index's own count of its bases (`IndexStats::base_bytes`, now in the role's start step and in `GET /api/v1/nodes/{id}/dns` as `index_bytes`) is 733 MiB: its arrays and the record data, without the allocation of each record's data. The threshold of 1.5 GiB is met with room; the compact layout of Spike A is not needed for M18.
- **The process is larger than the index.** After a start with 7.2 M RRsets the node's RSS is 2.32 GiB (musl) and 1.68 GiB (Windows) above an empty node. The role builds its index from one image of all its rows (`DnsData`), and at 7.2 M RRsets that image is 3.7 GiB while it exists (the same test counts it), so the start-up peak is the image and the index together; after the image is freed the allocator keeps part of it (musl keeps more). Building the index from the store's rows in pages instead of from one image would lower that peak; it is a follow-up for the feed and the index, recorded in `docs/dns.md` section 12.11. The store's own caches are small (36 MiB by default).

## The counting test

`TENKO_INDEX_RECORDS=N cargo test -p tenko-dns --release --test index_memory -- --ignored --nocapture` builds the image of the zonegen data set in memory, builds the index from it, drops the image and prints what the index holds. On Windows (release build, `7576349`):

| Records | RRsets | Image | Index build | Index holds | Octets per RRset | Bases (own count) |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100,000 | 120,009 | 61.7 MiB | 0.1 s | 15.1 MiB | 132 | 11.9 MiB |
| 1,000,000 | 1,200,009 | 622.4 MiB | 1.3 s | 151.7 MiB | 133 | 119.3 MiB |
| 6,000,000 | 7,200,009 | 3,745.7 MiB | 10.2 s | 926.4 MiB | 135 | 732.7 MiB |

The build of the index itself is 10.2 s at 7.2 M RRsets; the rest of the role's 35 s start on Windows is reading and decoding the rows from the store into the image.

## Method

| Item | Value |
| --- | --- |
| Machine | Intel Core i9-13900K (24 cores, 32 threads), 64 GiB RAM; Windows 11 Enterprise 10.0.26300; WSL2 Ubuntu 24.04.3, kernel 6.18.33.2-microsoft-standard-WSL2, 51 GiB RAM visible. Data directories on the host's F: drive (Windows) and the WSL2 ext4 volume |
| Binaries | WSL2: the static musl build (`--target x86_64-unknown-linux-musl`) at `ee93f3e` for every musl row. Windows: the release build with the web UI embedded at `843e1ec` for every Windows row (`ee93f3e` only changes the hand-over of queued deltas, which did not trigger in these runs) |
| Node | `roles = "controller,dns"` (or `"controller"` for the runs without the role), `[dns] workers = 4`, `[runtime] workers = 4`, a key file, the TLS mode `reverse_proxy` on loopback, the store at its defaults (`durability = "deferred"`, 4 + 32 MiB caches) |
| Data | `phase2-dns zonegen --records 1000000` and `--records 6000000`: `example.test.zone` (202 MiB at 6 M) and the reverse zones `2.0.192.in-addr.arpa`, `100.51.198.in-addr.arpa`, `113.0.203.in-addr.arpa` |
| Import | `tenko dns zone create` for the four zones, then `tenko dns import <zone> <file> --replace --wait-secs 3600` one after the other; the times are the client's, from the start of the command to the end of its job |
| Serving | The load generator asks for `host-{N-1}.example.test` once a second until it gets an answer: the import to serving time has a resolution of about one second |
| Restart | The node is stopped and started again; the step lines `store` and `dns` of the start give the load from the store (`dns ready in ... ms: 4 zone(s), 7200009 RRset(s) ..., index bases 732.7 MiB`) |
| RSS | Windows: the working set of the process; Linux: `VmRSS`. Read 2 to 3 s after each point |
| Host | Other sessions used the machine during parts of these runs (builds and test runs); the WSL2 1 M row with the role (85.7 s) started with a load average of 6 from a build that had just finished. The comparisons with and without the role were run back to back |

An earlier WSL2 run of the 6 M import (at `56d735c`) stopped when the import job outlived the client's default wait of 300 s; the job itself kept running. The runs above wait up to an hour.
