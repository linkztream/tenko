# M20: DNSSEC signing time and re-sign rate at 1 M records (Windows and WSL2 musl)

Verdict: FAIL on the shipped Linux binary, PASS on Windows. Windows 11 (release build): every case passes, the full pass of a million records takes 45 to 70 s and a 100-record change is signed again in 0.50 to 0.61 s. WSL2 with the static musl binary: NSEC passes (224 s with ECDSA P-256, 214 s with Ed25519), NSEC3 sits at the threshold and fails (ECDSA 317 and 321 s in two runs, Ed25519 319 and 295 s), and of 25 changes 24 are signed again within 0.32 to 0.85 s and one took 1.45 s. The musl figures are set by musl's allocator in the store's write path, not by the signer.

M20 of the Phase 2 plan (section 6) asks that the Spike A data set of a million records is signed in under 5 minutes with ECDSAP256SHA256 and with Ed25519, and that a 100-record change is signed again in under a second. This run measures WP6.3 at commit `dc303f2` (the WP6.3 branch with main merged): the leader service `dns.signer` of `tenko serve`, keys in the vault, the rows written through the store. Script: `scripts/run-m20-sign.sh` (raw lines and logs in `results/raw/m20-*`, not committed). Every figure is a single-node figure (plan section 2.10).

Machine: Intel Core i9-13900K (24 cores, 32 threads), 63.7 GiB RAM, Windows 11 Enterprise 10.0.26300; WSL2 on the same host (Ubuntu 24.04.3, kernel 6.18.33.2-microsoft-standard-WSL2, 51 GiB and 32 logical CPUs given to the VM, data directory on the VM's ext4 disk). Binaries: on Windows the release build of `tenko` (`F:/cargo-target-wp63/release/tenko.exe`); on Linux the static musl build that ships (`x86_64-unknown-linux-musl`, release). The machine was shared with other build sessions, so single figures carry some noise.

## Procedure

For each case (algorithm and denial) a new node with an empty data directory: setup and login through the client, `example.test` created as a primary zone with the counter serial, the zone file of `zonegen --records 1000000` (1,000,000 A records `host-{n}`, the SOA, NS and glue) imported with `tenko dns import --replace`. Then:

1. **Full signing.** `tenko dns dnssec enable example.test` with the algorithm (`--algorithm ecdsap256sha256` or `ed25519`, a KSK and a ZSK) and the denial (`--nsec3`: RFC 9276, SHA-1, no iterations, no salt). The time runs from the command until `tenko dns dnssec status` shows a signed serial: key generation, the RRSIGs of every RRset, the NSEC or NSEC3 chain, the DNSKEY, CDS and CDNSKEY sets, written in chunks of 4,000 rows. The zone ends with 3,000,011 rows.
2. **Re-signing a change.** 100 new names imported without `--replace`, five times. The time runs from the start of the import command until the status shows the serial of the signer's pass that follows the import (the serial before plus two): the import job, the client's wait for it, the signer's watch and its incremental pass with the write, so it is an upper bound of the re-signing alone. The time after the import command returned is the signer's own share.
3. The process RSS after the full pass (Windows: the working set; Linux: VmRSS).

## Where the time goes

- **The musl allocator.** On the musl binary everything that writes the store is four to seven times slower than on Windows, the import before signing included (239 to 257 s against 37 to 41 s; M18 saw the same gap). The workspace sets no `#[global_allocator]`, so the static binary runs on musl's own malloc, which serializes the many small allocations of the store's write path across threads; the signer's own work (hashing, signing on all cores, the chain) is a small part of the pass. (A glibc build, not a supported binary, signed the NSEC3 case in 79 s on the same VM.) A faster allocator in the shipped binary (a decision outside WP6.3: it adds a crate) is the likely fix for both M18's load and this.
- **NSEC3 against NSEC.** The NSEC3 pass writes the same number of rows plus a hashed owner per name, and the hashed owners are new store keys spread over the zone, so the write is larger and less ordered; on Windows the pass takes 70 s against 45 s.
- **A change.** About 0.4 s of a change is the import job and the client waiting for it; the signer reads the change from the store's change stream, signs the 100 new RRsets, their neighbours in the chain and the apex, and writes them in 20 to 60 ms (the column "after the import returned"). The one slow round on musl (1.45 s, Ed25519 NSEC3, round 5) most likely waited behind the store's snapshot of 1.4 GB, which the store builds back to back at this size on musl (the log shows one finished every 13 to 14 s, so one was being built during the round).

## Connection resets on the musl binary

During the full passes on the musl binary new API connections were reset now and then (`Connection reset by peer` on the first request of a client): 85 and 210 times over the status polls of one case, once on the first request after a long import, once twice in a row. The node kept running and logged nothing; the API port showed one listener and a few dozen sockets in TIME-WAIT, so no limit was reached. The Windows build saw none. The script now retries such a call up to five times a second apart and logs each retry with the socket states; every retried call succeeded. The cause is not found: it lies in the API listener or the WSL2 network path under the load of the musl write path, not in the signer.

## Reproduce

```sh
# Linux (the static musl binary that ships)
cargo build -p tenko --release --locked --target x86_64-unknown-linux-musl
bash bench/phase2-dns/scripts/run-m20-sign.sh --server-binary target/x86_64-unknown-linux-musl/release/tenko --records 1000000
# Windows (Git Bash, the release build)
bash bench/phase2-dns/scripts/run-m20-sign.sh --server-binary target/release/tenko.exe --records 1000000
# One case, fewer rounds
bash bench/phase2-dns/scripts/run-m20-sign.sh --server-binary ... --cases "ed25519:nsec3" --repeats 3
```

From the repository root; `--harness` names the `phase2-dns` binary when it is not on the PATH.
