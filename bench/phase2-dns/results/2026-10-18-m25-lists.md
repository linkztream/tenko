# M25: block list compile and match, a list of a million names (Windows and Linux musl)

Verdict: PASS (a list of 1,000,000 generated names compiles and builds its matcher in 1.04 s on Windows and 1.56 s with the static musl build on Linux, under the 2 s threshold, into a stored version of 10.8 MiB; a lookup takes 101, 156 and 251 ns for names of 2, 4 and 8 labels on Windows, 121, 160 and 270 ns on Linux, so the cost per label falls from about 50 to 31 ns (61 to 34 on Linux) as names get longer: constant per label at most, and independent of the list's size)

M25 of the Phase 2 plan (section 6) asks that a block list of 1 M names compiles under 2 s and that the match cost is constant per label. This run measures the compiler and the matcher of WP5.2 (`crates/tenko-dns/src/lists`, commit `320643f`) with the example `lists_bench` (`crates/tenko-dns/examples/lists_bench.rs`), which calls the same functions the `tenko` binary links: `compile_text` (parse and compile, the work of the compile job before its write) and `ListMatcher::build` (what the catalog does when a version arrives), then `ListMatcher::matches` (the query path). Each step ran 5 times; the tables give the median. Every figure is a single-node, single-thread figure (plan section 2.10). Script: `scripts/run-m25-lists.sh --binary <lists_bench>`.

Machine: Intel Core i9-13900K (24 cores, 32 threads), 63.7 GiB RAM, Windows 11 Enterprise 10.0.26300; the Linux run in WSL2 on the same host (Ubuntu 24.04.3, kernel 6.18.33.2-microsoft-standard-WSL2, 51 GiB given to the VM), so its figures are VM figures. Rust 1.99.0. Windows: the release build (`cargo build -p tenko-dns --example lists_bench --release --locked`); Linux: the static musl build (`--target x86_64-unknown-linux-musl`), the build that ships, checked static by the script. Other builds ran on the host at times; the medians of 5 rounds stayed within a few percent of single rounds taken before.

## The list

1,000,000 distinct names from a fixed seed: two to four labels, the last one of five top labels, the others 3 to 12 random letters and digits. Written as a hosts file (`0.0.0.0 name`, 30.7 MiB) and as a domain list (23.1 MiB). Random labels are the hard case for the stored form: names of real lists share their parents (many names under one registrable domain), which front coding and deflate shrink further. 9,185 of the names lie below another generated name and are dropped by the compiler (a listed name covers the names below it), so the version holds 990,815 entries.

## Compile

| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| hosts | Windows | 30.7 | 0.937 | 0.107 | 1.044 | 10.8 | 990,815 |
| domains | Windows | 23.1 | 0.918 | 0.108 | 1.026 | 10.8 | 990,815 |
| hosts | Linux musl | 30.7 | 1.314 | 0.250 | 1.563 | 10.8 | 990,815 |
| domains | Linux musl | 23.1 | 1.303 | 0.250 | 1.554 | 10.8 | 990,815 |

- **Compile** is parsing (comments, the hosts form, case folding, IDN), sorting a million keys, dropping duplicates and covered names, front coding and deflating (level 6). The sort and the deflate take most of it. The musl build is about 40 percent slower here, where the work allocates a million small keys: the musl allocator, as in M18.
- **The stored version** is 10.8 MiB: one store value, below the 16 MiB of a store batch, which the version, the removal of the one before and its audit record share. Front coded without deflate the same list took about 16 MB; versions above 64 KiB of entries are deflated for that reason. The limit of a version is 12 MiB (`MAX_COMPILED`); a list that compiles larger is refused with `dns.list.invalid` and keeps its old version.
- **The matcher** of the query path takes 40.8 MiB for these 990,815 names (a table of 2,097,152 slots of 8 octets and the names in wire form); the role holds one per enabled list.

## Match

100,000 query names per row, half at or below a listed name (a listed name with random labels in front, up to the row's label count), half under a top label no listed name has. All 50,000 hits matched and none of the misses.

| Labels | Windows ns per lookup | Windows ns per label | Linux musl ns per lookup | Linux musl ns per label |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 100.9 | 50.5 | 121.2 | 60.6 |
| 4 | 155.9 | 39.0 | 160.4 | 40.1 |
| 8 | 251.0 | 31.4 | 269.6 | 33.7 |

A lookup walks the labels of the name once and probes the table once per label (the hash of each suffix is extended by one label), so its time grows at most linearly with the labels: about 75 ns of fixed cost (the label offsets, the first probe's cache miss) and about 22 to 25 ns per further label. The list's size does not enter: the probe is one slot of a table at load factor below one half. A miss under an unlisted top label costs the same probes as a hit. On the query path the policy runs this for each enabled list (and for the allow lists before them), on names outside the zones only.
