# M18: zone load at 1 M RRsets with jemalloc in the musl binary (WSL2 musl)

Verdict: PASS at 1 M (the import of 1.2 M RRsets is served 51.5 s after it starts with jemalloc, against 176.2 s with musl's own malloc measured back to back; threshold 60 s). 6 M was not measured: the command-line client's 60 s request timeout ends the upload of the 212 MB zone file on both binaries (below), so M18 at 6 M stays as [2026-10-17](2026-10-17-m18-zone-load.md) left it.

M18 of the Phase 2 plan (section 6) loads the Spike A data set at 1 M and 6 M RRsets through the zone file import and the feed, and asks for a load under 60 s and an index under 1.5 GiB at 6 M. [2026-10-17-m18-zone-load.md](2026-10-17-m18-zone-load.md) failed the load on the musl binary (822 s at 6 M) and found the import path, not the feed, to be the cost, slowed further by musl's allocator. This run measures the musl binary with jemalloc as its global allocator (`crates/tenko/src/main.rs`, options in `.cargo/config.toml`) beside the binary without it and the allocators tried on the way; the choice of allocator and its options is explained on the M9 page, [../../phase1-server/results/2026-10-19-m9-idle-rss.md](../../phase1-server/results/2026-10-19-m9-idle-rss.md), whose binaries these are. The procedure of 2026-10-17 is now the script `scripts/run-m18-load.sh`. Every figure is a single-node figure (plan section 2.10).

## Results at 1 M

`zonegen --records 1000000`: example.test with 1,000,000 A records and three reverse zones, 1,200,009 RRsets in four zones. One node per binary, `roles = "controller,dns"`, 4 DNS and 4 runtime workers. Times in seconds, memory in MiB (VmRSS; peak VmHWM).

| Binary | Import jobs: three reverse zones + example.test | Import to serving the last name | RSS of an empty node at ready | RSS after the import | Restart: `store` / `dns` step | RSS after the restart (peak) |
|---|---|---:|---:|---:|---|---:|
| musl's malloc, `6a16654` | 6.6 + 6.9 + 7.4 + 154.3 = 175.2 | **176.2** | 76.0 | 886.4 | 6.4 / 7.9 | 853.0 (1,501.7) |
| mimalloc 0.1.52, defaults (fails OPS-15) | 2.4 + 2.4 + 2.4 + 30.0 = 37.2 | 38.2 | 165.4 | 1,041.5 | 5.7 / 5.8 | 1,349.1 (1,437.7) |
| mimalloc, purge delay 0 and no THP through the environment (fails OPS-15) | 2.4 + 2.6 + 2.6 + 33.6 = 41.2 | 42.4 | 78.6 | 359.1 | 6.2 / 6.4 | 820.6 (1,380.8) |
| jemalloc, two arenas, decay 0 | 2.9 + 2.9 + 2.9 + 36.0 = 44.7 | 45.7 | 81.2 | 350.5 | 5.8 / 7.5 | 784.6 (1,369.9) |
| jemalloc, decay 1000 ms (fails OPS-15) | 2.4 + 2.4 + 2.4 + 30.3 = 37.6 | 41.0 | 84.1 | 960.3 | 5.8 / 6.4 | 959.7 (1,419.9) |
| **jemalloc as shipped, `a5bc069`** | 4.1 + 3.7 + 3.5 + 39.0 = 50.2 | **51.5** | 78.8 | 723.6 | 6.5 / 7.3 | 760.2 (1,356.0) |

- **The import is 3.4 times faster** with the shipped jemalloc options (51.5 against 176.2 s to serving), and under the 60 s of M18 at this size. The faster allocator options (two arenas, or a decay of 1000 ms) import in 41 to 46 s, but cost idle memory or margin under OPS-15 (M9 page); the shipped options give up about 6 s of import for 10 MiB of idle margin.
- **The feed keeps up**: the role answers the last name about a second after the last import job ends with every allocator.
- **Index memory is unchanged**: the role's own count of its bases is 119.3 MiB at 1.2 M RRsets with every binary, as on 2026-10-17; the counting test of that page measures requested bytes and does not depend on the allocator. The process after a restart is smaller with jemalloc (760 against 853 MiB) and its start-up peak lower (1,356 against 1,502 MiB).
- **The baseline is slower than on 2026-10-17** (176 against 87 s to serving at 1 M, the same machine). The reason was not looked for: WP6.1 and WP6.3 have touched the import since `ee93f3e`, and the VM had been restarted. The comparison here is the back-to-back one.

## 6 M

The run at 6 M imported the three reverse zones (24.3, 19.2 and 19.8 s for 1.2 M PTR records each) and then failed on example.test: `tenko dns import` gives every request 60 s (`crates/tenko/src/client/mod.rs`), and the server reads and checks the whole 212 MB zone file within the request before the job starts. A dry run of the same file, which does the same reading and check without starting a job, answered after 59.7 s on the jemalloc binary and timed out after 60.4 s on the binary with musl's malloc. So neither binary can import this file through the client today, although the 2026-10-17 run (`ee93f3e`) imported the same file through the same client. A longer request timeout for uploads, or an upload that is checked by the job, is a follow-up for the import path; until then the 6 M figures of 2026-10-17 stand.

## Method

| Item | Value |
| --- | --- |
| Machine | Intel Core i9-13900K (24 cores, 32 threads); WSL2 Ubuntu 24.04.3, kernel 6.18.33.2-microsoft-standard-WSL2, 51 GiB RAM visible, data directories on the WSL2 ext4 volume |
| Binaries | The static musl builds (`--target x86_64-unknown-linux-musl`, release) of the M9 page; the shipped one is `a5bc069`, SHA-256 `e2b4d548c63191de` (prefix) |
| Node | `roles = "controller,dns"`, `[dns] workers = 4`, `[runtime] workers = 4`, a key file, the TLS mode `reverse_proxy` on loopback, the store at its defaults |
| Serving | The load generator asks for `host-999999.example.test` once a second until it is answered; over TCP, because UDP to the role on WSL2 loopback went unanswered on this day on every node, fresh ones included, while TCP answered (both read the same index) |
| Host | The runs ran one after the other; the shipped binary's run overlapped the idle phase of its M9 run, which uses no CPU |

```sh
cargo build -p tenko --release --locked --target x86_64-unknown-linux-musl
HARNESS=<phase2-dns> bash bench/phase2-dns/scripts/run-m18-load.sh \
  --server-binary target/x86_64-unknown-linux-musl/release/tenko --records 1000000
```

Raw lines (`m18-*.jsonl`, the meta files and the server logs) stay in WSL; they are not committed.
