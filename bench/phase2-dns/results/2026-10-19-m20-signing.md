# M20: NSEC3 signing at 1 M records with jemalloc in the musl binary (WSL2 musl)

Verdict: PASS for the case that failed on 2026-10-18 (ECDSA P-256 with NSEC3 on the shipped Linux binary): with jemalloc as the allocator the full pass of a million records takes 108 s against 312 s with musl's own malloc measured back to back, under the 300 s threshold, and each of five 100-record changes is signed again within 0.33 to 0.98 s. The connection resets of the 2026-10-18 page no longer happen.

M20 of the Phase 2 plan (section 6) asks that the Spike A data set of a million records is signed in under 5 minutes and a 100-record change again in under a second. [2026-10-18-m20-signing.md](2026-10-18-m20-signing.md) found the NSEC3 cases failing on the static musl binary (317 to 321 s with ECDSA P-256) and named musl's allocator in the store's write path as the cause. This run measures the change that replaces it: jemalloc as the global allocator of the musl binary, with its options compiled in (`crates/tenko/src/main.rs`, `.cargo/config.toml`; why jemalloc and not mimalloc: [../../phase1-server/results/2026-10-19-m9-idle-rss.md](../../phase1-server/results/2026-10-19-m9-idle-rss.md)). Only the failing case was run (ECDSA P-256, NSEC3); the NSEC cases and Ed25519 passed or sat at the threshold with the slower allocator and were not repeated. Every figure is a single-node figure (plan section 2.10).

## Results

`scripts/run-m20-sign.sh --cases ecdsa:nsec3 --records 1000000`, one new node per binary, run back to back on an otherwise idle machine:

| Binary | Import (s, not M20) | Full signing (s) | Change, median / largest (s) | After the import returned (s) | RSS after the pass | Calls retried after a connection reset |
|---|---:|---:|---:|---:|---:|---:|
| musl's malloc, `6a16654` | 235.2 | **311.6** | 0.357 / 0.384 (5.494, see below) | 0.030-0.037 | 214.6 MiB | 30 |
| jemalloc, two arenas (variant (d) of the M9 page) | 72.5 | 121.9 | 0.349 / 1.292 | 0.022-0.204 | 1,877.8 MiB | 0 |
| **jemalloc as shipped, `a5bc069`** | **72.4** | **108.4** | **0.589 / 0.983** | 0.027-0.222 | 620.6 MiB | **0** |
| For reference, 2026-10-18: musl's malloc, `dc303f2` | 244.7 | 316.5 and 321.4 | 0.382 / 0.407 | 0.03-0.04 | 2,101 MiB | 85 to 210 per case |
| For reference, 2026-10-18: Windows release build | 41.3 | 69.6 | 0.540 / 0.612 | 0.10-0.12 | 954 MiB (working set) | 0 |

Thresholds: full signing 300 s, a change 1 s.

- **The full pass is 2.9 times faster** with jemalloc (108.4 against 311.6 s), and the import before it 3.2 times (72.4 against 235.2 s). Both stay slower than on Windows (69.6 and 41.3 s on 2026-10-18), but the full pass is now well under the threshold.
- **Changes.** The shipped binary signed all five changes within a second (0.326, 0.342, 0.589, 0.703, 0.983 s); the signer's own share after the import returned grew to 0.12 to 0.22 s in the last three rounds, while the store was building its snapshots of 1.2 to 1.4 GB in the background (the same effect as the one slow round on 2026-10-18). The variant with two arenas had one round at 1.292 s; the shipped options have one arena, which the snapshot builds and the signer share.
- **The baseline's 5.494 s** in its first change round is an artefact: the call that reads the zone's serial before the round was reset by the server and failed after its retries, so the round waited from an empty serial. Without it the baseline's largest round is 0.384 s.
- **Memory under load.** The process holds 620.6 MiB after the full pass with the shipped options, against 1,877.8 MiB with two arenas; musl's malloc, the slowest, held the least at that moment.

## Connection resets

On 2026-10-18 new API connections to the musl binary were reset now and then during the full passes, with nothing logged. They happened again with musl's malloc in this run (30 retried calls, all on status polls during the pass, the API port showing one listener and 450 to 510 sockets in TIME-WAIT), and not once with jemalloc in either variant, through the same script on the same VM. So the resets follow the allocator, not the WSL2 network path; the likely reading is that under musl's malloc the server's API threads stall long enough under the write load for new connections to be dropped. That was not traced further here.

## Method

| Item | Value |
| --- | --- |
| Machine | Intel Core i9-13900K (24 cores, 32 threads), WSL2 Ubuntu 24.04.3, kernel 6.18.33.2-microsoft-standard-WSL2, 51 GiB and 32 logical CPUs given to the VM, data directory on the VM's ext4 disk |
| Binaries | The static musl builds (`--target x86_64-unknown-linux-musl`, release) of the M9 page: the baseline `6a16654`, variant (d) and the shipped `a5bc069` (SHA-256 `e2b4d548c63191de`, prefix) |
| Data | `phase2-dns zonegen --records 1000000`: example.test with 1,000,000 A records, the SOA, NS and glue |
| Procedure | As on 2026-10-18: setup, the zone with the counter serial, the import with `--replace`, `tenko dns dnssec enable example.test --algorithm ecdsap256sha256 --nsec3` timed until the status shows a signed serial, then five imports of 100 new names, each timed until the signer's pass after it |

```sh
cargo build -p tenko --release --locked --target x86_64-unknown-linux-musl
bash bench/phase2-dns/scripts/run-m20-sign.sh --server-binary target/x86_64-unknown-linux-musl/release/tenko \
  --harness <phase2-dns> --records 1000000 --cases ecdsa:nsec3
```

mimalloc, the allocator first chosen, was not run through M20: it failed OPS-15 first. Its import speed is on the M18 page.
