# M21: dynamic update rate end to end, 1,000 signed RFC 2136 updates per second for 60 s (Windows release and Linux musl, one node, same host)

Verdict: PASS (at 1,000 TSIG-signed updates per second for 60 s every one of 60,000 updates per run was answered NOERROR with a valid signature and none was lost; the p99 from the send of an update to its answer was 17.6 and 19.4 ms on the Windows release build and 14.9 and 15.5 ms on the static musl binary of the image, against the 250 ms threshold; a run at 5,000 per second for 30 s also passed on both, p99 36.9 and 35.9 ms)

M21 of the Phase 2 plan (section 6, DNS-11) asks for 1,000 updates per second sustained, with the p99 from the client's send to the answer under 250 ms, on one node. This run measures WP6.2: the update path of the `dns` role (TSIG, the access lists, the prerequisites against the index), the per-zone task that commits the updates waiting for a zone as one change set through the zone service and the store, and the answer only once the role's index holds the commit. Script: `scripts/run-m21-update.sh` with the load generator `crates/tenko-dns/examples/update_load.rs` (raw output `results/raw/m21-*.jsonl` and `.meta.txt`, not committed). Every figure is a single-node figure (plan section 2.10), and with the load generator on the same host every figure is a loopback figure: an upper bound of what the software does, without the delay of a real link.

Machine: Intel Core i9-13900K (24 cores, 32 threads), 63.7 GiB RAM, Windows 11 Enterprise 10.0.26300; WSL2 on the same host (Ubuntu 24.04.3, kernel 6.18.33.2-microsoft-standard-WSL2, 51 GiB given to the VM). Windows: the release build of `tenko` (`cargo build -p tenko --release --locked`), data directory in the user's temporary folder on the NVMe disk. Linux: the static musl binary of the image `tenko:wp62` built with `deploy/Dockerfile` from this branch (`x86_64-unknown-linux-musl`, release, jemalloc), copied out of the image, data directory in the VM's `/tmp`. The server code is the same in both builds (commit `9c9929e` and later; the later commits change tests, the UI, the lab, the docs and the load generator).

## Procedure

1. A new node, `tenko serve --roles controller,dns`, with an empty data directory; the API on loopback, the DNS role on port 15354.
2. Setup through the API (curl) under the Home profile (for updates the Standard profile behaves the same: the zone's `require_tsig` decides); a TSIG key `update.example.test` (HMAC-SHA256, a secret generated for the run) imported; an access list with the one entry `key: update.example.test`; the primary zone `example.test` with that list in `update.allowed` and `require_tsig`.
3. The load generator sends updates over UDP from one socket, paced at the rate (open loop), each signed with the key: delete the A RRset of one of 1,000 owners `m21-<n>.example.test` and add one address, the form of a DHCP client's DDNS update, so the zone stays at 1,000 names. A second thread takes the answers, matches them by id, checks the RCODE and verifies the answer's TSIG in the MAC chain. Five seconds of warm-up, then 60 seconds measured (30 seconds in the headroom runs). An update without an answer within 2 seconds counts as lost.
4. Two measured runs per platform on the same node, then one headroom run at 5,000 per second on a new node.

On WSL2, UDP over the loopback interface `lo` was dropped on the day of the run (a Python echo over 127.0.0.1 timed out as well, while TCP worked; WSL2 runs in VirtioProxy mode on this host), so the DNS role listened on the VM's Docker bridge address (`--dns-address`), a local address of the same host; the API and the metrics listener stayed on loopback. The Windows runs use loopback.

- Every answer of every run carried a TSIG that verified (`bad_signatures` 0) and the RCODE NOERROR; none came late or twice.
- The node's update counters agreed: `tenko_dns_updates_total{outcome="ok"}` 130,006 after the two runs and the readiness probes on each platform. On WSL2 one probe before the load was refused (`outcome="refused"` 1): it reached the node before the update path had read the new access list from the store; the script retries the probe until an update goes through.
- RSS after the two runs: 153.6 MiB (Windows, working set), 129.8 MiB (musl, VmRSS).
- **Where the time goes** (read from the design, not timed step by step in this run). An update waits for its zone's task, which commits whatever waits for the zone as one change set, so under load one commit carries several updates and the commit rate stays below the update rate (risk R52); the number of commits per run was not counted. The p50 of 5 to 7 ms is then one commit of the store with its inline job record plus the time until the role's index serves it (the feed's delta and the index's apply, which the path polls every millisecond). The tail (p99.9 up to 138 ms, the largest 185 ms) is likely commits that met a store snapshot or a larger fold of the index's overlay (section 12.11 of `docs/dns.md`); it stays well under the threshold.

## Reproduce

```sh
cargo build -p tenko --release --locked
cargo build -p tenko-dns --release --locked --example update_load
bash bench/phase2-dns/scripts/run-m21-update.sh --server-binary target/release/tenko \
    --load target/release/examples/update_load --repeats 2
# On WSL2 where loopback drops UDP: --dns-address <a local address of another interface>
```

On Linux the server binary is the static musl build (`--target x86_64-unknown-linux-musl`, or the binary of the image); the script refuses a dynamically linked one.
