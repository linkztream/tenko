# M17: one node over a real link, dnsperf, h2load and flamethrower from another host and from the workstation (Linux)

Verdict: Documented (the number that may be published under ADR 0009: 188,000 QPS on one core over UDP and 444,000 QPS on the node's four cores, 135,000 per busy core, from dnsperf on another VM over a virtual link; TCP 1.95 M QPS; DoT 1.14 M; DoH 226,000)

M17 of the Phase 2 plan (section 6, DNS-27, ADR 0009) asks for dnsperf and flamethrower figures of one Tenko node measured from a load generator on another host over a real link, and from the workstation, documented; E13 asks for them per core, over UDP and TCP, with and without metrics (the metrics side is M22, [2026-10-21-m22-metrics-cost.md](2026-10-21-m22-metrics-cost.md), from the same runs and the same hosts). ADR 0009 holds back every absolute number until such a two-host run exists, because the loopback figures of M16 are upper bounds with the load generator on the server's cores. This is that run. Every figure is a single-node figure (plan section 2.10): one `tenko serve` process with the roles `controller,dns`, the load on other machines.

Which number may be published, and why: the UDP figures from dnsperf on the load VM. They come from the shipped binary (the static musl build of 0.0.2 with jemalloc), from a tool the reader can run (dnsperf 2.14.0), over a link the queries really cross (two VMs, virtio, one bridge), with the server's CPU seconds read from the server host, so that per-core figures are measured, not assumed. The caveats that go with it: the link is virtual (both VMs on one Proxmox host, so the "wire" is the host's bridge and the two VMs may share physical cores), the CPU model is QEMU's generic virtual CPU, and the node has four vCPUs. The workstation run over the physical LAN is slower for a reason outside Tenko (below) and is not the number to publish.

## Beside the loopback figures of M16

UDP QPS per server core, the role of `tenko serve`, the same zone and query file. M16 ran on the workstation (an i9-13900K) with the load generator on the same cores, WSL2 with the musl binary of 2026-10-17 (before jemalloc); M17 runs on a 4-vCPU VM with a generic virtual CPU, with the load on another VM.

| Workers | M16 loopback, WSL2 musl | M17 real link, node VM | M17 TCP real link |
| ---: | ---: | ---: | ---: |
| 1 | 123,188 | 187,813 | 584,456 (2 runtime threads) |
| 2 | | 159,370 | 622,597 |
| 4 | 178,847 | 134,688 | 491,274 |
| 8 | 255,783 | | |

Reading:

- **One core over the link does more than one core on loopback** (188,000 against 123,000): on loopback the load generator's threads and the kernel's work for both ends share the cores the server is measured on, and the server's UDP path pays for the client's packets too. Over the link the node's core does only the server's half.
- **Per core falls from one to four workers** (188,000 to 135,000) and the four workers kept 3.3 of the 4 vCPUs busy. Two effects: `SO_REUSEPORT` hashes the 64 client sockets of dnsperf onto the four worker sockets unevenly (ADR 0009, R40), and both VMs run on one Proxmox host whose physical cores they share: at four workers the node wants four cores while dnsperf keeps five busy on the load VM. The same run with the harness instead of dnsperf (32 sockets) gave 177,000 per core at 3.8 cores busy in its better run and 119,000 in its other, which is the size of the host's noise (M22 measures it).
- **TCP is three to four times cheaper per query than UDP**, as in M16: the queries arrive pipelined (dnsperf keeps 4,096 in flight over 64 connections), so one read and one write carry many queries, where UDP costs a receive and a send per query. With one UDP worker TCP still has two threads: TCP, DoT and DoH run on the core runtime, whose thread count is `[runtime] workers` (at least 2; deviation 79 of the exit document).
- **DoT** costs about 1.7 times plain TCP per query (289,000 against 491,000 per core) at the maximum, and about 0.1 ms of latency at a moderate rate. **DoH** costs about eight times TCP per request (62,700 per core): every request is an HTTP/2 stream with its own headers and a base64url query in its path.
- **The latency at the maximum is queueing**: dnsperf keeps 1,024 (UDP) or 4,096 (TCP, DoT) queries in flight, so the p50 of a saturated run is the queue divided by the rate. The latency of the engine is the one at a moderate rate: DoT at 10,000 per second answers in 0.11 ms at p50 and 0.5 ms at p99 (over TLS 1.3, AES-256-GCM, with the internal CA's certificate), the 30 s flamethrower UDP run at 10,000 per second in 2.1 ms on average (flamethrower's own pacing in bursts every millisecond), and the M22 runs at 100,000 per second against a server of two workers give a UDP p50 of 0.12 to 0.16 ms below saturation (their p99 of 3.2 to 3.8 ms comes with the load VM's eight vCPUs 7.4 to 7.9 busy pacing the queries).

## The workstation run

dnsperf 2.14.0 and the harness ran in WSL2 Ubuntu 24.04 on the workstation (`192.0.2.30`, an i9-13900K) against the node (`192.0.2.10`), over the physical LAN to the Proxmox host. This WSL2 is in mirrored networking mode, not behind WSL2's NAT: the distribution has the workstation's own address on the LAN, and its packets go through the Hyper-V virtual switch of the workstation and then the physical network. Both tools stopped at 80,000 to 90,000 queries per second with the node's four workers 0.66 to 0.94 cores busy, so the node was not the limit: the path through the virtual switch was (WSL2's networking is known for a low packet rate; the latency of 10 to 25 ms at p50 and p99 is the 1,024 queries in flight divided by that rate). The run shows that the node answers clients on the physical network at the rate the workstation can send; it is not a server figure and is not the number to publish. A bare-metal client on the LAN is the run that would give one (the owner's hardware).

## flamethrower

flamethrower 0.12.0 (DNS-OARC, built from source on the load VM) ran over UDP, TCP, DoT and DoH at 10,000 queries per second and at its own maximum (50 generators of 20 queries per millisecond), on the first 100,000 lines of the query file (flamethrower reads the whole file before it sends and its time limit runs from before the read, so with the million lines a run stopped after the first burst):

| Protocol | Offered | Answers per second | Mean latency ms | Timeouts | Server cores busy |
| --- | --- | ---: | ---: | ---: | ---: |
| UDP | 10,000 | 9,751 | 2.1 | 0 | 0.47 |
| UDP | maximum | 153,709 | 9.3 | 456,725 | 1.70 |
| TCP | 10,000 | 94 | 2.9 | 0 | 0.02 |
| TCP | maximum | 967 | 5.7 | 0 | 0.04 |
| DoT | 10,000 | 90 | 43.3 | 0 | 0.02 |
| DoT | maximum | 833 | 40.7 | 0 | 0.02 |
| DoH | 10,000 | 0 | | 1,000 | 0.01 |
| DoH | maximum | 0 | | 10,000 | 0.02 |

- **UDP**: flamethrower sends from one thread; at its maximum it reaches about 150,000 to 250,000 per second (250,000 in a 5 s trial) and loses what it sends faster than its own loop reads the answers, while the node is 1.7 cores busy. Its UDP figure is the tool's limit.
- **TCP and DoT**: flamethrower opens a connection per burst and waits for it, so its TCP rate measures connection set-up, not queries (967 per second, 29,000 connections in 30 s); over DoT every answer arrived about 41 ms after its query, the signature of a small write held back until a delayed acknowledgement, while dnsperf over DoT against the same listener answered in 0.11 ms. Neither figure is the server's.
- **DoH**: flamethrower got no answer at all, even with one generator and one query in flight. dnsperf 2.14.0 over DoH answered with one or two requests in flight per connection (18,800 per second on one connection) and stalled with four or more; curl (100 parallel streams on one connection) and h2load (100 streams per connection, 64 connections) got every answer from the same listener, so the DoH figures above come from h2load. Which side the two tools disagree with was not found; the server answers standard HTTP/2 clients (curl, h2load, the rustls and hyper client of `acceptance_dns_tls.rs`).

The certificate: the internal CA's root was fetched from the node (`<data_dir>/tls/ca-root.pem`, subject `O = Tenko DDI, CN = Tenko DDI local CA ...`), and `openssl s_client -CAfile` on the DoT port and `curl --cacert` on the DoH port both verified the served chain against it (`Verify return code: 0 (ok)`, HTTP/2 200). The certificate carries the node's address (`[tls] addresses`).

## Where the time goes

- **UDP**: about 5.3 us of server CPU per query at one worker (188,000 per core) and 7.4 us at four, against 7.7 to 8.1 us on the workstation's loopback. The query path allocates nothing (ADR 0009, `tests/alloc.rs`); the rest is the kernel's receive and send per datagram on a virtual NIC (virtio), which is why the per-core figure is close to what NSD and Knot reach per core on a real 10 GbE link in the reference measurements ADR 0009 cites (165,000 to 190,000).
- **TCP**: 1.6 to 2.0 us per query; reads and writes are batched by the pipelining, so the parse, lookup and build dominate.
- **DoT and DoH**: the TLS records (AES-GCM, with AES-NI in the virtual CPU's flags) and, for DoH, the HTTP/2 framing, the header compression and the base64url decoding of every request.
- **The two VMs share a host**: the load VM kept five to six of its eight vCPUs busy in the saturation runs. When both VMs want more physical cores than the host has, both slow down, which shows as the spread between runs of the same configuration (366,000 and 444,000 at four UDP workers).

## Procedure

`scripts/run-m17-remote.sh` from the workstation, with ssh to both VMs (the real addresses on the command line, placeholders here):

```
phase2-dns zonegen --records 100000 --out-dir data/100000
scripts/run-m17-remote.sh --node user@node --node-addr 192.0.2.10 --load user@load --load-addr 192.0.2.20 \
    --server-binary <tenko musl> --harness <phase2-dns musl> --example <authoritative musl> \
    --data data/100000 --phases prepare
scripts/run-m17-remote.sh ... --phases "dnsperf tls flame harness workstation metrics stop report"
```

- `dnsperf`: for each worker count the node is stopped (by its pid), its configuration rewritten and started again; the role builds its index from the store in under a second. Then per transport two runs of `run-dnsperf.sh --rates 0 --duration 30 --threads 8 --clients 64` with `-q 1024` over UDP and `-q 4096` over TCP (a sweep at four workers: over UDP `-q 256` gave 474,000 without loss, 1,024 gave 533,000, 4,096 gave 496,000 with more loss; over TCP 4,096 gave 2.0 M against 1.5 M at 1,024), `-e` (EDNS) and `-O latency-histogram`. Before and after each run `server-cpu.sh` on the node reads the server's CPU seconds and RSS, and `/proc/stat` on the load host its busy CPU ticks.
- `tls`: the CA root fetched and both certificates checked; dnsperf `-m dot` (`-q 4096`) and h2load (`-c 10 -m 4 --rps 1000` for 10,000 per second, `-c 64 -m 32` for the maximum) on a list of 10,000 GET URIs made from the first 10,000 names of the query file (RFC 8484, base64url without padding).
- `flame`, `harness`, `workstation`: as in the tables; the harness with 32 clients, 64 in flight each, no warm-up, `--require-aa`.
- `report`: `report.tsv` with one row per run (the tables here are made from it).

Raw output (not committed): `results/raw/m17-<stamp>/`, one directory per run with dnsperf's or the tool's output, `steps.tsv` with the CPU readings, `meta.txt` with the hosts, the sysctls and the certificate checks, `report.tsv`.

## How to reproduce

1. Two Linux VMs on one bridge (or two hosts), ssh without a password from a third machine; on the load host `apt install dnsperf nghttp2-client`, flamethrower built from https://github.com/DNS-OARC/flamethrower, `curl`, `openssl` and `python3`; on the node `dig` and `python3`. Passwordless `sudo` on the load host for `tune-udp.sh`.
2. On the third machine: the static musl `tenko`, the harness and the example server built for musl (`cargo build -p tenko-dns --example authoritative --release --locked --target x86_64-unknown-linux-musl`), and `phase2-dns zonegen --records 100000 --out-dir data/100000`.
3. `run-m17-remote.sh ... --phases prepare`, then the measurement phases as above. The script restores the load host's sysctls at the end and on any exit, and stops the instance it started; `--phases stop` does both again.
