# M23: idle RSS with every role, the home zones and a full cache, on the musl binary (Linux)

Verdict: FAIL (102.46 MiB at most idle against 95.37 MiB by the M9 procedure with its 200 prefixes, ten home zones and the cache at its bound of 10,000 entries; 94.21 MiB, PASS, with 20 prefixes; 90.25 MiB, PASS, without the home zones and the cache)

M23 of the Phase 2 plan (section 6, OPS-15, E21) is M9 of Phase 1 again with the DNS module: the idle resident set of one node with every Phase 1 role plus `dns`, serving the home zones with a cache of 10,000 entries, on the static musl binary, against 100 MB (read as 100,000,000 bytes, 95.37 MiB, the stricter reading M9 uses). It ran on the node VM of M17 with the 0.0.2 binary that ships (musl, jemalloc), by the M9 procedure (`bench/phase1-server/m9-idle-rss.sh`) with two hooks that load the zones and fill the cache before the idle phase. Every figure is a single-node figure (plan section 2.10).

The samples of a run lay within 0.1 MiB of each other (102.38 to 102.46 MiB in the first run), so the run had settled: nothing grew or shrank while the node sat idle, and the cache kept its 9,984 entries to the end (4,968 of them stale at the end, kept for serve-stale after their TTLs of 300 s ran out). The start-up peak of every run was 98.8 to 98.9 MiB (VmHWM), before the zones and the cache.

## Where the memory goes

Against the control run (the Phase 1 M9 procedure on the same VM with the roles `controller,probe,dns`):

- **File-backed pages, +3.7 MiB** (69.4 to 73.1 MiB at the largest idle sample): the code of the binary that the import, the zone service, the reconciler's reverse-zone planner, the forwarder and the cache run, paged in once and kept resident. The binary is 135.9 MiB; its resident code grows with the features a node uses, as Phase 1's M9 found for the controller (deviation 70 of the Phase 1 exit). It is about the same with 20 prefixes (72.8 MiB).
- **Anonymous memory, +8.5 MiB with 200 prefixes** (20.9 to 29.4 MiB) and **+0.5 MiB with 20** (21.4 MiB, against the control's 20.9 MiB with ten times the prefixes): the cache of 10,000 entries, the index of the zones and the store's rows for them. With 200 prefixes the reconciler created 195 reverse zones for the M9 networks as soon as the first forward zone existed (P2-Q11: a prefix without `dns_reverse` becomes managed once its tenant has a forward zone), each with its SOA and NS rows in the store, its zone in the index and its state in the reconciler; with 20 prefixes there were 15. The cache and the ten home zones are therefore small; the difference between the two M23 runs (8.0 MiB of anonymous memory, 8.3 MiB in all) comes with the 180 more reverse zones and prefixes.
- **The idle figure is live memory, not the allocator's retention**: the musl build's jemalloc returns freed pages at once (`dirty_decay_ms:0`, `muzzy_decay_ms:0` in `.cargo/config.toml`), and the RSS right after the cache fill (102.48 MiB) is the RSS of the idle phase (102.38 to 102.46 MiB).

The 100 MB bound of OPS-15 holds for a home-sized node (94.21 MiB with 20 networks, ten zones and a full cache), by 1.2 MiB, and the M9 data set's 200 networks, which most homes do not have but which Phase 1 measured with, take it over by 7.1 MiB. On this VM the control run already idles at 90.25 MiB, against 85.31 MiB for the same procedure in WSL2 on 2026-10-19 (`bench/phase1-server/results/2026-10-19-m9-idle-rss.md`), so the margin Phase 1 left is smaller on a real Linux host than in WSL2. The candidates for room are those Phase 1 named (the start-up peak of the language packs and the OpenAPI document, the resident code of the binary: deviation 70 and section 4 of the Phase 1 exit) and, new with the DNS module, the reverse zones that P2-Q11 creates for every managed network.

## Method

| Item | Value |
| --- | --- |
| Host | The node VM of M17: 4 vCPU (`QEMU Virtual CPU version 2.5+`), 3.8 GiB, Ubuntu 24.04.5 LTS, kernel 6.8.0-147-generic, ext4. The owner's own Tenko service on the VM was idle and untouched; the measured instance ran as the ssh user from `~/m17/m23` on its own ports (API 18444, DNS 15353 on loopback) |
| Binary | `tenko 0.0.2`, the static musl build of `5bfd7ba`'s tree (static-pie, 135.9 MiB, jemalloc), the same file as M17 |
| Procedure | `bench/phase1-server/m9-idle-rss.sh --roles controller,probe,dns --kek file --prefixes 200 --dns-forwarder <load>:15354 --before-idle m23-before.sh --after-idle m23-count.sh --idle-secs 600` (the home-sized run with `--prefixes 20`; the control without the forwarder's use, the hooks or the zones). The script starts a fresh node with the Home profile, completes first-run setup and logs in with the CLI, creates the IPAM data set (a /8, four /16 supernets and /24 networks), runs the hook, samples `/proc/<pid>/status` every 30 s for 600 s, stops the node with SIGTERM (exit status 0 in every run) |
| Home zones (the before-idle hook) | Ten small zones written by `run-m17-remote.sh` and imported with `tenko dns zone create` and `tenko dns import --replace`: `lan.example.test` (60 hosts with A and AAAA, CNAME, MX, TXT, SRV), `iot.example.test` (40 hosts), `dmz.example.test` (10 hosts with A and AAAA), `guest.example.test` (5), `lab.example.test` (20), the reverse zones `2.0.192.in-addr.arpa`, `100.51.198.in-addr.arpa`, `113.0.203.in-addr.arpa`, `0.0.0.0.8.b.d.0.1.0.0.2.ip6.arpa` and `1.0.0.0.8.b.d.0.1.0.0.2.ip6.arpa`: about 437 records. Twenty seconds later the node served 205 zones with 827 RRsets (25 zones with 467 RRsets with 20 prefixes) |
| The cache | The Home profile's `[dns.cache]` defaults (10,000 entries, 16 MiB, serve-stale on). The forwarder (`[dns] forwarders`) points at the engine's example server on the load VM, which answers `host-{n}.example.test` authoritatively; `phase2-dns load --rd --qps 1000` sent 40,000 queries for 20,000 such names from the node's loopback in 40 s (39,999 answered, no errors), and `tenko dns cache list --json` paged through 9,984 entries afterwards and again after the idle phase (the bound is enforced per shard, so a full cache holds slightly fewer than 10,000) |
| What a hook adds | The hook runs before the idle phase, so its own requests (the CLI calls and 40,000 forwarded queries) are part of the state the node idles with, which is the point: a home node that has just been used |

The raw output (not committed): the M9 script's CSV of every sample and its summary under `~/m17/m23/raw` on the node and `results/raw/m17-<stamp>/m23-raw` on the workstation; the summary lines quoted above are from them.

## How to reproduce

```
scripts/run-m17-remote.sh --node user@node --node-addr 192.0.2.10 --load user@load --load-addr 192.0.2.20 \
    --server-binary <tenko musl> --harness <phase2-dns musl> --example <authoritative musl> \
    --data data/100000 --phases "m23 stop"                       # the procedure, 200 prefixes
scripts/run-m17-remote.sh ... --phases "m23 stop" --m23-prefixes 20
scripts/run-m17-remote.sh ... --phases "m23 stop" --m23-no-home   # the control
```

Each run takes about eleven minutes. The node needs `python3` (the hooks read the JSON of the CLI); the load host runs the upstream example server for the run and stops it after.
