# M23 again: idle RSS with every role, the home zones and a full cache, on the musl binary (Linux)

Verdict: FAIL (100.05 MiB at most idle against 95.37 MiB by the M9 procedure with its 200 prefixes, ten home zones and the cache at its bound, on this branch's musl binary built with fat LTO; 91.87 MiB, PASS, with 20 prefixes; 89.25 MiB, PASS, without the home zones and the cache)

M23 of the Phase 2 plan (section 6, OPS-15, E21) failed on 2026-10-21 at 102.46 MiB with the 0.0.2 binary ([2026-10-21-m23-idle-rss.md](2026-10-21-m23-idle-rss.md), deviation 145 of `docs/plans/phase-2-exit.md`). This is the same measurement, after measuring where the memory goes and making the binary smaller, on the same node VM by the same procedure (`bench/phase1-server/m9-idle-rss.sh` through the `m23` phase of `run-m17-remote.sh`). Every figure is a single-node figure (plan section 2.10).

The idle phase is 600 s, sampled every 30 s; each figure is the largest of the 21 samples, which lay within 0.1 MiB of each other in the two runs with zones and between 88.10 and 89.25 MiB in the control. The cache kept its 9,984 entries to the end (4,943 of them stale at the end).

The binary is this branch's static musl build with `lto = "fat"` and `codegen-units = 1` (113.9 MiB): `main`'s binary had grown from 0.0.2's 135.9 MiB to 143.7 MiB with the Phase 3 crates (the DHCP engine and its role are in every binary), and the profile change brings it below 0.0.2. Against 0.0.2 the three runs are 1.0 to 2.4 MiB smaller, all of it in file-backed pages; the anonymous memory is the same.

## Where the memory goes

### What a zone costs

Measured on the workstation in WSL2 with the M9 procedure (200 prefixes, the `dns` role, 60 s idle, no home zones and no cache), once with one forward zone created before the idle phase (the reconciler then creates the 195 reverse zones, P2-Q11) and once without; and inside `tenko-dns` with a counting allocator.

| What | Per two-RRset zone | For 195 zones | How it was measured |
| --- | ---: | ---: | --- |
| The catalog and its index (`ZoneIndex`, the zone row), built at once from an image | 848 B | 0.16 MiB | `tests/index_memory.rs`, `a_small_zone_costs_the_catalog_a_few_kib` (stats_alloc) |
| The same, zones applied one delta at a time, as a running node receives them | 1,258 B | 0.24 MiB | the same test |
| The NOTIFY task a zone gets at its first SOA (a 336-octet future, the task header, a watch channel, a child token) | about 1 KiB | about 0.2 MiB | `-Zprint-type-sizes` of `tenko-dns` |
| Everything else the zones add outside `tenko-dns` (the store's rows, the reconciler's state, the change feed and the audit of each creation) | about 17 KiB | about 3.4 MiB | the anonymous memory of the two WSL2 runs (+3.8 MiB) less the rows above |
| Code paged in by zone creation (file-backed, once, not per zone) | | 1.5 MiB | the file-backed memory of the two WSL2 runs |
| **The 195 reverse zones in all** | | **5.3 MiB** | 96.88 MiB without them, 102.18 MiB with them (WSL2) |

So the DNS side of a small zone costs 2 to 3 KiB, as the brief expected a zone should; its index and its task are not where the memory goes, and the zone structures of `tenko-dns` were left as they are. Ruled out: the store's page cache (`[store] sm_cache_mib = 4` instead of 32 gives the same figures within 0.1 MiB, with and without the zones) and the SSE replay ring (one ring of 256 frames, filled by the prefixes before any zone exists). A heap profile of the node itself was not possible: jemalloc's profiling crashes at start in the static musl binary (its backtrace unwinder), so the remainder outside `tenko-dns` is measured as a whole and not attributed further.

| Phase | RSS | Anon | File |

With 20 prefixes the same phases read 82.11 MiB (anon 15.29) after the prefixes and 91.86 MiB (anon 21.47) after the hook. The anonymous memory therefore splits roughly as: 7.0 MiB for the 200 prefixes of the M9 data set (1.5 MiB for 20: about 32 KiB per further prefix that stays after the creation), 6.2 MiB for the ten home zones, the cache of 10,000 entries and the 40,000 forwarded queries that filled it, and about 2.2 MiB for the 180 further reverse zones (12 KiB each on the node, 17 to 20 KiB in WSL2).

### The file-backed pages

The code segment is the largest part of the idle set: 70.6 MiB of file-backed pages on the node. Every page of code a node runs once stays mapped while there is no memory pressure, and the kernel maps the neighbouring pages already in the page cache with each fault (fault-around), so the resident code follows the size of the binary more than the code a node runs. Fat LTO in one codegen unit makes the code segment 77.8 MiB instead of 82.8 MiB and the read-only data 20.9 instead of 26.2 (thin LTO makes the code larger, 88.2 MiB); in WSL2 with the procedure's 200 prefixes it lowered the idle node from 96.88 to 90.49 MiB without zones and from 102.18 to 95.77 MiB with the 195 reverse zones. Its cost is build time: the musl release build takes about 13 minutes instead of 3. The dev profile, the tests and the gates are untouched.

## The next levers

M23 by the procedure misses by 4.7 MiB. In the order of their size:

1. **The IPAM data set**: about 32 KiB of anonymous memory per prefix that stays after the creation (5.8 MiB between 20 and 200 prefixes, before any zone). The M9 procedure creates 200 prefixes; most homes have fewer. This is outside the DNS module (`tenko-ipam`, the store's change feed and the audit) and was not measured further.
2. **The cache and the forwarder**: the ten home zones, 10,000 cache entries and the forwarder's state take about 6 MiB together; the cache's own share was not separated from the home zones in these runs. The Home profile's bound of 10,000 entries is the plan's figure.
3. **Per reverse zone outside `tenko-dns`**: 12 to 20 KiB per zone in the store, the reconciler and the change feed, 2.2 MiB for the 180 zones that 200 prefixes add over 20.
4. **The resident code**: 70.6 MiB of file-backed pages. Dropping cold code from the process after start (`madvise`) needs `unsafe` or a new dependency; a smaller binary (features a node does not run, fewer monomorphised copies) is the other way.

## Method

| Item | Value |
| --- | --- |
| Host | The node VM of M17: 4 vCPU (`QEMU Virtual CPU version 2.5+`), 3.8 GiB, Ubuntu 24.04.5 LTS, kernel 6.8.0-147-generic. The owner's own service on the VM was idle and untouched; the measured instance ran as the ssh user from `~/m23` on its own ports (API 18444, DNS 15353 on loopback) |
| Binary | `tenko 0.0.2` from this branch at `32f2b93` (the release profile with fat LTO), the static musl build, jemalloc with the options of `.cargo/config.toml` |
| Procedure | As on 2026-10-21: `run-m17-remote.sh --phases "m23 stop"` (and `--m23-prefixes 20`, `--m23-no-home`), which runs `m9-idle-rss.sh --roles controller,probe,dns --kek file --prefixes N --dns-forwarder <load>:15354 --before-idle m23-before.sh --after-idle m23-count.sh --idle-secs 600` on the node, with the engine's example server as the upstream on the load VM |
| Home zones and cache | The ten zones of the hook (about 437 records), then 40,000 forwarded queries for 20,000 names at 1,000 per second (40,000 and 39,999 answered); `tenko dns cache list` paged 9,984 entries before and after the idle phase |
| The WSL2 runs of the tables above | The workstation (i9-13900K, WSL2 kernel 6.18), the same M9 script with a hook that creates one forward zone (or none) and waits 40 s, 60 s idle; the binaries of this branch with the release profile before and after the LTO change, and one with `[store] sm_cache_mib = 4` |

## How to reproduce

```
scripts/run-m17-remote.sh --node user@node --node-addr 192.0.2.10 --load user@load --load-addr 192.0.2.20 \
    --server-binary <tenko musl> --harness <phase2-dns musl> --example <authoritative musl> \
    --data data/100000 --remote-dir m23 --phases "m23 stop"          # the procedure, 200 prefixes
scripts/run-m17-remote.sh ... --phases "m23 stop" --m23-prefixes 20
scripts/run-m17-remote.sh ... --phases "m23 stop" --m23-no-home     # the control
cargo test -p tenko-dns --release --test index_memory -- --ignored a_small_zone --nocapture
```

Each node run takes about eleven minutes. The raw output (not committed): the M9 script's CSV and summary of each run under `~/m23/m23/raw` on the node and `~/exitfix/m23` on the host that drove the runs.
