# M26 to M28 with perfdhcp: the binary over the link and on loopback, and the engine alone (musl)

Verdict: DOCUMENTED, and above the fallback line of P3-Q1 on the lab VMs. The shipped binary (`tenko serve --roles controller,dhcp`, the static musl build of `deploy/Dockerfile`, every lease committed to the replicated store before its ACK), measured with ISC's perfdhcp from the load VM over the link: about 10,000 4-way exchanges per second within 0.1 percent drops, about 11,400 per second closed loop with the engine's own client, and at 1,000 exchanges per second a p99 from REQUEST to ACK of 19 ms (p50 1.1 ms), the server's own histogram agreeing (p99 at most 25 to 50 ms). The fallback line of P3-Q1 is fewer than 1,000 exchanges per second sustained or a p99 from REQUEST to ACK above 100 ms at 1,000 per second; both figures are clear of it, by a factor of ten in rate and five in latency. At 5,000 per second the p99 is about 126 ms. The engine alone (the example server, no store) answers 20,000 per second to perfdhcp and about 106,000 to its own client on the same VM: the store's commit is the cost, as plan section 2.1 expected.

M26 asks for the 4-way exchanges per second with every lease committed before the ACK, M27 for the renewals per second, M28 for the p99 from DISCOVER to ACK and the commit's share of it (plan section 6). Every figure is a single-node figure (plan section 2.12): one server process on the node VM, perfdhcp on the load VM (the link) or on the node VM itself (loopback, an upper bound). The engine-only rows are the perfdhcp side of WP7.3's loopback rows ([2026-10-22-m26-m28-loopback.md](2026-10-22-m26-m28-loopback.md), own client on Windows).

## The binary: setup

- **Machines.** The node VM: QEMU virtual CPU, 4 logical CPUs, 3.8 GiB RAM, Ubuntu 24.04.5 LTS, kernel 6.8.0-147-generic; its data directory's fsync probe at start gave p50 0.3 ms, p99 0.8 ms. The load VM: the same with 8 logical CPUs. Both on the owner's Proxmox host, on one bridge (`node` and `load` here; their addresses stay out of the repository). The node's UDP sysctls are the defaults and were not changed; the load VM's were raised for the two-host run by `tune-udp.sh` and restored after it. A Tenko 0.0.2 service runs on the node VM on other ports and was idle.
- **Binary.** `tenko` 0.0.2 from `main` at a5f9416 with this branch, copied out of the `tenko:lab` image built from `deploy/Dockerfile` (static-pie musl, checked by the script; the same binary the lab ran). `scripts/node-setup.sh` starts it as the ssh user with its own data directory under the Lab profile, `roles = "controller,dhcp"`, `[dhcp] listen = [{ address = "<node>", mode = "relay" }]`, `port = 6767`, `relay_port = 6868`, the workers of the rung, and creates the scope `198.18.0.0/15` with one pool of 131,053 addresses and a 3,600 s lease through the API; every run starts from a new data directory.
- **Load.** perfdhcp 2.4.1 as a relay agent (`-l <load> -L 6868 -N 6767`, option 118 for the scope), 100,000 clients with a fixed seed, 20 s per run; the own client is the example's `load` at the same address. `run-perfdhcp.sh --kind tenko --binary <tenko> --client <example> --node <node> --load <load> --node-addr <node> --load-addr <load> --tune` for the link, and with node and load both the node VM at 127.0.0.1 for loopback. Every rung twice, the better run counts (for M28 the lower p99 from REQUEST to ACK); the server's histograms come from its loopback metrics listener.

The rungs at 2,000 and 7,500 lost at most 0.01 percent. The losses past 10,000 per second are REQUESTs: OFFERs stay fast (the offer is in memory) while the ACKs queue behind the commits, and perfdhcp counts an ACK later than its drop time as lost. 4 workers, the better of two runs by the p99 of REQUEST to ACK:

| Where | Rate /s | perfdhcp DO p50 / p99 ms | perfdhcp RA p50 / p99 ms | Server REQUEST to ACK p50 / p99 | Server commit p50 / p99 |
|---|---:|---|---|---|---|
| Two hosts | 1,000 | 0.073 / 0.206 | 1.10 / 19.1 | ≤ 2.5 / ≤ 25 ms | ≤ 2.5 / ≤ 25 ms |
| Two hosts | 5,000 | 0.046 / 0.701 | 3.65 / 126 | ≤ 5 / ≤ 250 ms | ≤ 5 / ≤ 250 ms |
| Loopback | 1,000 | 0.031 / 0.209 | 0.98 / 21.0 | ≤ 1 / ≤ 25 ms | ≤ 1 / ≤ 25 ms |
| Loopback | 5,000 | 0.027 / 1.062 | 3.68 / 124 | ≤ 5 / ≤ 250 ms | ≤ 5 / ≤ 250 ms |

The other run of each row: over the link 27.5 ms and 132 ms (server p99 ≤ 50 and ≤ 250 ms), so both runs at 1,000 per second are below the 100 ms line; on loopback 151 ms and 1,631 ms, the second with 7 percent of the REQUESTs lost, where perfdhcp and the node compete for 4 vCPUs. The commit is almost all of the time from REQUEST to ACK at every rate: the server's histograms of the two coincide bucket for bucket. DISCOVER to OFFER, which commits nothing, stays below a millisecond at p99.

The own client's DISCOVER to ACK over the link at 1,000 per second had a p99 of 0.5 to 0.7 s (p50 1.1 to 1.6 ms), which neither perfdhcp's timestamps nor the server's histogram show for the same rate; at 5,000 per second it agrees with them (p99 107 to 127 ms). The slow tail is on the client's side of the link (its single receiving thread at a low rate), not the server's, and is left out of the verdict.

## The engine alone: setup

- **Machine.** The node VM: QEMU virtual CPU, 4 logical CPUs, 3.8 GiB RAM, Ubuntu 24.04.5 LTS, kernel 6.8.0-147-generic, on the owner's Proxmox host. Its UDP sysctls are the defaults and were not changed (`rmem_max` and `wmem_max` 212,992, `netdev_max_backlog` 1,000). A Tenko 0.0.2 service runs on the VM on other ports and was idle.
- **Server.** `crates/tenko-dhcp/examples/dhcp_server.rs` built with `cargo build -p tenko-dhcp --release --locked --example dhcp_server --target x86_64-unknown-linux-musl` (static-pie, checked by the script), `serve --listen 127.0.0.1:6767 --relay-port 6868 --workers N --store queue --idle-exit 3`: one relay listener with `SO_REUSEPORT` sockets per worker, one scope `198.18.0.0/15` with 131,053 pool addresses, lease 3,600 s. `queue` is the `LeaseStore` contract with no rows behind it (the hand-off, the committer's drain and the completion): every ACK leaves after its change came back committed, but nothing is written to disk.
- **Load.** perfdhcp 2.4.1 (Ubuntu's `kea-admin`) on the same VM, as a relay agent at 127.0.0.1 (`-L 6868 -N 6767`, option 118 `198.18.0.0` for the scope), 100,000 simulated clients with a fixed seed (`-R 100000 -s 1`), 20 s per run. The own client is the example's `load` (a relay agent with option 118, one sender and one receiver thread).
- **Procedure.** `bench/phase3-dhcp/scripts/run-perfdhcp.sh --kind example --binary <musl example> --client <musl example> --node <vm> --load <vm> --node-addr 127.0.0.1`: every rung twice against a fresh server, the better run (fewer drops, then the higher rate); the ladder per worker count stops after the first rung that loses more than 1 percent. Raw output (every perfdhcp report, the server's counters, the meta file) stays on the measuring host, not in the repository.

## The engine alone: M28

4 workers, the better of two runs. perfdhcp's percentiles come from its packet timestamps (`-x t`); the own client measures from the DISCOVER to the ACK; the server's figures are the bucket that holds the quantile of its own histograms:

| Rate /s | perfdhcp DO p50 / p99 ms | perfdhcp RA p50 / p99 ms | Own client DISCOVER to ACK p50 / p99 ms | Server REQUEST to ACK p99 | Server commit p99 |
|---:|---|---|---|---|---|
| 1,000 | 0.102 / 2.163 | 0.114 / 2.156 | 0.25 / 4.61 | ≤ 1 ms | ≤ 1 ms |
| 5,000 | 0.039 / 0.497 | 0.058 / 0.469 | 0.16 / 0.49 | ≤ 250 µs | ≤ 100 µs |

The slower tail at 1,000 per second than at 5,000 is most likely the VM's: at the lower rate the vCPUs idle between packets and wake late (an earlier run of the same rung gave a perfdhcp RA p99 of 0.23 ms; the server's own REQUEST to ACK stayed within 1 ms in one run and 2.5 ms in the other). With no store behind the commit, these figures say nothing about the fallback line of P3-Q1 (p99 from REQUEST to ACK above 100 ms at 1,000 per second); they bound what the engine adds.

## Caveats

- Loopback figures are upper bounds; server and load generator share 4 vCPUs. For the engine alone perfdhcp is the limit, not the server: it answered every packet it received at every rung.
- The engine-only rows use the queue store, which commits nothing to disk; the binary's rows commit every lease to the store (one node, the Raft log on the VM's virtual disk). The two together show the commit's share: the step from about 20,000 to 10,000 exchanges per second and from sub-millisecond to 19 ms at p99.
- The VMs share a hypervisor with the owner's other machines; a run can meet noise from them, which is why every rung runs twice. A node on its own hardware with a local NVMe disk will do better; a slower disk worse (the store warns at start when the median fsync takes more than 10 ms).
- Kea's and ISC's published figures compare only with the caveats of plan section 6 (`bench/phase3-dhcp/README.md`): other hardware, Kea's threading settings, other perfdhcp options, and a memfile backend whose lease write is not a replicated commit. The DNS reference points of Phase 2 do not apply.
- WSL2 was not used for these rows (risk R68); the node VM is a Linux kernel on a hypervisor, not bare metal.
