# M31: DDNS rate end to end, the stand-in (own client, loopback, Windows release, one node)

Verdict: FAIL on the latency thresholds, PASS on the rate (own client, loopback, Windows; the stand-in, not the M31 figure). At 1,000 lease commits per second with option 81 for 60 s, every one of 60,000 names per run was answered by the DNS role of the same node and none was lost, and the DDNS queue kept up; but the p99 from the ACK to the answered A record was 551 and 578 ms against the threshold of 250 ms, and the DORA p99 with DDNS (574 and 472 ms) was not within 10 percent of the same DORA without names (279 and 82 ms on fresh nodes). The experiments below place most of the tail in the extra store and reconciler work that every DHCP name causes on the node, not in the DDNS worker's own path. The perfdhcp row of M31 on the musl binary is a follow-up for when WP7.6's harness is on `main`.

M31 of the Phase 3 plan (section 6) asks for 1,000 lease commits per second with DDNS, a p99 from ACK to the answered A record below 250 ms, and a DORA p99 within 10 percent of M28, measured with perfdhcp with option 81 against one node with a Tenko zone. perfdhcp is a Linux tool and WP7.6's lab is not on `main` yet, so this run measures the same quantities with the crate's own client on loopback on Windows by the method of M21 (a paced open loop, one latency per operation, a timeout that counts as lost). Every figure is a single-node figure and a loopback figure from a client on the same host: an upper bound of what the software does, labelled "own client, loopback, Windows".

Machine: Intel Core i9-13900K (24 cores, 32 threads), 63.7 GiB RAM, Windows 11 Enterprise 10.0.26300, the machine of M21. Server: the release build of `tenko` from this branch (`cargo build -p tenko --release --locked`), data directory in the user's temporary folder on the NVMe disk. Client: `crates/tenko-dhcp/examples/ddns_load.rs` (release).

## Procedure

`bench/phase3-dhcp/scripts/run-m31-ddns.sh` (raw output under `results/raw/`, not committed):

1. A new node per run: `tenko serve` with the roles `controller,dns,dhcp`, the modules IPAM, DNS and DHCP, an empty data directory, the DNS role on a loopback port, a relay-mode DHCP listener on loopback with 4 workers, the store's defaults.
2. Setup through the API under the Home profile; the primary zones `lan.example.test`, `18.198.in-addr.arpa` and `19.198.in-addr.arpa`; the IPAM network `198.18.0.0/15` (RFC 2544's benchmarking range) with a pool of about 131,000 addresses; its scope with one-hour leases and DDNS on into `lan.example.test`.
3. The load client acts as a relay agent (`giaddr`, option 118, option 61 per client) and starts 1,000 four-way exchanges per second, paced, each client once: 5 s of warm-up, then 60 s measured. With names, DISCOVER and REQUEST carry option 81 with the flags S and E and the name `m31a-<n>`, so the server writes an A record, a DHCID record and a PTR record for each lease. An exchange without its ACK within 2 s counts as lost.
4. For every acknowledged client a second thread asks the DNS listener for `m31a-<n>.lan.example.test` once per 10 ms pass until an answer with RCODE 0 holds the leased address; the DDNS latency is from the receipt of the ACK to the receipt of that answer (it includes up to one polling period). An update not answered within 5 s counts as lost.
5. The baseline: the same DORA load with no option 81 on a fresh node of the same configuration (the DDNS worker runs and has nothing to write).

## Where the time goes

The experiments of the day, each on a fresh node unless said otherwise, the same load at 1,000 per second (ms):

| Variant | Measured | DORA p99 | ACK to A p50 | ACK to A p99 |
|---|---|---:|---:|---:|
| Window 10 ms (one change set per zone every 10 ms) | 30 s | 549 | 58 | 507 |
| Window 40 ms | 30 s | 188 | 59 | 230 |
| Window 40 ms | 60 s | 1,455 | 121 | 1,101 |
| Window 100 ms | 60 s | 632 | 120 | 603 |
| Window 100 ms, the outcome row not written (an experiment build) | 60 s | 585 | 115 | 450 |
| Window 100 ms, no store snapshot during the run (`snapshot_every_entries` 1,000,000, `snapshot_every_log_mib` 4,096) | 60 s | 624 | 111 | 612 |
| Window 100 ms, the IPAM reconciler's debounce at 300 s | 60 s | 364 | 110 | 324 |
| Window 100 ms, no `dns` role in the process (no catalog to follow; no name answered) | 30 s | 569 | | |

- **The window.** With one change set per zone every 10 ms the store takes about 300 more proposals per second than without DDNS; 100 ms cuts that to about 30 and lowers the tail at 60 s. The p50 from ACK to answer is then about the window plus one zone write plus the DNS role's catch-up. The window is the default of the code (`DdnsSettings::window`).
- **The tail grows with the run.** The 30-second runs stay near or under the threshold, the 60-second runs do not. Per lease DDNS adds three RRsets, a share of a zone journal entry, a zone audit record and job record per change set and the rewritten lease row; the store holds about 2.3 times the rows of the baseline at the end (440,000 against 196,000) and builds three snapshots in a minute instead of one. Snapshots alone are not the tail (the run without snapshots is no better).
- **The IPAM reconciler.** It watches `dns.rrsets` and runs after its debounce of 2 s on any change, and each run reads the zones whole (`ipam::observe::dns` takes `ipam` and `manual` records only, so DHCP's records give it nothing to do). Holding it off for the run halves the tail (364 and 324 ms). A reconciler that skips change sets touching only `dhcp` RRsets is the IPAM package's change, proposed below.
- **Not the DNS role.** Without the `dns` role the DORA tail with DDNS is the same, so the catalog's overlay copies (`docs/dns.md` section 12.11) are not what slows the lease commits; they may add to the ACK-to-answer figure.
- **Not the worker's own writes.** Leaving out the outcome row changes little.
- The client's prober asks each waiting name once per pass (10 ms; 2 ms in the first runs, which loaded the DNS role with up to 50,000 queries per second), so the ACK-to-answer figure holds up to 10 ms of polling.

## Follow-ups

- **perfdhcp with option 81** against the musl binary on the lab node when WP7.6's harness is on `main` (the M31 figure; this file is the stand-in).
- **The IPAM reconciler** (IPAM package): skip change sets of `dns.rrsets` whose RRsets are all of the origin `dhcp`, since the DNS observations read `ipam` and `manual` records only; then measure again.
- **The store's share** (WP7.2 and the store): the lease commits' tail under the extra write volume of DDNS (the rows per lease and the size of the change sets); the commit duration histogram per run would show whether the DORA tail is the commit or the workers' table lock while the feed applies the outcome rows.
- **Run longer and on Linux**: the 60-second figures grow over the run; a 10-minute run on the musl binary is the next measurement once the reconciler change is in.

## Reproduce

```sh
cargo build -p tenko --release --locked
cargo build -p tenko-dhcp --release --locked --example ddns_load
bash bench/phase3-dhcp/scripts/run-m31-ddns.sh --no-baseline --rate 1000 --duration 60    # with names, a fresh node
bash bench/phase3-dhcp/scripts/run-m31-ddns.sh --baseline-only --rate 1000 --duration 60  # the baseline, a fresh node
# Experiments: --snapshot-every N, and RECONCILER_DEBOUNCE=<seconds> in the environment.
```

The binaries default to `$CARGO_TARGET_DIR/release/` (or `target/release/`). On Linux the server binary must be the static musl build; the script refuses a dynamically linked one unless `--allow-dynamic`.
