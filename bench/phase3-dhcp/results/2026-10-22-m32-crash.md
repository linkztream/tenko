# M32 (E24) on the workstation: twenty kills under lease load, the 100,000-lease rebuild and the commit latency of the lease path (Windows release, one node)

Verdict: PASS (20 kills of a node under lease load, 144,681 ACKs received and checked: none lost, none regressed, every one with its history row, no address on two clients, the rebuilt table equal to the rows and the client index after every kill; a table of 100,000 leases rebuilt from the store in 170 ms against the 5 s of the plan; at 1,000 lease commits per second the p99 from the hand-off to the released ACK was 8.45 ms, the largest 23.28 ms)

This run measures WP7.2 of `docs/plans/phase-3-plan.md`: the lease change as one batch through the store's coalescer, the ACK released on the durable commit once the role's table holds it, the table rebuilt from the store, and the crash test of E24 (M32, the twenty SIGKILLs of the workstation; the five power-offs of the lab VM are the owner's step, procedure below). Script: `scripts/crash-test.sh` (raw output `results/raw/m32-*.txt`, not committed). Every figure is a single-node figure (plan section 2.12).

**What is measured, and what is not.** The `dhcp` role is not in the binary before WP7.5, so the node is the test entry point of `crates/tenko-dhcp/tests/lease_crash.rs`, and the figures come from the release build of the test binaries (the `--release` profile, the optimisation of the shipped binary), not from `tenko serve`: the lease path from the hand-off to the ACK is the production code (`tenko_dhcp::lease`, the Raft store with its default configuration), but there are no sockets, no DHCP messages and no engine (WP7.3) in front of it. The latency is therefore the commit's share of M28 (`tenko_dhcp_commit_duration_seconds`), not the REQUEST to ACK time; M26 to M28 measure that through the binary with perfdhcp. Windows only: the Linux run (the static musl build) comes with the binary of WP7.5 and the lab VM runs.

Machine: Intel Core i9-13900K (24 cores, 32 threads), 63.7 GiB RAM, Windows 11 Enterprise 10.0.26300; the data directories in the user's temporary folder on an NVMe SSD; rustc 1.99.0; branch of WP7.2 from `main` at `1ef0b3c`.

## Procedure

`bash bench/phase3-dhcp/scripts/crash-test.sh --kills 20 --secs 30`, three release tests one after another:

1. **The commit latency** (`lease_rebuild.rs`, `commit_latency_at_a_paced_rate`). A new Raft store; the production lease store (`StoreLeases`) with its committer and the default limits (queue 4,096, 512 batches in flight, commit wait 2 s). 720 leases on the three documentation networks, granted and then renewed in turn, paced at 1,000 changes per second (open loop) for 30 s. Each change is one batch: the lease row, the client index row when it moves, the history row. The time runs from the hand-off (`submit`) to the completion of the ticket, which comes after the store's answer and after the role's table applied the row: the moment the worker may send the ACK.
2. **The rebuild** (`a_large_table_rebuilds_from_the_store_in_time`). 100,000 lease rows and their 100,000 client index rows written to a new Raft store in batches of 1,000, the store closed, opened again, and the role's table built from it page by page (`rebuild_from_view`, pages of 4,096 rows), with the count of rows and index entries checked.
3. **The crash test** (`lease_crash.rs`, `the_node_loses_no_acknowledged_lease`). One data directory for all twenty runs. A run starts the node as a child process of the test binary: it opens the Raft store, rebuilds its table (the READY line gives the times), and runs 200 clients against one scope (192.0.2.0/24, a pool of 240 addresses, one-hour leases): a client without a bound lease gets an address from the reference allocator and the offer hold and is granted it, a client with one renews it (85 %) or releases it (15 %), 64 changes outstanding at a time (closed loop, about 10,000 changes per second). The node writes a line to its standard output for each ticket that completed as committed, after the completion; a line the harness has read is an ACK the client received. The harness kills the node after 20 ms (every fifth run) or a pseudo-random 0.3 to 1.5 s (SIGKILL on Unix, `TerminateProcess` on Windows; the pid of the child it started), reads what reached the pipe, opens the data directory and checks against every ACK received so far:
   - the row of the ACK's address was written at the ACK's revision or later, and at that revision it holds the ACK's client, state and end (no acknowledged lease lost or regressed);
   - the ACK's history row is there (the batch is atomic);
   - the table rebuilt from the store equals the rows and the stored client index, and the index is the one the rows imply (each client's latest row in a scope);
   - in the history, no address is granted to a client while another client's binding on it had not ended, and no client holds two bound rows.

## Results

The commit latency, 1,000 changes per second for 30 s:

| Changes | Failed | Achieved (/s) | p50 (ms) | p90 (ms) | p99 (ms) | p99.9 (ms) | Max (ms) | Raft entries | Snapshots |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 30,000 | 0 | 1,000 | 3.57 | 5.25 | **8.45** | 14.09 | 23.28 | 15,704 | 1 |

Separate runs of the same test the same day, 10 s each: p99 8.24, 13.36 and 10.75 ms at 1,000 per second; 10.08 ms with a snapshot every 1,000 entries (4 snapshots in the run), so the snapshots are not the tail; 10.76 ms at 3,000 per second (30,000 changes, 4,679 entries: the coalescer folds about six batches into an entry). One earlier run straight after a crash test on the same disk gave p99 150.93 ms (max 245 ms): the disk was still busy with the twenty removed data directories, which is why the script now measures the latency first.

The rebuild:

| Leases | Rebuild (ms) | Open of the store (ms) | Fill (ms) | Threshold |
|---:|---:|---:|---:|---|
| 100,000 | **170** | 12 | 913 | 5,000 ms: PASS |

The crash test, twenty kills:

| Kills | ACKs received and checked | Lost | Regressed | Missing history rows | Address on two clients | Table differs from rows or index |
|---:|---:|---:|---:|---:|---:|---:|
| 20 | 144,681 | 0 | 0 | 0 | 0 | 0 |

- After the twenty kills the store held 191 lease rows and 145,407 history rows: 726 changes committed whose ACK had not reached the harness when the node died (the client would retry and find its lease, risk R58), and none the other way.
- Each restart opened the store in 6 to 31 ms and rebuilt its table of up to 191 rows in under 1 ms.
- The earlier run of the day (`--secs 10`) passed the twenty kills too: 136,687 ACKs, none lost.

**Against the reference points.** M21's RFC 2136 path (Phase 2, the same workstation, the Windows release build) gave p99 17.6 and 19.4 ms at 1,000 updates per second from the client's send to the answer; that path also commits through the coalescer and waits for its index, plus the zone service, the inline job record and the wire. The lease path's commit share, 8.45 ms at p99, is about half of it, as the plan expected (section 2.1: "a few milliseconds median and a p99 near M21's"). It is far inside the fallback line of P3-Q1 (p99 above 100 ms at 1,000 per second), but M28 decides that with the engine and perfdhcp in front.

## The power-off runs on the lab VM (the owner's step, M32)

Five power-offs of the node VM under the same load, with the ACKs kept on another host. Prepared by the lead; the owner powers the VM off.

1. On the node VM (Linux), build the test binary in release: `cargo test --release --locked -p tenko-dhcp --test lease_crash --no-run` (or copy it from a Linux build host); note its path (`target/release/deps/lease_crash-<hash>`).
2. From the load VM (or the workstation), start the node over SSH with its output kept there:
   `ssh <node-vm> 'TENKO_LEASE_CRASH_CHILD=/var/tmp/e24/data /path/to/lease_crash-<hash> child_node --exact --ignored --nocapture --test-threads 1' | tee -a acks-<n>.txt`
3. After 5 to 60 seconds, power the VM off from the Proxmox host (`qm stop <vmid>`: a hard stop, no shutdown), then start it again (`qm start <vmid>`).
4. Copy `acks-<n>.txt` to the VM and check the data directory against it:
   `TENKO_LEASE_CRASH_VERIFY=/var/tmp/e24/data TENKO_LEASE_CRASH_ACKS=acks-<n>.txt /path/to/lease_crash-<hash> verify_after_power_off --exact --ignored --nocapture`
   It prints `POWER-OFF OK` with the counts, or fails naming the first lost or regressed ACK.
5. Repeat from step 2 on the same data directory, five times, concatenating the ACK files (each check uses every ACK so far: `cat acks-*.txt > acks-all.txt`).

The disk of the VM must honour flushes (no `cache=unsafe` on the virtual disk); with write-back caching the host must have a battery or the run measures the host's cache, not the node.

## Reproduce

```sh
bash bench/phase3-dhcp/scripts/crash-test.sh --kills 20 --secs 30
# or the parts:
cargo nextest run --release --locked -p tenko-dhcp --test lease_crash --run-ignored all \
    -E 'test(=the_node_loses_no_acknowledged_lease)' --no-capture   # TENKO_CRASH_KILLS=20
cargo nextest run --release --locked -p tenko-dhcp --test lease_rebuild --run-ignored all --no-capture
```
