# Spike B results: Linux (WSL2), 2026-10-09

Raw UDP DNS throughput and latency of the spike responder on Linux, with the
shared-socket and the SO_REUSEPORT (one socket per worker) variants, plus the
`domain` / `hickory-proto` comparison on Linux. The crate recommendation and
the overall I/O conclusion are in
[`2026-10-09-windows.md`](2026-10-09-windows.md#recommendation); this file
holds the Linux measurements they draw on.

**This is WSL2, not bare-metal Linux.** The guest is a Hyper-V VM on the same
Windows machine as the Windows results, sharing its CPUs. All traffic is
loopback inside the guest kernel: client and server run on the same machine
and share its CPUs. The numbers say nothing about NIC, driver or network
behaviour.

| Build | `cargo build --release`: fat LTO, 1 codegen unit, `panic = "abort"`, no debug info |
| Crates | `domain` 0.12.3, `hickory-proto` 0.26.3, `tokio` 1.53.2, `socket2` 0.6.5, `hdrhistogram` 7.6.0, `sysinfo` 0.39.6, `criterion` 0.8.2, `stats_alloc` 0.1.10 (same `Cargo.lock` as Windows) |
| Address | `127.0.0.2:5399` (see below) |

**127.0.0.1 does not work in this WSL2 distro.** UDP and TCP traffic to
127.0.0.1 never reached a local socket (checked with a plain Python socket
test: 127.0.0.1 timed out; 127.0.0.2, `::1`, the eth address and the
`loopback0` address all worked). All Linux runs therefore use 127.0.0.2,
which is still the `lo` device. The load generator binds its sockets to the
target's loopback address, and the tests take the address from
`SPIKE_B_LOOPBACK` (`SPIKE_B_LOOPBACK=127.0.0.2 cargo test --release`; all 43
tests pass, including the Linux-only SO_REUSEPORT test).

Other jobs were building other parts of the repository on the Windows host
during the measurements. The guest cannot see that load; it shows up as
lower or noisier numbers. Each configuration was run with three client
layouts and the tables keep the best one, which reduces but does not remove
this effect.

## Method

Commands (from `bench/spike-b-udp`, binary built into
`CARGO_TARGET_DIR=/home/plm/target/spike-b-udp`):

```
export BIN=/home/plm/target/spike-b-udp/release/spike-b-udp LISTEN=127.0.0.2:5399
scripts/run-matrix.sh results/raw/linux-wsl2.jsonl               # shared socket
scripts/run-matrix.sh results/raw/linux-wsl2.jsonl --reuseport   # one SO_REUSEPORT socket per worker
scripts/run-unloaded.sh results/raw/linux-wsl2-unloaded.jsonl
scripts/run-ab.sh results/raw/linux-wsl2-ab.jsonl
$BIN report --input results/raw/linux-wsl2.jsonl --out results/raw/linux-wsl2-tables.md
```

- Each run: `matrix` starts `serve` as a child process, 2 s warm-up, 20 s
  measured, then kills it. Workers 1, 2, 4, 8, 16, 32; both backends; both
  I/O modes; with and without `--reuseport`: 144 runs, all with 0 errors.
- Load: closed loop, 256 queries in flight in three layouts: 8 client
  sockets x 32, 32 x 8 and 64 x 4. Each client socket is one OS thread.
  Random `host-{n}` names out of 100,000, 5 % non-existent names
  (NXDOMAIN), EDNS OPT with UDP size 1232 on every query. Every response is
  checked (ID, QR, AA, TC, question, RCODE, counts).
- The tables show, per configuration, the run with the highest QPS of the
  three layouts.
- Latency under load is a closed-loop latency: with 256 queries in flight,
  p50 is roughly 256 / QPS (Little's law). Compare latencies only between
  runs with the same number of queries in flight; the unloaded latency is
  measured separately with one query in flight.
- Server CPU is the server process's user + kernel CPU time over the
  measured 20 s (via `sysinfo`), so it includes the `recvfrom`/`sendto`
  system calls. Peak RSS is sampled every 100 ms.

| Workers | threads, shared socket | threads, SO_REUSEPORT | tokio, shared socket | tokio, SO_REUSEPORT |
| ---: | ---: | ---: | ---: | ---: |

How the kernel spread the load: a separate 10 s run per row with 16
workers and the `domain` backend; the server's own per-worker packet
counters, printed on SIGINT (they include the 1 s warm-up and the drain):

| Mode | Sockets | Client sockets x in flight | QPS | Server CPU (cores) | Workers that got traffic | Packets per busy worker |
| --- | --- | --- | ---: | ---: | ---: | --- |
| threads | 16 x SO_REUSEPORT | 8 x 32 | 2,412,282 | 6.81 | 7 of 16 | 3.60 M to 3.86 M |
| threads | 16 x SO_REUSEPORT | 64 x 4 | 2,645,795 | 13.31 | 15 of 16 | 1.25 M to 2.28 M |
| tokio | 16 x SO_REUSEPORT | 8 x 32 | 1,783,630 | 7.88 | 7 of 16 | 2.07 M to 2.94 M |
| tokio | 16 x SO_REUSEPORT | 64 x 4 | 1,768,373 | 12.62 | 14 of 16 | 1.23 M to 1.50 M |
| threads | 1 shared | 8 x 32 | 3,360,943 | 15.87 | 16 of 16 | 2.30 M to 2.33 M |

What this shows:

1. SO_REUSEPORT distributes by flow (a hash of the source and destination
   address and port), not by load. With 8 client sockets only 7 of 16 server
   sockets received anything, so the server could use at most about 7 cores
   (the threads server used 4.8, 6.8 and 6.7 cores in the 8 x 32 matrix
   runs at 8, 16 and 32 workers).
   With 64 client sockets 14 to 15 of 16 sockets were used, still unevenly
   (the busiest worker got 1.8 times the packets of the least busy one in
   the threads run). A shared socket spreads packets evenly over all
   workers (within 1.5 %).
2. With enough flows, SO_REUSEPORT gave the highest throughput measured:
   4,043,709 QPS with 32 blocking threads and 64 x 4 clients, at 15.46
   server cores (261,576 QPS per server core). The best shared-socket run
   was 3,279,796 QPS with 16 threads at 15.86 cores (206,855 QPS per core).
3. The shared socket with blocking threads did not scale past 16 workers.
   With 32 workers it reached 2,907,949 QPS (32 x 8 clients) but collapsed
   to 167,349 QPS with 8 x 32 clients while the server used 18.5 cores.
   That is consistent with contention on the one socket once runnable
   threads outnumber the 32 vCPUs; it was not investigated further.
   The same configuration with SO_REUSEPORT reached 2,334,506 QPS.
4. At 8 workers the best shared-socket run (2,732,602 QPS, 8 x 32
   clients) beat the best SO_REUSEPORT run (1,910,285 QPS, 32 x 8). With
   the same 32 x 8 layout SO_REUSEPORT was ahead (1,910,285 against
   1,539,167 QPS); with 8 x 32 the flow hash left sockets idle (4.8 server
   cores, 1,732,414 QPS). Few, busy client sockets are cheaper for the load
   generator, which favours the shared socket in this setup. SO_REUSEPORT
   pays off when the number of distinct client flows is large compared
   with the number of sockets. Production resolver
   traffic comes from many source ports, so the 32 x 8 and 64 x 4 layouts
   are the closer model; the spike did not test a real traffic mix.
5. tokio: SO_REUSEPORT raised the peak from 1,651,950 (shared, 16 workers)
   to 2,287,706 QPS (32 workers). tokio stayed below blocking threads in
   every configuration from 8 workers up.

On Linux, `hickory` reached a median of 83 to 87 % of the `domain`

does not. That explanation is likely but was not measured.

## Conclusions (Linux, WSL2)

- Highest throughput measured: N blocking threads, each with its own
  SO_REUSEPORT socket: 4.04 M QPS at 32 workers (15.5 server cores) with
  64 client sockets. It needs many client flows; with 8 client sockets the
  flow hash left more than half of the sockets idle.
- One shared socket with N blocking threads is even and simple and reached
  3.28 M QPS at 16 workers, but did not scale past 16 workers and collapsed
  in one 32-worker configuration.
- tokio (one multi-threaded runtime) was the slowest design from 8 workers
  up: 1.65 M QPS on a shared socket, 2.29 M with SO_REUSEPORT.
- `hickory-proto` reached 83 to 87 % of the `domain` throughput in paired
  runs; in the micro-benchmarks a round trip took 145 ns with `domain` and
  388 ns with `hickory-proto` (0 against 6 allocations).
- Peak RSS stayed between 10.0 and 11.5 MiB in every run.
