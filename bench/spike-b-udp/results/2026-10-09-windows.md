# Spike B results: Windows, 2026-10-09

Spike B answers two questions for the DDI architecture:

1. What raw UDP DNS request/response throughput and latency does the spike's
   I/O design reach, and how does it scale with the number of workers?
2. Which DNS wire-format crate should DDI build on: `domain` (NLnet Labs) or
   `hickory-proto`?

This file has the Windows measurements and the [Recommendation](#recommendation).
The Linux measurements (WSL2, including SO_REUSEPORT) are in
[`2026-10-09-linux-wsl2.md`](2026-10-09-linux-wsl2.md) and are folded into
the recommendation.

**All numbers are loopback numbers**: client and server run on the same
machine and share its CPUs. They say nothing about NIC, driver or network
behaviour.

## Summary

- Windows, one worker with `domain`: about 146,000 to 162,000 QPS, about
  6.2 µs of server CPU per query (user + kernel). Throughput grew roughly
  linearly to 8 workers (597,000 to 752,000 QPS across the four backend and
  mode columns), little from 8 to 16 (754,000 at best) and not further at
  32. The two I/O modes (tokio tasks, blocking threads) were close; in
  quiet paired runs blocking threads were 1 to 4 % ahead.
- Linux (WSL2): up to 4,043,709 QPS with 32 blocking threads on 32
  SO_REUSEPORT sockets; up to 3,279,796 QPS on one shared socket.
- Crates: `domain` parses and builds with 0 heap allocations per query;
  `hickory-proto` needs 6 (A answer) to 10 (NXDOMAIN) in its encoder. Full
  round trip in memory: 153 ns against 535 ns on Windows, 145 ns against
  388 ns on Linux. In paired end-to-end runs `hickory-proto` reached a
  median of 90 to 94 % of the `domain` QPS on Windows (single pairs 89 to
  96 %) and 83 to 87 % on Linux (single pairs 82 to 88 %). Both crates
  produced byte-identical responses for the tested cases.
- Recommendation: build the hot path on `domain`; see below for the
  feature comparison and risks.

## Method

Commands (Git Bash, from `bench/spike-b-udp`):

```
cargo build --release
LISTEN=127.0.0.1:5399 scripts/run-matrix.sh results/raw/windows.jsonl
LISTEN=127.0.0.1:5399 scripts/run-unloaded.sh results/raw/windows-unloaded.jsonl
LISTEN=127.0.0.1:5399 scripts/run-ab.sh results/raw/windows-ab.jsonl
target/release/spike-b-udp report --input results/raw/windows.jsonl --out results/raw/windows-tables.md
cargo bench --bench codec
```

- Server: `serve` answers from an in-memory zone `example.test` with
  100,000 names `host-{n}.example.test` (A records in the RFC 5737 ranges),
  looked up in a `HashMap`. The per-packet hot path (`backend::respond`) is
  the same generic function for both crates; only `Codec::parse` and
  `Codec::build` differ. Each worker reuses one receive buffer, one response
  buffer and one lookup key.
- I/O modes on Windows (no SO_REUSEPORT load balancing): `tokio` = a
  multi-threaded runtime with N worker threads and N tasks sharing one
  `UdpSocket`; `threads` = N OS threads blocking in `recv_from`/`send_to` on
  one socket (duplicated handles). SO_RCVBUF/SO_SNDBUF 8 MiB.
- Each run: `matrix` starts `serve` as a child process, 2 s warm-up, 20 s
  measured, then kills it. Workers 1, 2, 4, 8, 16, 32; both backends; both
  modes: 72 runs.
- Load: closed loop, 256 queries in flight in three layouts: 8 client
  sockets x 32, 32 x 8 and 64 x 4. Each client socket is one OS thread.
  Random `host-{n}` names, 5 % non-existent names (NXDOMAIN), EDNS OPT with
  UDP size 1232 on every query. Every response is checked (ID, QR, AA, TC,
  question, RCODE, counts); 0 errors in all runs.
- Tables show, per configuration, the run with the highest QPS of the three
  layouts. Latency under load is closed-loop latency: with 256 queries in
  flight, p50 is roughly 256 / QPS (Little's law), so compare latencies only
  at the same number of queries in flight. Unloaded latency (one query in
  flight) is measured separately.
- Server CPU: user + kernel CPU time of the server process over the
  measured 20 s (via `sysinfo`), so it includes the socket system calls.
  Peak RSS: working set sampled every 100 ms.

### Observations

1. One worker handled 146,000 to 157,000 QPS (`domain`, matrix) at about
   one core. The paired runs below put the server's cost at 6.2 µs of CPU
   per query at one worker; the in-memory parse, lookup and build take
   about 0.15 µs of that (criterion), the rest is socket I/O, kernel and
   scheduling.
2. Up to 8 workers throughput grew roughly linearly (`domain` / tokio:
   157,486, 272,732, 450,251, 688,788 QPS for 1, 2, 4, 8 workers). From 8
   to 16 workers it grew little or not at all, and 32 workers were slower
   than 16 in three of the four columns.
3. Three of the four best runs at 16 workers used the 8 x 32 layout, where
   the load generator's 8 threads were fully busy (7.99 cores). Layouts
   with more client threads gave lower totals because client and server
   then compete for the same 32 logical processors (client + server CPU
   reached 28 to 30 cores). The ceiling of about 750,000 QPS is therefore a
   ceiling of this machine running both sides, not of the server alone.
4. QPS per server core fell from 133,000 to 160,000 at 1 worker to 76,000
   to 98,000 at 8 and 45,000 to 56,000 at 16. In the paired runs the CPU
   per query rose from 6.2 µs at 1 worker to 7.6 to 7.8 µs at 4 workers on
   the one shared socket.
5. tokio against blocking threads on Windows: in the matrix the best runs
   of the two modes ranged from tokio 18 % higher to threads 26 % higher,
   with no consistent direction for `domain`; for
   `hickory` threads was ahead at every worker count, but the
   `hickory` / tokio runs include those with the heaviest other load. In
   the quieter paired runs blocking threads were 1 to 4 % ahead of tokio
   at 1 and 4 workers. Unloaded, the tokio server used more CPU for about
   the same work (0.67 to 0.78 cores against 0.48 to 0.54 cores at 26,000
   to 36,000 QPS), most likely for parking and waking runtime threads
   between packets (not measured). Unloaded p50 latency was 19 to 38 µs in
   both modes, varying from run to run.
6. Timeouts: 4 of 72 runs had 144 to 248 timeouts each (at most 0.003 % of
   their queries), and in each of them the same number of responses
   arrived after the 1 s timeout (`unexpected`). The counts are multiples
   of 31 (8 x 32 layout) or 4 (64 x 4 layout), which is consistent with
   single client threads stalling for over a second on the loaded machine
   and losing almost all of their in-flight queries at once. It was not
   investigated further.
7. Peak RSS (working set) was 17.4 to 19.8 MiB in every run.

## Micro-benchmarks (criterion, Windows)

`cargo bench --bench codec`. In memory, one thread, no I/O. The captured
query is an A query for `host-4242.example.test` with an EDNS OPT (UDP size
1232).

- `parse`: `Codec::parse` (header, sole question, OPT; fills the lookup key).
- `build_a` / `build_nxdomain`: `Codec::build` of the A answer / the
  NXDOMAIN answer with the SOA in the authority section, into a reused
  `Vec<u8>`.
- `roundtrip`: the server's complete per-packet function `respond` (parse,

Where `hickory-proto` 0.26.3 allocates (from its source): every
`Name::emit` allocates a `Vec` of label offsets, and `BinEncoder` stores
each label suffix it may later point to as a separate `Vec<u8>` in a
`Vec<(usize, Vec<u8>)>`. That gives 6 allocations for the A answer and 10
for the NXDOMAIN answer (SOA owner, MNAME, RNAME). `Name::emit` stores these
suffixes even when compression is switched off. Parsing allocates nothing
in the lower-level path (names up to 32 octets of label data stay inline);
the high-level `Message::from_vec` allocates 2 `Vec`s. `domain` 0.12.3
parses zero-copy (`Message<&[u8]>`, `ParsedName<&[u8]>`) and compresses
names with `StaticCompressor` (a fixed table of 24 entries) into the reused
`Vec<u8>`, so it allocates nothing.

## Recommendation

### DNS wire-format crate: `domain`

Use `domain` (NLnet Labs) for the authoritative and forwarder hot path.

- **Measured cost.** 0 heap allocations per query for parse + lookup +
  build, against 6 to 10 in `hickory-proto`'s encoder. 153 ns against
  535 ns per in-memory round trip on Windows, 145 ns against 388 ns on
  Linux. End to end, `hickory-proto` reached a median of 90 to 94 % of the
  `domain` throughput on Windows and 83 to 87 % on Linux in paired runs,
  at 0.5 to 1.1 µs more server CPU per query. The gap grows as the I/O gets cheaper
  (Linux, and later batching), because the codec becomes a larger share of
  the per-query cost.
- **Zero-copy parsing.** `Message<Octs>` and `ParsedName` borrow the packet.
  A forwarder can read header and question of an upstream response and
  rewrite the ID in place without decoding records into owned values.
  (This argument was not measured; the spike only builds answers.)
- **Allocation-free building with compression.** `MessageBuilder` writes
  into any octets builder (here a reused `Vec<u8>`) with a choice of name
  compressor, including the fixed-size `StaticCompressor`. With
  `hickory-proto` 0.26.3 every emitted name allocates.
- **Same wire output.** For the tested answers (A, NXDOMAIN with SOA,
  apex SOA, with and without EDNS) both crates produced byte-identical
  responses, so the choice does not change behaviour on the wire.
- **Smaller footprint.** 16 transitive dependencies with default features
  (including its proc-macro crate and `rand`) against 50 for
  `hickory-proto` (which pulls in `url`, `idna` and the ICU crates); the
  spike binary is 311,808 bytes (Windows) / 366,528 bytes (Linux) smaller.
- **Authoritative features.** Zone file parser, TSIG, DNSSEC record types
  (always compiled), DNSSEC signing and validation, XFR handling and a zone
  tree all exist in `domain`, several of them behind `unstable-*` feature
  flags (see the table and the risks).

`hickory-proto` remains the stronger choice for ecosystem breadth (far more
users, `hickory-resolver` and `hickory-server` built on it, dual MIT /
Apache-2.0 license). Both licenses are on the allow list in `deny.toml`
(`BSD-3-Clause` for `domain`, `MIT OR Apache-2.0` for `hickory-proto`).

### Risks

- **API churn in `domain`.** The crate is pre-1.0 and its documentation
  says the API is undergoing large-scale changes, collected in the `new`
  module (`unstable-new`). Much of what an authoritative server needs beyond
  the wire format (signing, validation, XFR, zone tree, server transport)
  is behind `unstable-*` flags, which carry no stability promise.
  Mitigation: keep the crate behind a small internal trait, as this spike
  does with `Codec`, pin minor versions, and plan for one migration.
- **Smaller user base.** About a seventh of `hickory-proto`'s downloads;
  fewer people find bugs before DDI does. Mitigation: fuzz the parse and
  build paths (the repository has a `fuzz/` directory).
- **Generic API.** `domain`'s octets-generic builders are harder to use.
  An example from writing this spike: moving from the authority builder
  back to the answer builder silently rewinds the authority section; the
  first version of the NXDOMAIN response lost its SOA that way and only the
  tests caught it.
- **`hickory-proto` also churns.** It is pre-1.0 as well, and 0.26 moved
  the networking parts out of the proto crate, so choosing it would not
  remove migration risk.
- **Spike limits.** One A record per name, so no answer ever needed
  truncation in the benchmark (truncation is covered by unit tests only);
  no DNSSEC, no TCP, no forwarder path measured.

### I/O design

**Windows.** Windows has no SO_REUSEPORT load balancing, so the only
multi-worker design measured is one socket shared by N workers. N tokio
tasks on a multi-threaded runtime and N blocking threads performed about
the same (no consistent winner in the matrix; blocking threads 1 to 4 %
ahead in the quieter paired runs), both scaled roughly
linearly to 8 workers (about 700,000 QPS) and stopped scaling between 8 and
16 workers on this machine, where the load generator competes for the
same CPUs. The CPU per query on the shared socket rose with the worker
count (6.2 µs at 1 worker, 7.6 to 7.8 µs at 4). Idle tokio workers cost
more CPU than blocked threads. Conclusion for Windows: one shared socket
with a modest number of workers (up to about 8) is enough; neither mode is
worth optimising for further. Higher Windows throughput would need
different socket APIs (for example Registered I/O), which this spike did
not test.

**Linux (measured on WSL2, see the Linux file).** SO_REUSEPORT with one
socket per worker gave the highest throughput measured: 4.04 M QPS with
32 blocking threads (262,000 QPS per server core), against 3.28 M QPS for
the best shared-socket run (16 threads, 207,000 QPS per core). The shared
socket did not scale past 16 workers and collapsed to 167,000 QPS in one
32-worker configuration. SO_REUSEPORT spreads load by flow hash, not by
load: with 8 client sockets only 7 of 16 server sockets got traffic, with
64 client sockets 14 to 15 of 16, unevenly. tokio on one multi-threaded
runtime was the slowest design from 8 workers up (1.65 M QPS shared, 2.29 M
with SO_REUSEPORT).

Proposed direction for the ADR:

- One UDP socket per worker thread on Linux (SO_REUSEPORT), with the worker
  doing receive, answer and send without handing packets to other threads;
  one shared socket on Windows. Keep the per-packet hot path free of
  allocations, as in this spike.
- Prefer blocking threads (or one single-threaded runtime per worker) over
  one multi-threaded tokio runtime for the UDP fast path. Thread-per-core
  tokio runtimes were not measured.
- Not measured, candidates for the next spike: `recvmmsg`/`sendmmsg` and
  UDP GSO/GRO batching, steering SO_REUSEPORT with a BPF program to fix the
  flow-hash imbalance, CPU pinning, and a bare-metal Linux run with the
  load generator on a separate machine.
