# Spike C results: embedded UI and SSE (Windows, 2026-10-09)

Question (ADR 0003): can the SolidJS SPA be embedded in the server binary and served by the Rust
API process, with live updates over SSE, and what does it cost? This file records how it was
measured, the numbers, and a recommendation. How to build and run everything: `../README.md`.

  synthetic bundle (codegen smallest, then rust-embed, then include_dir).
- Raw embedding adds about the payload size (1,870,336 to 1,874,944 B for 1,858,529 B of files).
- Pre-compressed variants add the br + gzip bytes: 12,288 to 14,336 B for `ui/dist`

  without gzip. From the bundle table it would drop the 1,858,529 B of raw data from the
  synthetic variant; its decoder size and runtime cost were not measured.

## SSE: fan-out cost

`measure fanout --threads 8 --rate 100 --duration-secs 10`: N connected clients; the emitter
POSTs 100 events per second (about 140 B frames) over one keep-alive connection; every client
counts events and records the delivery latency from just before the POST to receipt. CPU is the
server's CPU over the emit window plus 2 s drain, divided by delivered events. With no emits
(keep-alive only) the server used 0 to 16 ms CPU per 5 s in every run. Coalescing

- With 1,000 clients and 100 events/s, all 1,000,000 events of every run were delivered
  (about 100,000 deliveries per second).
- Without coalescing each delivery costs 15 to 54 us of server CPU on this machine (one task
  wake-up and one loopback socket write per client per event). 32 worker threads cost more and
  vary more (15.5 to 53.5 us) than 4 worker threads (15.0 to 21.8 us).
- The raw endpoint (frames encoded once) and axum's `Sse` (formatted per client) are not
  distinguishable at this load: the spread between runs is larger than the difference.
- Coalescing events into one write per client per 50 ms tick cut the CPU per delivered event to
  2.0 to 4.6 us, at the price of the tick in latency (p50 about 37 ms, p99 about 69 ms).
- At 5,000 clients without coalescing the server could not absorb 100 events/s: the emitter's
  POSTs slowed down to 30 to 33 events/s with 32 workers (150,000 to 166,000 deliveries/s) and
  50 to 51 events/s with 4 workers (252,000 to 257,000 deliveries/s). With 50 ms coalescing and
  4 workers it kept 100 events/s, 500,000 deliveries/s, at 1.2 to 1.3 cores.
- One event to all clients, idle otherwise (previous section): 5.9 ms for 1,000, 74 ms for
  10,000 and 156 ms for 20,000 clients.

## Embedding crates: ergonomics

| | include_dir 0.7.4 | rust-embed 8.13.0 | build.rs codegen (no crate) |
|---|---|---|---|
| Embedding | `include_dir!("$OUT_DIR/ui")`, env vars built in | `#[derive(RustEmbed)]`, `$OUT_DIR` needs feature `interpolate-folder-path` | `include!` of a generated `&[GenFile]` table of `include_bytes!` |
| Metadata | none; paths use `\` on Windows and needed normalising | SHA-256 per file at compile time, optional mime, mtime | anything `build.rs` computes (ETag, content type) |
| ETag cost at start-up | hash every file (touches all pages: +1.72 MiB WS for the synthetic bundle) | none | none |
| Debug builds | embed | read from disk unless `debug-embed` (a built-in dev mode) | embed |
| Compression | none | `compression`: deflate or zstd inside the binary, but `get()` inflates on every call and the folder must be under the manifest directory; the stored stream is not a gzip or br representation, so the spike serves identity from it | whatever `build.rs` writes |
| Binary size vs codegen | +1,536 B (empty) to +8,704 B (synthetic, pre-compressed) | +512 B to +4,608 B | baseline |
| Extra dependencies | include_dir + proc macro | proc macro (syn, sha2, walkdir, shellexpand, mime_guess) and rust-embed-utils (sha2, walkdir) | none (build deps already needed for compression: brotli, flate2, xxhash-rust) |

## Recommendation

1. **Embedding: no embedding crate. Generate a static asset table in `build.rs` with
   `include_bytes!`.** `build.rs` is needed for pre-compression anyway. It also computes the ETags
   and content types at build time, so start-up does no hashing and leaves asset pages untouched
   until they are served. The table is a plain `&'static [GenFile]` with no proc macro. Measured
   difference to the crates: smallest binary (by 0.5 to 8.7 KB), same cold start (17.2 ms median
   to health), no WS cost from start-up hashing. If a crate is preferred, rust-embed (compile-time
   hashes, disk reads in debug builds) is the better fit. Do not use rust-embed `compression`: it
   copies the UI into the heap (+2.23 MiB private for 1.8 MB), adds 7 ms of start-up for 1.8 MB, and
   serves only identity. `include_dir` works, but it gives no metadata.
2. **Compression: pre-compress at build time (brotli q11 and gzip 9 next to identity) and pick the
   variant by `Accept-Encoding`. Do not use `CompressionLayer` for static assets.** Runtime
   compression adds 1.17 MB of binary, costs 8 to 10 times the CPU per JS request, cuts JS
   throughput by 2 to 3 times, and its bodies are larger. Keep all three representations:
   identity for clients without `Accept-Encoding`, gzip for browsers on plain-HTTP non-loopback
   origins (lab mode; browsers advertise `br` only on secure contexts, which was not checked here
   beyond loopback), and br for TLS. Pre-compression costs the br + gzip bytes in the binary
   (12 KB today, 836 KB for the 1.8 MB synthetic bundle). If binary size ever matters more, embed
   only br + gzip and inflate gzip on demand for identity (not built or measured). Compressing
   dynamic API JSON is a separate decision and was not measured.
3. **Caching and serving rules** (as implemented and checked in a browser):
   - `/assets/*` (hashed): `Cache-Control: public, max-age=31536000, immutable`.
   - `index.html` and every SPA fallback: `Cache-Control: no-cache` plus a strong ETag per
     representation (`"<hash>"`, `"<hash>.br"`, `"<hash>.gz"`) with `Vary: accept-encoding`.
     `If-None-Match` is compared weakly, ignoring the coding suffix, and a match is a 304.
   - SPA fallback for every GET/HEAD miss outside `/assets/`. DDI routes contain FQDNs and
     addresses, so "path has a dot" must not decide. A miss under `/assets/` is 404, and so is a
     miss under `/api/` (JSON). No directory listing.
   - On every response: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
     COOP/CORP `same-origin`, and
     `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
     img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none';
     base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. The current UI runs under it
     without violations. Add HSTS when served over TLS.
4. **SSE pattern:**
   - One `tokio::sync::broadcast` channel carries events that are encoded once into `Bytes` SSE
     frames.
   - A ring of the last 256 events serves `Last-Event-ID`. The replay snapshot and the
     subscription are taken under the publish lock, so a reconnect sees no gap and no duplicate.
   - Event ids are monotonic across restarts. A client that sends an unknown or too old id, or
     that lags behind the channel, gets an `event: reset` and refetches its state instead of being
     buffered.
   - One shared keep-alive timer task sends a comment every 15 s. Graceful shutdown is a
     broadcast message that ends every stream.
   - Use `TCP_NODELAY`, `retry: 3000` and a deep listen backlog.
   - Add per-tick coalescing as soon as events times clients gets large. Only a 50 ms tick was
     measured: at 1,000 clients it cut the CPU per delivered event from 15 to 43 us to 2.0 to
     4.6 us, and the tick becomes the latency budget (p50 about 37 ms, p99 about 69 ms).
   - Write the stream as a raw `Body::from_stream` of pre-encoded frames, which makes a coalesced
     batch one write. axum's `Sse` type measured the same for memory and, within noise, for CPU.
   - Give the API/UI role its own small runtime (2 to 4 worker threads), not one worker per core.
     In 5 of 6 paired fan-out runs 4 workers used 1.7 to 3.5 times less CPU per delivery than
     32 workers (in the sixth, axum run B, 32 workers used 15.5 us against 21.8 us). The 4-worker
     runs varied less. Idle private memory was 0.7 to 1.7 MiB lower with 4 or 2 workers.

6. **What to watch at enterprise scale:**
   - **Fan-out CPU, not memory, is the SSE limit.** Each delivery costs tens of microseconds
     without coalescing. Coalesce, filter server-side per subscription (topics or scopes, so
     clients only receive what they display), and size the API runtime separately from the DNS
     and DHCP data plane.
   - **Event ids in a cluster.** For `Last-Event-ID` to work against any controller node, ids
     must be cluster-wide and ordered, for example the Raft commit index. A per-process ring then
     becomes a replay from the replicated log or from a shared window.
   - **Browsers.** HTTP/1.1 allows 6 connections per origin, and each tab's `EventSource` keeps
     one. Serve the UI over HTTP/2 with TLS, or share one stream across tabs (SharedWorker or
     BroadcastChannel). The spike is HTTP/1.1 only.
   - **Reconnect storms.** After a restart every client reconnects within `retry`. Add jitter on
     the client side and keep the deep backlog. At 100 events/s the replay ring (256 events) bridges a
     disconnect of 2.56 s, and the channel (1,024 events) lets a slow connected client fall 10 s
     behind before it is reset; beyond that clients refetch state.
   - **Intermediaries.** Proxies and load balancers may buffer or idle-close streams. Keep the
     15 s keep-alive and `X-Accel-Buffering: no`, and document timeouts above 15 s.
   - **Limits and auth.** Cap SSE connections per session and in total. `EventSource` sends
     cookies but cannot set headers, so authenticate the stream with the session cookie and keep
     the emit path internal. Per-connection memory sits in the HTTP/1.1 connection (hyper
     keeps 8 KiB read and write buffers per connection, from source); `axum::serve` does not expose
     hyper's connection settings, so tuning would need a custom hyper accept loop.
   - **Measure again on Linux** and with client and server on separate hosts before treating the
     CPU figures as capacity numbers.

## Not measured

- Linux (all numbers are Windows), and separate client and server hosts.
- HTTP/2 and TLS (the spike serves HTTP/1.1 on plain TCP).
- Browser behaviour beyond the checks above: no multi-tab or `EventSource` reconnect test in a
  browser.
- `vite dev` with the real `ui/vite.config.ts` and HMR. Only the proxy block was checked.
- Kernel memory per socket (nonpaged pool), handle counts, and client-side memory.
- More than 20,000 SSE clients. The dynamic port range here has 64,511 ports per client address.
- Graceful shutdown with a real console ctrl-c. It was tested in-process with a shutdown future:
  every stream received `event: shutdown`, the stream closed and the server task finished.
- zstd content coding, Range requests and `If-Modified-Since` on embedded assets (not
  implemented).
- A minified large bundle. The synthetic bundle is unminified and compresses better than real
  output.
- The br+gzip-only variant (identity inflated on demand) and dynamic JSON compression.
- CPU below the 15.625 ms tick resolution. Event delivery latency includes the emitter's POST
  round trip.
