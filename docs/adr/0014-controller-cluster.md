# ADR 0014: The controller cluster

- Status: Accepted
- Date: 2026-10-10

## Context

ADR 0002 chose one Raft group (openraft over redb) for the replicated store and ran it with a single voter through Phase 1 Slices 1 and 2. Slice 3 turns it into a cluster of controllers (OPS-03, E9): three controllers that lose one and keep accepting writes without losing a committed one. The pieces were in place: `RaftStore` had learners, membership changes and a transport trait; the cluster port (`docs/cluster.md`) carried gRPC over mutual TLS between nodes and controllers with an internal CA. Open were the transport between controllers, how a controller joins, how writes reach the leader from any controller, which membership changes are allowed, how a controller learns the installation's key encryption keys, and what leader-only work means (plan section 2.3, owner decisions S3-Q2, S3-Q3 and S3-Q5 of 2026-10-10).

## Decision

1. **One Raft group over the cluster port.** openraft stays pinned at `=0.9.25`. Controllers exchange Raft messages through two gRPC services on the cluster port, `Raft` (append entries, vote, snapshot streaming) and `Cluster` (join, forwarded writes and read indexes, members, state digests, key transfer, the hand-over of leadership, forwarded membership changes). Payloads are openraft's own request types and Tenko's write batches in CBOR, each tagged with a wire version (`openraft-0.9/cbor-1`, `tenko-batch/cbor-1`, `tenko-cluster/cbor-1`); a peer with another tag is refused with `cluster.forward.wire`, so a rolling upgrade never mixes encodings and an openraft upgrade is a planned change of the whole cluster (R19).
2. **Controllers are enrolled nodes.** A controller joins with a single-use enrolment token for the role `controller` (at most an hour, created only by an administrator signed in within the last five minutes, R22). It gets a node id from the registry (1001 and up), which is also its Raft id, and a certificate with the role `controller`; its record in `cluster.nodes` lets the cluster list, renew and revoke it like any node. The first controller keeps the Raft id 1 it was started with and gets a node record and a member record when the first peer joins. A controller's cluster identity lives under `<data_dir>/node/` with a sealed key, because start step 3 runs before the vault opens; the first controller's key moves there from the vault at the first join.
3. **Who may call.** Both services require the role `controller` in a certificate of the installation's CA (other CAs and revoked serials fail the TLS handshake). `Cluster` also requires a node record that holds the presented certificate. `Raft` accepts a controller whose record the callee has not replicated yet (a learner catching up from an empty store knows nobody), refuses one whose record does not hold the certificate, and refuses a message that speaks for another node than its sender.
4. **Endpoints from member records.** Peers dial the cluster port named in `cluster.members` (written at join), not the address in the Raft membership; the latter is only a fallback while the record replicates.
5. **Learner first, odd voters only.** A joining controller is added as a learner without waiting. The leader promotes caught-up learners (`[cluster] auto_promote`, `promote_lag_entries` for 10 seconds, in contact) and only to an odd number of voters: one voter and one caught-up learner wait for a second learner, because two voters are less available than one (R21). An administrator overrides with `force`. A dead voter is replaced in one joint change (`replace`), so the cluster never passes through two or four voters. Removal revokes the removed controller's certificates.
6. **The join copies the data before the controller serves.** `tenko cluster join` enrols, receives the key encryption keys, opens an empty store marked as joining (such a directory is never initialized as a cluster of its own), opens its cluster port, joins as a learner and waits until it has the cluster's data, from the log or a snapshot. It refuses a cluster whose data format its binary does not know (`cluster.join.format_newer`), writes the format marker from the format record it received and writes `[node] id`, `[node] address` and `[cluster] listen` into the configuration. `tenko serve` then always starts on a member store; a store directory remembers its node id and refuses to open under another one.
7. **Writes go to the leader, reads stay local.** A follower forwards the encoded batch to the leader (`Cluster.Propose`), which validates and proposes it like a local write; the follower returns once it has applied the commit itself, so a write is readable at once on the controller that served it (read-your-writes). A forward goes to another leader only when the answer proves nothing was queued (the callee does not lead, or the connection could not be made); a lost answer returns a timeout, and the caller's idempotency key or precondition makes a retry safe. Preconditions keep the meaning of ADR 0011 because every replica checks them at apply. A linearizable read on a follower asks the leader for a read index and waits until it applied that far; `Local` and `AtLeast` reads stay local.
8. **Quorum state.** Every member reports whether it reaches a quorum: `single`, `healthy`, `electing` (no leader, since when), or `isolated` after `[cluster] isolation_after_ms` without contact (a leader by its last quorum acknowledgement, a follower by its last message from the leader), with the revision it last applied. The partition layer (ADR 0013) refuses writes on a member that is not single or healthy.
9. **Hand-over of leadership.** openraft 0.9 has no transfer call. A step-down holds new writes, waits until the chosen voter has every entry, stops the leader's heartbeats so the followers' leader leases expire, and asks that voter to campaign (`Cluster.Campaign`); held writes then go to the new leader.
10. **Membership changes from any controller.** Promotion, replacement, removal and step-down are accepted by every controller and run on the leader; a follower hands them over (`Cluster.Change`). A promotion or removal is an inline job `cluster.edit` (step `cluster.member`) on the controller that took the request, so the API answers with its job id like every other edit. The Raft change cannot commit in one write with the job record, so the audit record (`cluster.member.*`) is a separate write by the leader.
11. **Leader-only work** runs under the supervisor of plan section 2.3 with an epoch counter as a precondition on every write, so a deposed leader cannot write (R20). This package contributes the hourly prune of the node registry (`cluster.prune`); until the supervisor is wired, the maintenance task of a controller prunes only while it leads.
12. **Key encryption keys.** One KEK per installation (S3-Q5). The joiner sends a one-time X25519 public key with the id of its enrolment token; a member seals every generation it holds to that key (HKDF-SHA-256, AES-256-GCM) inside the mutual TLS channel, the joiner opens it and seals the generations again with its own KEK provider. A join transfer is single use per token (`cluster.kek_transfers`); a member that lacks generations after an online rotation fetches them at start the same way without a token. Every transfer is audited as `vault.kek.transfer` with the generation ids, never the material, and the material never enters the store. The sealing format and the rotation are WP3.4a's (`docs/secrets.md`).
13. **State digests.** `Cluster.Digest` hashes every non-empty table at a revision; `tenko cluster verify` and `GET /cluster/digests` compare the members.
14. **Node state across controllers.** The node registry stays one set of tables in the store. Every controller follows the revocation table with a watch and applies a change to its TLS verifier and its open sessions at once. A certificate of a node that this controller has not replicated yet is looked up with a linearizable read before it is refused. Each controller records the nodes connected to it (`cluster.connections`) and clears its own records at start, so every controller shows the same connected view; a record of a controller that is no longer a member counts as disconnected. `Hello` lists the cluster ports of every member, the answering controller first.

## Consequences

- A cluster needs every controller to reach every other controller's cluster port (8444/TCP); nodes keep dialling the cluster port directly and learn all controllers' endpoints from `Hello`.
- Writes on a follower cost one extra round trip to the leader and wait for the follower's own apply (M12 measures it).
- A cluster of three survives the loss of one controller; a cluster of two does not survive the loss of either, which is why promotion keeps the voter count odd.
- The first controller's cluster key moves out of the vault at the first join and is from then on protected like a probe's key (DPAPI on Windows, a 0600 file on Linux).
- Raft and the store's write batches are encoded with the serde forms of openraft 0.9 and Tenko's types; an upgrade of openraft or a change of those forms needs a new wire tag and a coordinated upgrade of every controller.
- Membership changes, step-down and the digest work from any controller: a follower hands them to the leader.
- A connect or disconnect of a node is a write on the controller that holds the connection, so a cluster with many nodes writes a little more than a single controller; heartbeats stay in memory.

## Alternatives considered

- **A separate port or protocol between controllers.** A second listener and a second TLS setup for no gain: the cluster port already has mutual TLS with roles and revocation.
- **Endpoints from the Raft membership (`BasicNode`).** The first controller was initialized with an empty address, and an address in the Raft log cannot change without a membership change; member records can.
- **Joining inside `tenko serve`.** The first start of a joiner would have to skip the data-format step and start the vault on an empty store; copying the data in `tenko cluster join` keeps the start order of `tenko serve` the same for every member.
- **Rejecting writes on followers (clients go to the leader).** Every client, the UI behind a load balancer and every internal writer would have to find the leader; forwarding hides it and keeps read-your-writes on the controller a client talks to.
- **Automatic promotion to any voter count.** A cluster of two voters stops on the loss of either; waiting for the second learner avoids that window (R21).
- **A KEK per controller with every data key wrapped once per controller** (S3-Q5 option b): changes the envelope format and makes every join and rotation rewrap everything.
