# ADR 0016: Backup and restore

- Status: Accepted
- Date: 2026-10-11

## Context

OPS-07 asks for a consistent, encrypted backup of an installation, a check of a backup without restoring it, scheduled backups and a restore on a new host. Until Slice 3 the only backup was the operator's copy of a stopped data directory together with a separate copy of the key-encryption key (`docs/upgrades.md` 7.2). That copy is consistent only while the server is stopped, is not encrypted, and fails to restore whenever the key copy is lost, which is the common failure at home.

The owner decided S3-Q11 on 2026-10-10: one encrypted file holds the store snapshot, the key generations wrapped under the backup key, the imported TLS files and optionally the configuration; the backup key comes from a passphrase (Argon2id) or a recipient key file; restore needs only the file and that secret; scheduled backups run on the leader, are off by default, and Standard and Hardened warn after 7 days without a good backup; Phase 1 offers no download through the UI. Risk R36 applies: a backup is a copy of every secret and of the key-encryption key.

Two properties of the store shape the design. A Raft snapshot of the store (`TNKSNAP1`, `tenko_store::raft`) is the whole state machine at one log id, written in table and key order with a trailing SHA-256. Its metadata carries the Raft membership, so a snapshot of a three-controller cluster names three voters, and a store started from it waits for peers that a restore on a new host does not have.

## Decision

1. **One framed container, `TKBK1`.** A backup is one file, `tenko-backup-<UTC time>-n<node>.tkbk`, written to a `.part` name, synced and renamed. Nothing in it is readable without the backup key: the plain header holds only what is needed to find and unwrap that key. Integers are big-endian.

   ```text
   header  = "TKBK1" | flags u8 = 0 | archive id (16) | chunk size u32 | slot count u8 (1..=8)
             | slots | SHA-256 of every header byte before it (32)
   slot    = 0x01 passphrase | memory KiB u32 | passes u32 | lanes u32 | salt (16) | nonce (12)
                             | wrapped file key (48)
           | 0x02 recipient  | recipient tag (8) | ephemeral X25519 public key (32) | nonce (12)
                             | wrapped file key (48)
   body    = chunk 0 | chunk 1 | ... | last chunk
   chunk i = AES-256-GCM(payload key, nonce = 0 (3) | i u64 | last u8, plain chunk,
                         aad = header hash) | tag (16)
   ```

   A chunk holds exactly `chunk size` plain bytes (the writer uses 1 MiB; a reader accepts 64 KiB to 8 MiB), except the last, which holds fewer, possibly none, and carries the last flag in its nonce. Reordered, dropped, appended or truncated chunks and any changed byte fail authentication; a changed header fails its hash before any key derivation runs.

2. **Keys.** A random 256-bit file key is wrapped once per slot with AES-256-GCM under a slot key, with the additional data `"tenko-backup/1 slot" | archive id | slot type`. A passphrase slot derives its slot key with Argon2id from the passphrase and a random salt; the writer uses the Hardened parameters of the password hashes (64 MiB, 3 passes, 1 lane) and a reader refuses parameters outside 19 MiB to 1 GiB, 1 to 16 passes and 1 to 8 lanes, so a crafted file cannot make a reader allocate without bound. A recipient slot follows the construction of the key transfer (`tenko_vault::transfer`, HPKE base mode with DHKEM(X25519) and HKDF-SHA-256): a fresh ephemeral key, `dh = X25519(ephemeral, recipient)`, the slot key from HKDF with the salt `"tenko-backup/1 recipient"` and the info `ephemeral public key | recipient public key | archive id`; the recipient tag is the first 8 bytes of the SHA-256 of the recipient public key. The payload key is HKDF-SHA-256 of the file key with the archive id as salt and the info `"tenko-backup/1 payload"`. A recipient key file is created by `tenko backup keygen`; its public half (`tkbr1:` and base64url) is all the server ever holds, so the server can write scheduled backups that it cannot read. A passphrase is never stored. A wrong passphrase or key fails at the slot, before any output exists.

3. **Plain stream and manifest.** The decrypted body is `"TKBM" | manifest length u32 (at most 1 MiB) | manifest (JSON) | parts`, the parts back to back in the order and with the lengths the manifest lists, and nothing after the last one. The manifest (`format` `tenko-backup/1`) names the Tenko version, the data-directory format of the store, the source node and the voters, the revision, the audit head, the store digest (the SHA-256 that `RaftStore::digest` computes over every table, with its revision, table and row counts), the fingerprint of the internal CA root, the key generation identifiers with the active one, and the parts with their size, SHA-256 and encoding (`identity` in format 1; a later version may compress without a format change). The parts are `store.snapshot` (a `TNKSNAP1` file and its Raft metadata in the manifest), `kek.generations` (`"TKBG" | version 1 | count u8 | count × (id length u8 | id | key (32))`, oldest first and the active generation last, as the transfer payload), `tls.certificate` and `tls.key` (the imported files of TLS mode b, both or neither), `config` (the `tenko.toml` the server runs with, optional) and `leases`, empty and reserved for Phase 3 so that leases do not change the format. A reader refuses another major format, a missing required part and a hash mismatch; it verifies and ignores a part it does not know.

4. **Creation.** The source is a state copy, never the live files: `RaftStore::copy_state_to` writes a compacted state file from one read transaction while writes go on (online), or `tenko_store::format::copy_closed_store` copies a stopped store (offline, `tenko backup create --data-dir`, refused while a server runs on it). The copy is opened as a scratch store under the source's node id; its digest is taken, then `snapshot_now` and `current_snapshot` give the `TNKSNAP1` file that goes into the archive. The live store is never asked to snapshot, so its log, its followers and its snapshot rotation are untouched. The key generations come from the loaded ring (`KekProvider::export_material`); the material exists in memory only, in zeroizing buffers, and leaves the process only inside the archive. The scratch directory is removed whatever the outcome.

5. **Online and scheduled backups.** `POST /system/backups` (administrators, a sign-in within five minutes, audited `sys.backup.create`) writes a backup into the target directory of the controller that answers, wrapped to the configured recipient and, when the request carries one, to a passphrase. It runs as the inline job `backup.create`: the archive is written first, then its record (`backup.runs`) and audit record commit in the job's one write. The settings (`backup.settings`: enabled, interval in hours, keep count, target directory, recipient, whether to include the configuration) are replicated and changed through the API with audit (`sys.backup.settings`); the target directory falls back to `[backup] target_dir` of the host and then to `<data_dir>/backups`. The schedule is the leader service `backup.schedule`: it runs a backup when the interval has passed since the last good scheduled one, records it fenced by the leader epoch, and then keeps the newest `keep` archives of the target directory. Scheduled backups are off by default and need a recipient. One backup runs at a time per controller.

6. **Verification.** `tenko backup verify <file>` and `tenko backup restore --dry-run` do everything a restore does in a temporary directory and then remove it: unwrap the key, check every chunk and every part hash, install the snapshot into a fresh store, compare its digest with the manifest, verify the whole audit chain, open every envelope of `vault.secrets` with the generations of the archive (the values are wiped at once) and compare the CA fingerprint. A backup counts as good only when it was written completely; the server does not verify its own archives again.

7. **Restore.** `tenko backup restore <file> --data-dir <new>` needs a data directory without a store and a stopped server. It seals the key generations with the provider of the target host's configuration (`KekConfig::import_with`, the identifiers kept, so every envelope opens), then creates the store as a learner that has never been initialized and installs the snapshot into it with a membership of one voter, this host's `[node] id`, and a vote at the term of the snapshot's last log id. Opening it again as a single voter elects it at the next term, so the restored controller leads a cluster of one whatever the source's membership was. The digest, audit and envelope checks of item 6 then run on the restored store; any failure removes everything the restore wrote. The format marker is written from the stored format record of the snapshot, so a backup of an older format is migrated at the first start like any older data directory, and a newer one is refused. The internal CA, its key and the controller and node records come with the store, so enrolled nodes keep trusting the controller and reconnect without enrolment. The imported TLS files and the configuration are written to `<data_dir>/restored/` for the operator to place; the restore never overwrites a configuration. The restore leaves `<data_dir>/restored.json`; the first start records it as `backup.restore` with the audit record `sys.backup.restore`, shows a notice in `/system/status` until the next good backup, and deletes the file.

8. **Clusters.** A backup of any member restores to a single controller. The other controllers rejoin it with empty data directories through `tenko cluster join`, as when a cluster grows (ADR 0014); they receive the key generations through the sealed transfer. Records of the old members stay in the store until an administrator removes them.

9. **Status.** `GET /system/backups` and an optional `backup` fragment of `/system/status` report the settings, the last good and the last failed backup, the age of the last good one and the restore notice, with the warnings `backup.stale` (Standard and Hardened: no good backup for 7 days, counted from the end of first-run setup when there never was one), `backup.failed` and `backup.restored`.

## Consequences

- A restore on a new host needs one file and one secret. Losing both the passphrase and the recipient key loses the backup; the documentation says to keep the recipient key offline and to test restores with `verify`.
- Whoever holds a backup and its secret holds every secret of the installation (R36). Backups are always encrypted, the server keeps no secret that opens them, creation and restore are audited, and the UI offers no download in Phase 1.
- Creation costs one compacted copy of the state plus one snapshot file of scratch space beside the target directory, and about the time of a re-seed plus a sequential write of the snapshot; M14 measures it.
- The store keeps its own snapshot format; the backup carries `TNKSNAP1` files unchanged and depends on `RaftStore::receive_snapshot` and its install path, which the store's tests already cover for joining learners.
- A restored controller starts a new Raft history at a higher term. Members of the old cluster must not be started against it with their old data directories; they rejoin empty.

## Alternatives considered

- **An archive of the data-directory files (tar or zip).** Simple, but a copy of a running store is inconsistent, the files carry the membership and node identity of the source, and the key generations would sit beside the data under the same protection only if the archive itself were encrypted, which a general archive format does not do.
- **The key generations outside the backup (S3-Q11 option b).** Two secrets, and a restore that fails whenever the key copy is lost.
- **age or OpenPGP containers.** Mature formats, but new dependencies, and neither bounds the KDF parameters a crafted file can ask for; the construction here reuses the primitives the vault already uses from `aws-lc-rs`.
- **Restoring the state file directly.** Faster than a snapshot install, but the state file names the source's voters, so the restored store would wait for peers it does not have; rewriting the membership would reach into the store's private metadata.
