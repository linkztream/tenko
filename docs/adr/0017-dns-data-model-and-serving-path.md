# ADR 0017: DNS data model and serving path

- Status: Proposed
- Date: 2026-10-17

## Context

Phase 2 builds DNS (ROADMAP Phase 2, [phase-2-plan.md](../plans/phase-2-plan.md)): an authoritative engine, a forwarder and cache with policy zones, transfers, dynamic updates, DNSSEC and views. Every Phase 2 package builds on one set of contracts (WP4.0): where zones live, how the engine learns them, who writes them, how a query is answered, and how the wire format is read and written. The owner accepted the plan's decisions on 2026-10-17 (P2-Q1 to P2-Q16), among them P2-Q2 (zones in the replicated store, one feed trait), P2-Q3 (updates through the controllers, SERVFAIL without quorum) and P2-Q12 (an origin per RRset), and gave a direction the same day: Phase 2 builds and measures a single node, the multi-node data plane is Phase 5 (plan section 2.10).

ADR 0002 put all replicated state in one Raft group and ADR 0011 made every write a batch of the coalescer; ADR 0004 made `dns` a role of the one binary; ADR 0009 chose `domain` behind a `Codec` trait for the wire format and blocking UDP workers with zero allocations per query; ADR 0013 and ADR 0014 settled partitions and the controller cluster; ADR 0015 settled roles, grants and scoped tokens. What remained open: the shape of the DNS rows, the feed that turns them into an index, the write path of the engine, the ownership of records, the place of views in the lookup, what of the cluster is built now, and the `domain` version to pin (risk R38).

The `domain` evaluation of WP4.0: 0.12.3, released on 2026-09-25, is the newest release on crates.io (no 0.13 or pre-release exists). It is the version Spike B measured and the one already in the lock file through `tenko-scan`, and its release notes are mostly hardening of the parsers this project feeds untrusted input to (a limit of 255 compression pointers per name, bounded CNAME chains in `Message::canonical_name`, length checks on variable-length record data, no panics in the zone file parser on invalid UTF-8 or an empty TXT). The API that Tenko uses (`Message::from_octets`, `sole_question`, `MessageBuilder` with `StaticCompressor` and push limits, `OptBuilder::push_raw_option`, the RFC 1035 record types over `Name<[u8]>`) is the one Spike B used; nothing had to change. Its `tsig` feature pulls `ring`; the `unstable-*` features (zone tree, XFR, signing, server transport) move between minor versions.

## Decision

1. **Zones live in the replicated store.** Zones, RRsets, views, forwarding rules, access lists, TSIG key metadata, block lists and their compiled versions, the IXFR journal and the signing state are rows of the `dns` namespace in the one Raft group (ADR 0002): `dns.zones`, `dns.rrsets` (key zone, scope, owner name, type), `dns.views`, `dns.forwarders`, `dns.acls`, `dns.keys.meta`, `dns.lists`, `dns.list_versions`, `dns.journal`, `dns.sign_state`. No DNS setting lives in a node-local file. The model is `tenko_core::dns`; secrets (TSIG keys, DNSSEC private keys) are vault secrets with the purposes `tsig` and `dnssec`, never rows.
2. **The engine serves from an index and never reads the store on the query path.** The `dns` role builds an in-memory index from the rows and answers from it only: no store read, no lock a writer holds, no allocation per query (ADR 0009). The index is fed through one `ZoneFeed` trait (`tenko_dns::feed`) that delivers an image at a revision and then deltas in revision order, or a new image after a snapshot install; the engine never holds a store handle. A rebuild swaps atomically (M1). In Phase 2 the only production feed is the in-process feed of a controller that runs the `dns` role (WP4.3); `MemFeed` and `MemIndex` are the reference implementations and the test oracle of the production index.
3. **One lookup path and one view model.** Every transport (UDP workers, TCP, DoT, DoH) calls the same `Resolver`: view selection, the authoritative lookup, the policy zones, then the forwarder and cache. A view is a list of match rules (client subnet, transport, interface address, query type, time of day, query name; all must match; the first view in order wins) and a map from zones to scopes with weights; a query no view matches sees the default scope of every zone (the implicit default view). The cache is keyed by view. EDNS, cookies, minimal responses and RFC 8482 belong to the lookup, not to the transport.
4. **The engine never writes zone data.** A dynamic update is checked by the engine (TSIG, ACL, prerequisites against the index) and becomes one change set that the store commits through the coalescer; the client is answered when the index holds the change, and with SERVFAIL when the store refuses the write (no quorum, OPS-26). On the single node of Phase 2 the change set is a function call; in Phase 5 the same change set travels over the cluster channel (`Dns.Update`). Zone transfers in (Tenko as secondary) and DHCP updates (Phase 3) use the same path.
5. **Every RRset has an origin.** `manual` (API, UI, zone file), `ipam` (the DNS actuator), `dynamic` (RFC 2136, with the TSIG key name), `dhcp` (Phase 3), `ad` (Phase 4). A person may replace any RRset (the reconciler restores an `ipam` RRset a person changed); the actuator touches only `ipam` RRsets; dynamic updates, DHCP and AD replace an `ipam` RRset only when the zone's update policy allows (`Origin::may_replace`).
6. **Single node first, cluster-aware.** Phase 2 builds exactly what would otherwise be rebuilt: the rows in the store, the feed and index traits with the in-process implementation, the change-set write path, the origin field, the per-worker metrics, the `dns.*` audit actions, and the `dns` role as a role. The node-sync declaration is made now and consumed by nobody: the `dns` role receives every `dns.*` table except `dns.sign_state` (`Subset::role_tables`) and may ask for the secret purposes `tsig` and `dnssec` (public parts only). The node-file feed, the subset stream, `Dns.Update`, a `dns` node without a controller and per-node zone selection are Phase 5. Every Phase 2 measurement is a single-node figure.
7. **Record data is stored in wire form.** An RRset holds the uncompressed wire form of each record's data (`Rdata`), names lowercase (RFC 4034, section 6.2), so the engine copies it into answers without converting and an unknown type round-trips as RFC 3597 data. `RecordData` is the typed view of A, AAAA, CNAME, DNAME, MX, NS, PTR, SOA, SRV, TXT, CAA, DS, DNSKEY, RRSIG, NSEC, NSEC3, NSEC3PARAM, TLSA, SVCB and HTTPS for the API and the validation; TXT strings longer than 255 octets are split on input (DNS-24). Owner names are `DnsName` (canonical lowercase, wildcards, RFC 2317 labels, the root); their keys sort a name and its subtree as one range.
8. **The codec is allocation-free and differential-tested.** `Codec` (`tenko_dns::codec`) parses the header, the one question, OPT with the cookie, and TSIG with the positions its verification needs, and builds answers from a fixed-capacity `AnswerBuf` with EDNS (payload 1232, DO echoed, the extended RCODE), cookies, extended errors (RFC 8914) and the truncation rules (answer or authority overflow: header, question and OPT with TC; additional overflow: left out). The production codec `DomainCodec` is on `domain`; a second implementation on `hickory-proto` (a dev-dependency only) must agree on requests and octets over a corpus, and a counting allocator fails a test when parse, build or a lookup allocates.
9. **`domain` is pinned at exactly 0.12.3, with the `std` feature only.** The workspace declares `domain = "=0.12.3"` without default features. `tsig` stays off because it pulls `ring`; TSIG MACs are computed with `aws-lc-rs` (already in the tree for rustls and WebAuthn) over the positions the codec records. The `unstable-*` features are not used: zone trees, transfers and signing are Tenko's own code over the stable record types (risk R38). A later version is adopted only through a change that passes the differential corpus.
10. **Authorization uses three scopes in the roles of ADR 0015.** `dns.read` reads the DNS configuration, `dns.write` creates, changes, deletes and runs it, `dns.keys` is every action on TSIG and DNSSEC keys. The viewer holds `dns.read`, the operator `dns.read` and `dns.write`, the administrator all three, the auditor none; a scoped token reaches them through the roles of its grants, as ADR 0015 decided for every permission. The DNS object kinds (`zone`, `dns_view`, `dns_forwarder`, `dns_acl`, `dns_key`, `dns_list`) are global-only for grants in Phase 2; changing keys needs an interactive session.
11. **The data format moves to 3 once for the phase.** The `dns` namespace, the DNS object kinds and the system component `dns` are values a format 2 binary cannot decode, so format 3 is an empty migration that keeps such a binary away; the tables later Phase 2 packages add are additive.

## Consequences

- The engine is a pure function of the rows it was fed and keeps serving them when every controller is gone (OPS-02); a rebuild after a snapshot install does not interrupt answers.
- A write through the API, an RFC 2136 update, a zone transfer in and the DNS actuator all end in one change set with an audit record, so the audit trail and the IXFR journal see every change, and a partition answers SERVFAIL for updates instead of diverging copies.
- Phase 5 adds a feed (the node file) and a transport (`Dns.Update`), not a redesign; the declarations of the node subset and the secret purposes are already in place and tested.
- Record data in wire form costs a decode on every API read and write and saves a conversion on every query. Names inside imported record data outside the `DnsName` character set (an NSEC chain over names with arbitrary octets) are refused; a later decision can widen the name type if an import needs it.
- Pinning `domain` exactly means a security fix in a later patch release needs a deliberate update; the update runs the differential corpus and the codec tests.
- TSIG without the `domain` feature means Tenko owns the MAC computation; the codec gives it the positions (start of the TSIG record, the MAC, the original id), and the fuzz target `dns_codec` covers the parsing.
- The scopes add no new permission vocabulary: tokens and grants carry roles, as before.
- A binary of format 2 refuses a Phase 2 data directory; going back needs the copy taken before the migration (docs/upgrades.md).

## Alternatives considered

- **`dns` nodes as Raft learners** (P2-Q2 option b). Ships the whole store to every node and ties node upgrades to the Raft version. Rejected.
- **Internal IXFR between controllers and nodes** (P2-Q2 option c). Duplicates the transfer code for an internal purpose and loses the non-zone tables (views, lists) that nodes also need. Rejected.
- **Nodes accept updates locally and reconcile** (P2-Q3 option b). Diverging copies need a merge rule no DNS client expects. Rejected.
- **Records stored as presentation text or as typed values only.** Text needs a parse on every answer build; typed values only lose unknown types and need a conversion on the query path. Rejected for the wire form with a typed view.
- **The newest `domain` with the `tsig` and `unstable-*` features.** Brings ring into a graph that uses aws-lc-rs everywhere else, and APIs that move between minor versions. Rejected; the stable base API suffices.
- **`hickory-proto` as the production codec.** Measured slower and allocating in Spike B (ADR 0009). Kept as the differential implementation only.
- **Building the multi-node data plane in Phase 2.** The owner's direction of 2026-10-17 moves it to Phase 5 so that a working node is measured first.
- **Token-only DNS scopes** (a token carries `dns.read` as a special scope). ADR 0015 rejected a separate token vocabulary; the scopes are permission sets of roles instead.
