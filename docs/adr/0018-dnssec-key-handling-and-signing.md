# ADR 0018: DNSSEC key handling and signing

- Status: Proposed
- Date: 2026-10-18

## Context

DNS-12 asks for DNSSEC signing, online and offline, with NSEC and NSEC3 and automatic key rollover driven by CDS and CDNSKEY. The Phase 2 plan (section 2.7) and the owner's decision P2-Q4 of 2026-10-17 settled the shape: signing on the controllers with keys in the vault, imported signed zones for the offline case, ECDSAP256SHA256 as the default and Ed25519 offered; keys never leave the vault except in the backup (OPS-07). TGL-13 gives the signing default per security profile, OPS-09 asks that time synchronisation be treated as a dependency because signatures have validity windows, and E19 asks for a zone signed by Tenko with NSEC and NSEC3 that an external validator accepts, through a ZSK rollover.

ADR 0017 put zones and their records in the replicated store, made the engine serve from an index and never write, gave every RRset an origin, and pinned `domain` at 0.12.3 with the `std` feature only, so signing is Tenko's own code over the stable record types. ADR 0016 made the backup a copy of the store snapshot and the key generations. What remained open: where the signer runs and what it writes, how keys are generated, stored and loaded, how the denial chains are built and kept current, when signatures are renewed, how keys roll, how an imported signed zone is served, and what a node does with signed data.

## Decision

1. **The controllers sign; nodes serve signed data and never sign.** The signer is the leader-only service `dns.signer` (`tenko_dns::dnssec::signer`). It keeps every zone whose policy says `online` signed and writes what it generates as rows of the zone through the zone service, one change set per pass: DNSKEY, CDS and CDNSKEY at the apex, NSEC or NSEC3 records (and NSEC3PARAM), and one RRSIG row per owner holding the signatures of its RRsets. These rows carry the origin `dnssec`; no other writer may change them, and in a zone signed online no other writer may write those types at all (`dns.record.origin`). The records list leaves them out unless asked (`?origin=dnssec`); the zone file export carries them. A node receives them like any other row and answers from its index.
2. **Keys are vault secrets.** A key is generated with `aws-lc-rs` (ECDSA P-256 with SHA-256, algorithm 13, by default; Ed25519, algorithm 15, when the policy says so), its private key stored as a system secret of the vault (purpose `dns.dnssec`, owned by the key; node sync knows the role purpose `dnssec` for public parts only) in the same batch as its metadata in `dns.sign_state` (role, algorithm, key tag, public key, state, the times it was published, activated and retired). A zone has a KSK and a ZSK, or one CSK when its policy sets `csk`. The signer decrypts a key when a pass needs it and keeps it in memory only while it leads; the private key is never shown and never sent to a node. Turning signing off retires the keys and keeps them; turning it on again takes them up, so the DS at the parent stays valid. Removed keys lose their secret.
3. **What a key does follows its state.** Published, active and retired keys stand in the DNSKEY set; active ZSKs (or the CSK) sign the zone's data; the KSK (or CSK), published or active, signs the DNSKEY, CDS and CDNSKEY sets; CDS and CDNSKEY (RFC 7344) list the key-signing keys the parent should hold, and the status shows the same as SHA-256 DS records. The DS is put at the parent by the operator; Tenko does not talk to registrars.
4. **Signing is Tenko's code over the stored wire form.** Names and record data are stored lowercase (ADR 0017), so the canonical form of RFC 4034 section 6 is the stored octets in sorted order. A signature's inception is an hour before the signing time; its expiration is `signature_validity_days` later less a random jitter of up to half of `resign_before_days`, so a zone signed at once is renewed spread over days. The canonical form and the signatures are tested against the vectors of RFC 4034, 4035, 5155, 5702, 6605 and 8080 and checked independently in the tests (the stored rows and the answers with DO, rebuilt from `hickory-proto`'s canonical encoding and verified with the DNSKEYs), and E19 validates a signed zone with `delv` and `dnssec-verify` from the BIND image.
5. **Denial is NSEC by default, NSEC3 with RFC 9276 parameters on request.** The NSEC chain links every owner that holds data and is not below a cut or a DNAME, in canonical order. NSEC3 uses SHA-1, zero extra iterations and no salt by default (the policy may set others), opt-out off, with a record for every chain owner and every empty non-terminal above one; NSEC3PARAM stands at the apex. NSEC and NSEC3 records take the smaller of the SOA's TTL and MINIMUM (RFC 9077).
6. **Passes are incremental.** The signer follows the store's change stream of `dns.rrsets` and `dns.zones` (its own commits left out) and signs again what changed: the changed RRsets, the owners whose NSEC must point elsewhere, and for NSEC3 the empty non-terminals above a change and the hashed owners before it in hash order. A change of the zone's settings, a change of keys, the timer and a start after a change of leader run a full pass, which streams the zone once in canonical order and keeps every signature it can (same key, labels and TTL, more than the renewal time left; after a start whose missed changes the store no longer holds, a kept signature must also verify). A pass that writes anything moves the serial once per scope and journals its rows, so IXFR carries the signatures; a pass larger than an import would journal (10,000 records) resets the scope's journal, as an import does, so a secondary takes the next transfer as AXFR. A full pass of a large zone writes its rows in chunks and the serial, the apex and the state last.
7. **The timer renews ahead.** `next_resign` in the signing state is the earliest expiry less `resign_before_days`; when it comes, a full pass renews every signature with less than `resign_before_days` and a day left, so the next pass of a zone is about a day later rather than at every expiry.
8. **Rollovers are jobs.** `POST /dns/zones/{id}/dnssec/rollover` (scope `dns.keys`, audited `dns.key.rollover`) and the schedule of `zsk_rollover_days` start the job `dns.dnssec.rollover`. A ZSK rolls by pre-publication (RFC 6781 section 4.1.1.1): publish the new key, wait the DNSKEY TTL and the propagation delay, let it sign and retire the old one, wait the largest TTL of the zone and the delay, remove the old key. A KSK or CSK rolls with both keys signing the DNSKEY set and both in CDS and CDNSKEY until a person confirms the new DS at the parent (a manual step of the job), then the new key takes over and the old one is removed after the wait. The propagation delay is the SOA refresh, at most an hour, when the zone has secondaries, else nothing. Every step is idempotent and reads where the rollover stands from the keys' states and times, so a step that runs again after a restart or a change of leader sleeps what is left of its wait; each step and key change is audited (`dns.dnssec.rollover`, `dns.dnssec.key_state`). One rollover runs per zone (`dns.dnssec.rollover_running`). An algorithm change of a signed zone is not a rollover: the new algorithm applies to the keys generated after signing is switched off and on again.
9. **Offline signing is an imported signed zone.** With `mode = imported` the zone's own DNSSEC records (written by a zone file import or the API, origin `manual`) are served as they are; the signer only reads their earliest expiry, hourly, and removes any row of its own. The health findings warn 7 days before that expiry.
10. **Answers carry DNSSEC records only for DO.** With the DO bit (RFC 3225) an answer carries the RRSIGs of its RRsets (with the TTL of the covered RRset) and, in the authority section, the NSEC or NSEC3 proof for NXDOMAIN, NODATA, wildcard answers and delegations without DS (RFC 4035 section 3.1, RFC 5155 section 7.2), each signed; without DO nothing changes. The authoritative side never sets AD. A DS query at the apex of a zone whose parent the node also serves is answered by the parent. The proof is found in the index without allocating (the NSEC3 hash and the hashed owner are composed in fixed buffers), and the truncation rules of the codec apply to these records like to any others.
11. **Profile defaults and health findings.** A zone created without a policy is signed online under the Hardened profile when it is a primary zone served outside (not under a private suffix such as `home.arpa`, `local`, `internal`, `test`, nor a reverse zone of a private range), and unsigned under Home, Standard and Lab (TGL-13). The findings `dns.dnssec.clock_skew` (the controller's clock more than 5 minutes behind the zone's last signing), `dns.dnssec.expiring` (an imported zone within 7 days of expiry), `dns.dnssec.resign_overdue` (less than half of `resign_before_days` left on a zone signed online) and `dns.dnssec.expired` appear in `/system/status` and the zone's DNSSEC status, naming the zone (OPS-09).
12. **The backup carries the keys like every secret.** The private keys are envelopes of `vault.secrets` in the store snapshot, and the key generations that open them are in the backup (ADR 0016), so a restored installation signs with the same keys and the parent's DS stays valid. Nothing else exports a private key.

## Consequences

- One copy of each private key exists, in the vault of the controllers; a node that is lost or stolen holds no signing key, and signing happens once per change instead of once per node.
- Signing needs a controller that leads. While no controller leads, nodes keep serving the signed data they have; signatures expire after `signature_validity_days` without a leader, and the findings say so before.
- Every pass that writes moves the serial: a secondary sees one more serial step per change and one per renewal pass, and after a pass that reset the journal it transfers the whole zone once.
- A signed zone holds about twice the rows of an unsigned one (an NSEC or NSEC3 row and an RRSIG row per owner); the index and the store grow accordingly. M20 measures the time.
- The RRSIG row of an owner has one TTL (the smallest of its covered RRsets) while answers carry each signature with its covered RRset's TTL; the zone file export writes the row's TTL, which validators do not use.
- NSEC3 owner names are ordinary names of the index: a query for a hashed owner name itself is answered as a name that exists without data.
- The waits of a rollover occupy a worker of the job runner while they sleep; one rollover per zone at a time keeps that small.

## Alternatives considered

- **Signing on each node from a replicated private key** (P2-Q4 option b). Sends every private key to every node and signs N times. Rejected.
- **Offline signing with an external signer only** (P2-Q4 option c). Covers strict operators but gives the home user no automatic signing. Kept as the imported mode, not as the only mode.
- **The `domain` crate's `unstable-sign` feature.** Its API moves between minor versions and brings what ADR 0017 kept out; the signing code here is small and tested against the published vectors.
- **RSA/SHA-256 (algorithm 8) as the default.** Larger keys and signatures and slower signing; RFC 8624 recommends ECDSAP256SHA256 for signing. Not offered.
- **Signing inside every write of the zone service.** Would make each write wait for signatures and spread key access over every writer; a follow-up pass keeps keys in one service and is the plan's design.
- **Keeping signatures in memory and adding them while answering.** Moves signing to the nodes in effect and breaks transfers to secondaries, which need the records.
- **A double-DS KSK rollover without CDS.** Needs the parent's DS changed before the zone's keys; publishing both keys with CDS lets parents that read CDS follow, and the manual step covers the rest.
