# ADR 0019: DHCP data model and lease path

- Status: Proposed (point 3 is superseded by ADR 0025 for where a lease lives, and the fallback of point 4 becomes the production path)
- Date: 2026-10-21

## Context

Phase 3 builds DHCP (ROADMAP Phase 3, [phase-3-plan.md](../plans/phase-3-plan.md)): a DHCPv4 server on one node that serves every network of the reference environment through relay, acts as IPAM's DHCP actuator (DHCP-16), writes names into Tenko zones (ADR 0020), and closes with DHCPv6 and the Kea JSON export. Every Phase 3 package builds on one set of contracts (WP7.0): where the configuration and the leases live, how the role learns them, how scopes relate to IPAM, what a lease commit is and when the client is answered, how the wire format is read and written, and what of the cluster is built now.

ADR 0002 put all replicated state in one Raft group and said, in its point 4, that DHCP leases do not go through global Raft because every DORA is a write; DHCP-07 and ARCHITECTURE.md say the same and ask for a local lease WAL per node. ADR 0004 made `dhcp` a role of the one binary; ADR 0005 made IPAM the intent hub; ADR 0011 made every write a batch of the coalescer; ADR 0017 settled the same questions for DNS (rows in the store, an index fed by one trait, no writes from the engine, single node first). Since then the store has been measured on one node: the coalescer sustained 1,000 changes per second with immediate durability and about 3,000 closed loop (M5), and the RFC 2136 path through the zone service, the coalescer and the index answered with p99 15 to 19 ms at 1,000 updates per second (M21).

The owner decided on 2026-10-21 (plan section 7): a lease is a row in the replicated store, committed before the ACK, with no separate lease WAL, and if the measured performance is too poor an asynchronous publication model is reconsidered (P3-Q1); failover pairs and their chaos test are Phase 5, and Phase 3 builds the lease model so that pairing is placement, not redesign (P3-Q2); a scope is an IPAM prefix with a DHCP policy and a reservation is the IPAM host with mode `reserved`, with no second register (P3-Q4); the gateway relays every network to one node (P3-Q5); the role writes the IPAM observation at commit (P3-Q8).

## Decision

1. **Configuration lives in the replicated store.** Server settings, scopes, shared networks, pool settings, exclusions, option definitions and option sets, classes, policies, MAC filters and reservation-level options are rows of the `dhcp` namespace in the one Raft group (ADR 0002). No DHCP setting lives in a node-local file except the listeners and workers of `[dhcp]`. The model is `tenko_core::dhcp`.
2. **One model with IPAM.** A scope (`dhcp.scopes`) is keyed by the IPAM prefix it serves and adds only the DHCP policy: lease times, the option set, the DDNS settings, the shared network, the classes it admits, the restricted flag. Pools are IPAM ranges of role `dhcp_pool`; exclusions are the other ranges of the prefix, the addresses IPAM holds for hosts that are not `dynamic`, and explicit exclusion ranges. A reservation is the IPAM host with mode `reserved`: its interface's MAC or client identifier (DUID for DHCPv6) and its address inside a served prefix. Reservations are derived by the role from the IPAM rows; there is no reservation table and no actuator that copies them.
3. **A lease is a row in the store, committed before the answer.** `dhcp.leases` (key VRF and address) with `dhcp.leases.by_client` and the bounded `dhcp.history` are written through the coalescer. A REQUEST, renewal, rebind, release, decline or expiry becomes one batch: the lease row, its client index row, its history row and, when it changed, the IPAM observation fact of the source `dhcp:<node>` (written with the rules of `tenko-ipam::observe::ingest`, through a helper of that crate). The ACK or REPLY leaves only after the commit returns. A DISCOVER writes nothing: the offered address is held in memory for the offer lifetime. Renewals commit like new leases, because a renewal that is not durable can let the address be given to another client after a crash. Point 4 of ADR 0002 is superseded for leases by this decision once this ADR is accepted.
4. **The engine commits through one trait and keeps a fallback open.** The engine calls a `LeaseStore` trait; its production implementation is the store. If M26 or M28 of the plan fall below the line the owner confirms with the plan (proposed: fewer than 1,000 4-way exchanges per second sustained, or a p99 from REQUEST to ACK above 100 ms at 1,000 per second, on the musl binary on one node), an asynchronous publication model (a local durable log first, publication to the store after the answer) is reconsidered as a second implementation of the trait, in a change that supersedes point 3.
5. **The role serves from in-memory tables and never reads the store while answering.** A `DhcpFeed` trait in the shape of ADR 0017's `ZoneFeed` delivers an image at a revision and then deltas in revision order, or a new image after a snapshot install. From it the role builds a configuration image (precompiled scopes, effective option lists per scope and policy, compiled classes and policies, derived reservations, filters) and a lease table indexed by address and by client. The role applies its own commits to the table at once and the feed's copy of them idempotently, so the table equals the rows. No DORA path reads the store (OPS-02).
6. **While the store refuses a write the role promises nothing it has not committed.** The behaviour is the plan's P3-Q14; the recommendation is to answer a renewal of an unexpired lease with the time it still has, without writing, to drop new requests, and to show the state in the health view.
7. **The codec is Tenko's own and allocation-free.** DHCPv4 (`tenko_dhcp::v4`) and DHCPv6 (`tenko_dhcp::v6`) are parsed as borrowed views over the received octets with one pass over the options (RFC 3396 concatenation into a per-worker scratch buffer) and answered from a fixed-capacity reply builder; the DORA path allocates nothing up to the commit hand-off, enforced by the counting-allocator test. `dhcproto` is a dev-dependency only, for a differential test over a corpus, as `hickory-proto` is for DNS. Every parser has a fuzz target before it merges (API-15).
8. **Relay first; sockets follow ADR 0009.** Scope selection reads the link selection sub-option (RFC 3527) or option 118 (RFC 3011), then giaddr, then the receiving interface; option 82 is kept on the lease and echoed. A `relay` listener binds a unicast address and receives only relayed traffic; a `direct` listener also answers clients on its link, by broadcast, or by unicast through `AF_PACKET` on Linux with `CAP_NET_RAW`. Workers are blocking UDP threads with `SO_REUSEPORT` on Linux and a shared socket on Windows; a worker hands the change to the coalescer and does not wait on the disk.
9. **Single node first, cluster-aware.** Built now because it would be rework later: the lease row carries the fields of ISC's failover draft (`draft-ietf-dhc-failover-12`): the binding state, `ends`, `cltt`, `tstp`, `tsfp`, `atsfp`, the node that wrote it and its pool share, empty on one node; the allocator asks a `PoolOwnership` trait (on one node every address is the node's; RFC 3074 buckets or a backup share later); every lease time comes from a `grant_time` function (the scope's time on one node, capped by the MCLT with a partner); lease reads, releases and history go through the node-command interface; the `dhcp` role's node-sync subset is declared (every `dhcp.*` table except `dhcp.history`, the IPAM rows the reservations derive from, the secret purpose `dhcp.failover`) and consumed by nobody. Because leases are rows, a second node fed with the same rows sees the first node's leases; the failover protocol of Phase 5 then decides who may allocate what and what to do while the nodes cannot reach each other. Deferred to Phase 5: the protocol, partner-down, RFC 8156, the chaos test (DHCP-18), a `dhcp` node fed through node sync, relay between Tenko nodes. Every Phase 3 measurement is a single-node figure.
10. **Authorization and personal data.** `dhcp.read` reads the configuration and the leases, `dhcp.write` changes the configuration and releases leases; the viewer holds `dhcp.read`, the operator both, the auditor none (ADR 0015). Scope objects follow their prefix's grants (IAM-01); the other DHCP object kinds are global-only for grants. Reading leases or history is audited as `dhcp.lease.read`, because a lease holds a MAC address, a client identifier and often a host name; history has a retention per profile.
11. **The data format moves to 4 once for the phase.** The `dhcp` namespace and its object kinds are values a format 3 binary cannot decode, so format 4 is an empty migration; the tables later Phase 3 packages add are additive.

Note (E32, 2026-10-26): the memory this decision costs on one node was measured in WP9.5 and reduced without changing the decision. The fixed tables that point 7's allocation-free path needs (the workers' pending commits, the hand-off queue of point 4's `LeaseStore`, the offer slots, the conflict probe's tables) are sized from the configuration image, a slot per address it can lease with a floor of 256 and the configured sizes as caps, and grow when a new image is applied, off the DORA path; point 5's lease table keeps a compact row (the fields the DORA path reads inline, the rest in one boxed byte string) instead of the store's row. The rows in the store, the wire format and the commit before the answer are unchanged ([dhcp.md](../dhcp.md) section 10.8, `bench/phase3-dhcp/results/2026-10-26-e32-after-memory.md`).

## Refinements from the contracts (WP7.0)

The contracts package wrote the decision into code and settled what it left open (`docs/dhcp-contracts.md`, section 14, has the full list); the status stays Proposed until the owner accepts the plan.

- **Option sets by owner.** `dhcp.option_sets` is keyed by the owner of a set (`OptionOwner`: the server, a shared network, a scope, a pool, a policy or an IPAM interface), one set per owner. Scopes, shared networks, pools and policies carry no options field, and the plan's `dhcp.host_options` is the set of `OptionOwner::Host`; there is no separate table. The image merges the sets per code from the least to the most specific level.
- **The commit hand-off.** The DORA path builds a `PendingChange` whose every field is fixed-capacity and hands it to `LeaseStore::submit`, which copies it into a bounded queue and returns at once; the committer builds the batch (the lease row, the client index row, the history row, from WP8.1 the observation fact) and reports each ticket committed or refused. The counting-allocator test covers the path up to that hand-off and checks that a deliberate allocation in `submit` fails it.
- **The client index** (`dhcp.leases.by_client`, key scope and client identity of RFC 4361 and RFC 6842) points at a client's latest row in a scope, and the in-memory table keeps the row with the later client transaction time, so the role's own commits and the feed's copies of them give one state whatever their order.
- **Authorization objects.** A scope authorizes as `dhcp_scope` with its prefix's identifier and is a scoped kind whose anchors are the prefix's; classes, policies, option definitions and filters are global-only; the server-wide configuration authorizes on the `dhcp_scope` singleton.
- **The values of Slice 9 now.** The option kinds include the IPv6 kinds and the model has `Lease6`, so that DHCPv6 adds tables and no enum values, and format 4 stays the one format of the phase.
- **The fixtures.** The size limit of the compatibility fixtures is raised to 8 MiB rather than compressing them, which would change the committed fixtures of earlier formats.
- **The differential crate** is `dhcproto` 0.15.0, MIT, pinned and a dev-dependency only; `cargo deny` accepts it.

## Consequences

- One durability story: leases are in the backup with the configuration and the keys (OPS-07), and in the change stream the reconciler, the DDNS worker and, in Phase 5, a second node read. There is no second recovery format to test.
- Every lease change is a store commit. Throughput is bounded by the coalescer and latency by its commit; M26, M28 and M29 measure both and the log growth, and decide whether point 4's fallback is needed.
- On one node the store refuses only on a disk failure or through the test hook. In Phase 5 a controller quorum loss would stop new leases, which conflicts with OPS-02's "keep allocating leases from local state" until the failover protocol or the fallback model serves from local state; the plan records the document changes for DHCP-07, ARCHITECTURE.md, OPS-02 and OPS-26.
- Leases are personal data in the replicated store; in Phase 5 they reach every controller. Access is scoped and audited, and history is bounded.
- The move job's DHCP step becomes a wait for the role to serve the revision that holds the reservation, and its observation step completes on the lease's fact; nothing polls.
- A reservation needs an IPAM host; a migration in Phase 4 creates hosts for the reservations it imports.
- Owning the codec means owning its bugs; the fuzz targets and the differential corpus are the guard.

## Alternatives considered

- **A local lease WAL per node outside Raft** (DHCP-07 and ADR 0002 point 4 as written, P3-Q1 option b). One local fsync per group of leases and serving without quorum, at the cost of a second durability format with its own recovery, backup and replication, and a separate channel for observations. Kept as the fallback of point 4, not taken now.
- **A node-local `redb` database for leases** (P3-Q1 option c). The same trade as the WAL with a heavier commit. Rejected.
- **DHCP scopes and reservations as their own objects, kept in step with IPAM by an actuator** (P3-Q4 option b). Two registers, a drift check and conflict rules between them. Rejected.
- **The reconciler reading the lease table on a schedule** (P3-Q8 option b). Polling, which DHCP-16 rules out. Rejected.
- **`dhcproto` as the production codec.** It decodes into owned structures and allocates per message; kept as the differential implementation.
- **Building the failover pair in Phase 3** (P3-Q2 option b). The owner's direction moves it to Phase 5; the fields and traits of point 9 keep it a protocol and a placement.
