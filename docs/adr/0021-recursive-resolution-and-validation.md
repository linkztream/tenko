# ADR 0021: Recursive resolution and validation

- Status: Proposed
- Date: 2026-10-22

## Context

DNS-03 asks for Tenko's own full recursive resolver, DNS-13 for DNSSEC validation with RFC 5011 trust anchor maintenance and negative trust anchors, and DNS-34 for QNAME minimisation and aggressive use of the validated cache. ADR 0007 point 2 put them after the forwarder, in Phase 5: a large, security-sensitive component with little benefit over forwarding for the first deployments. Phase 2 delivered the forwarder, the cache, RPZ, DoT and DoH ([phase-2-exit.md](../plans/phase-2-exit.md)); the first deployment runs at home, and the owner's backlog of the test drive (2026-10-18) and the request of 2026-10-22 ask for recursion so that no second resolver is needed beside Tenko. What changed is that the "first deployments" exist and that the forwarder, the cache, the upstream pool and the signer's DNSSEC code are in place to build on. This ADR supersedes the "later" part of ADR 0007 point 2; the rest of ADR 0007 stands. The plan is [dns-recursion-plan.md](../plans/dns-recursion-plan.md); where in the delivery order the slice runs is the owner's decision REC-Q1 there.

ADR 0009 made the UDP worker path allocation-free and put everything else on tokio; ADR 0017 put every DNS setting in the replicated store, made the engine serve from an index, fixed one lookup path and one view model, and pinned `domain` at 0.12.3 with the `std` feature only; ADR 0018 made the controllers sign with keys in the vault and gave `tenko_dns::dnssec` the canonical form, the crypto over `aws-lc-rs` and the NSEC3 hashing. What remained open: how a name outside the zones is resolved without an upstream, where validation sits and whose code it is, where the trust anchors live and who keeps them current, what the caches hold, how recursion and forwarding share one lookup order, and what the single-node rule means for a resolver.

## Decision

1. **The resolver is Tenko's own iterative engine, on the forwarder's task pool.** A name that no zone, stub zone or forwarding rule answers is resolved from the root hints by the algorithm of RFC 1034 section 5.3.3 with priming (RFC 8109), referral following under the bailiwick and ranking rules of RFC 2181 and RFC 9471, name-server address lookups as sub-queries, CNAME and DNAME chasing, and a work budget per client query (queries sent, restarts, depth, time); identical client queries in flight are joined. The engine runs where forwarded queries run, on tokio behind the forwarder's queue and in-flight limit, and answers through the same reply path. Steps 1 to 7 of the query path on the worker stay allocation-free (ADR 0009); the engine allocates as the forwarder does.
2. **One lookup order, one more route.** A forwarding rule has a mode, `forward` (its upstreams) or `recurse` (no upstreams), and a view has a resolution, `recurse`, `forward` or `refuse`, with the profile's default when absent. The longest suffix among rules and stub zones decides, as in Phase 2; with no route the view's resolution applies. The recursion access list of the view (TGL-22) is unchanged and is checked before any route. The configuration file's default forwarder is used only where a view says `forward`.
3. **Every query to an authority carries EDNS with 1,232 octets, DO, a client cookie and 0x20, from a fresh source port.** No fallback to a query without EDNS on a timeout (DNS flag day 2019); one retry without EDNS on FORMERR or NOTIMP; TCP on a truncated answer; a server's capabilities, lameness per zone and cookie are remembered in the infrastructure cache for its TTL; the source port is fresh per exchange for authorities (the 64-use socket policy stays for upstreams).
4. **Three caches per node, bounded per profile, never shared between nodes.** The answer cache of Phase 2 keeps one entry per view, name, type and class (DO and CD leave the key) with the authority's answer, its signatures, its validation state and the positions of its RRSIG records, so a hit renders the answer for the client's flags on the worker without allocating: signatures only for DO, SERVFAIL for a bogus entry unless CD, AD for a secure entry. The infrastructure cache holds zone cuts, name servers, addresses, capabilities and validated key sets, read on the runtime only. The denial cache holds validated NSEC and NSEC3 records per zone in canonical order for RFC 8198 and RFC 8020, looked up on the worker without allocating. Resolution failures are cached per RFC 9520.
5. **Validation is Tenko's own code over the signer's primitives, on the runtime, before the cache.** The validator walks the chain from the nearest trust anchor through DS and DNSKEY, verifies signatures over `dnssec::canonical` with `dnssec::crypto` (extended with RSA, ECDSA P-384 and the SHA-1 and SHA-384 digests through `aws-lc-rs`; the signer keeps signing with 13 and 15), proves denial with NSEC and NSEC3 (opt-out, the closest encloser, wildcards, the iteration cap of RFC 9276), and gives every answer one of the states secure, insecure, bogus or indeterminate, rendered on the wire as RFC 4035 and RFC 8914 say. A zone whose DS names only unsupported algorithms is insecure, never bogus. Cost caps bound the signature verifications, key candidates and hash computations per RRset and per client query (the KeyTrap class). Forwarded answers are validated too; a rule may switch it off. The `domain` crate's validator is not used (ADR 0017 point 9 keeps its unstable features out).
6. **Trust anchors are rows of the store, shipped in the binary, kept current by RFC 5011 on the leader.** `dns.trust_anchors` holds one row per zone with its keys, their RFC 5011 states and their source (shipped, operator, RFC 5011); the root's keys come from the IANA XML of RFC 7958 embedded in the binary with their validity and are replaced at an upgrade where the stored set still equals the previous shipped set. The leader-only service `dns.trust_anchors` runs the RFC 5011 state machine through the installation's own resolver and audits every state change; a node whose anchors are all revoked reports it and keeps failing validation rather than switching it off. Negative trust anchors (`dns.ntas`, RFC 7646) have an expiry of at most seven days, need `dns.keys` and an interactive session, and are audited on creation and expiry. Both tables are in the `dns` subset of node sync, consumed by no node until Phase 5.
7. **Root hints are shipped and primed, never downloaded.** A hints file may replace them (the lab's root). RFC 8806 (a local root) is an option for a later package, as a zone the resolver uses and the engine never answers to clients.
8. **QNAME minimisation is on, relaxed; aggressive NSEC is on.** RFC 9156 in the mode that falls back to the full name for a zone whose servers break on a minimised query, remembered in the infrastructure cache; strict is a setting. The minimised queries fill the infrastructure cache; only the final answer fills the answer cache.
9. **Privacy: recursion with minimisation is the default; forwarding over DoT is one rule away.** The resolver sends no client subnet (RFC 7871) and strips it from clients' queries; nothing of a client reaches an authority. The query log is unchanged (OPS-06). RFC 9539 and DNS64 are hooks named in the plan, not built.
10. **Special-use and locally served names never reach an authority.** RFC 6761, RFC 6303, RFC 8375 and RFC 7686: a zone or a rule of the node answers them, else the resolver does, with a per-installation exception list for labs.
11. **Metrics, the log and the status say how an answer was found.** The resolution kind, the validation state, the sub-query count and the extended error join the query log entry (fixed-size); new metric families count resolutions, authority exchanges, validation outcomes, denial-cache answers and the infrastructure cache (per-shard atomics, OPS-21); the node status shows priming, the root servers and the trust anchor states.
12. **Single node first, cluster-aware.** Built now: the rows and the subset, the leader service behind an `AnchorResolver` trait, the node commands for status, priming and the infrastructure cache, the caches per node. Deferred to Phase 5: a `dns` node without a controller validating with synced anchors, and every measurement that needs more than one node. Every figure of the slice is a single-node figure against the lab's own root; nothing in a test or benchmark touches the real root servers.

## Consequences

- A node answers the Internet's names by itself; the household's and the enterprise's queries go to the authorities of each name, not to one upstream, and DNSSEC validation is Tenko's rather than an upstream's. The operator who prefers one upstream keeps a DoT root rule, which wins over the default.
- The answer cache changes shape once: entries carry a state and are rendered per client; the cache browse, the serve-stale rows of the lab and the Phase 2 cache measurement are redone in the same change.
- The infrastructure and denial caches add memory per node, bounded per profile and measured against OPS-15; the Home bounds are small.
- Validation needs a correct clock (OPS-09): a wrong clock makes every signed name fail loudly, which the health view names; it never makes validation switch itself off.
- The root KSK roll of 2026 and 2027 is followed by RFC 5011; a node off for longer than a hold-down needs a release with the new anchor or the operator, and says so.
- The engine, the validator and the new parsers are new attack surface on the path from the Internet in; the budget, the caps, the bailiwick rule, cookies, 0x20, fresh ports and the fuzz targets are the defences, and the plan's exit criteria exercise each in the lab.
- Phase 5 adds a feed of the anchors to nodes and a resolver the leader asks over the cluster channel, not a redesign.

## Alternatives considered

- **Keeping the resolver in Phase 5** (ADR 0007 as written). The reasons for "later" were the risk and the small benefit early; the benefit now exists at home and the code it builds on is in place. Superseded for the "later" part only.
- **A recursive engine on the UDP workers.** Would put sub-queries and waits on the allocation-free path of ADR 0009. Rejected: the engine runs where forwarded queries run.
- **The `domain` crate's validator** (behind an unstable feature) or another crate. Rejected: ADR 0017 keeps `domain`'s unstable features out, the module would still need Tenko's caches, anchors and errors around it, and one DNSSEC implementation in the tree is one to fuzz and own.
- **A cache keyed by DO and CD with one entry per flag combination**, as Phase 2 has. Rejected: a validating resolver always asks with DO and renders per client; one entry with a state is smaller and is what the denial cache needs.
- **Validation on the worker for cache hits.** Rejected: verification allocates and costs milliseconds; the state is computed once on the runtime and stored.
- **Anchors in a node-local file** (BIND's and Unbound's managed-keys files). Rejected: every DNS setting is a row (ADR 0017); nodes receive them through node sync in Phase 5 and the audit trail sees every RFC 5011 state change.
- **Anchors fetched from the project's release source.** Kept as a possible second path (plan REC-Q6); not built, since RFC 5011 and shipped anchors cover the cases that matter.
- **A local root (RFC 8806) by default.** Rejected for now: a zone kind the engine lacks and a transfer dependency, for a benefit the home does not need; an option later.
- **Client subnet (RFC 7871).** Rejected: personal data to authorities and a cache keyed by client prefix; views already select by the query's source.
- **Forwarding over DoT as the default for every profile, recursion opt-in.** Rejected: the owner's goal is a resolver that needs no upstream; the DoT rule stays one command away.
