# ADR 0026: Kerberos and directory identity

- Status: Accepted (the owner decided ID-Q1 to ID-Q18 of the plan on 2026-10-25, ID-Q13 with the LDAPS chain-import addition of point 8)
- Date: 2026-10-25

## Context

Two gaps against the enterprise DDI products are to be closed properly from the start (the owner's decision of 2026-10-25, after the comparison with Infoblox, BlueCat and EfficientIP): secure dynamic updates from Windows clients and domain controllers, and directory-based sign-in for administrators. The plan is [identity-plan.md](../plans/identity-plan.md); this ADR records the architecture it recommends.

**Secure updates.** In Active Directory a "secure" dynamic update is GSS-TSIG (RFC 3645): the client negotiates a security context with TKEY (RFC 2930) using Kerberos (RFC 4120) inside SPNEGO (RFC 4178), and signs each update with a GSS MIC token (RFC 4121) on that context (CON-03). Tenko today authorizes updates from Windows only by source address ([active-directory.md](../active-directory.md) section 4), which does not authenticate the sender, does not bind a record to its creator, and leaves the Hardened profile unable to host an AD zone that takes updates. DNS-28 and OPS-11 assumed SSPI on Windows under a gMSA or domain account, and "krb5" with a keytab on Linux.

Three facts of the product constrain the choice:

- The Linux release is a static-pie musl binary, shipped in a distroless image and run by systemd as the unprivileged account `tenko`; root is never needed after installation (ADR 0023), and no process running as root reads a file the account can write.
- Every crate forbids `unsafe` code; an exemption needs an ADR (CON-01). Dependencies carry licenses on the allow list of `deny.toml`, which bans the `openssl` crates; nothing copyleft is copied into the repository (ADR 0022, CONTRIBUTING).
- The Windows service runs as its virtual account `NT SERVICE\tenko` on a host that need not be joined to the domain.

A GSS-TSIG server is an acceptor only: it never talks to a KDC on the update path. It needs the service account's long-term key, a clock and a replay cache to accept the client's ticket, and the session key to verify and produce MIC tokens. Producing a MIC is one HMAC-SHA1-96 under a key derived once per context, which Tenko already computes for TSIG with `aws-lc-rs` without allocating. Creating, testing and rotating the account needs a Kerberos client (AS, TGS and the change-password protocol of RFC 3244) on the controller.

**Directory sign-in.** Tenko's accounts are all local today (IAM-03 to IAM-10). IAM-11 asks for SSO through OIDC and SAML, IAM-12 for LDAP and AD group mapping, IAM-13 for Kerberos SPNEGO, all in Phase 5. The roles, scope rules and grants of ADR 0015 are what any external identity must map onto.

The options for Kerberos were compared in section 2 of the plan: the system GSSAPI library (MIT or Heimdal, through `libgssapi` or `cross-krb5`); a pure-Rust stack on Devolutions' `sspi` and `picky-krb`; Tenko's own acceptor on `picky-krb`; native SSPI on Windows beside a pure-Rust stack on Linux; and a helper process.

## Decision

1. **One pure-Rust Kerberos implementation on every platform.** A new crate `tenko-krb` accepts SPNEGO-wrapped and raw Kerberos tokens with keys Tenko holds, produces the AP-REP for mutual authentication, verifies the PAC's server signature and reads its SIDs, keeps the replay cache, and computes and verifies RFC 4121 MIC tokens itself over `aws-lc-rs`. Its client half (AS, TGS, change password) is used by the controller only. The Kerberos library under it is `sspi` (MIT OR Apache-2.0) with `picky-krb` (MIT OR Apache-2.0), unless the spike of WP13.0 shows that `sspi` does not build on musl and on the Windows target, does not pass `cargo deny`, cannot complete the Windows exchange, or adds more than 3 MiB to the stripped musl binary; then Tenko's own acceptor and client over `picky-krb` alone. `tenko-krb` is the only crate that names either library. The spike's figures are added to this ADR before it is accepted.

   **Refined by the spike of WP13.0 (2026-11-05).** The Kerberos library under `tenko-krb` is `picky-krb` 0.13.1 alone, with Tenko's own acceptor and client over its types and ciphers; `sspi` 0.23.1 is kept as a reference and not depended on. The spike built both: `sspi` builds on `x86_64-unknown-linux-musl` and checks on both Windows targets, adds 1.71 MiB to the stripped static musl binary over a baseline that already links `aws-lc-rs` (1.26 MiB over the `picky-krb` design), 79 crates (41 new to the workspace, among them the exact pre-release pins `picky` 7.0.0-rc.27, `rsa` 0.10.0-rc.18 and `pkcs1` 0.8.0-rc.4) and 41 s to a clean release build; `cargo deny` fails on RUSTSEC-2023-0071 (`rsa`, declared unfixable upstream) and would need a permanent ignore for an RSA path Tenko never calls. Its acceptor completed the MIT and Samba exchanges under the standard Kerberos OID in raw and SPNEGO form, with the MICs computed by Tenko over `aws-lc-rs` verified by MIT both ways, but answered the Microsoft Kerberos OID under the standard one (refused by MIT), failed AES-128 session keys, keeps the replay cache per context, ignores the authenticator's GSS checksum and the ticket flags, and exposes neither the sequence numbers nor the ticket contents an acceptor needs for GSS-TSIG and the PAC. The `picky-krb` design adds 0.45 MiB, 40 crates (17 new names, no pre-release pin), passes `cargo deny` without an exception, and completed every exchange of the spike with both key sizes and all three framings in 559 lines of acceptor code whose twelve decisions are recorded in `bench/spike-krb/RESULT.md`. No Windows-issued token was available; the Windows exchange stays the first check of the owner's lab, replayed through the spike's fixtures. The `Acceptor` interface of `tenko-krb` is the one the spike used, so that `sspi` can return behind it if upstream splits its Kerberos acceptor from `picky` and `rsa`.

   **Decided by the owner after the spike (2026-11-05).** `tenko-krb` depends on no Kerberos library. The DER codec of the Kerberos structures (RFC 4120 section 5: the AP-REQ and AP-REP, the ticket, the authenticator, `EncryptedData`, `EncryptionKey`, the principal name and the checksum), the PAC reader ([MS-PAC]) and the AES-CTS cipher of RFC 3962 are Tenko's own code; the AES block function (ECB and CBC without padding) and HMAC-SHA1 come from `aws-lc-rs`, which the workspace already links, as the MIC tokens and the key derivation of the spike do. The reasons: the acceptor logic was Tenko's already (559 lines over the library's types), a third of `picky-krb` would have stayed unused, its ciphers would have been a second AES implementation beside `aws-lc-rs`, and the parsers in the unauthenticated update path are the code Tenko most wants to read, test and fuzz itself. The price is about 1,000 to 1,300 more lines and two to three builder-days in WP13.1; the spike's recorded exchanges against MIT and Samba are the octet-exact tests of the codec and the cipher, and every decoder gets a fuzz target. `picky-krb` and `sspi` stay references, and the `Acceptor` interface stays the one the spike used.
2. **No system Kerberos library, no native SSPI, no helper process.** The static musl binary stays static; the Windows binary uses the same code; no `unsafe` code is added to Tenko; nothing is read from `krb5.conf` or a credential cache.
3. **NTLM, RC4, DES and 3DES are not accepted.** Kerberos is the only mechanism a Tenko acceptor selects in SPNEGO; the account is AES only (`msDS-SupportedEncryptionTypes` = 24). These are structural rules, not toggles.
4. **The account is an AD computer account owned by Tenko.** The administrator pre-stages it with a static PowerShell block from the documentation (name, organizational unit, `DNS/<fqdn>` SPNs, AES encryption types, a one-time password); Tenko changes the password through RFC 3244 so that only Tenko knows it, derives the AES keys, and rotates the password every 30 days by default, keeping the previous key version until the next rotation. A keytab made with `ktpass` or `msktutil` may be imported instead, with the password left to the administrator. Tenko never receives a directory administrator's credential and never generates a script for an administrator to run. One account serves the installation, with one SPN per node name and `HTTP/<fqdn>` for web sign-in.
5. **The keys are a system secret in the vault.** Purpose `dns.krb`, never revealed, encrypted at rest (NEVER-01), delivered to the `dns` role by the watcher that delivers TSIG keys and to Phase 5 nodes through node sync's purposes. No keytab file exists on disk on either platform.
6. **GSS-TSIG is a key type of the TSIG module.** The keyring holds HMAC keys or GSS contexts; contexts are negotiated by TKEY (modes 3 and 5) off the query path, held per node in memory with bounds per node and per client address, expire with the ticket or after an hour, and are not replicated; a restart drops them and clients negotiate again.
7. **Ownership is per name, with the Windows rules.** A table `dns.name_owners` records the owner (SID, principal) of each name in a zone with ownership on; the creator owns a new name, DnsUpdateProxy members leave names unowned, privileged groups (by SID, from the PAC) may change any name, locator names are for privileged principals only, manual records are protected, records imported without an owner may be claimed only by the host they name, and an owner is held for a period after its last record goes. The Windows zone modes (none, nonsecure and secure, secure only) map onto the existing update policy, with `require_tsig` meaning "TSIG or GSS-TSIG required".
8. **Directory sign-in is OIDC, LDAP and Kerberos; not SAML, RADIUS or TACACS+.** OIDC uses the authorization code flow with PKCE, state and nonce through the `openidconnect` crate (MIT) over `rustls`; LDAP uses `ldap3` (MIT OR Apache-2.0) with its `rustls` and `aws-lc-rs` feature, over LDAPS or StartTLS (plain LDAP only in the Lab profile, with a clear-text warning), a read-only service account for lookups and directory checks, the user's own bind for the password, and `tokenGroups` for nested AD groups; Kerberos sign-in to the web UI (RFC 4559) reuses the acceptor of point 1. The LDAP provider setup makes LDAPS easy so that nobody runs plain LDAP for want of a certificate: it fetches the certificate chain of the domain controllers from the configured server, shows it with its fingerprints, and pins it after the administrator confirms; a pasted or uploaded PEM file and the system trust store are the other sources (the owner's addition to ID-Q13, 2026-10-25). Both clients live in a new crate `tenko-directory`. SAML is not built (no pure-Rust service provider free of libxml2 and OpenSSL that is mature enough for the signature checks SAML depends on; Keycloak bridges a SAML-only provider).
9. **Directory groups become rights at sign-in, not as stored grants.** Mappings of a group (SID, DN or claim value) to a role and scope rule (ADR 0015) are evaluated at sign-in and at each directory check and held on the session; a person record is created at first sign-in, keyed by the immutable subject (`iss` and `sub`, `objectGUID`, SID); a user whom no mapping matches is refused. Break-glass (IAM-09) and service accounts (IAM-10) stay local in every profile; under Hardened, once a provider is verified, local person accounts other than break-glass cannot sign in.

## Consequences

- **Licenses.** Every new dependency is permissive and on the allow list: (`sspi`, `picky-krb` and `picky`, MIT OR Apache-2.0, were candidates; after the owner's decision of 2026-11-05 none of them is linked) `openidconnect` and `oauth2` under MIT or MIT OR Apache-2.0, `ldap3` under MIT OR Apache-2.0, their RustCrypto dependencies under MIT OR Apache-2.0. Nothing copyleft is linked; Samba (GPL) and Keycloak (Apache-2.0) are run only as containers in the lab. No OpenSSL enters the graph. The AGPL keytab crates (`kerberos_keytab`, `himmelblau_kerberos_keytab`) are not used; Tenko writes its own keytab import parser.
- **Advisories.** `openidconnect` 4 depends on `rsa` 0.9, which carries RUSTSEC-2023-0071 (a timing attack on private-key operations); Tenko uses only public-key verification. `cargo deny` then needs an ignore with that reason, accepted by the lead, or Tenko verifies ID tokens with `aws-lc-rs` itself. `sspi` pins pre-release versions of `picky` and `rsa`; they are taken at exact versions and upgraded as changes of their own, or dropped with the fallback of point 1.
- **Binary size and memory.** The release binary is about 124 MB unstripped today. The Kerberos stack is budgeted at 3 MiB of the stripped musl binary and the slice at 4 MiB (M47); `reqwest`, `rustls` and `aws-lc-rs`, which OIDC and LDAP need, are already linked. Idle memory without contexts may rise by at most 0.5 MiB (M48), since the idle target (M23) is already at its limit; 10,000 contexts may cost up to 8 MiB.
- **Safety.** No `unsafe` code in Tenko. The new parsers (SPNEGO, AP-REQ, the authenticator checksum, the PAC, keytabs, TKEY, MIC tokens) get fuzz targets before they merge. The per-message path of GSS-TSIG allocates nothing, like TSIG.
- **Platforms and ADR 0023.** Nothing changes in the unit, the MSI or the installer: no new file, capability or account. The Windows service keeps its virtual account; OPS-11's gMSA or domain account is no longer needed, and DNS-28, CON-03 and OPS-11 are reworded.
- **The directory.** Each installation that uses GSS-TSIG has one computer account in AD whose password only Tenko knows and rotates; an administrator who resets it must adopt it again or import a keytab, which the daily self-test reports. Clean-up scripts that disable inactive computer accounts see it active, because rotation and the self-test log it on.
- **Key compromise.** An attacker who controls the service account can read the account's keys and forge tickets to Tenko's own DNS and web services (a silver ticket against Tenko); that is power the attacker already has over Tenko. The keys give no access to anything else in the domain, since the account holds no other rights.
- **Operations.** Kerberos depends on time; the self-test reports skew above 60 s. Updates and web sign-in work while the KDCs are down for tickets already issued; the account's rotation and self-test need a KDC.
- **Interop proof.** A container lab (Samba AD as the controller and directory, MIT clients, Keycloak) runs weekly; the Windows proof (domain controllers and clients registering, `dcdiag`, domain join) is owner-run (API-18).
- **Later options kept.** Native SSPI on Windows, a gMSA, SAML and SCIM can be added behind `tenko-krb` and `tenko-directory` without changing the update path, the ownership model or the session model.

## Alternatives considered

- **The system GSSAPI library (MIT or Heimdal).** Mature and the interop reference (BIND, Samba). Rejected: the static musl binary cannot link a shared library, `dlopen` needs `unsafe` and a host package, the distroless image has none, and the keytab and `krb5.conf` would be new files on disk outside the vault.
- **Native SSPI on Windows with a pure-Rust stack on Linux.** Keeps the key in the LSA on Windows. Rejected: `unsafe` FFI (or `cross-krb5`, which brings the system GSSAPI back on Linux), a domain-joined Windows host with a gMSA or domain account, and two implementations of one protocol to keep in step.
- **A helper process holding the key.** Keeps the binary static. Rejected: two artifacts and a local protocol to secure, a host package on Linux, and little gain under ADR 0023's threat model, since an attacker controlling the service account can ask the helper to sign.
- **The new pure-Rust `krb5` crate (2026).** Claims an acceptor with keytabs, MIC tokens and the PAC. Not chosen: created in October 2026 by one author, tested against MIT only; kept as a reference.
- **A wizard that creates the account with an administrator's LDAP credential.** Least friction. Rejected: it hands a credential that can create directory objects to a system whose service account the threat model assumes may be compromised.
- **SAML through `samael`.** Rejected: libxmlsec1 and OpenSSL through FFI, against the static binary and `deny.toml`.
- **Groups synchronized into stored grants.** Rejected: a failed synchronization leaves stale rights; mappings evaluated per session expire with the directory check.
