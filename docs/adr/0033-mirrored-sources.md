# ADR 0033: Mirrored sources: a pushed migration source with a token that writes one mirror and nothing else

- Status: Proposed (the owner decided the design on 2026-11-01 and 2026-11-05, WT-Q1, WT-Q2, WT-Q11 of `docs/plans/windows-takeover-plan.md`; Accepted when WP14.1 has built the push and E73 has passed)
- Date: 2026-11-05

## Context

The Windows takeover ([windows-takeover-plan.md](../plans/windows-takeover-plan.md), Slice 14) moves the DHCP service of a small Active Directory domain from the domain controllers to Tenko with no client noticing. The takeover needs the controllers' DHCP data live: the scopes with their options, the reservations and, at the moment of the switch, every lease Windows granted until it stopped answering, so that each client keeps its address and its name (section 2.7 of the plan). Today's runbook copies that data once by hand from `Export-DhcpServer` and deletes every record Windows DHCP wrote before the switch.

Every connector so far is pulled: a plugin instance that the host polls ([ADR 0012](0012-connector-plugins.md)), and [MIGRATION.md](../MIGRATION.md) named PowerShell remoting for the Windows source. Pulling Windows DHCP needs Kerberos or NTLM credentials with DHCP rights stored in Tenko and a channel through which Tenko runs commands on a domain controller: a compromised node would hold a domain credential and a foothold on the controller. [ADR 0023](0023-no-root-after-installation.md) draws the privilege boundary the other way: a more privileged account never runs what a less privileged one wrote.

### Threat model

The adversaries, in the order of [security-audit-plan.md](../plans/security-audit-plan.md) section 1.2:

1. **A compromised Tenko node (A3)**, which must gain nothing on the controllers: no credential, no command, no file it can change there.
2. **A stolen mirror token**, taken from the controller or from the wire, which must give neither data of the installation nor a way to change what Tenko serves.
3. **A hostile push**, forged or replayed, which must change nothing a person did not later decide on, and must not exhaust the node.

## Decision

1. **A mirrored source is pushed to, never polled.** A *mirror* is a new kind of source beside the plugin instances: a row of `migrate.mirrors` with a name, a kind label (`[a-z0-9-]{1,32}`, `windows-dhcp` for the exporter of `deploy/windows/mirror/`; never an enumeration of products, so that a Kea or dnsmasq script can push the same IR under its own label), the expected interval (60 s), the token's id, the last accepted sequence, the hash of the last snapshot and the times of the last push and the last change (`tenko_core::migrate::Mirror`). An exporter on the source's own host reads the source and sends `PUT /api/v1/migrate/mirrors/{id}/snapshot` over HTTPS on the API port. Tenko opens no connection to the source host, holds no credential of it, and cannot make the exporter do anything: the answer carries the accepted sequence and whether the snapshot changed, nothing else (WT-Q1).
2. **The envelope is the source-neutral IR, strict.** A push is one `MirrorSnapshot` (`tenko_core::ir::mirror`): `format` (1), `sequence`, `taken_at` (the source host's clock, so that a lease's remaining time is computed against it and clock skew between the host and the node shortens or lengthens no lease), `source { kind, server, adapter, adapter_version }`, `dhcp` (the `DhcpIr` of [ADR 0006](0006-connector-architecture.md), MIG-01) and `losses` (the `LossReport`). The envelope and the origin carry `deny_unknown_fields`; every value that has a Tenko type is parsed into it; the content is validated whole (scopes that are networks named once, ranges, reservations and leases inside their scope with a client identity, leases of scopes the snapshot holds, options with a code and a value, bounded loss entries), and a snapshot that does not validate is refused with the path of the first error (422 `migrate.mirror.invalid`). Nothing of a refused push is stored. The mapping from the source onto the IR lives in the exporter (WT-Q2): the core receives what any adapter would send and validates it. The fixture `crates/tenko-core/tests/fixtures/mirror/snapshot.json` is the contract between the exporter and the core, held byte for byte by both sides' tests.
3. **The mirror's token writes one mirror and nothing else.** Creating a mirror creates a service account `mirror-<name>` with no grants and one scoped token whose only special scope is `mirror:<id>` (`tenko_auth::model::TokenScope::Mirror(MirrorId)`, the wire form `mirror:<id>`). The push route accepts exactly that scope for exactly that mirror, as `Action::Execute` on the mirror; every other operation of the API answers 403 to that token, the reads of its own mirror included, so a stolen token gives neither data nor reach. The scope is minted by the creation of the mirror and by the token replacement on the mirror card; a request for it through the token API is refused. The token is shown once, expires within TGL-05 like every token (365 days under Home, WT-Q11), raises the finding `migrate.mirror.token_expiring` fourteen days ahead, and is replaced from the mirror card; the old one stops at once.
4. **The exporter is static, ships with the release and runs with read rights only.** It is in the release assets and in the repository, versioned with Tenko and listed in `SHA256SUMS`; the documentation says to compare the digest before copying it to the controller. Tenko never serves it, never generates it and never updates it: a compromised node cannot change what runs on a controller. The exporter runs under a domain account that is a member of `DHCP Users` and of no privileged group, refuses to start when its own token is a member of one, pins Tenko's certificate authority root by its SHA-256 fingerprint (shown on the mirror card) and stores the token with DPAPI for the task's account (WP14.1 builds this; E72 proves it).
5. **Bounds and replays.** A body of at most 8 MiB (gzip allowed, 32 MiB inflated), at most 1,000 scopes, 10,000 reservations and 100,000 leases; a strictly increasing `sequence` per mirror (an older or equal one is a replay, 409 `migrate.mirror.sequence`); at most one push per 10 s per mirror (429 `migrate.mirror.rate`). A refused push is audited as `migrate.mirror.refuse` at most once a minute per mirror. The constants are `tenko_core::ir::mirror::MAX_*`.
6. **Storage and freshness.** `migrate.snapshots` holds one row per mirror, the latest accepted envelope with its hash. A push whose hash equals the stored one writes no row and no audit record; it moves the freshness in the leader's memory only, which is written to the mirror row at most every ten minutes. A steady mirror therefore costs the store one small write every ten minutes, and the lease path is never touched ([ADR 0030](0030-durability-classes-of-the-lease-path.md), [ADR 0031](0031-the-lease-table-is-the-observation-source.md): no fact rows, nothing on the commit path). A changed push writes the snapshot row and the audit record `migrate.mirror.push`. The mirror is stale after three missed intervals: the card says so and the system status carries `migrate.mirror.stale`; a mirrored scope that turns active again while Tenko's scope serves raises `migrate.mirror.scope_active`.
7. **The loss report is acknowledged, never dropped.** Policies, filters, superscopes and failover relationships go to the loss report (WT-Q2), with the codes `migrate.loss.*`. An entry is acknowledged per scope by an administrator's interactive session (`migrate.loss_acks`, keyed by the mirror and the entry's key, holding the entry's hash); the acknowledgment holds while the entry recurs unchanged and lapses when it changes. The prepare and the takeover refuse a scope with an unacknowledged entry.
8. **Cluster-aware.** The mirror rows, the snapshots and the acknowledgments are in the replicated store; any controller accepts the push and writes through the store; the freshness lives in the leader's memory and is rebuilt from the row on a leader change, so a mirror reads as stale until its next push, at most a minute.

### Choices within the decision

a. **The scope carries the mirror's id as a payload, and `TokenScope` keeps `Copy`.** `MirrorId` is a sixteen-octet UUID, so `TokenScope::Mirror(MirrorId)` is as copyable as the two scopes before it and the token record's `scopes` list stays the one place every authorization check reads. The alternative the plan allowed, a field of its own on the token record, would have put the mirror's right outside that list and needed a second rule against a mirror token that also carries another scope. On the wire and in the store the scope is a string; a format 5 binary cannot parse `mirror:<id>` as a scope, which is one of the values that raise the data format to 6.
b. **Data format 6.** The namespace `migrate` of table names, audit actions and error codes, the object kinds `mirror` and `takeover` and the token scope are values a format 5 binary cannot decode (`tenko_core::names::NAMESPACES` refuses an unknown namespace while decoding the journal, a snapshot or an audit record), so the format is raised once for the phase with an empty migration, as format 4 was for Phase 3 ([dhcp-contracts.md](../dhcp-contracts.md) section 13). The tables later Phase 4 packages add in the namespace are additive.
c. **Writes are interactive.** Creating, changing and deleting a mirror, replacing its token and acknowledging losses need a session: `tenko_auth::roles::interactive_only` covers the kinds `mirror` and `takeover`, so a personal token is refused, as for users, settings and keys. Reads are `migrate.read` (operators and administrators); writes `migrate.write` (administrators).
d. **Two additive IR fields.** The exporter reads the server-level DNS settings beside each scope's, and Windows allows a reservation name that is not a host name (`Living Room TV`): `DhcpIr.server_ddns` and `IrReservation.source_name` were added with serde defaults, so every field the exporter fills has a place (plan section 3.1; WT-Q10). `SourceLocation` no longer writes its absent fields, so the fixture carries only what the exporter writes.

## Consequences

- Tenko holds no Windows credential and connects to nothing on Windows; the controller's side is one static script with read rights. The privilege boundary of ADR 0023 holds in both directions: the node writes nothing a controller runs, and the controller's account can read DHCP and write one mirror.
- A mirror token is the one token class that reaches exactly one operation. `ad.mirror_token` of WP14.4 walks the served OpenAPI document with it and expects 403 everywhere but the push.
- An exporter for any other server pushes the same envelope under its own kind label; nothing in the core assumes Windows.
- The cost is a mapping written in PowerShell beside the Rust adapters, held to the fixture by the exporter's tests (R146), and a yearly token replacement, made visible fourteen days ahead (WT-Q11).
- Data format 6: a format 5 binary refuses a data directory this version wrote; a return to the previous release needs the pre-migration copy (`docs/upgrades.md`).
- Risks R138 (the mirror lags at the switch), R145 (the token leaks) and R146 (the mapping drifts) are those of the plan; the takeover waits for the push that shows the source's scope inactive, a forged snapshot changes only what a person later prepares or takes over behind the diff and the acknowledgments, and the fixture is the contract.

## Alternatives considered

- **Tenko pulls over WinRM or PowerShell remoting** (the design of MIGRATION.md): needs Kerberos or NTLM credentials with DHCP rights in Tenko and a channel through which a compromised node runs commands on a controller. Rejected (WT-Q1).
- **A Tenko component installed on the controller that Tenko instructs**: the same channel with an installed foothold, which the privilege boundary of ADR 0023 forbids. Rejected.
- **A periodic `Export-DhcpServer` file copied to Tenko by hand**: no credentials, but not live; the cutover becomes a race with the copy. Rejected.
- **The full export XML pushed raw and mapped by a Windows adapter inside Tenko**: a Windows-specific parser in the core and a large document on the wire every minute. Rejected (WT-Q2).
- **Configuration only, leases left to the renewals**: gives up the takeover's continuity (the address protection between the switch and each client's rebinding, the INIT-REBOOT answer, the record adoption). Rejected (WT-Q2).
- **A non-expiring mirror token as an exception to TGL-05**: avoids a yearly chore but makes one token class an exception to a never-relaxed rule. Rejected (WT-Q11).
- **A field of its own for the mirror id on the token record, or a `TokenScope` without `Copy`**: see choice a.
