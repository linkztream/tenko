# ADR 0035: Client certificates for integrations

- Status: Proposed (the decisions IC-Q1 to IC-Q11 of [integration-client-certificates.md](../plans/integration-client-certificates.md) section 10 are the owner's; Accepted when the owner has decided them)

## Context

An integration (an automation host, a backup job, a provisioning script) talks to Tenko as a service account with a scoped bearer token `tnk_…` ([ADR 0015](0015-scoped-authorization.md), IAM-10). Whoever holds the token text acts as the account until the token expires (TGL-05: 90 days under Standard) or an administrator revokes it, from any address that reaches the API listener. The token renewal package (IAM-20, IAM-21, TGL-46) shortens that window: a token renews itself with a separate renewal secret, the reuse of a renewed secret revokes the token family, and a token can be bound to a source address. Both secrets are still bytes in a file on the integration host, so a copy of that host's disk, a backup of it, or a reverse proxy that sees the traffic carries the integration away.

The owner wants the next step: an integration proves itself with a private key that never travels over the network and can sit in a TPM (Trusted Platform Module, the key store chip of the host), through a client certificate that Tenko's own certificate authority issues.

What exists:

- **The internal CA** (`crates/tenko-cluster/src/ca/`) is an ECDSA P-256 root whose key is a system secret in the vault of the controllers. It issues the API server certificate (TLS mode `internal_ca`) and node certificates with the URI subject alternative names `urn:tenko:node:<id>` and `urn:tenko:role:<role>` and both server and client authentication. A node enrolls with a single-use token and a PKCS#10 request (`POST /api/v1/nodes/enroll`); `csr_public_key` checks the request's self-signature, requires a P-256 key and uses nothing else from the request. Nothing issues a client certificate to anything but a node (`docs/audit-export.md` says so for the audit sink).
- **The API and UI listener** (8443) builds its rustls configuration with `with_no_client_auth` (`ca/tls.rs`). In `reverse_proxy` mode it speaks plain HTTP and only to trusted proxies; in `plain` mode (Lab) to everyone. The per-connection facts `ConnInfo` (`tenko-api/src/server/forwarded.rs`) carry the peer, whether TLS ended here, the mode and a PROXY protocol header; the handshake in `listener.rs` never reads the peer's certificates.
- **The cluster port** (8444) requires mutual TLS 1.3 with a node certificate of the installation's root and an unrevoked serial (`mtls.rs`, `NodeClientVerifier`); it opens on demand and is the most sensitive port of the product ([ADR 0014](0014-controller-cluster.md)). Revocations live in `cluster.revocations`, keyed by serial with a required `node` field, and every controller follows that table with a store watch.
- **Only controllers run the API.** A node without the controller role runs the cluster client alone; DNS and DHCP run inside a controller's process until Phase 5.
- **Tokens** are stored under the SHA-256 of their text in the replicated table `auth.scoped_tokens`. `ScopedTokenRecord` has no `deny_unknown_fields`, so an older build reads a record with a field it does not know and ignores that field.

## Decision

1. **A separate integration CA.** The controllers keep a second ECDSA P-256 root, the integration CA, created at the first enrollment code (create-if-absent, audit `cluster.integration_ca.create`), its key a vault system secret of its own purpose. It signs integration certificates and nothing else; the existing root keeps signing server and node certificates and never signs an integration certificate. The cluster port and the node's check of a controller trust only the existing root, so an integration certificate fails chain building there (`UnknownIssuer`) before any Tenko code reads it; the integration listener trusts only the integration root, so a node certificate fails there the same way.

2. **What an integration certificate says.** Subject `CN=tenko-integration`; exactly one URI subject alternative name `urn:tenko:service-account:<account id>`; extended key usage client authentication only; key usage digital signature; basic constraints not a CA; a random 126-bit serial like every certificate of the internal CA; no DNS name, address, `urn:tenko:node:` or `urn:tenko:role:` name. Validity starts one hour back (the CA's clock skew) and lasts the lifetime of TGL-47. The integration listener's verifier refuses, after the chain check, any certificate that lacks that one URI, carries a node or role URI, carries server authentication, or is a CA, so the separation holds even if the trust anchors were ever mixed up. The account id, not its name, is the identity: a deleted account recreated under the same name is another account.

3. **A dedicated integration listener.** Integration certificates are presented only on a listener of their own (default `[::]:8445`, `[integrations] listen`), never on 8443 and never on the cluster port:
   - TLS 1.3 only in every profile, ALPN `h2` and `http/1.1`; a client certificate of the integration CA is mandatory, so a peer without one never reaches HTTP. The certificate request names only the integration root.
   - The server certificate is always one of the existing internal root, issued for the controller's configured host names and addresses, in every TLS mode of 8443; the integrator pins that root by the fingerprint the enrollment code carries.
   - No session tickets and no session cache: every connection runs the full handshake, and the verifier runs at every connection.
   - It reads no PROXY protocol header and no forwarded header; the client address is the TCP peer.
   - It opens on demand like the cluster port: while an enrollment code is waiting or an integration certificate is active, unless `[integrations] listen` sets it explicitly or `[]` turns it off.
   - It serves the same API router as 8443. Only bearer tokens are read there, never a session cookie.
   - Every request re-checks the connection's certificate against the in-memory state (expiry, revocation, the account's generation), so a revocation or an expiry ends a long-lived HTTP/2 connection at its next request, and the controller also closes the connections of a revoked serial.

4. **Reverse proxy and plain modes.** A client certificate forwarded by a proxy is never trusted, in any mode and any profile: no header (`X-SSL-Client-Cert`, `X-Forwarded-Client-Cert`, `ssl-client-cert` or another) and no PROXY protocol TLS field is read as a certificate. An installation behind a proxy keeps its proxy for people; integrations that use certificates reach the controllers' integration listener directly (or through a TCP pass-through that leaves TLS end to end). The rule is written in this ADR, in `docs/certificates.md` and beside `ConnInfo`, and a test of package CC8 proves it (plan section 9).

5. **Enrollment with `openssl` and `curl`.** An administrator in an interactive session signed in within the last five minutes (`require_fresh_person`; a token is refused) creates a single-use enrollment code for one service account: `POST /api/v1/integrations/enrollments`, at most one hour, optionally limited to a source prefix, optionally replacing a lapsed lineage (decision 7). The code `tnki.<id>.<secret>.<fingerprint>` carries the SHA-256 of the internal root in hexadecimal, so a shell compares it with `openssl x509 -fingerprint -sha256`; the controller keeps only a digest of it, like a node enrollment token. On the automation host the integrator generates a P-256 key in a file or in a TPM, makes a PKCS#10 request with it and sends the request with the code to the public route `POST /api/v1/integrations/enroll` (body `application/pkcs10`, code as the bearer credential). The request's self-signature must verify over a P-256 key; names, extensions and attributes in it are ignored. Refused: a used, expired or withdrawn code, a source outside the code's prefix, an account that is no longer a service account, disabled or of another generation, another key type, a key that is already in a certificate of any account or that was in a revoked one, and an account that already holds eight active lineages. The answer is the certificate in PEM. The private key never leaves the host, and Tenko cannot tell whether it is in a TPM (no key attestation in this step).

6. **Renewal.** The integrator renews over the integration listener with the current certificate alone, no token needed: `POST /api/v1/integrations/certificate/renew` with a new PKCS#10 request, for a new key or the same key. A renewal is accepted in the last third of the lifetime and at most once an hour (`integration.renew.not_due`, `integration.renew.too_soon`); the new certificate continues the lineage. The replaced certificate works until the new one is first presented, then for 15 more minutes, as for nodes. A renewal presented with a certificate the lineage has already replaced is reuse: the lineage is revoked with every token bound to it (IAM-24). Tokens bound to the lineage follow a new key in the same write.

7. **Lapse.** There is no grace period: an expired certificate fails the handshake, and tokens bound to it are refused. The expiry alarm (OPS-29, "certificates about to expire") fires when a lineage enters the last sixth of its lifetime without renewing. Recovery is a new enrollment code that names the lapsed lineage in `replaces`; at enrollment its bound tokens move to the new key. A revoked lineage cannot be replaced: its tokens were revoked with it.

8. **Certificate-bound tokens (what the certificate protects).** A service-account token can be bound to a certificate lineage in the manner of RFC 8705: its record holds the SHA-256 of the lineage's current SubjectPublicKeyInfo. A bound token is accepted only on the integration listener, over a connection whose certificate is valid, unrevoked, names the token's owner and carries the bound key; 8443 refuses it with `auth.token.certificate_required`. A token is bound when an administrator creates it with `binding: "certificate"` (it binds to the first certificate of its own account that presents it, and is refused on 8443 from the start) or when its renewal (IAM-20) is made over the integration listener. Binding is one-way. Bound tokens use a distinct text prefix, `tnkb_`, so that a build that does not know binding refuses them at its prefix check instead of reading them as bearer tokens (the rollback rule of ADR 0015, R25). The binding is to the key, not to the certificate as RFC 8705 has it, so that a renewal with the same key (the TPM case) keeps the binding; `docs/CONFORMANCE.md` records the difference.

9. **Revocation.** Integration certificates are recorded in a table of their own, `auth.client_certs` (serial, account, account generation at issue, lineage, key digest, validity, state `active`, `replaced` or `revoked`, reason), not in `cluster.revocations`, whose record names a node and whose prune and controller exception are node rules; an older build never reads the new table, so a rollback refuses integration certificates instead of reading them wrongly. The mechanism is reused: an in-memory set (`RevocationSet`) per controller, refreshed by a watch on the table, and a kill switch per connection. What revokes: an administrator (`DELETE /api/v1/integrations/certificates/{serial}`, the whole lineage, no fresh sign-in needed, audit `auth.client_cert.revoke`); deleting or disabling the service account, which also takes effect at once through the account generation the record carries; reuse of a lineage (decision 6); reuse detection of a bound token family (IAM-21), since a reused bound renewal proves that someone else used the key. The key digest of a revoked certificate never enrolls again.

10. **TGL-47** sets the certificate lifetime and whether service-account tokens must be bound: Home 90 days, not required; Standard 30 days, not required; Hardened 7 days, required for every token an administrator creates for a service account; Lab 365 days, not required. The plan drafts the row.

## Consequences

- A stolen bound token is worthless: it is refused on 8443, and on the integration listener it needs the key. A copy of the integration host's disk is worthless when the key is in a TPM; with a key in a file it carries the integration away until the next legitimate renewal reveals the copy or the lineage expires (at most 30 days under Standard).
- Integrations that use certificates need a firewall path from the automation host to TCP 8445 of a controller, and they bypass the reverse proxy. People keep using 8443 as before; browsers never see a certificate request.
- The installation has a second root to keep. Its rotation is not part of this step (the root lasts ten years like the first).
- The token and certificate checks on the integration listener cost one in-memory lookup and a 32-byte comparison per request; the full handshake per connection costs one ECDSA verification more than a resumed one, which a keep-alive client pays once.
- `tenko-api`'s connection facts gain the verified client identity, which becomes the one place a route can learn of a client certificate.
- The token model gains a binding and a second prefix; both land after the renewal package, which owns those files.
- The audit export's client certificate for a TLS sink ([audit-export.md](../audit-export.md)) stays supplied by the operator: it is Tenko's own outgoing identity, another purpose than an integration's.
- What is left for later: a certificate that replaces the token altogether, PROXY protocol on the integration listener for a TCP pass-through, TPM key attestation, RSA keys, and a client command that enrolls and renews.

## Alternatives considered

- **One root, integration certificates told apart by their URI only.** No second key to keep, rejected: the cluster port's chain check would accept an integration certificate, and only the node-name check would stand between an integration host and the Raft services. A separate root refuses it before Tenko code runs.
- **An intermediate CA under the existing root.** Rejected for the same reason: the cluster port trusts the root, so the chain builds.
- **Optional client authentication on 8443.** One port fewer, rejected: rustls has no post-handshake authentication, so the request comes in every handshake, and a workstation that holds an integration certificate (an integrator testing from a desktop) gets a certificate prompt in the browser on every visit; the certificate request names the integration root to every scanner; and it cannot work in `reverse_proxy` or `plain` mode, where 8443 speaks plain HTTP to proxies only, so a second path would be needed anyway.
- **Choosing the configuration by server name on 8443.** No browser prompt, rejected: it needs a DNS name (an address sends no server name), does not work behind a proxy either, and makes a name the only separation on a port shared with people.
- **A route on the cluster port.** Rejected: the port is closed on a single node, carries gRPC only, and is the most sensitive port; opening it to integration hosts' networks and widening its trust anchor exposes the Raft and cluster services to every integration host.
- **Trusting a certificate forwarded by the proxy.** Rejected: a header is the proxy's claim, not proof that the key is on the client; the proxy, or a misconfiguration that passes a client's own header through, could mint any integration identity.
- **The certificate protects only the renewal call.** Smaller, kept as a step inside decision 8 (a bound renewal), rejected as the goal: the token stays a bearer token for its whole lifetime, so a stolen token works until it expires.
- **The certificate replaces the token.** The simplest client, kept for later: it changes the authentication model, loses the per-token subset of grants and the separate revocation of a token, and needs the integration listener for every route on the first day.
- **Reusing `cluster.revocations`.** Rejected: its record requires a node, an older build would fail on or misread a row without one, and its prune and controller rules are node rules.
- **RFC 8705's certificate thumbprint as the binding.** Rejected: every renewal would break the binding, including a same-key renewal from a TPM.
