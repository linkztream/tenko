# ADR 0035: Client certificates for integrations

- Status: Accepted. The owner decided IC-Q1 to IC-Q11 of [integration-client-certificates.md](../plans/integration-client-certificates.md) section 10 as recommended, except IC-Q4: TLS 1.3 by default, with a setting that allows TLS 1.2 on the integration listener for older Windows Server installations (decisions 3 and 10).

## Context

An integration (an automation host, a backup job, a provisioning script) talks to Tenko as a service account with a scoped bearer token `tnk_…` ([ADR 0015](0015-scoped-authorization.md), IAM-10). Whoever holds the token text acts as the account until the token expires (TGL-05: 90 days under Standard) or an administrator revokes it, from any address that reaches the API listener. The token renewal package (IAM-20, IAM-21, TGL-46) shortens that window: a token renews itself with a separate renewal secret, the reuse of a renewed secret revokes the token family, and a token can be bound to a source address. Both secrets are still bytes in a file on the integration host, so a copy of that host's disk, a backup of it, or a reverse proxy that sees the traffic carries the integration away.

The owner wants the next step: an integration proves itself with a private key that never travels over the network and can sit in a TPM (Trusted Platform Module, the key store chip of the host), through a client certificate that Tenko's own certificate authority issues.

What exists:

- **The internal CA** (`crates/tenko-cluster/src/ca/`) is an ECDSA P-256 root whose key is a system secret in the vault of the controllers. It issues the API server certificate (TLS mode `internal_ca`) and node certificates with the URI subject alternative names `urn:tenko:node:<id>` and `urn:tenko:role:<role>` and both server and client authentication. A node enrolls with a single-use token and a PKCS#10 request (`POST /api/v1/nodes/enroll`); `csr_public_key` checks the request's self-signature, requires a P-256 key and uses nothing else from the request. Nothing issues a client certificate to anything but a node (`docs/audit-export.md` says so for the audit sink).
- **The API and UI listener** (8443) builds its rustls configuration with `with_no_client_auth` (`ca/tls.rs`). In `reverse_proxy` mode it speaks plain HTTP and only to trusted proxies; in `plain` mode (Lab) to everyone. The per-connection facts `ConnInfo` (`tenko-api/src/server/forwarded.rs`) carry the peer, whether TLS ended here, the mode and a PROXY protocol header; the handshake in `listener.rs` never reads the peer's certificates.
- **The cluster port** (8444) requires mutual TLS 1.3 with a node certificate of the installation's root and an unrevoked serial (`mtls.rs`, `NodeClientVerifier`); it opens on demand and is the most sensitive port of the product ([ADR 0014](0014-controller-cluster.md)). Revocations live in `cluster.revocations`, keyed by serial with a required `node` field, and every controller follows that table with a store watch.
- **Only controllers run the API.** A node without the controller role runs the cluster client alone; DNS and DHCP run inside a controller's process until Phase 5.
- **Tokens** are stored under the SHA-256 of their text in the replicated table `auth.scoped_tokens`. `ScopedTokenRecord` has no `deny_unknown_fields`, so an older build reads a record with a field it does not know and ignores that field.

## Decision

1. **A separate integration CA.** The controllers keep a second ECDSA P-256 root, the integration CA, created at the first enrollment code (create-if-absent, audit `cluster.integration_ca.create`), its key a vault system secret of its own purpose. It signs integration certificates and nothing else; the existing root keeps signing server and node certificates and never signs an integration certificate. The cluster port and the node's check of a controller trust only the existing root, so an integration certificate fails there before any Tenko code reads it; the integration listener trusts only the integration root, so a node certificate fails there the same way. A valid signature of the integration root is necessary and never sufficient: decision 9 accepts only certificates the store records.

2. **What an integration certificate says.** Subject `CN=tenko-integration`; exactly one URI subject alternative name `urn:tenko:service-account:<account id>` in the canonical hyphenated form; extended key usage client authentication only; key usage digital signature; basic constraints not a CA; a random 126-bit serial like every certificate of the internal CA; no DNS name, address, `urn:tenko:node:` or `urn:tenko:role:` name. Validity starts one hour back (the CA's clock skew) and lasts the lifetime of TGL-47. The integration listener's identity reader refuses, after the chain check, any certificate that lacks that one URI, carries any other name, carries another extended key usage, or is a CA, so the separation holds even if the trust anchors were ever mixed up. The account id, not its name, is the identity: a deleted account recreated under the same name is another account.

3. **A dedicated integration listener.** Integration certificates are presented only on a listener of their own (default `0.0.0.0:8445` like the cluster port's `0.0.0.0:8444`, `[integrations] listen`), never on 8443 and never on the cluster port.
   - **TLS.** TLS 1.3 by default in every profile, ALPN `h2` and `http/1.1`; a client certificate of the integration CA is mandatory, so a peer without one never reaches HTTP, and the certificate request names only the integration root. No session tickets, no session IDs and no session cache in either version: every connection runs the full handshake and the verifier runs at every connection.
   - **TLS 1.2,** only while the third part of TGL-47 allows it (decision 10), for automation hosts whose own TLS stack has no TLS 1.3 (Windows Server 2019 and older). In TLS 1.2 the client's certificate travels before encryption starts, so an observer on the path learns which certificate a connection presents: the service account's id, the serial, the validity and the public key, and from that which host acts as which account and when. The observer never learns the private key, a token or a request, and cannot use the certificate without the key. TLS 1.2 is limited to the suites rustls offers (ECDHE key exchange with AES-GCM or ChaCha20-Poly1305), the Extended Master Secret is required (RFC 7627; a client without it fails the handshake), and rustls has no renegotiation. While it is allowed, the health view shows a warning row, beside the deviation the UI shows for every toggle and the audit record of the change.
   - **Server certificate.** Always a certificate of the existing internal root, issued for the controller's configured host names and addresses, in every TLS mode of 8443. The integrator never installs that root in a machine-wide trust store: the documented scripts pass it per call (`curl --cacert`) or compare its SHA-256 with the fingerprint the enrollment code carries (PowerShell's certificate validation callback), so the root vouches for this one connection only.
   - **Resources of its own.** Its own connection cap (512), a cap of 16 connections per source address checked before the handshake, and a handshake timeout of 5 seconds, apart from the API server's limits, so that a flood on one listener does not starve the other.
   - **Only integrations.** It reads no PROXY protocol header and no forwarded header (the client address is the TCP peer), and no session cookie. It serves the authenticated routes of the API and the renewal route, and none of the public routes (sign-in, enrollment, the CA root, node enrollment). Every request except renewal must carry a bearer token owned by the account the certificate names; any other token is refused (`integration.token.wrong_account`).
   - **Re-checked at every request** against the certificate records of decision 9, so a revocation, a replacement past its overlap, an expiry or an end of the account ends a long-lived HTTP/2 connection at its next request; the controller also closes the connections of a revoked serial.
   - **Cut off from the quorum.** When the controller has been `isolated` or `electing` (ADR 0014, decision 8) for more than 30 seconds, the listener answers every request with 503 `integration.isolated`: a controller that cannot hear the cluster cannot know of a revocation made elsewhere. A single controller is never isolated.
   - **Opening.** It opens on demand like the cluster port, while an enrollment code is waiting or an integration certificate is active, unless `[integrations] listen` sets it explicitly or `[]` turns it off; and it opens only after the first full load of the certificate records succeeded.

4. **Reverse proxy and plain modes.** A client certificate forwarded by a proxy is never trusted, in any mode and any profile: no header (`X-SSL-Client-Cert`, `X-Forwarded-Client-Cert`, `ssl-client-cert` or another) and no PROXY protocol TLS field is read as a certificate. An installation behind a proxy keeps its proxy for people; integrations that use certificates reach the controllers' integration listener directly (or through a TCP pass-through that leaves TLS end to end). The rule is written in this ADR, in `docs/certificates.md` and beside `ConnInfo`, and a test of package CC8 proves it (plan section 9).

5. **Enrollment with `openssl` and `curl`, the code's secret never sent.** An administrator in an interactive session signed in within the last five minutes (`require_fresh_person`; a token is refused) creates a single-use enrollment code for one service account: `POST /api/v1/integrations/enrollments`, at most one hour, optionally limited to a source prefix. The code `tnki.<code id>.<account id>.<secret>.<fingerprint>` carries the secret (256 bits) and the SHA-256 of the internal root, both in hexadecimal, so a shell compares the fingerprint with `openssl x509 -fingerprint -sha256`. The controller needs the secret to check the HMAC, so it keeps it as a system secret in the vault while the code can be used and deletes it when the code is used, withdrawn or expired; the code's record never holds it. On the automation host the integrator generates a P-256 key (in a file, or in a TPM with an authorization value), makes a PKCS#10 request with it, and computes an HMAC-SHA-256 with the code's secret over a fixed label, the code id, the account id and the DER of the request's SubjectPublicKeyInfo in its one canonical form (named curve, uncompressed point; another encoding of a P-256 key is refused, so a key has one digest). The public route `POST /api/v1/integrations/enroll` receives the request, the code id and that HMAC, never the secret, so whoever sees the request in transit (a proxy, a log) can neither redeem the code for another key nor use the certificate, which is worthless without the key. The integrator's scripts pass headers from a file, never on the command line. Plain HTTP, or a proxy that does not state the scheme, is refused outside the Lab profile and withdraws the code, as node enrollment does. The request's self-signature must verify over a P-256 key; names, extensions and attributes in it are ignored. Refused: an unknown, used, expired or withdrawn code, a wrong HMAC, a source outside the code's prefix, an account that is no longer a service account, disabled or of another `tokens_generation`, another key type, a key that is already in a certificate of any account or that was in a revoked one, and an account that already holds eight active lineages. The certificate and its record are written in one batch that consumes the code, and the certificate is answered (PEM) only after that write committed. The private key never leaves the host, and Tenko cannot tell whether it is in a TPM (no key attestation in this step).

6. **Renewal.** The integrator renews over the integration listener with the current certificate alone, no token needed: `POST /api/v1/integrations/certificate/renew` with a new PKCS#10 request. A key in a file is replaced at every renewal (the documented POSIX script makes a fresh key each time); renewing with the same key is meant for keys a TPM holds, which cannot be copied. The server accepts either, since it cannot tell them apart. The rules follow token renewal:
   - Within a lineage there is at most one *current* certificate and one *pending* successor. A renewal is accepted in the last third of the current certificate's lifetime and at most once an hour; before that the route answers 200 with a body that says the renewal is not due and when it will be, while a new certificate is answered with 201 and the PEM, so a script never mistakes a refusal for "nothing to do".
   - A renewal from the current certificate while its successor has not been presented yet replaces that successor (the answer was lost): the unseen successor is withdrawn and a new one issued.
   - When the successor is first presented it becomes current and its predecessor becomes *replaced*. A replaced certificate passes for every route for 15 more minutes (the overlap, as for nodes); after that it passes the handshake for the renewal route only, and a renewal from it is reuse: the lineage is revoked with every token bound to it (IAM-24). Reuse is counted only once the successor has been presented.
   - Every renewal is audited (`auth.client_cert.renew`), with the old and new serial and whether the key changed.

7. **Lapse.** There is no grace period: an expired certificate fails the handshake, and tokens bound to its lineage are refused. The expiry alarm (OPS-29, "certificates about to expire") fires when a lineage enters the last sixth of its lifetime without renewing. When a lineage expires, its bound tokens are revoked. Recovery is a new enrollment, a new lineage, and new tokens bound to it, which an administrator creates as for any new integration. No token ever moves from one lineage to another.

8. **Certificate-bound tokens (what the certificate protects).** A service-account token can be bound to a lineage in the manner of RFC 8705. The binding is set when the token is created: the administrator names the lineage (one of the account's active lineages), and it never changes. The token record holds the lineage id; at every use the server compares it with the lineage of the connection's certificate record. A key change at renewal therefore rewrites no token. A token renewed under IAM-20 keeps its binding.
   - **Prefix and record agree.** Bound tokens use the text prefix `tnkb_`, so a build that does not know binding refuses them at its prefix check (the rollback rule of ADR 0015, R25) and never reads, or writes back, their record. A `tnkb_` token whose record names no lineage is refused, and so is a `tnk_` token whose record names one: a record whose binding was lost never reads as unbound.
   - **The binding is checked first.** For a bound token the binding (the integration listener, a certificate whose record is acceptable under decision 9, of the token's owner and of the token's lineage) is checked before anything else of the token: before its expiry, before the reuse detection of IAM-21 and before the counter of wrong renewal secrets. A bound token presented without the key (on 8443, or with another certificate) is refused with `auth.token.certificate_required` and audited (`auth.token.binding_refused`), and nothing else happens: no reuse detection, no counter, no revocation. Whoever lacks the key can neither use a bound token nor revoke it.
   - The binding is to the lineage, not to the certificate as RFC 8705 has it, so a renewal keeps the binding; `docs/CONFORMANCE.md` records the difference.

9. **The certificate records are an allow-list.** Every integration certificate has a record in `auth.client_certs` (serial, account, the account's `tokens_generation` at issue, lineage, key digest, validity, state `pending`, `current`, `replaced`, `withdrawn` or `revoked`, the time it was first presented, reason). A certificate is accepted, at the handshake and at every request, only when its serial has a record in an accepting state (`pending` on its first presentation, `current`, or `replaced` under the rules of decision 6), the record's account matches the certificate's, the account is a service account that is not disabled, and its `tokens_generation` is not above the record's. An unknown serial is refused: a certificate signed by a controller that has left the cluster and kept a copy of the integration CA key, or one whose recording write lost, is worthless. Each controller keeps the records in memory, loaded in full at start (the listener opens only after that load) and followed by a watch on the table; the table is new, so an older build never reads it and a rollback refuses integration certificates instead of reading them wrongly. `cluster.revocations` stays as it is: its record names a node, and its prune and controller exception are node rules.
   - **What revokes:** an administrator (`DELETE /api/v1/integrations/certificates/{serial}`, the whole lineage, no fresh sign-in needed, audit `auth.client_cert.revoke`); deleting the service account (its `tokens_generation` rises, which ends the certificates at once, and the records are revoked in the same pages as its tokens); disabling it (refused while disabled); reuse of a lineage (decision 6); reuse detection of a bound token family (IAM-21), which under decision 8 can fire only after the key was proven, so it means someone else holds the key. Revoking a lineage revokes its bound tokens, and the key digest of a revoked certificate never enrolls again.

10. **TGL-47** sets three things: the certificate lifetime, whether service-account tokens must be bound, and whether the integration listener accepts TLS 1.2. Home 90 days, not required, TLS 1.3 only; Standard 30 days, not required, TLS 1.3 only; Hardened 7 days, required for every token an administrator creates for a service account, TLS 1.3 only, and allowing TLS 1.2 is refused as a setting; Lab 365 days, not required, TLS 1.3 only. Allowing TLS 1.2 is a deviation the UI shows and the audit log records, like every toggle change. Tightening the requirement of binding revokes the unbound tokens of service accounts in the same change, after the settings page has listed them; loosening it again revives nothing. The plan drafts the row.

## Consequences

- A stolen bound token is worthless: it is refused on 8443, and on the integration listener it needs the key; presenting it without the key cannot revoke anything either. A copy of the integration host's disk is worthless when the key is in a TPM. With a key in a file it carries the integration away until the next legitimate renewal, which replaces the key: the copied certificate stops working 15 minutes after the new one is first presented, and a renewal from it after that is reuse and revokes the lineage. A thief who never renews is therefore not revealed, only cut off, at the latest one lifetime (30 days under Standard) after the copy.
- An installation that allows TLS 1.2 for an old automation host shows, to an observer on the path, which certificate that host presents; the deviation stays visible until it is turned off.
- Integrations that use certificates need a firewall path from the automation host to TCP 8445 of a controller, and they bypass the reverse proxy. People keep using 8443 as before; browsers never see a certificate request.
- The installation has a second root to keep. Its rotation is not part of this step (the root lasts ten years like the first).
- The token and certificate checks on the integration listener cost two in-memory lookups and an identifier comparison per request; the full handshake per connection costs one ECDSA verification more than a resumed one, which a keep-alive client pays once.
- `tenko-api`'s connection facts gain the verified client identity, which becomes the one place a route can learn of a client certificate.
- The token model gains a lineage and a second prefix; both land after the renewal package, which owns those files. A key change at renewal writes one certificate record and no token.
- A lapsed or revoked lineage costs its tokens: recovery needs new tokens from an administrator, never a move of the old ones.
- On a POSIX automation host the `openssl` call that computes the enrollment HMAC shows the code's secret in its arguments for the moment it runs; the documented script says to run it on a host where other users cannot read process arguments. PowerShell computes it in process.
- The audit export's client certificate for a TLS sink ([audit-export.md](../audit-export.md)) stays supplied by the operator: it is Tenko's own outgoing identity, another purpose than an integration's.
- What is left for later: a certificate that replaces the token altogether, PROXY protocol on the integration listener for a TCP pass-through, TPM key attestation, RSA keys, a client command that enrolls and renews, and name constraints on the internal root at its next rotation.

## Alternatives considered

- **One root, integration certificates told apart by their URI only.** No second key to keep, rejected: the cluster port's chain check would accept an integration certificate, and only the node-name check would stand between an integration host and the Raft services. A separate root refuses it before Tenko code runs.
- **An intermediate CA under the existing root.** Rejected for the same reason: the cluster port trusts the root, so the chain builds.
- **Optional client authentication on 8443.** One port fewer, rejected: rustls has no post-handshake authentication, so the request comes in every handshake, and a workstation that holds an integration certificate (an integrator testing from a desktop) gets a certificate prompt in the browser on every visit; the certificate request names the integration root to every scanner; and it cannot work in `reverse_proxy` or `plain` mode, where 8443 speaks plain HTTP to proxies only, so a second path would be needed anyway.
- **Choosing the configuration by server name on 8443.** No browser prompt, rejected: it needs a DNS name (an address sends no server name), does not work behind a proxy either, and makes a name the only separation on a port shared with people.
- **A route on the cluster port.** Rejected: the port is closed on a single node, carries gRPC only, and is the most sensitive port; opening it to integration hosts' networks and widening its trust anchor exposes the Raft and cluster services to every integration host.
- **Trusting a certificate forwarded by the proxy.** Rejected: a header is the proxy's claim, not proof that the key is on the client; the proxy, or a misconfiguration that passes a client's own header through, could mint any integration identity.
- **The certificate protects only the renewal call.** Smaller, kept as a step inside decision 8 (a bound renewal), rejected as the goal: the token stays a bearer token for its whole lifetime, so a stolen token works until it expires.
- **The certificate replaces the token.** The simplest client, kept for later: it changes the authentication model, loses the per-token subset of grants and the separate revocation of a token, and needs the integration listener for every route on the first day.
- **TLS 1.3 only, with no setting.** Rejected by the owner: Windows Server 2019 and older have no TLS 1.3 in their own TLS stack, and integrations there must still work. The setting is off by default and refused under Hardened.
- **Reusing `cluster.revocations`.** Rejected: its record requires a node, an older build would fail on or misread a row without one, and its prune and controller rules are node rules.
- **RFC 8705's certificate thumbprint, or the key digest, as the binding.** Rejected: every renewal would break a thumbprint binding, and a key digest copied into every token would make each key change a paged rewrite of tokens that races token renewal; the lineage id never changes.
- **A deny-list of revoked serials.** Rejected: whoever holds a copy of the integration CA key (a controller removed from the cluster) could sign certificates that pass; only recorded certificates pass.
- **Binding a token to the first certificate that presents it, or moving tokens to a replacing lineage.** Rejected: both let whoever holds an enrollment code for the account take over existing tokens without the old key. A binding is named at creation and never moves.
- **A name-constrained intermediate for the listener's server certificate.** Left out: it limits the damage of an internal root installed in a machine-wide trust store, and the integrator never installs it there (decision 3); the intermediate would add an issuing key and chain handling for no gain within that rule. Name constraints on the internal root itself belong to its rotation.
- **Sending the code's secret with the enrollment.** Rejected: a proxy or a log on the way could redeem the code for its own key; the HMAC proves the secret without sending it.
