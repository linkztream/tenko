# ADR 0038: A takeover script from the release, approved in the UI: a delegated session bound to one run

- Status: Proposed (the owner decided the approach on 2026-11-20, `docs/plans/windows-takeover-plan.md` section 2.16; WT-Q15 to WT-Q20 decided on 2026-11-20 as recommended; Accepted when E144 and E145 pass)
- Date: 2026-11-20

## Context

The Windows takeover ([windows-takeover-plan.md](../plans/windows-takeover-plan.md), Slice 14) as first designed asked the operator for about 85 commands and UI actions and about 30 values across Windows and Tenko, with the runbook open throughout (plan section 2.16.6). The owner decided on 2026-11-20 that one script, run by the administrator on a domain-joined Windows machine, does the Windows side as that administrator and the Tenko side through Tenko's API, under three conditions: the script comes from the release and never from the node; it never executes text Tenko sends, only checked values in fixed commands; and it signs in to Tenko through an approval a signed-in person gives in the UI, so that the takeover stays the decision of an interactive session, while the Windows credential stays in the script's process and the server holds no Windows right. He set aside entering the Windows credential into Tenko and running the Windows side from the Tenko host.

Two rules stand in the way of a script calling the takeover's operations. The flip refuses everything but an interactive session (`needs_a_session`, [ADR 0034](0034-zone-flip-and-adoption.md) decision 4), and `interactive_only` refuses every token on the kinds `mirror` and `takeover` ([ADR 0033](0033-mirrored-sources.md) choice c). A token for the script would break both rules; a session copied from a browser would carry no binding and no limit. Nothing in `tenko-auth` turns a person's approval into a session for a program, and the account self-service operations (`tenko-auth/src/service/account.rs`) accept any session that signed in recently, without passing through `authorize`.

## Decision

1. **The script is part of the release, and the release is its only source.** The takeover script, the exporter and its installer ship as one archive and as loose files, with `SHA256SUMS` and the release's provenance attestation, without an Authenticode signature (no budget, and no free publicly trusted route, WT-Q15); the release refuses to publish them without both. A locked-down domain brings them in with Tenko's release through its own intake, whose check command (the attestation and the digest list) prints the start line with the verified digest built in, and, where application control enforces script rules, signs them with its own certificate. Every way the file arrives ends in that one line, which hashes the file on disk and only then starts it; the scripts are ASCII with CRLF line ends, enforced in CI, so that a copy pasted into a file has the released digest. Text pasted into a console cannot be verified by Windows, so its only protection is its source: no page of Tenko shows the script, a command line or a digest (WT-Q20), and in a tiered domain a page of an application server is a lower tier. Without a certificate the chain is as strong as the account that publishes the releases, which holds a hardware security key. The script needs Full Language and compiles nothing at run time, so that an organization can sign it as released.
2. **The script runs as the administrator, in an elevated process on a controller or a privileged access workstation**, opens Kerberos-only sessions by FQDN without a second hop, and uses the logon it runs under; it never asks for or holds a credential (WT-Q18).
3. **Tenko's answers are values.** The script checks each against what Windows reports, the node's DNS answers and the pinned connection (plan section 2.16.3), and binds it to typed parameters of fixed commands; it never builds a command, a script block or a command line from one, parses only JSON through its own helper, follows no redirect, and prints Tenko's text without control characters. The decision to start the window, a value from the node, is confirmed at the console before phases 4 and 5. Values the reverse restores come only from the local state file and must be of classes the sitting's fresh discovery confirms; what the reverse writes into Windows from Tenko is bounded to lease values and to a zone's records after the person confirmed every difference from the record set read at the flip.
4. **The approval is a device-style grant with a bound code.** The script sends its plan (the zones, servers, scopes, the mirror host, the node name and the operations) and a P-256 key made in memory, without a credential; Tenko validates the plan against its own limits and answers with an id and a nonce, which the script refuses when they arrive more than 5 s after its request by its own stopwatch. Both sides compute an 80-bit code from the domain, the SHA-256 of the root of a chain the script built by signature verification with the host name matched, the plan's hash, the key and the id. The person signs in, types the code, reads the plan and approves with a sign-in within five minutes (a passkey under Hardened). A script behind an interceptor, including one that appends Tenko's real root to its own chain, cannot match. The script pins the root as soon as the approval's answer is checked, collects the session once by signing the nonce over that pinned connection, and hands the root to the exporter.
5. **The result is a delegated session, never fresh and never a token.** A session of the approving administrator (`Principal::User`) with a field `delegation` naming the run; a bearer secret (`tnka_`), never a cookie, accepted only from its approval's source address. A default-deny allow-list of routes in the authentication layer, ahead of every handler, decides what it reaches, so the account routes are closed to it; every requirement of a recent sign-in refuses it, and the mirror creation that mints a token is checked by an explicit rule against the approval's time on Tenko's own clock. Each listed handler checks its body against the plan; the run's plan and stage are held in the authentication image. Nothing a run creates answers or forwards before the window: zones are created not served and forwarding rules inactive, and the flip switches both on. The flip and the takeover open to it only after the person starts the window, a second fresh interactive action that it can never take.
6. **Lifetime, end and audit.** At most eight hours or the profile's absolute lifetime, idle at most 15 minutes under every profile, both measured by Tenko on its own clock and never against a time the script sends; it ends with the run's stage, the script's exit, **Revoke**, and the approver's disabling. Every operation it calls is audited with the approver and the run.
7. **The run is an object.** `migrate.runs` holds the plan, the phases, the window with its bindings, the mirrors and the takeovers; the UI's **Windows takeover** page shows it.

## Consequences

- No token reaches the flip, the takeover or the window. The interactive rule now reads "a person's session, or a session a person delegated to one run for that run's plan, after that person's second decision for what serves"; under Hardened the takeover line's sentence "no script acts as `admin`" now reads "a script acts as an administrator only through a session that administrator approved with a passkey, narrowed to one plan".
- Every short timed rule of the run is measured by a monotonic stopwatch on the side that applies it, never by comparing two machines' clocks, and an adopted lease takes its remaining time from the Windows server's own clock and its end from Tenko's (plan section 2.17).
- The administrator's actions for the reference domain fall to about 19 to 22 in a single sitting and one more when the DNS and DHCP windows are split, the values to two (plan section 2.16.6, E146); a locked-down domain adds its intake once per release.
- A compromised node still decides what it serves after the flip and the takeover, as any DNS and DHCP authority does, and as an AD-integrated DNS authority with a domain computer account it reaches further into a typical domain (plan section 2.16.3; the owner's acceptance is WT-Q19). It can lie or stall during the run; it cannot obtain the Windows credential, run code on Windows, start the window's Windows changes without the console, or make the script act on objects Windows did not report.
- New surface: one route without a credential (bounded per /64, rate-limited, strictly parsed), a signature check, an allow-list that must be extended deliberately for any route the script later needs (R221), a not-served state for zones and an inactive state for forwarding rules.

## Alternatives considered

- **The Windows credential entered into Tenko, or the Windows side run from the Tenko host.** A compromised node would hold, or see pass, a domain administrator's credential; remoting from Linux needs Kerberos or NTLM set up on the host and packages outside the release. Set aside by the owner.
- **A personal or service-account token for the script.** Opens the flip and the takeover to tokens, which the interactive rule exists to refuse.
- **The browser's session cookie given to the script.** No binding, no narrowing, the cross-site rules of a cookie, and a secret the person copies by hand.
- **The delegation checked inside `authorize` only.** The account routes never call it, and a recently approved session would reach them: a passkey or a token on the approver's account from a stolen secret.
- **The plan sent after the approval.** The person would approve an empty envelope, and the narrowing would be whatever the client sent next.
- **RFC 8628 as written, the code sent by the server.** The code would prove nothing about the TLS identity the script reached.
- **A client certificate of the integration CA for the script (ADR 0035).** It identifies a service account, not a person's decision.
- **A proof of the script's key on every request (RFC 9449).** Left out: the session is bound to its source address, and the secret lives only in the elevated process that holds the domain credential too.
- **A copy of the scripts on the node, served or fetched over SSH.** A file the service writes or serves is the compromised service's file; a root-owned copy lags the node's version under in-app updates and comes from a lower tier (plan section 2.16.1).
- **An Authenticode signature by the project.** No budget and no free trusted route; a project root imported by each administrator would widen their trust beyond one file; where signatures are enforced, the organization's own counts.
