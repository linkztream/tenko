# Build economics plan: where the build time and the build disk go, and what to change

- Status: Proposed on 2026-11-12. Nothing here is built; the owner decides the questions of section 11 (BE-Q1 to BE-Q6)
- Date: 2026-11-12
- Scope: the cost of building and testing Tenko on the development workstation and on GitHub's hosted runners: the lead's merge gate, a builder's package, the integration test binaries, the disk the cargo target directories take, the CI jobs, the release build and the UI test suites. Written against `main` at `5a2b5a47`. The owner's priority order decides every trade-off (security, then performance, then usability, then features), and no measure here may weaken what the gate proves; where a measure changes what a check proves, the plan says so and asks
- Measured on: the development workstation (Windows 11, 32 logical processors, 64 GB of memory, the build disk an SSD; rustc and cargo 1.99.1 as `rust-toolchain.toml` pins, cargo-nextest 0.9.148), GitHub's hosted runners (`ubuntu-latest` with 4 cores, `windows-latest`), and the Linux environment inside Windows (WSL, Ubuntu 24.04) for what is said about Linux

Terms used below, explained once. **CI** (continuous integration) is the set of checks GitHub runs on every push (`.github/workflows/ci.yml`). The **gate** is the lead's script that applies the builders' commits onto `main` in a checkout of its own (it picks each commit, a **cherry-pick**) and runs every check before a merge. A **builder** is a session that builds one package of work in its own git worktree. **rustc** is the Rust compiler and **cargo** the build tool that drives it. A **target directory** is where cargo puts everything it compiles (`CARGO_TARGET_DIR`); a **profile** is a named set of compiler settings (`dev` for development and tests, `release` for the shipped binary). A **crate** is one Rust library or program, the unit cargo compiles; the **workspace** is the set of crates of this repository (19 under `crates/`). A **dependency** is a crate from crates.io; a **dev-dependency** is one used only by a crate's tests; a **procedural macro** is a crate that generates code at compile time (`serde`'s derives, `utoipa`'s attributes that describe the HTTP API as an **OpenAPI** document, `clap`'s argument parser); a **build script** (`build.rs`) runs before its crate compiles (here it generates the code of the **gRPC** remote calls between nodes with `prost` and `tonic`, and embeds the web **UI**, or a placeholder page, the **UI stub**, when `TENKO_UI_STUB=1`). **Features** are optional parts of a crate switched on at build time; `--all-features` switches all of them on, and two builds with different features compile the affected crates twice. A **unit** is one run of rustc in cargo's plan: one crate's library, its unit tests, one test binary, one build script. A **test binary** is the program cargo links for one test target: each file `crates/<crate>/tests/<name>.rs` is its own test binary (an **integration test**), and each crate's own `#[cfg(test)]` modules form one more (the **unit tests**). **Linking** joins the compiled pieces of a program into one executable; on Windows the linker of Microsoft's C++ tools (**MSVC**, `link.exe`) also writes a **PDB** file (program database: the symbols and debug information beside the `.exe`). **rlib** and **rmeta** are cargo's compiled library and its metadata-only form (what `cargo check` and `clippy` produce). Cargo decides whether a unit must be compiled again from its **fingerprint**, a record of the unit's inputs and settings. **Incremental compilation** (`CARGO_INCREMENTAL=1`) keeps a cache of the compiler's intermediate results to recompile an edited crate faster; it costs disk and is off in the gate and CI. **LTO** (link-time optimization) optimizes across crates when the release binary is linked: **fat** LTO does it over the whole program in one unit, **thin** LTO in parallel pieces; **codegen units** are the pieces one crate is split into for parallel code generation; `.text` is the part of a binary that holds its machine code. **LLVM** is the compiler back end rustc uses; **rust-lld** is LLVM's linker, which ships inside the Rust toolchain itself; **mold** is a third-party linker. **musl** is the C library of the static Linux release binary. **nextest** (`cargo-nextest`) is the test runner of the gate and CI: it runs every test in its own process and writes a **JUnit** report (an XML file with each test's result and duration). **clippy** is Rust's linter; **vitest** runs the UI's unit tests in **jsdom** (a browser imitation in Node.js), **Playwright** its end-to-end (**e2e**) tests in a real browser. **i18n** (internationalization) is the UI's translation catalog. A **runner** is a GitHub-hosted virtual machine that runs one CI job; **job-minutes** are the sum of all jobs' durations of a run, the **wall time** of a run is from its start to its last job's end; **rust-cache** is the CI action that restores compiled dependencies from an earlier run; a **shard** is one of several jobs that split a suite between them. A **jobserver** is the token pool through which cargo and rustc agree how many compilers run at once; on Windows it is a **named semaphore**, a counter of free tokens that any process can open by its name. **sccache** and **cargo-hakari** are third-party build tools (section 4). The **trust base** is all the code that must be trusted for the shipped binary to be what the source says: the compiler, the linker, every dependency and every build tool. **WSL** is the Linux environment inside Windows. An **SSD** is a solid-state disk; an **SMR** (shingled magnetic recording) hard disk is one whose random writes are slow; the disk that holds the repository and the worktrees is one. Sizes of files and directories are given in the binary units that `du` and `ls` print (1 MB = 1,048,576 bytes, 1 GB = 1,024 MB, written MiB where the project's own figures use that name); the binary-size figures of section 6 are decimal (10⁶ bytes), as the 2026-10-31 analysis gave them. Measurement numbers such as M23 are the project's own (the phase plans' series); this plan's builds are B1 to B7, its spikes (small trial changes on a copy) S1 to S6, its measures BE-1 to BE-15 and its questions BE-Q1 to BE-Q6.

## Summary

- **The gate** takes 30 minutes alone on the machine and 37 to 43 with builders compiling beside it, every compiling step then about twice as long. About 12 minutes of a run alone is compiling the workspace in five configurations that share almost nothing; the rest is running tests (nextest 5.6 to 7.6 minutes, Playwright 7.7 to 9.4, vitest 2.5 to 3.5).
- **A build** of all test binaries takes 267 s clean and 237 s after a change in `tenko-core`, at 16 jobs. 54 % of its work is the 266 integration test binaries (1,346 of 2,513 unit-seconds); only 16 % is the 453 dependency units. The last stretch of most rebuilds is `tenko-api`'s library followed by its unit tests, which wait for it because the crate names itself as a dev-dependency.
- **Disk**: one build writes 22.2 GB, 63 % of it PDB files. Cargo never deletes an old copy: the gate's test directory held 312 GB this morning, 228 GB of it in copies no run uses any more, and one day of 13 builders left 483 GB.
- **The spikes** (on copies, not merged): one test binary per crate cut `tenko`'s rebuild by 30 % and its test binaries' disk by 79 % (`tenko-api`: −95 %), with the same tests passing; rust-lld, already in the toolchain, cut the same rebuild by 27 %; removing `tenko-api`'s dependency on itself cut the rebuild after a change in it by 25 to 31 %; the linker argument `/DEBUG:NONE` drops the PDB files, 63 % of a build's disk, without changing the executables or the link time.
- **The machine**: a job pool that all sessions share works with cargo on Windows without installing anything (S5).
- **CI**: a push run takes 26.6 minutes on average, its critical path is the Rust job on Linux (22.6), one job repeats another's build, and the Rust tests could run on two runners.
- **Nothing to install** is recommended. Section 9 ranks fifteen measures with their baselines, section 10 groups them into five packages, and section 11 asks the owner six questions.

Compiling is about 12 minutes of a run alone on the machine and up to 21 with builders beside it (regenerate, two clippy runs, the test build, the fuzz check, the embedded build); running tests about 15 to 18 minutes (vitest 2.5 to 3.5, nextest 5.6 to 7.6, Playwright 7.7 to 9.4). The morning run was 6.6 minutes longer than the evening run, 5.4 of them in the nextest step (build 3.5 minutes longer, run 1.9 minutes longer), and the noon run 12.6 minutes longer, with every compiling step about twice as long (regenerate 3:00 against 1:30, clippy 2:30 against 1:00): that is what builders compiling beside the gate cost it. The runs merged different commits (8, 11 and 5), so part of the difference is the work itself; the steps that compile about the same thing each time grew with the load (Windows clippy 1:00 → 2:30, Linux clippy 0:54 → 2:01, fuzz check 1:07 → 1:37). A fourth run, 11:37 to 12:13 with three builder sessions beside it, took 35:30 (nextest ran 6,884 tests in 309 s).

**The run of the tests.** The JUnit report of the evening run sums 1,987 test-seconds over 6,832 tests in 269 binaries; at 6 threads that is 331 s, against 337 s measured, so the run is bound by the sum of the tests' own durations divided by the thread count. By crate: `tenko-auth` 490 s, `tenko` 489 s, `tenko-api` 399 s, `tenko-dns` 127 s, `tenko-ipam` 96 s, `tenko-store` 91 s; the longest binaries are `tenko-api`'s unit tests (297 s for 1,188 tests) and `tenko-auth::sign_in_lock` (131 s for 26 tests, which wait out real sign-in delays). The test lint's baseline counts 338 `sleep` and 322 `deadline` findings; the test-health work owns them, and each one removed shortens this step (section 9, measure BE-14). Raising `--test-threads` above 6 was tried on 2026-10-31 and made wait-bound acceptance tests fail under load (the lead's record of that day); it is not proposed here.

**Five configurations, little sharing.** The gate compiles the workspace in five configurations that share almost nothing:

1. the default-features dev build for the OpenAPI document (`cargo-target-verify`);
2. clippy with `--all-features`, in check mode (same directory; check artifacts are not build artifacts, B6 below reuses nothing from a build);
3. clippy in WSL for Linux, default features (its own directory, another operating system);
4. the `--all-features` test build (`cargo-target-verify-tests`);
5. the default-features build with the real UI (same directory as 4, but every crate whose features differ is compiled again, and `tenko-api`'s build script reruns because `TENKO_UI_STUB` changed: B5 below, 139 s at 16 jobs, 20 workspace units and 49 dependencies);

plus the fuzz package. What could be shared, and at what cost to what the gate proves:

- **One default-features build instead of two (1 and 5).** Run the OpenAPI regeneration in `cargo-target-verify-tests` with the stub, then let the embedded build recompile only `tenko-api` and `tenko` (56 s and 24 s in B5). It proves the same; it saves one default build per gate and that build's share of `cargo-target-verify`. Estimated gain about one minute per run (not measured: it depends on how much the previous run left warm).
- **One feature set for tests and the shipped server (4 and 5).** Not proposed: the end-to-end suite and the OpenAPI document must come from the shipped feature set (without `test-hooks` and `release-signatures`), and the tests must cover the optional features. Building the tests with default features only would stop testing `release-signatures`, `test-hooks` and the API client; that weakens the gate.
- **clippy from the build's artifacts (2 and 4).** Not possible: clippy needs its own check-mode compilation of every workspace crate. What can shrink is its dependency part (126 of 668 unit-seconds in B6), which a check build compiles once per directory and keeps.
- **`cargo nextest archive`.** Packs the built test binaries into one file that another machine or job runs without compiling. On the workstation it saves nothing (the gate builds and runs in one place); in CI it lets one job build and two others run (section 5).
- **The Linux clippy.** It is the same command CI's `Rust (Linux)` job runs on every push (`cargo clippy --workspace --all-targets --locked -- -D warnings`). Its value in the gate is a red main avoided (a fix commit and a 26-minute CI run) for 1 to 2 minutes; it stays. Its target directory is on C: under WSL's `/home`, which the builder rules forbid for everyone else (3.9 GB today); moving it to `/mnt/f/` costs WSL's slower file access to the Windows disk (not measured).
- **The gate's job count.** The gate runs `CARGO_BUILD_JOBS=6` although it is meant to run alone. The same kind of rebuild (after a change in `tenko-core`) took 237 s at 16 jobs here (B2) against 5:19 and 8:49 for the gate's test builds at 6 jobs; the commits and the load differ, so this shows the size of the effect, not its exact value. With the job pool of section 8 the gate could take more jobs when the builders are idle.

## 2. Where the time goes in a build

**How measured.** `cargo test --workspace --all-features --locked --no-run --timings` (the build the gate's nextest step starts, without the run) in a target directory of its own (`F:/cargo-target-build-econ`), with the gate's environment (`CARGO_INCREMENTAL=0`, `CARGO_PROFILE_DEV_DEBUG=line-tables-only`, `TENKO_UI_STUB=1`) and `CARGO_BUILD_JOBS=16`, from a copy of `5a2b5a47` on F: (`git archive`), one command at a time, never while the gate ran. A rebuild is measured by touching the crate's `src/lib.rs` (its modification time; with incremental compilation off, cargo then compiles that crate and everything that depends on it in full, which is what any edit costs). "Unit-seconds" are the sum of the durations of all units in cargo's timing report (a unit is one compiler run: one crate's library, its unit tests, one integration test binary, one build script): the CPU-side work, independent of the job count. What else ran is in the measurement log (section 12): from none to eleven compiler processes of other sessions at a time.

| # | Build | Wall | Units compiled | Unit-seconds |
|---|---|---|---|---|
| B1 | clean, all test binaries of the workspace | 267 s | 778 | 2,513: workspace 2,101 (325 units), dependencies 413 (453 units) |
| B2 | after touching `tenko-core` | 237 s | 315 | 2,104 (all workspace) |
| B3 | after touching `tenko-dhcp` | 167 s | 140 | 1,210 |
| B4 | after touching `tenko-api` | 151 s | 89 | 907 |
| B5 | `cargo build -p tenko`, default features, after B1–B4 in the same directory | 139 s | 69 | 267: 20 workspace units (222 unit-seconds) and 49 dependencies (45 unit-seconds) compiled again because their features differ |
| B6 | `cargo clippy --workspace --all-targets --all-features`, same directory | 128 s | 612 | 668: nothing reused from the build (check artifacts are not build artifacts) |
| B7 | `cargo test -p tenko --all-features --no-run` after B1–B6, the first `-p` build in the directory | 207 s | 79 | 865: 78 workspace units compiled again, because `-p` with `--all-features` switches on the features of that one package only (section 8) |

**What dominates.**

1. **The integration test binaries**: 266 units, 1,346 of the 2,513 unit-seconds of the clean build (54 %), median 4.5 s, longest 12.1 s; by crate `tenko` 432 s (60 binaries), `tenko-dhcp` 228 s (47), `tenko-api` 200 s (23), `tenko-ipam` 184 s (41). A test file is small; most of each unit is linking the code under test into one more executable and writing its PDB. In the `tenko-dhcp` rebuild they are 924 of 1,210 unit-seconds (76 %).
2. **`tenko-api`**: the library 65 to 68 s and its unit tests 90 to 96 s, the two longest units of every build that touches it. `tenko`'s library tests (65 s), `tenko-ipam`'s (50 to 55 s) and `tenko-dns`'s (31 to 46 s) follow.
3. **Dependencies**: 413 unit-seconds in all, compiled once per target directory and feature set; the largest are aws-lc-sys's build script (36 s, the C library of the crypto provider), `syn` (13 s), `openraft` (9 s), `utoipa-gen` (6 s). The procedural macros cost most where they are used, not where they are compiled: utoipa's `ToSchema` derive appears 916 times in 131 files of 8 crates (185 in `tenko-core`), serde's derives about 1,330 times; their generated code is compiled inside the workspace crates' units above.

**What the crate graph forces.** `tenko-core` (25,800 lines) is under 16 of the 18 other crates (all but the two empty placeholders `tenko-migrate` and `tenko-connect-windows`), so a change there rebuilds 2,104 of 2,513 unit-seconds (B2, 84 %). `tenko-dhcp` is not a leaf: it depends on `tenko-ipam`, `tenko-dns` and `tenko-scan`, and `tenko-api` and `tenko` depend on it, so a DHCP change rebuilds the API, the server and their 83 test binaries besides its own 47 (B3). `tenko-api` (108,700 lines with its unit tests, 23 integration test files) depends on 11 workspace crates; everything above it is `tenko`.

**The critical path** of B2 (from the report's start times): `tenko-core` 12 s → `tenko-dns`/`tenko-cluster` about 30 s → `tenko-ipam` 36 s → `tenko-api` library 65 s, ending at 144 s → `tenko-api` unit tests 92 s, ending at 236 s, the end of the build. The unit tests of `tenko-api` start only when its library is complete, because `crates/tenko-api/Cargo.toml` names the crate as its own dev-dependency (`tenko-api = { path = ".", features = ["client"] }`, to switch on the `client` feature for its tests); without that edge they would start with the library, at about 80 s. Spike S3 (section 3) removed that edge in a copy: in two pairs of rebuilds after touching `tenko-api`, run back to back, the build took 173 s against 232 s and 153 s against 221 s (−25 % and −31 %), and the unit tests started at 1.5 s, beside the library.

**Splitting `tenko-api`.** The library and its unit tests are 157 s of serial work at the end of almost every rebuild. A split along the route areas (DNS, DHCP, IPAM, auth, system; the 45 area routers of `routes/mod.rs`) into crates that compile in parallel would cut that span roughly by the share of the largest part, but it is a large change in the most-edited crate, it moves the `utoipa` registration the 2026-10-31 analysis wants to change anyway (section 6), and the self-dependency of S3 buys part of the gain for one line. This plan ranks the split after both (section 9, BE-15).

## 3. The 266 integration test binaries

**How measured.** The clean build B1 and its timing report (each integration test binary is one unit: compiling its test file and linking it); the files in `debug/deps` after B1 (one `.exe` and one `.pdb` per binary); and spikes on copies of the source outside the repository (never on a branch):

- **S1, one binary for `tenko`.** In a copy (`merged/`), `crates/tenko/Cargo.toml` gets `autotests = false` and one `[[test]] name = "all" path = "tests/all.rs"`; `tests/all.rs` declares `mod serve_support; mod cluster_support;` and, for each of the 60 files, `#[path = "<file>.rs"] mod <file>;`; in each file `mod serve_support;` becomes `use crate::serve_support;` (and the same for `cluster_support`). The files stay where they are. It compiled at the first attempt and lists the same tests as the original (170 tests, 28 ignored, `cargo nextest list`).
- **S2, the faster linker.** The same builds with `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_LINKER=rust-lld.exe`: LLVM's linker, which ships inside the pinned toolchain (`lib/rustlib/x86_64-pc-windows-msvc/bin/rust-lld.exe`), so nothing is installed.
- **S4, the PDB files.** Two settings of the profile did not shrink them: `strip = "debuginfo"` for the package left them as they were (22 MB for `acceptance_dns`, 486 MB for `tenko`'s unit tests), and `debug = false` for the package shrank them only to 20 and 427 MB. On Windows rustc passes `/DEBUG` to the linker whatever the profile says, and the PDB holds mostly the symbol table of all the code linked in, not the package's line tables. The lever that does remove them, the linker argument `/DEBUG:NONE` (`RUSTFLAGS="-C link-arg=/DEBUG:NONE"`), was measured once: after one build that compiled everything again (259.6 s: `RUSTFLAGS` is part of every unit's fingerprint), the rebuild of `tenko` wrote no PDB at all, against 62 PDB files of 2,061 MB in the comparable rebuild; the executables kept their size to the byte (`acceptance_dns` 11,470,848 bytes both ways); and the link time did not change (the 60 test binaries 449 unit-seconds, median 8.2 s, against 450 and 7.7 s; the rebuild 68.6 s against 64.4 s, within the day's spread). What a missing PDB costs, shown on a one-file crate with a failing assertion run under nextest with `RUST_BACKTRACE=1`: with the PDB the output names the thread, the location (`panicked at src\lib.rs:3:27`), the message, and a backtrace of eight frames with function names and `file:line` (`panic_demo::check at .\src\lib.rs:3`, `panic_demo::parse at .\src\lib.rs:1`, the test function, the standard library's frames); without it the thread, the location and the message are printed the same, and the backtrace is empty: every frame line is gone. The location comes from the compiled panic message, the frames from the PDB.
- **S3, `tenko-api` without itself as a dev-dependency.** The line `tenko-api = { path = ".", features = ["client"] }` removed from the copy's `crates/tenko-api/Cargo.toml` (with `--all-features` the `client` feature is on anyway; the lockfile changes by that one edge, so these builds ran with `--offline` instead of `--locked`), then the workspace test build after touching `tenko-api`, alternated with the original. Results in BE-5 below and in section 2.
- **S6, a deleted test binary.** One test executable and its PDB deleted from the target directory, then the build run again: does cargo notice and link it again? (Section 4, option 1.)

Every row rebuilds the crate `tenko` (its library, its binary, its unit tests and its integration tests) after touching `crates/tenko/src/lib.rs`, with the same features (`cargo test -p tenko --all-features --no-run`), 16 jobs:

| Today: 60 binaries, MSVC `link.exe` | 64.4 s (73.3 s for the first such run) | 450 (median 7.7 s per binary) | 547 | 715 MB exe + 1,564 MB PDB = 2,279 MB |

How firm these figures are: the baseline run started while six compilers of two other sessions ran, the S1 and S2 runs while none did, and runs of the same build varied by about ±20 % on the shared machine during the day. The library unit, which links nothing, took 29.0 s in the baseline, 32.5 s in S1 and 23.5 s in S2, which bounds the load effect; the unit-second figures of the test binaries (450 against 11.2 and 267) are far outside that band, the wall-time percentages less so. The 97 unit-seconds of S1 are the library (32.5 s), its unit tests (44.6 s), the binary (7.7 + 0.9 s) and the one test binary (11.2 s); today's 547 are the same four units (96 s together) plus the 60 binaries (450 s). With one binary the build's last unit is no longer a test binary but `tenko`'s own unit tests (44.6 s in this rebuild; 65 s in B1, where every crate compiled at once), so a further gain there needs the unit tests to compile faster, not fewer binaries.

**Extrapolation to the workspace, with its caveat.** In B1 the 266 binaries are 1,346 of 2,513 unit-seconds and about 16.4 GB of the 22.2 GB the build writes (one exe and one PDB each). `tenko`'s binaries are among the cheaper ones to link, because most of its tests start the server as a separate process (`CARGO_BIN_EXE_tenko`) instead of linking it; `tenko-api`'s 23 binaries each link the whole API (exe and PDB about 350 MB together, mean 8.7 s per unit) and gain more per binary; S1 on `tenko-api` measures that (rows below). If every crate's integration tests became one binary, and each merged binary linked in about the time of its largest file today plus a share for the code added, the integration binaries would cost about 200 instead of 1,346 unit-seconds and about 3 to 4 GB instead of 16.4 GB per build (estimate). The caveat: merging changes nothing in the run (nextest still starts one process per test); a crate whose tests are few and small (`tenko-connect-proxmox` and `tenko-connect-hass`, two files each) gains little; and the wall-time gain of a whole build is smaller than the unit-second gain, because the critical path runs through the libraries and their unit tests (section 2), not through the test binaries.

**S1 on `tenko-api`.** The same change in the copy (`tests/all.rs` with `mod dhcp_support;` and 23 `#[path]` modules; in 6 files `mod dhcp_support;` became `use crate::dhcp_support;`) compiled at the first attempt; under nextest 1,395 tests ran and passed, the same count as the gate's report for `tenko-api`. Disk: 23 binaries with their PDBs 8.0 GB, the one merged binary 111 MB plus a 310 MB PDB, 421 MB (−95 %). In B1 the 23 binaries took 200 unit-seconds (mean 8.7 s each); in the merged copy's first build the one binary took 16.5 s. A paired timing of `tenko-api`'s rebuild in both layouts was planned and did not fit into the machine's free windows; the two first `-p tenko-api` builds that were run (343 s and 220 s) each include a feature-set warm-up like B7 and are not comparable.

**Options.**

1. **Delete the old generations (no new tool).** After a gate run, keep for each test binary name the newest executable and its PDB, and delete the older copies of the same name (`<name>-<hash>.exe` and `.pdb` in `debug/deps`); leave everything else alone, in particular the procedural macros' `.dll` and `.pdb` files, which a run does not rewrite and whose loss would make cargo compile them and everything above them again. A small script of a few lines in the gate does it. S6 checks that cargo notices a deleted test binary and links it again: with `tenko-api`'s `dhcp_leases` test executable and its PDB deleted, the next `cargo test --workspace --all-features --no-run` compiled exactly one unit, that binary, and finished in 6.9 s; both files were back (98 MB and 276 MB). Measured effect on this morning's directory: of 248 GB of executables and PDBs, 20 GB belonged to the copies this morning's run wrote, so about 228 GB would go. For a builder: remove the directory at the end of the package, as the rules already say (the 483 GB were that rule not yet followed).
2. **A clean start for the gate's directories once a week** (`cargo clean`): one clean build, 267 s at 16 jobs, about seven minutes at the gate's 6.
3. **Fewer test binaries** (section 3): −79 % of the integration binaries' disk for `tenko`, −95 % for `tenko-api`.
4. **No PDBs for test binaries in builders' directories.** S4 (section 3): the profile settings do not shrink them; the linker argument `/DEBUG:NONE` removes them, leaves the executables as they are and neither costs nor saves link time; it would take the 63 % of a build that the PDBs are. Without a PDB a test's panic still names the thread, the file and line and the message, but a backtrace (`RUST_BACKTRACE=1`) is empty. The setting goes through `RUSTFLAGS`, which is part of every unit's fingerprint: a directory must always be built with the same value, or each change compiles everything again (as the linker switch of S2 did). So it fits a builder's own directory, set once in the builder's environment; the gate keeps its PDBs, so that a failure in the gate still has its backtrace.
5. **A shared compiler cache: sccache** (an install). It wraps every rustc call and serves a library from its cache when the inputs hash the same, across target directories. It would share the dependencies between builders (413 of 2,513 unit-seconds in a clean build) but not the links of the test binaries (it does not cache linking), and not the workspace crates, which differ per worktree; it does not shrink a target directory (the artifacts are still copied into it), it adds a cache directory of its own, and it adds to the trust base a program that wraps every compilation on the machine and could alter its output. Measured share it could save: at most the 413 unit-seconds of dependencies per clean build, and nothing in the rebuilds of section 2. **Not recommended.**
6. **One target directory shared by all builders (no new tool).** Cargo locks a target directory for the length of a build, so the sessions would build one after another: a build queue for free, and the dependencies compiled once. Against it: every `-p` build in a different feature set adds another generation of the workspace crates (B7 compiled 78 workspace units again for `-p tenko`), worktrees at different commits overwrite each other's fingerprints of shared crates, and a builder waits for another's whole build. **Not recommended**; the job pool of section 8 queues more finely.
7. **cargo-hakari** (an install, used at development time only; it wraps no compilation, it writes a crate). It generates a "workspace-hack" crate that makes every crate's dependencies use the same feature set, so `-p` builds and `--workspace` builds share dependency artifacts. Here the divergence is mostly in the workspace crates' own features, which hakari does not unify: in B5 the 49 dependencies built twice cost 45 unit-seconds, the 20 workspace units 222; in B7 the `-p` build compiled 78 workspace units and 1 dependency again. Its gain would be the 45 seconds; it adds a generated crate to the workspace and a check to CI. cargo's own setting for this (`resolver.feature-unification = "workspace"`) is still unstable in cargo 1.99.1 ("ignoring `resolver.feature-unification` without `-Zfeature-unification`"). **Not recommended now**; revisit when cargo stabilizes the setting.
8. **Another linker: mold** (an install). It links only Linux (ELF) programs, not Windows ones, so it would not touch the workstation's links at all; on Linux, rust-lld is already the default linker of rustc for `x86_64-unknown-linux-gnu`. **Not recommended**; for Windows, rust-lld (S2) needs no install.
9. **Fewer profiles and feature sets.** The gate builds the workspace with `--all-features` (tests) and with default features (OpenAPI, embedded build), CI with default features only. Both are needed: the e2e and OpenAPI runs must use the shipped feature set (no `test-hooks`, no `release-signatures`), and the tests must cover the optional features. What can go is the second copy of the default build: the gate builds it twice, once in each directory (section 1).

## 8. The builders' way of working, and sharing the machine

**The machine.** A 24-core desktop processor with 32 logical processors, 64 GB of memory (17.5 GB free at 08:50 with five sessions working, 20 to 35 GB during this plan's measurements), the build disk F: an NVMe SSD, the system disk C: another (61 GB free), and D:, which holds the repository and every builder's worktree, an SMR hard disk. The sources are read from D:, the target directories written to F:.

**What a builder compiles under the load rule.** A builder runs `cargo clippy -p <crate> --all-targets --all-features` and `cargo nextest run -p <crate> --all-features` for each crate it changed, with `CARGO_BUILD_JOBS=4` and `CARGO_INCREMENTAL=0`, in its own target directory. Three facts from the measurements:

1. **A `-p` build is a feature set of its own.** `cargo test -p tenko --all-features` right after the workspace build compiled 78 workspace units again (B7, 207 s), because `--all-features` with `-p` switches on the features of that one package only, while the gate's `--workspace --all-features` switches on all of them. Every builder's first `-p` build of a day is therefore close to a full build of the crates under it, and its artifacts are a generation of their own on disk (section 4). cargo's setting that would unify the features (`resolver.feature-unification = "workspace"`) is unstable in cargo 1.99.1.
2. **The edit-compile loop.** Not measured at 4 jobs or with incremental compilation: those runs (`-p tenko-dhcp`, an edit, at 4 and at 16 jobs, with and without `CARGO_INCREMENTAL`) were planned and dropped when the machine's free windows closed. What the other measurements give: a builder's first `-p` build is about the 865 unit-seconds of B7, which at 4 jobs take at least 216 s (865 / 4) and in practice longer, because 4 jobs leave the critical path waiting; after that, an edit redoes the edited crate, the crates above it in the `-p` set and their test binaries: 900 to 1,200 unit-seconds when the crate sits under `tenko-api` (B3, B4), most of it the test binaries, which is where BE-3, BE-4 and BE-13 help a builder most.
3. **What `CARGO_INCREMENTAL=0` saves.** Incremental compilation keeps the compiler's intermediate results per crate in `incremental/`: this morning the gate's two directories still held 8.9 GB and 20 GB of it from runs before the rule. Its gain for one crate's edit-compile loop was not measured here; its cost is disk per crate and per feature set, and it stays off in the gate and CI, where every build starts from other commits.

**Why the machine froze on 2026-11-11.** Five builders ran whole-workspace checks while the gate ran: 5 × 4 + 6 = 26 compiler jobs on 32 logical processors, each compiler of a large crate and each link of a large test binary taking gigabytes of memory (not measured per unit here; the PDB of `tenko`'s unit tests alone is 486 MB), on top of the test processes nextest starts (each acceptance test starts one or more servers) and the owner's own work. The job counts are per cargo process: nothing limits the sum across sessions, and nothing ranks the owner's interactive work above the builds.

**What would let six builders and the gate share the machine.**

1. **One job pool for the whole machine (no new tool).** cargo accepts a jobserver handed to it by its parent: `MAKEFLAGS=--jobserver-auth=<name>` (or `CARGO_MAKEFLAGS`), where on Windows the name is a named semaphore. A small PowerShell script (eight lines in the spike) creates the semaphore with N tokens and holds it; every builder and the gate start cargo with that variable, and then all their `rustc` jobs together never exceed N plus one per cargo process. Spike S5 (eight generated crates of 6,000 small functions each, about 3 s of compiling apiece, in a scratch target directory): `cargo build -j 8` alone ran 8 compilers at once and took 4.6 s; with a pool of one token (`MAKEFLAGS=--jobserver-auth=tenko-build-econ-pool`, and the same with `CARGO_MAKEFLAGS`) it took 10.7 s, as long as the same build with two jobs (`-j 2`, 12.8 s): one token plus the one every cargo process holds itself (cargo's timing report showed up to 3 units in progress, since it counts a unit from its start, including the moments it waits for a token); two such builds started together in two target directories with a pool of two tokens never ran more than 4 compilers between them (sampled every 2 s), against 16 without the pool. So cargo 1.99.1 on Windows honors a machine-wide pool across sessions, with nothing installed. What it does not cover: the test processes nextest starts, the linker's own threads, Docker builds in WSL, and node; the gate's nextest keeps its `--test-threads 6`.
2. **Lower priority for builders (no new tool).** A Windows process passes its priority class to the processes it starts, so a builder's shell started at "below normal" (`Start-Process -Priority BelowNormal`, or `start /belownormal` in a command prompt) runs its compilers and tests below the owner's applications and below the gate. It does not limit memory.
3. **A memory floor before a heavy command.** This plan's measurements waited, before each heavy command, until more than 20 GB of memory was free and the WSL virtual machine (where Docker builds run) used less than 2 CPU-seconds in 10 s. Docker Desktop's `com.docker.build.exe` cannot serve as the sign of a running build: it stays alive while idle (0.5 CPU-seconds in all between 09:47 and 10:02 today). The same check in the builders' and the gate's commands would keep two heavy phases apart.
4. **A build queue** (one heavy command on the machine at a time, a lock file). The simplest to reason about, and the slowest: today's load rule already keeps whole-workspace commands to the gate; a queue for `-p` builds would make builders wait for each other's whole builds. The job pool gives the same protection with finer grain.

Recommended: the job pool for every session including the gate, builders at below-normal priority, and the memory floor before every heavy command. The pool's size follows from memory, not from the processor count: the freeze of 2026-11-11 had 26 compilers at once and ran out of memory, and every cargo process adds one compiler of its own to the pool's N. With the gate and six builders (seven processes), N = 12 allows at most 19 compilers; start there, log the free memory beside each gate run, and raise N only while the floor of 20 GB holds. The load rule stays.

## 11. Questions for the owner

**BE-Q1. May the gate and the builders link test and development builds on Windows with `rust-lld`?**
- (a) Yes, in the environment of the gate and the builders only; release builds, CI and the Windows service smoke keep MSVC's linker. **Recommended**: 27 % off a crate's rebuild in the one paired measurement and about 40 % off each test binary's link, nothing installed (the linker ships in the pinned toolchain and is already rustc's linker on Linux), and the shipped binaries are untouched, so security and performance are unchanged and the builders' and the gate's time gains.
- (b) Yes, for every Windows build including the release, through `.cargo/config.toml`. Not recommended: the shipped Windows binary would change linker without a measurement of its own.
- (c) No.

**BE-Q2. One integration test binary per crate?**
- (a) Yes, for the 14 crates with more than two test files, the files left in place (`#[path]`), starting with `tenko-api` and `tenko`, every caller adjusted in the same change. **Recommended**: the largest measured gain in build work and disk (−82 % of the work of `tenko`'s rebuild, −79 % and −95 % of the test binaries' disk in the two crates measured), and nothing changes in what the tests prove (nextest keeps one process per test; the callers that use plain `cargo test` get name filters with a count check).
- (b) Only `tenko-api` and `tenko`.
- (c) No.

**BE-Q3. How should builders and the gate share the workstation?**
- (a) A machine-wide job pool (a named semaphore held by a small script, 12 tokens to start with), used by every cargo; builders at below-normal priority; a 20 GB memory floor before heavy commands; the load rule stays. **Recommended**: it caps what froze the machine without installing anything, and the gate can then use more jobs.
- (b) Priority and the memory floor only, no pool.
- (c) The load rule alone, as today.

**BE-Q4. No debug information (PDB files) in the builders' target directories?**
- (a) Yes: `/DEBUG:NONE` in the builders' environment; the gate keeps its PDBs, so a failure in the gate keeps its backtrace. **Recommended** (measured: no PDB written, executables unchanged, no time lost; 63 % of what a full test build writes): a builder's failing test still prints where it failed and why; only the frames of a backtrace are lost, and the builder can rebuild with PDBs for a debugging session.
- (b) Also in the gate.
- (c) No.

**BE-Q5. Install a build tool (sccache, cargo-hakari, mold)?**
- (a) No new tool. **Recommended**, from the measurements: sccache could share only the dependencies, 413 of 2,513 unit-seconds of a clean build and none of a rebuild, and would wrap every compilation on the machine; hakari's share is the 45 unit-seconds of dependencies built twice in B5, while the workspace crates' own features, which it does not unify, cause the rest; mold cannot link Windows programs, and rustc already links Linux ones with LLD. Each would add to the trust base for little.
- (b) sccache for the dependencies.
- (c) cargo-hakari.

**BE-Q6. Resume the parked binary package of 2026-10-31 (route registration without the document, `strip`, one crypto provider, the duplicate versions) now?**
- (a) Yes, as P4, after the three small packages. **Recommended**: it is a performance gain for every server start (CPU and memory) and a smaller trust base, the first two of the owner's priorities, and it also shortens the build of the crate on most critical paths.
- (b) Later, after 0.1.0.
