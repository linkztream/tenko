# Cluster update plan: one action updates the whole installation, one member at a time

- Status: Accepted on 2026-11-12: the owner took the recommendation of every question of section 8, CU-Q1 to CU-Q12. It replaces S3-Q14 (a) of [slice-3-plan.md](slice-3-plan.md), "the UI installs nothing on a cluster", by the orchestrated update described here, which S3-Q14 itself left to be revisited. The packages wait for the changes named in WP19.1 and for the order section 5 gives with the cluster recovery plan
- Date: 2026-11-12
- Scope: OPS-08 (rolling upgrades) and the cluster half of OPS-24 (in-app updates), plus a general rule for new behavior that an older member cannot read. Written against `main` at `6595569b`. Requirement IDs refer to [REQUIREMENTS.md](../REQUIREMENTS.md), toggles (TGL) to [SECURITY-PROFILES.md](../SECURITY-PROFILES.md). Exit criteria, measurements and risks continue the project's series from E121, M86 and R197 (the dashboard history plan ends at E120, M85 and R196); the slice number is the lead's, and this plan calls it Slice 19 with packages WP19.0 to WP19.8, provisionally

The owner's request, in short: an installation should run one version of the software, so one action updates every member to one version, one member at a time, never all at once, and it stops by itself the moment something is not right. The second half: behavior that an older member cannot read switches on only when every member runs a version that knows it, as the data format already does.

Terms used below, explained once. A **member** is any process of the installation that runs the `tenko` binary: a **controller** (a member of the replicated store, either a **voter**, which counts toward the **quorum**, the majority of voters that must agree before a write is committed, or a **learner**, which receives the data but does not vote) or an **enrolled node** (a process enrolled with a certificate that serves a role such as `probe`, and later `dns` or `dhcp`, without holding the store). The **leader** is the voter that orders the writes; a **step-down** hands leadership to another voter. A **run** is one execution of the update action. A **gate** is the list of checks that must hold before the run touches the next member. **Probation** is the existing period after an update in which a new version must become ready or switch itself back. To **drain** a member is to take it out of client traffic before it stops. A **soak** is a period in which an updated member must stay healthy before the next one starts. The **point of no return** is the moment after which the old version can no longer read the data, so going back needs a backup. The **installation level** (section 2.8) is a stored number that says which new behavior every member can read.

Other terms of the trade, in a few words each. **Raft** is the agreement protocol the controllers use to keep one ordered log of writes. A **linearizable** read sees every write committed before it started. A step is **idempotent** when running it twice has the effect of running it once; an **idempotency key** makes a second submission of the same request return the first one's result. A **compensation** is the code that undoes a finished step when a job rolls back. A write is **fenced** when it carries the leader's epoch and is refused if that leader has been replaced. The **cluster port** is the port on which members talk to each other with **mutual TLS** (both sides prove themselves with a certificate of the installation). **Air-gapped** means the installation never contacts the internet. An **SOA** query asks for the record at the top of a DNS zone, which every server of the zone answers. A **stub resolver** is the small DNS client in every computer, which asks the servers it was given in turn. **Anycast** and **VRRP** are two ways to move clients to a surviving server: the same address announced from several places, or one address that moves between machines. **p99** is the value that 99 of 100 measurements stay under. **musl** is the C library of the static Linux binary that the project ships. A **golden test** compares output with bytes saved in the repository. A **fuzz hook** feeds a parser random input to find crashes. A **junction** is the Windows form of a directory link. `ExecStartPre=` is the line of a systemd unit that runs a command before the service starts; **SCM** is the Windows Service Control Manager. The **supply chain** is the path a binary takes from its build to a running machine.

## 1. What exists

**1.1 The update of one controller** ([upgrades.md](../upgrades.md) section 8, `crates/tenko/src/upgrade/`). An install is a job of kind `sys.update` in the job engine, pinned to the controller that installs (`spec.node`), with the group limit 1 and 60 minutes (90 with the backup). Its steps: `sys.update.backup` (optional, 30 min), `sys.update.fetch` (30 min, inside the pinned release location), `sys.update.verify` (size and SHA-256 against the manifest, 5 min), `sys.update.check` (the new binary's `upgrade version`, then a copy of the store and the new binary's `upgrade check --disposable --json` on it, 13 min in the code, where section 8.5 of upgrades.md says 12; only the verdicts `current` and `migration_needed` pass) and `sys.update.switch` (the attempt record `attempt.json` in state `restarting`, `previous` and `current` moved). Every step is idempotent and has a compensation, so a failed job leaves the running server unchanged. The process that submits the job writes the attempt record `installing` on its own disk, and on success a task of that same process (`follow`) waits 2 s and requests a restart; the server stops gracefully and exits with status 12, and the service manager starts the binary that `current` names. The new version runs on probation: it is confirmed when its start returned (the listeners are up and the store is open); a failed start step, a second start or a watchdog after `updates.ready_timeout_secs` (180 s by default) switches it back with exit status 12, and the previous version restores the pre-migration copy when the new one had migrated. The outcome is audited once (`sys.update.confirm`, `sys.update.rollback`). Nothing confirms more than a successful start: the probation does not look at catch-up, at the roles or at the cluster.

**1.2 A cluster today.** The install is refused with 409 `update.install_blocked`, reason `cluster`, when the store has more than one voter (learners and enrolled nodes do not count, so a single voter with learners or probes installs alone and leaves them at their version); the check, the notice and the notes still work. The decision is S3-Q14 (a) of 2026-10-10: an install job on one member would switch a binary without knowing the state of the others, orchestration across hosts is a new supply-chain path with partial failures on several machines, and the manual procedure is safe; orchestration was to be revisited. The manual procedure ([upgrades.md](../upgrades.md) section 7.7) is: `tenko cluster upgrade-check` with the new binary, a backup, then each member in the printed order (learners, the voters that follow, the leader last after `tenko cluster step-down`), each stopped, checked, switched and started, and the next only when `tenko cluster members` shows the new version, a lag near 0 and recent contact, and `tenko health` reports it ready. `upgrade-check` (`crates/tenko/src/cluster/upgrade.rs`) tests that the new binary speaks every member's Raft wire version, shares a protocol major with each, and knows the stored data format; it computes the order (learners, followers, leader, by node id). It does not check health, lag or quorum.

**1.3 Two versions at once rest on four rules** (section 8.10): the order above with one member down at a time; a shared Raft wire and protocol major (a new Raft wire needs a planned stop of the whole cluster); the data format kept until every voter's binary knows the new one; and the way back by switching the link until the leader migrates, by backup after. The data format rule is `crates/tenko/src/upgrade/rolling.rs`: every member writes a member record after each start (`Peers::announce`, audited as `cluster.member.announce`) with its version, protocol majors, Raft wire and the formats its binary knows; the leader service `upgrade.migrate` looks every 10 s and migrates, fenced by the leader epoch (a number that changes with every leader, so a deposed leader's write is refused), once every voter's record lists the new format; a voter without a record blocks. `GET /system/status` shows `data_format.pending` with the voters that block. A joining controller whose binary does not know the stored format is refused (`cluster.join.format_newer`). There is no notion of an installation version or of a lowest version of all members; other behavior that an older member cannot read is handled feature by feature (the known devices of [SECURITY-PROFILES.md](../SECURITY-PROFILES.md) work only on the controllers that know them; [ADR 0031](../adr/0031-the-lease-table-is-the-observation-source.md) says the members upgrade together because an earlier binary cannot decode a lean history row). The store's write model ([ADR 0011](../adr/0011-store-write-model.md)) makes additive changes safe, since values are CBOR with defaults on new fields; a change being merged now makes a member that cannot apply a committed write stop at that entry, report it in the status and answer not ready, instead of going on.

**1.4 Enrolled nodes.** The only role that runs as an enrolled node today is `probe`; `dns` and `dhcp` run inside the controllers and read the store directly. A standalone `dns` or `dhcp` node, fed by node sync into a node store, and the DHCP failover pair are Slice 12 ([ha-plan.md](ha-plan.md): the nodes are WP12.1 and WP12.2, the pair's stored row WP12.0 and its protocol, with the paused state of a restarting partner, WP12.3; all open). A node's registry record (`crates/tenko-cluster/src/model.rs`) holds its roles, `last_seen` (written at connect, at disconnect and at most every 5 minutes), the version from its heartbeat (every 10 s by default) and the agreed protocol major; the last heartbeat itself is held only in the memory of the controller that holds the node's connection. The record has no operating system or platform field, and the controllers have none in the member record either. Commands go to nodes through the table `cluster.node_commands` and the stream `Commands.Subscribe`; a node answers an unknown command kind with `rejected`; the kinds today are `scan.*` for probes and the `dns.*` and `dhcp.*` commands of the roles that run in the controllers. Nothing updates a node's binary: there is no update command, no update logic in `crates/tenko/src/node/`, and the controller serves no release files. The only version checks for nodes are the protocol major at enrollment and in the handshake, and [cluster.md](../cluster.md) section 4.2 already says "upgrade controllers first": a controller that introduces a new protocol major keeps the old one for one release. The product stores no grouping of nodes that back each other up; Slice 12 brings the pair as a stored row (DHCP) and the zones a `dns` node serves.

**1.5 The job engine** (`crates/tenko-jobs`). Jobs, their steps and transitions live in the replicated store. The leader runs every unpinned job as the leader service `jobs.runner`, and every write it makes carries the fence of its epoch; a deposed leader's drive ends at its first write. Every controller also runs a runner for the jobs pinned to it, under a lease; the leader's runner takes only unpinned jobs and a pinned runner only its own node's, so a job pinned to a member that is gone waits for it and is never run elsewhere (and its time limit is not enforced while nobody runs it). After a restart or a change of leader, jobs are resumed: a step found running runs again when its handler is idempotent, otherwise it fails with `jobs.step.interrupted`. A step can finish, skip, ask a person to act (`Manual`) or wait for an observation with a deadline (`Wait`); a passed deadline, a failed step, the job's own time limit, an interrupted step that is not idempotent and a cancel (`POST /jobs/{id}/cancel`) all roll the job back, which compensates the finished steps in reverse. What the engine lacks for this plan: a pause, a stop that waits for an operator's choice between going on and going back (a `Manual` task today is one confirmation, not a choice), and a guarantee of one job of a kind across the whole cluster (the group limit counts per runner). Every transition is audited (`jobs.job.*`, `jobs.step.*`).

**1.6 Readiness and catch-up.** `GET /health/ready` answers 503 while the server starts or stops, while the store is shut down or when a local read fails; it does not check that the member has caught up with the leader. At start a controller waits up to `cluster.catch_up_timeout_secs` (120 s) for a read through the leader, then starts "isolated". The leader knows each member's replication (`matched`, `lag_entries`, `last_contact_ms` in `GET /cluster/members`), and promotion already defines "caught up" as at most `promote_lag_entries` (100) behind with contact in the last 10 s. `GET /cluster/members` and the status carry the quorum state (`single`, `healthy`, `electing`, `isolated`) and the leader. Step-down hands leadership to the most caught-up voter in contact; writes wait meanwhile rather than fail. Per-role status (`GET /nodes/{id}/dns`, `/dhcp`) answers only for the member that serves the request; nothing sends a test query or a test lease to a member.

**1.7 The cluster lab** (`deploy/compose/lab-cluster/`): three controllers behind HAProxy, which checks `GET /api/v1/health/ready` every 2 s, takes a controller out after two failed checks, and retries a failed connection on another controller (`retry-on conn-failure`, `option redispatch`); two probes; a driver container with `dig`, `curl` and `python3`. The smoke runs an open-loop writer at 100 writes a second and reports failed writes against a fault time. A mixed-versions run exists by hand (`TENKO_IMAGE_1` to `_3`), and `crates/tenko/tests/cluster_mixed_versions.rs` runs the order in-process with an older binary given in `TENKO_OLD_BIN`. The lab runs the product's image, and an install from the UI is refused in a container (`container`), so the lab cannot exercise an in-app update today.

**1.8 A related fact this plan designs around.** On an installed Linux node, the unit's start-up step (`ExecStartPre=`) runs the binary the installer placed, which after an in-app update is an older version than the one that runs. A separate change, planned now, makes a node run one version only. Section 2.15 says what this plan needs from it.

## 2. The design

### 2.1 The action

An administrator chooses a target version and starts one run. The run updates every member of the installation to that version, one member at a time, and before each member checks that the previous one is back, caught up, serving and past its probation, and that the cluster can lose the next member without losing its quorum or a role. When any check fails or a time limit passes, the run halts: it starts no further member and touches nothing more; the operator sees which member, which check and why, and chooses to retry, to take the updated members back, or to end the run. When every member has passed its gate, the run finishes: the data format migration and the raise of the installation level (section 2.8) happen at that one moment, which is the point of no return. A single install on one member of a cluster stays refused, and the refusal now covers every installation with more than one member, a single voter with learners or enrolled nodes included: once there is more than one member, only a run installs.

### 2.2 Scope and order

1. **Controllers first: learners, then the voters that follow, the leader last after a step-down.** This is the order `upgrade-check` prints and the manual procedure follows, with the same reasons: a learner's restart costs nothing; a follower's restart leaves the quorum in place; the leader goes last so that leadership moves once, to a voter that already runs the new version (the run names that voter as the step-down's target, the one with the most entries among the updated voters, rather than letting the step-down pick any). With a single voter there is no step-down: its restart pauses writes as a single node's update does today, and the run resumes when it leads again (CU-Q4). Within each group the order is by node id, so a run is predictable and a resumed run continues where it stopped.
2. **Then the enrolled nodes, one at a time** (probes today; `dns` and `dhcp` nodes once Slice 12 has them). Controllers first because (a) the protocol rule of [cluster.md](../cluster.md) section 4.2 already requires it: a newer controller speaks the old protocol major for one release, a newer node is refused by an older controller when the major changed; (b) the controllers drive the run and serve the release files (section 2.9), so the code that updates the nodes is the new version's, already proven on the controllers; (c) a node that fails its update keeps serving at the old version beside up-to-date controllers, which the protocol rule covers, while the reverse order would leave old controllers commanding new nodes.
3. **Strictly one member of the whole installation at a time.** A member is "away" from the moment the run drains it until it has passed its gate; at no moment are two members away. This is the only mode of the first release (CU-Q3).
4. **Members that back each other up.** For controllers, the gate's quorum rule covers the store (section 2.4, check 9), and the roles a controller serves in-process (DNS, DHCP) are served by the others meanwhile, which the gate verifies (check 10). For enrolled nodes the product knows today no grouping; Slice 12 adds two: the DHCP pair (a stored row naming both partners) and the zones a `dns` node serves. The rule: a member may go away only when every member that shares a pair or a served zone with it is ready and serving. When the product cannot tell what a member's partners are, it treats every other member with a common role as a partner, so the rule above still holds with strictly one member away. A member whose role no other member serves (one DNS server, or a single voter, whose restart pauses writes) is named in the preflight with the expected outage ("DNS answers stop for about 20 s on node X while it restarts"), and the run starts only after an explicit acknowledgment (CU-Q4). A cluster of exactly two voters is refused: every restart of either voter loses the quorum, so the run could not even record its own progress; the preflight says to add a third voter or to remove one first.

### 2.3 Before anything changes: the preflight

The run's first step checks, and refuses with one list of every reason:

- Every member is known, reachable and healthy: every voter and learner in contact and caught up, the quorum `healthy`, a leader, every enrolled node connected; no member's store has stopped applying; no install, attempt or other run in progress.
- The new binary fits every member, by the rules of `upgrade-check` (Raft wire, protocol major, stored format). The leader downloads and verifies the new binary for its own platform first and runs its fit logic as it runs its dry run today: the new binary decides whether it fits, with the member records given as input (a new form `tenko upgrade fit --json`, which reads the records from a file the running server writes into the check directory).
- A release file exists for the platform of every member (members announce their platform from WP19.0), and in an air-gapped installation each needed file has been uploaded.
- Every Linux member reports that its start runs only binaries of the layout (section 2.15).
- The backup rule of section 8.12 of upgrades.md, once for the run (CU-Q9).
- No member is in a container (CU-Q11), and every member runs from the layout under a service manager (the existing `layout_missing` and `unsupervised` reasons, now asked of each member).
- The installation runs at most two versions, the target is newer than or equal to every member's, and members already at the target pass their gate first and are then skipped. This lets a run finish an upgrade that was begun by hand.

The preflight prints the order with each member's expected outage, as `upgrade-check` prints it today.

**Membership holds still during a run.** While a run is active and not halted, joins, promotions (including the automatic promotion of learners, `cluster.auto_promote`), removals and enrollments are refused with 409 `update.run_active`, because they change both the order and the quorum the gate counts on. While a run is halted they are allowed (an operator may need to remove a dead member), and Retry then runs the preflight again and recomputes the remaining order.

### 2.4 One member, and the gate before the next

For a **controller**, the leader submits the existing `sys.update` job pinned to that member, with the run's release (from the source or from the leader, section 2.9). The member's pinned runner runs fetch, verify, check (the dry run on a copy of its own store) and switch, unchanged. The submission does not go through today's install path, which writes the attempt record on the submitter's disk and has the submitter restart itself on success: that would restart the leader together with the member. What is new on the member: a follower of every `sys.update` job pinned to it, whoever submitted it, which writes the member's own attempt record and requests the member's restart on success (today only the submitting process does), and no process ever restarts for a job pinned to another member; a **drain** before the restart (the member answers `GET /health/ready` with 503 `draining` for `updates.drain_secs`, 5 s by default, so that a load balancer and an anycast or VRRP health check take it out of rotation before it closes its listeners); and the attempt's outcome written to its member record (`update: {job, state}`), so the leader sees the confirmation in the store and not only in the member's local file and audit record. The steps of an install pinned to a member never run on another member: the engine's runners already keep to their own jobs, and each step also checks that it runs on `spec.node` and fails otherwise, with a test of both. Since a pinned job whose member is gone is run by nobody, its own time limit does not fire; the run's member step keeps its own deadline from the submission (check 1) and halts when it passes.

For the **leader**, the run first checks that every other controller runs the target and has passed its gate, then asks for a step-down to a named, updated voter. The leader service that drives the run moves with leadership (section 2.7); the new leader, which already runs the new version, continues the same step and treats the old leader as a follower.

For an **enrolled node**, the controller that holds the node's stream sends the command `node.update` with the version, the digest and where to fetch the file (section 2.9); the node runs the same steps locally (fetch from the controller, verify, a dry run against its own data, switch, drain, restart, probation) and reports the outcome in its heartbeat and in the command's report. Since a node's heartbeat lives only in the memory of the controller that holds its connection, that controller writes the node's update state and its gate checks into a row of the run in the store, which the leader reads.

**The gate.** Each check, whether it exists today, and its limit. A check that passes moves to the next; the next member starts only when all have passed in one evaluation (the leader reads the controllers' records and the nodes' rows of the run linearizably in one pass).

| # | Check | Exists today? | Limit |
|---|---|---|---|
| 1 | The member's install job succeeded (fetch, verify, dry run, switch) | Yes: the job's state | The job's limit (60 min, 90 with a backup), counted by the run from the submission |
| 2 | The member restarted into the target version: its member record (controllers) or heartbeat (nodes) announces it | Yes: `cluster.member.announce`, the heartbeat's `version` | `ready_timeout_secs` + 120 s from the switch |
| 3 | Its probation is confirmed: the record says `confirmed` for this job | New: the outcome in the member record (today only the local `attempt.json` and the audit) | Same as 2 |
| 4 | It is ready: `GET /health/ready` answers 200 | Yes; the leader asks through the cluster port (new call, `Peer.Ready`) | 60 s after 3 |
| 5 | It has caught up: at most `promote_lag_entries` (100) behind the leader, contact in the last 10 s, and its applied revision at or past the revision the leader committed when the member confirmed | Yes for the first two (promotion's rule); the revision comparison is new | `catch_up_timeout_secs` (120 s) after 4 |
| 6 | Its store has not stopped at a write it cannot apply | With the change being merged (section 1.3) | Checked at once |
| 7 | It serves its roles: for `dns`, the member answers a query for the SOA of a zone it serves, sent to its own listener and reported with the status; for `dhcp`, the role's workers run and the leases it holds are loaded (and, once Slice 12 has the pair protocol, the pair is back in its normal state); for `probe`, its heartbeat and configuration revision are current | Partly: the per-role status exists for the local member only; the self-query and its report through the cluster port are new | 120 s after 5 |
| 8 | It stays good for the **soak**: checks 4 to 7 hold, and its start count does not rise, for `updates.soak_secs` (120 s by default, CU-Q6) | New | The soak itself |
| 9 | The cluster can lose the next member: the quorum is `healthy`, there is a leader, and every voter other than the next one is in contact and caught up; before the leader's turn, also every other controller runs the target and has passed its gate | Yes for the quorum and the replication figures; the versions from the member records | 120 s |
| 10 | Every partner of the next member (section 2.2, point 4) is ready and serving | New (uses checks 4 and 7 of the partners) | 120 s |

A limit that passes, or a check that fails outright (a refused dry run, a switch back, a stopped store), halts the run (section 2.5). The times are settings under `[updates]` with these defaults, so an operator with a slow migration can lengthen them; the run records the values it started with.

### 2.5 Stopping and going back

| What happens | What the member does (exists) | What the run adds |
|---|---|---|
| The download, the verification or the dry run fails | The job compensates: nothing on the member changed | Halts before the member was drained. Nothing in the installation changed |
| The new version does not start, crashes, or misses its probation | It switches itself back and restarts the previous version, restoring its pre-migration copy if it had migrated | Waits until the member announces the old version, is confirmed back, ready and caught up (checks 2 to 7 against the old version), then halts. The installation is at the old version |
| The member comes back neither new nor old within the limits | Nothing more it can do (the residual risk of section 8.6 of upgrades.md) | Halts with "member unreachable". The quorum and the roles still hold, because the gate checked that the cluster could lose this member (except for a member acknowledged under CU-Q4). The status names the manual recovery (section 9.7 of upgrades.md) |
| A later check fails (not caught up, not serving, a failed soak) | The member is confirmed and runs the new version | Halts. The operator decides whether this member goes back |
| The leader changes, or the member driving the run restarts | | Continues the same run (section 2.7) |

**What must never happen**, each a test in section 3: a second member drained while the first has not passed its gate; the leader restarted for another member's update; the leader updated while any other voter is behind or not updated; the migration or the level raise before every member passed its gate; a second run; an install step executed on another member than the one it is pinned to; a take back that nobody chose (by a time limit, a failed step or the generic job cancel); a member taken back after the point of no return.

**Resting at two versions.** A halted run stays a run, with its state and the reason, until the operator acts. The status of every member carries the warning `update.run.halted` (with the member, the check and the code), the Cluster page shows the run and each member's version, `tenko cluster update status` prints it, and the installation level and data format stay where they were, so the members of the new version behave as the old version: nothing is written that the old members cannot read (section 2.8).

**The operator's choices on a halted run.**

- **Retry**: the run runs the preflight again, evaluates the gate of the halted member again (or submits a new install for it, when it went back; the install's idempotency key carries the attempt number, so a retry is a new job and a resumed step is not) and continues. For a cause outside the product (a full disk, a network problem), fix it and retry.
- **Take back**: the members this run changed go back to the previous version, in the reverse order, one at a time, each through its `previous` link (no download, no dry run: the previous version is installed and its data format is the stored one), each with the same gate. When the current leader is one of them, it steps down first to a named voter that already runs the previous version, as the leader steps down to an updated one on the way up. Members that were at the target before the run and were skipped are not touched. Possible only before the point of no return; afterward the way back is the backup (section 7.7 of upgrades.md).
- **End here**: the run ends and leaves the installation at two versions, with the warning `update.versions_mixed` until it is at one version again (by a new run or by hand).

Pause (section 2.11) is not a halt: the current member completes its gate, then the run waits.

**Only the operator takes members back.** The job engine rolls a job back by itself on a passed deadline, a failed step, the job's own time limit or a cancel; for the run each of these becomes a halt. The run's job has no overall time limit (its member steps have the gate's limits), its waits end in a halt and not in a rollback, the generic `POST /jobs/{id}/cancel` refuses a run and points to the run's own routes (which need an administrator and a fresh sign-in, section 2.10), and the compensation of a member step runs only when an administrator chose Take back. Each compensation also refuses to run once the stored data format or the installation level is newer than the previous version knows.

**The point of no return.** Today the leader migrates the data within 10 s of the last voter announcing the new format, which during a run would be the old leader's first start, before its probation. So from the start of a run the automatic migration (and the raise of the level) is held, and the hold stays until a run finishes: the run's last step migrates and raises, after the last member's gate (CU-Q5 asks whether that step waits for the operator's word). The finish has no compensation: it is the point of no return, and if it fails halfway (a migration commits in several batches) it halts with the step resumable, never with a take back. When a run ends without finishing (End here, or after a Take back), the hold remains, so the installation does not migrate behind the operator's back; the next run's finish releases it, or, after a manual procedure, the administrator's "Release hold" (with a fresh sign-in, audited), which first checks that every member runs a binary that knows the new format and is ready and caught up. An installation that never ran a run keeps today's behavior.

### 2.6 What happens to clients during a run

Writes: a follower's restart does not touch the write path; the leader's step-down makes writes wait, not fail; the drain takes each member out of a load balancer before it stops, so a client behind one sees no refused connection. DNS: each member's listener answers until the drain ends; a stub resolver with two server addresses moves on at its timeout; an anycast or VRRP setup withdraws the member during the drain through the readiness route. DHCP in the controllers: a client whose server restarts retries; with Slice 12's pair protocol, the restarting partner announces its pause and the other serves every client. Sections 3 and 4 measure the first two.

### 2.7 Who drives the run

The run is one job of the job engine, kind `sys.update.cluster`, unpinned, so the leader's runner drives it, and every write it makes is fenced by the leader's epoch. Its steps are fixed at submission: the preflight, the backup, the staging of the release files, one step per member in the order of section 2.2, and the finish. Its state is the job's record in the replicated store plus one row `sys.update.run` that holds the target, the settings it started with and the halt reason; the row is created in the same write as the job with the condition that no run is active, which makes "one run" a property of the store, not of a runner.

Every member step is written to be re-entered: it reads where its member stands (the pinned install job and its state, the member's record, the gate) and continues from there; it never submits a second install job for its member within one attempt (the install job carries the run's id, the member and the attempt number as its idempotency key). So when the leader changes in the middle (a crash, a network fault, or the planned step-down before the leader's own update), the next leader's runner resumes the same job at the same step, and the deposed leader's next write is refused by the fence. A step that waits does so with the engine's `Wait` on an observation (the member record, the job, the gate) with the gate's limit as deadline; what the engine has to gain (WP19.1):

- a halt: a step outcome that holds the job and offers the operator retry, take back or end, instead of rolling back on a passed deadline, a failed step or a time limit (section 2.5);
- a job kind that the generic cancel refuses, and a step that has no compensation (the finish);
- a pause between steps;
- the follower of pinned `sys.update` jobs on every member (section 2.4).

The leader's own update is the step after its step-down; at that moment another voter, already updated, leads and drives. Every member including the one that started the run restarts during it, and the run survives each restart because its state is in the store and its steps are re-entrant. The audit records are the engine's plus the run's own (section 2.10).

### 2.8 The second half: switching new behavior on

**The rule.** Anything an older member cannot read is written only when every member runs a version that knows it: a data format, a new variant or a field with meaning in a replicated write, a new table that readers must understand, a new kind of command to a node, a new message between controllers. The data format already follows this rule for stored data, through the migrator and its follower (section 1.3). The plan generalizes it into one stored signal so that a builder has one place to ask "may I write this yet".

**The installation level.**

- Each binary has a `LEVEL`, a whole number, and a table of levels with what each switches on and the version that brought it, compiled in like the format registry. A release that adds such a behavior raises `LEVEL` by one; a release that adds only things old members ignore safely does not.
- Each member reports its `LEVEL` with its version: controllers in the member record, enrolled nodes in the heartbeat and the registry.
- The installation's level is one row in the replicated store. The leader raises it to the lowest `LEVEL` of all voters, learners and enrolled nodes that are not removed, fenced by its epoch and audited (`cluster.level.raise`); outside a run it does so in the same leader service and on the same tick as the data format migration; during a run only at the run's finish. It never goes down.
- A builder asks `level.allows(Level::X)` (a read of that row from the view the write is planned on). A write that needs a higher level is refused with 409 `cluster.level_required`, with the level, the current level and the members that hold it back; a producer of node commands or controller messages does not send the new kind until allowed. A member whose binary knows a level below the stored one is refused at join and at start, as a newer data format is, so an old binary cannot come back into an installation that writes what it cannot read.
- An enrolled node that is offline holds the level back; the status names it, and removing the node or bringing it back unblocks the raise (CU-Q10).
- A single controller without enrolled nodes raises its level at start, as it migrates; with enrolled nodes it waits for them like a cluster.
- The data format stays its own number, because migrations convert stored data; the level says what may be written. The finish raises both in one step.

**What each guarantees.** The run alone brings the installation to one version, one member at a time, and makes the time at two versions short; but during that time a new member could write something the old ones cannot read, and an old member would then stop at that entry (the change of section 1.3): no divergence, but a member lost in the middle of the update. The level alone makes two versions safe for as long as they last, because the new behavior stays off; but nothing brings the installation to one version, and a forgotten member holds every new behavior back. Together: the run moves the members, the level stays down until the last member has passed its gate, and the new behavior switches on at the finish, when the whole installation reads it. The stop at an unreadable entry remains as the backstop for a check that a builder forgot.

What remains outside the level: whether an old binary ignores an unknown field or refuses it is a separate rule about the encodings; the level is how a writer knows that no reader is old.

### 2.9 Where the binaries come from

- **The leader stages the release once per platform** (CU-Q7): from the release source, inside the pinned release location and with every check of section 8.11 of upgrades.md, or from the files an administrator uploaded (air-gapped, or under Hardened, which takes uploads only). The staging step then copies every platform's file to every controller, each verifying it, before any member is touched, so that whichever controller leads later (after the planned step-down, or after a fault) can serve every member and node. The staged files are removed when the run ends.
- **Members fetch from the current leader over the cluster port** (mutual TLS with node certificates, new call `Release.Fetch(version, platform)`), into their own `updates/<version>/`, bounded by the manifest's size. Each member verifies size and SHA-256 against the manifest entry that the run names in the store, and the signature when signed releases exist; a file that does not match is removed and the member's job fails. A member never needs the internet, and an air-gapped installation uploads each platform's file once.
- **The manifest** is the one the leader fetched or that was uploaded, stored and replicated as today. An install from the source never takes its file from an uploaded manifest, as today.
- **Mixed operating systems**: each member gets its platform's file; the preflight refuses a run for which a platform's file is missing (`no_asset`), naming the members.

### 2.10 Permissions, sign-in, backup and audit

- Starting, retrying, taking back, ending, pausing and resuming need an administrator of the system (`Administer` on the system object, as an install). Starting needs a fresh sign-in (within 5 minutes) in every profile, since one action changes every member (CU-Q8); a personal API token cannot start a run, so the CLI uses a session from `tenko login`. Hardened takes uploaded files only, as for an install.
- The backup rule of an install applies to the run: a good backup younger than one hour, a backup taken by the run's first step, or an explicit skip where the profile allows it. The backup before the run is the rollback point after the finish.
- Audit: `sys.update.run.start` (target, order, settings, backup decision, the administrator), `.member` (each member's start and outcome), `.halt` (member, check, code), `.retry`, `.take_back`, `.end`, `.pause`, `.resume` and `.finish`, plus the existing per-member `sys.update.install`, `sys.update.download`, `sys.update.confirm`, `sys.update.rollback`, `sys.upgrade.migrate` and `cluster.member.announce`, and the new `cluster.level.raise`. Each job kind and audit action gets its English and Swedish labels.

### 2.11 When it runs

A run starts only when an administrator starts it. The start dialog may set a start time and a window end: the run waits until the start time, and after the window end it starts no further member (the member under way completes its gate) and pauses until the operator resumes it or the next window opens (CU-Q2). Pause and resume are available at any time. Nothing starts a run by itself: the check for updates keeps only notifying.

### 2.12 What the operator sees

- **The Cluster page** gets an "Update all" panel. Before a run: the target (the newest release, or another one the manifest offers), the preflight with every reason it refuses, the order with each member's expected outage, the backup's age, the acknowledgments of section 2.2 when needed, and Start. During a run: one row per member, in the order of the run, with its name, kind (learner, voter, leader, node and role), platform, version now and target, state (waiting, staging, installing, dry run, switching, draining, restarting, probation, gate, soak, done, halted, back), the check it waits on with the time left, and its last message; the run's buttons (Pause, Resume, Retry, Take back, End). A halted run shows the reason in the panel and in the status bar.
- **The status bar** shows "Updating 2 of 5" during a run and the warning while the installation rests at two versions; the update notice links to the panel on a cluster.
- **The Updates page** on a cluster shows the notes as today and, in place of the install button, a link to the panel.
- Events: the run's transitions reach the UI over the existing `jobs` topic, and the member rows through `cluster` events, so the panel needs no polling.

### 2.13 The command line

`tenko cluster update check --version <v>` prints the preflight and the order (the `upgrade-check` report extended by health, lag, quorum, platforms and partners); `tenko cluster update start --version <v> [--at <time>] [--until <time>] [--backup run|skip]`, `status`, `pause`, `resume`, `retry`, `take-back`, `end`. The client asks the server; it installs nothing itself. `tenko cluster upgrade-check` stays as it is for the manual procedure.

### 2.14 Windows members, mixed systems, containers

- **Windows**: the service restarts after status 12 with a delay of 10 s; each restart counts as a failure, the fourth within a day leaves the service stopped, and a failed update that switches back uses up to three (the switch, the failed start, the switch back) (section 9.3 of upgrades.md). The run counts with the delay in check 2. A Windows member that switched back cannot be retried or taken back the same day without risking the fourth restart: Retry and Take back for it wait until its restarts of the last day are below three, and the panel says until when. A Windows member that updated cleanly has used one restart. A Windows member is otherwise updated like any other.
- **Mixed systems** in one installation are handled by platform (section 2.9).
- **Containers**: an image is the unit of deployment, so a member in a container is not updated in place; the preflight refuses a run with such a member (CU-Q11 asks whether a later package should instead wait at that member for the operator to replace its image).
- **The cluster lab** runs in containers. The exit checks of section 3 need its controllers to run like installed hosts: the release binary from the layout on a data volume, under a supervisor that restarts on status 12. The container marker files then must not block the install; WP19.2 adds a lab image that runs this way and has the root-written configuration's explicit `updates.container = false` take precedence over the marker files (CU-Q12).

### 2.15 What the plan needs from the one-version change on Linux nodes

The run restarts each member and relies on the member's own switch back. It needs from the change of section 1.8: (1) every start of a member after a switch (the run's restart, a later crash restart, a switch back) runs only binaries of the layout, the version the run installed or the one it switched back to, so that the start that probation watches is the whole start; (2) the member can report this in its member record or heartbeat (the preflight refuses a Linux member that does not); (3) the switch back keeps working: the previous version's start runs with its own binary. WP19.1 starts after that change is merged; on 2026-11-12 it had not started.

### 2.16 What stays and what is reused

`tenko cluster upgrade-check`, the manual procedure of section 7.7 of upgrades.md and its notes stay as the fallback, for installations in containers and for the case where a run cannot be used. The run reuses: the fit rules and the order function of `upgrade-check` (moved into the new binary's `upgrade fit` and the run's planner, one implementation for both), the install job's five steps unchanged, the attempt record and probation, the member records and announce, the leader-gated migration, step-down, the promotion's caught-up rule, the job engine's fencing and resumption, and the backup rule of an install. Nothing of the manual path is removed. The block reason `cluster` stays for a single install on a cluster member, now for every installation with more than one member, with the text pointing to the run.

### 2.17 A forced recovery step during a run

The cluster recovery plan ([cluster-recovery-plan.md](cluster-recovery-plan.md)) lets an operator make one surviving controller the only voter of a new history when the quorum is gone for good, and numbers each history with a signed **generation** that every call between controllers carries; a controller of a superseded history fences itself, and a restore of a cluster backup starts a new generation too. A run never continues across such a step, and both sides refuse. On the recovery side, the forced step halts an active run in the same batch that writes the generation record (halt reason `cluster.recover`), and the run's own cluster-port calls (`Peer.Ready` for the gate, `Release.Fetch` for the files) carry and check the generation as the other calls between controllers do, so a superseded member's answer is a refusal that the gate counts as a failed check. On the run's side, the run row records the generation the run started in, and every step reads the stored generation before it acts and halts with `cluster.recover` when it differs; this also stops a run that a restored backup brings back, whose job would otherwise resume. A run halted for `cluster.recover` offers only End here, because its order and its gate counted voters that are gone, and the preflight of a new run refuses while any controller is superseded and neither rejoined nor removed; the halt leaves joins and removals allowed (section 2.3), as the recovery needs. A run that an old majority kept driving behind a partition stops when those controllers fence and stays in their kept copies; the members it updated keep their version, and the next run brings the installation to one. The migration hold stays across the step, as after any run that did not finish. In the other direction, the level of section 2.8 serves the recovery plan: a superseded controller that rejoins passes the level check at join, and once the release that knows generations has raised the level, "every member knows generations" is a read of the level instead of a list of versions.

Replace S3-Q14.** (a) The run of this plan on clusters; (b) keep the manual procedure and only extend `tenko cluster upgrade-check` with the gate's checks (health, catch-up, quorum) as a guide. Security: (a) makes every member's update a dry-run-checked, audited action that a replaced leader cannot continue (fenced), with a halt, where (b) relies on a person following ten steps per member; (a) adds a new way for a binary to reach a machine, the copy from the leader to the other members (R203). Performance: equal. Usability: (a) is one action; (b) is about ten commands per member. **Recommendation: (a).**

**Decided (2026-11-12): (a).** On a cluster the run replaces S3-Q14 (a); the manual procedure stays as the fallback.

**CU-Q2. When a run may start.** A *maintenance window* is an agreed period in which interruptions are allowed. (a) Only when an administrator presses Start; (b) (a) plus an optional start time and window end in the start dialog, after which no further member starts and the run pauses; (c) automatic updates on a schedule. Security: (c) installs without a person's decision at the moment, which no profile allows today. Usability: (b) lets a run begin at night without anyone at the screen, and never runs past the window. **Recommendation: (b).**

**Decided (2026-11-12): (b).** A run starts when an administrator presses Start, with an optional start time and window end.

**CU-Q3. How many members at once.** (a) Strictly one member of the installation at a time; (b) several at once when they share no role, pair or zone. Security and usability: (a) is the owner's rule as stated and the simplest to prove; (b) is faster for large installations but rests on the product knowing right which members stand in for each other (a DHCP pair, two DNS servers of the same zones). Performance: (a) takes longer, about the restart plus the gate per member. **Recommendation: (a), and (b) only if a large installation asks for it.**

**Decided (2026-11-12): (a).** Strictly one member of the installation at a time.

**CU-Q4. A role or the writes with no second member.** One DNS server, or a single voter (with learners or enrolled nodes), whose restart pauses DNS answers or writes for its restart, about 20 s. (Two voters are always refused, section 2.2: the run could not record its progress.) (a) The preflight names the outage and the run starts only after an explicit acknowledgment; (b) refuse such a run. Security: equal (the outage happens with the manual procedure too). Usability: (b) leaves such installations to the manual procedure, which has the same outage without the gate. **Recommendation: (a).**

**Decided (2026-11-12): (a).** The preflight names the outage and the run starts only after an explicit acknowledgment; two voters stay refused.

**CU-Q5. The point of no return.** After the last member's gate, the data migrates and the level rises, and from then on the way back is the backup. (a) The run finishes by itself; (b) the run waits for an administrator's "Finish" (with a fresh sign-in), and until then the new behavior stays off and Take back stays possible; (c) (a) by default with (b) as an option in the start dialog. Security: (b) keeps the cheap way back longer, but keeps the installation without the new behavior while nobody acts. Usability: (a) reaches the owner's goal, one version and its behavior, without a second visit. **Recommendation: (c).**

**Decided (2026-11-12): (c).** The run finishes by itself; the start dialog offers to wait for the administrator's Finish instead.

**CU-Q6. The soak.** How long an updated member must stay healthy before the next starts: (a) 0; (b) 2 minutes; (c) 10 minutes; a setting in every case. Security: a longer soak catches a slow failure (a leak, a crash under load) on one member instead of several. Performance: each minute is added per member (a three-controller, two-node installation: 10 minutes for (b), 50 for (c)). **Recommendation: (b).**

**Decided (2026-11-12): (b).** Two minutes, the default of the setting `soak_secs`.

**CU-Q7. Where members get the release file.** (a) The leader stages it once per platform, copies it to the other controllers, and every member fetches it from the leader over the cluster port (the members' own encrypted connection, on which each side proves itself with its certificate); (b) every member downloads it from the release source itself. Security: (a) needs one host with access to the release source instead of all, and each member still verifies the digest; (b) has no file moving between members. Performance: (a) downloads once per platform. Usability: (a) works for nodes in networks without internet and for air-gapped installations (those that never contact the internet) with one upload per platform. **Recommendation: (a).**

**Decided (2026-11-12): (a).** The leader stages the file per platform and copies it to the other controllers; members fetch it over the cluster port and verify its digest.

**CU-Q8. The fresh sign-in.** A *step-up* is a sign-in within the last five minutes. (a) Starting a run needs a step-up in every profile, Home and Lab included; (b) as an install today: Standard and Hardened only. Security: (a) puts one confirmation of identity before an action that touches every machine. Usability: one sign-in at most once per run. **Recommendation: (a).**

**Decided (2026-11-12): (a).** Starting a run needs a fresh sign-in in every profile.

**CU-Q9. The backup before a run.** (a) As an install today: a backup younger than an hour, one taken by the run, or an explicit skip where the profile allows; (b) a backup is always required, no skip. Security: (b) always keeps a way back after the point of no return; (a) lets a home installation without a backup target run. **Recommendation: (a), with the run's default answer "take a backup".**

**Decided (2026-11-12): (a).** The backup rule of an install, with "take a backup" as the run's default answer.

**CU-Q10. An enrolled node that is offline.** (a) The preflight refuses the run until the node is back or removed; (b) the run updates the others and the node is updated when it returns, while it holds the installation level back. Security: (a) never leaves a known old member behind; (b) updates the rest without waiting for a node that may be gone for good. Usability: (b) does not let one dead probe block everyone. **Recommendation: (a) in the first release; (b) as a later option.**

**Decided (2026-11-12): (a).** An offline enrolled node blocks the run until it is back or removed; (b) may come later as an option.

**CU-Q11. Members in containers.** (a) The preflight refuses a run with a member in a container (such installations use the manual procedure, section 7.5 of upgrades.md); (b) a later package lets the run wait at such a member until the operator has replaced its image, then gates it as usual. Security and performance: equal. Usability: (b) brings container installations into the run with one manual step per member. **Recommendation: (a) now, (b) when container clusters are used.**

**Decided (2026-11-12): (a).** The preflight refuses a run with a member in a container; (b) when container clusters are used.

**CU-Q12. The lab's container setting.** Today a container is recognized by the setting or by marker files, the empty files `/.dockerenv` and `/run/.containerenv` that container engines place in every container; either blocks an install. (a) An explicit `updates.container = false` in the configuration file (which only root writes) takes precedence over the marker files, so the cluster lab, and system containers (containers that run a whole system with its own service manager, like a small virtual machine) can run updates; (b) the lab runs the exit checks on virtual machines instead. Security: (a) moves the decision to the root-written file, which already holds the release location; the image keeps setting `true`. Usability: (a) keeps the exit checks in the compose lab that the weekly job runs. **Recommendation: (a).**

**Decided (2026-11-12): (a).** An explicit `updates.container = false` in the configuration file takes precedence over the marker files.
