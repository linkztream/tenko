## 1. Scope and exit

### 1.1 Goal

**The domain this is for.** The reference domain is small and common: one zone for everything (the AD domain zone is also the zone of the clients, with about sixty names registered by Windows DHCP, each with a DHCID record because name protection and aging are on), `_msdcs` as a zone of its own, AD-integrated storage, two controllers that both run the DNS Server and the DHCP Server role, reverse zones, conditional forwarders, one scope over the whole client network served by both DHCP servers through one failover relationship (load balance assumed; section 2.15 says what differs for hot standby and for split scopes), about thirty reservations with mixed naming, no DHCP policies, no IPv6, and fewer than five domain-joined Windows machines whose own DNS registration is switched off per machine by a registry value. Every name and address in this plan is a placeholder as in [active-directory.md](../active-directory.md): `corp.example.test`, `_msdcs.corp.example.test`, `dc1` and `dc2` at `192.0.2.5` and `192.0.2.6`, `tenko1` at `192.0.2.53`, the client network `192.0.2.0/24` with its reverse zone `2.0.192.in-addr.arpa`.

**What changes.** Today's runbook ([active-directory.md](../active-directory.md), steps 1 to 11) copies the zones once by transfer, exports and re-imports them as `manual` records, builds the DHCP scope by hand from `Export-DhcpServer`, and before the DHCP switch deletes every record Windows DHCP wrote (step 10), so that each client is without a name until it renews. This slice replaces the copies by live feeds and the deletion by an adoption:

1. **DNS by transfer, kept live.** Tenko is a secondary of every AD zone (AXFR and IXFR with NOTIFY from the controllers) until the operator flips a zone. The flip turns the secondary into a primary in place and keeps every record with its provenance (section 2.6); the controllers then hold their copies as secondaries of Tenko.
2. **DHCP by a mirror.** A static PowerShell script, scheduled every 60 s on each controller that runs DHCP (one mirror per server, section 2.15) under an account that can only read DHCP, reads the scopes, the options at every level, the reservations and the active leases, turns them into the source-neutral intermediate representation (IR) of [MIGRATION.md](../MIGRATION.md) and pushes it to Tenko's API over HTTPS with a token that can do nothing but write that one mirror. Tenko never holds a Windows credential and never connects to Windows.
3. **A takeover per scope.** In the UI and the CLI, one action converts the mirrored leases to Tenko leases with their remaining time, adopts the A, DHCID and PTR records of the mirrored leases and reservations as Tenko DHCP's own (with Tenko's DHCID; the proof is the mirrored lease or reservation, not a renewal), and, once Windows has been made silent (never by deactivating its scope, which refuses its clients' renewals; section 2.17), activates the Tenko scope and records what it did. The reverse action makes the Tenko scope silent again and leaves the records; Windows then answers again.
4. **One script drives it** (amended 2026-11-20, section 2.16). The administrator runs `Tenko-Takeover.ps1` from the release on a domain-joined machine; it discovers the domain, shows what it will change, does the Windows side with the credential it asks for and the Tenko side through a session a signed-in person approves in the UI with a code. The person starts the window in the UI after reviewing what was found.
5. **A rehearsal first.** Step 0 of the runbook is a second line of the Windows lab ([`deploy/compose/lab-ad/windows/takeover/`](../../deploy/compose/lab-ad/windows/takeover/README.md)): both lab controllers with Windows DNS and Windows DHCP in a failover relationship, a Windows client on a DHCP reservation, and the lab's Tenko node serving nothing until the takeover, run by the lab's operator, an inside observer on the admin workstation and the lead (section 2.13).

**What stays.** The controllers stay controllers, Tenko joins nothing and holds no directory data (CON-11). Under the Home profile the controllers register their locator records by unsigned RFC 2136 updates accepted by address (today's footing, section 4 of the runbook); the Hardened profile becomes possible with GSS-TSIG in Slice 13 ([identity-plan.md](identity-plan.md) WP13.0 to WP13.4), which stays as planned and follows this slice. Nothing in the core assumes Windows: the mirror is a source kind that any adapter can feed with the same IR (Kea, BIND, dnsmasq and OPNsense adapters are its siblings), and the takeover acts on the IR and on records, never on Windows. Active Directory integration is always an option, never a requirement.

- **The IR** (`crates/tenko-core/src/ir.rs`, `ir/dhcp.rs`). `DhcpIr { server_options, option_defs, classes, scopes, superscopes, policies, filters, failover, leases }`; `IrScope { cidr, name, description, active, lease_secs, ranges, exclusions, reservations, options, ddns: Option<DdnsPolicy>, superscope, restricted, delay_ms, origin }`; `IrReservation { ip, client: IrClientId { mac, client_id }, name: Option<HostName>, bootp, options, .. }`; `IrLease { ip, scope, client, hostname, expires, state: IrLeaseState { Active, ActiveReservation, Declined, Expired, Other }, origin }`; `SourceLocation { sheet, row, column }`. `HostName` takes one or more labels, so a fully qualified name fits. No consumer of `DhcpIr` exists; the Windows XML mapping is a written specification ([dhcp-contracts.md](../dhcp-contracts.md) section 11).
- **Connectors** (`crates/tenko-connect`). `MigrationSource` (`migration.rs`) and the plugin host (`host/`, ADR 0012) are pull-based: `ConnectorInstance { plugin, settings, secrets, poll_interval_secs (60 to 86,400), writes_enabled, .. }`. `tenko-connect-windows` and `tenko-migrate` are placeholders of about 25 lines.
- **Tokens** (`crates/tenko-auth/src/model.rs`). `ScopedTokenRecord { owner, grants: Vec<TokenGrant>, scopes: Vec<TokenScope>, expires_at, .. }`; `TokenScope` is a `Copy` enum with `metrics` and `audit:read`; the right of a request is the intersection of the token's grants and its owner's; TGL-05 caps the lifetime (Home 365 days).
- **Secondary zones** (`crates/tenko-dns/src/xfr/in.rs`, `zone/secondary.rs`). AXFR and IXFR in, NOTIFY accepted only from the configured primary's address; the copy is written with the origin `transfer`; a secondary is read only (409 `dns.zone.secondary`), and the same code refuses a write to a `transfer` RRset in a primary zone ([dns.md](../dns.md) section 10.7). Transfers out need `transfer.allow` and, for Windows, `transfer.require_tsig = false`, per zone with no profile override (`xfr/out.rs`, `refusal()`).
- **Updates** (`crates/tenko-dns/src/update/`). `manual`, `dynamic`, `dhcp` and `ad` RRsets may be changed by an update, `ipam` only with `may_replace_ipam`, `transfer` and `dnssec` never; every changed RRset becomes `dynamic`. Home and Standard follow the zone's `require_tsig`, Hardened always requires a signature, Lab never (`policy.rs`).
- **DHCP engine** (`crates/tenko-dhcp/src/v4/engine/mod.rs` `request`, `allocator.rs`). RENEWING or REBINDING for a free pool address with no record is ACKed and creates the lease with the scope's lease time, not the old remaining time; INIT-REBOOT with no reservation and no lease row of the client is silent (RFC 2131); an address held by another client's row is NAKed on an authoritative scope. The client is option 61 when sent, else `htype` and `chaddr` (`tests/engine.rs` lines 225 to 305).
- **DDNS** (`crates/tenko-dhcp/src/ddns/`). DHCID per RFC 4701 types 0, 1 and 2 with SHA-256 over the identifier and the canonical name (`dhcid.rs`); the planner treats a name as the lease's own only when the DHCID RRset has the origin `dhcp` and the computed bytes (`plan.rs` `dhcid_is`); `manual`, `dynamic`, `transfer`, `dnssec` and `ad` names are refused whatever `conflict` says; there is no adoption mode (`take_over` exists only for `ipam`). The worker follows `dhcp.leases`, takes the name from option 81 or, with `legacy_clients`, option 12 on the row, and removes a lease's names when its name or client changes.
- **Building a scope by API.** `POST /dhcp/scopes`; pools are IPAM ranges of role `dhcp_pool` (`POST /prefixes/{id}/ranges`); `POST /dhcp/scopes/{prefix}/exclusions`; `PUT /dhcp/option-sets/{owner}`; reservations through `POST /addresses/reserve` (an IPAM host of mode `reserved`, keyed by client identifier, else MAC); the spreadsheet import covers hosts, not scopes. An address with a `dns_name` in IPAM gets no DDNS: the IPAM actuator writes its records with the origin `ipam`.
- **Lease rows** (ADR 0031). The lease table is the observation source; a new cold field is added with a serde default and a presence bit without a data format change (`granted` did so); the store's format is 5.
- **Jobs** (`tenko-jobs`, [jobs.md](../jobs.md)). Steps, rollback, audit, and a task that waits for a person (`POST /jobs/{id}/steps/{index}/complete`).

## 2. Design decisions the packages share

### 2.1 The mirror's transport and trust

A **mirrored source** is a new kind of source beside the plugin instances: Tenko does not poll it, it is pushed to. Its row holds a name, a `kind` label (`windows-dhcp` for this exporter; a label of `[a-z0-9-]{1,32}`, never an enumeration of products, so that a Kea or dnsmasq script can push the same IR under its own label), the expected interval (60 s), the token's id, the last accepted sequence, the hash of the last snapshot and the times of the last push and the last change.

The trust rules (ADR 0033, proposed):

1. **Push only.** The exporter calls `PUT /api/v1/migrate/mirrors/{id}/snapshot` over HTTPS on the API port. Tenko opens no connection to the controller, holds no Windows credential and has no way to make the script do anything: the answer carries the accepted sequence and whether the snapshot changed, and the script logs it and acts on nothing else (WT-Q1).
2. **A token that can write one mirror and nothing else.** Creating the mirror creates a service account `mirror-<id>` (named by the mirror's id, so that the mirror's name is a display name that may hold spaces and be renamed without a side effect) with no grants and one scoped token whose only special scope is `mirror:<id>`. The token may be bound to the source prefixes the exporter pushes from, by the source binding of scoped tokens (IAM-21, [access.md](../access.md) section 7.2): a push from elsewhere is refused like an unknown token and audited as `auth.token.source_refused`. Under Hardened a mirror is created, enabled or given a new token only with at least one prefix, and a mirror whose token has none stops pushing when the profile is switched, with the finding `migrate.mirror.unbound` (section 2.11). A prefix is at least a /16 or a /48. An installation holds at most 32 mirrors. The push route accepts exactly that scope for exactly that id; every other operation answers 403 to that token, including reads of its own mirror, so a stolen token gives neither data nor reach. The token is shown once, expires within TGL-05 (WT-Q11), and is replaced from the mirror card; the old one stops at once.
3. **The script is static and comes with the release.** It is in the release assets and in the repository, versioned with Tenko and listed in `SHA256SUMS`; the documentation says to compare the digest before copying it to the controller. Tenko never serves it, never generates it and never updates it: a compromised Tenko node cannot change what runs on a controller (the privilege boundary of ADR 0023: a more privileged account never runs what a less privileged one wrote).
4. **The script runs with DHCP read rights only.** A domain account (a group managed service account where the domain has a KDS root key, else a user account with a long random password) that is a member of `DHCP Users` and of no privileged group, with the right to log on as a batch job on the controllers that run DHCP. The script refuses to start when its account is a member of `Domain Admins`, `Enterprise Admins`, `Administrators`, `DHCP Administrators` or `DnsAdmins` (a check of its own token's groups), so a convenient misconfiguration fails loudly.
5. **The script verifies Tenko.** The install script takes the SHA-256 fingerprint of Tenko's certificate authority (shown on the mirror card) and the script accepts only a chain ending in it; nothing is added to the controller's trust store. The token is stored with DPAPI for the task's account (`ConvertFrom-SecureString` without a key), readable by nothing else on the controller.
6. **Bounds and replays.** A body of at most 8 MiB (gzip allowed, 32 MiB inflated), at most 1,000 scopes, 10,000 reservations and 20,000 leases, so that a snapshot at every bound is written in one store batch with room to spare (the owner's decision of 2026-11-20: what one store batch holds with room to spare. With the exporter's item sizes the snapshot row at every bound is about 11.8 MB of the 16 MiB batch; 50,000 leases alone take 10.4 MB, so neither 100,000 nor 50,000 fit); a strictly increasing `sequence` per mirror (an older or equal one is refused as a replay, 409 `migrate.mirror.sequence`); at most one push per 10 s per mirror (429); the body is read whole first, within the server's deadline for request bodies (408 `sys.body_timeout`), and only then does the push take the node's one decode, so that a slow body holds no other mirror; one push of a mirror is in flight on a controller at a time (429 for the next), so the bodies arriving hold at most 8 MiB per mirror. The IR is parsed with the strict serde types of `tenko-core` (`deny_unknown_fields` on the envelope), so a value that does not validate is refused whole with the path of the first error (422 `migrate.mirror.invalid`); nothing of a refused push is stored.

DNS data does not use the mirror: it comes by the existing zone transfer, AXFR and IXFR with NOTIFY, address-restricted on both sides because Windows DNS does not sign transfers ([dns.md](../dns.md) section 10.13).

### 2.2 The exporter

`deploy/windows/mirror/` holds three files and their tests:

- `Tenko-DhcpMirror.ps1`, the exporter: PowerShell 5.1 and 7, the `DhcpServer` module only, no other module and nothing downloaded. One run reads `Get-DhcpServerv4Scope`, `Get-DhcpServerv4ExclusionRange`, `Get-DhcpServerv4Reservation`, `Get-DhcpServerv4OptionValue -All` at server, scope and reservation level, `Get-DhcpServerv4OptionDefinition`, `Get-DhcpServerv4DnsSetting` per scope and at server level, `Get-DhcpServerv4Lease` per scope, `Get-DhcpServerv4FilterList` and `Get-DhcpServerv4Filter`, whose enabled lists it carries (amended 2026-11-21, as built), and, only to report them, `Get-DhcpServerv4Policy`, `Get-DhcpServerv4Superscope` and `Get-DhcpServerv4Failover`. It maps them onto `DhcpIr` with the mapping of [dhcp-contracts.md](../dhcp-contracts.md) section 11 (the XML element names there are the cmdlets' property names), writes a loss entry for every policy, filter entry Tenko cannot match, superscope, failover relationship, scope `Delay`, BOOTP-only scope and lease state other than active, active reservation, declined and expired, and pushes the envelope of section 3.1. Lease expiry times are converted to UTC; the envelope carries `taken_at` from the controller's clock, and Tenko computes each lease's remaining time as `expires` - `taken_at`, two times of the same clock, and applies it to its own reception time (section 2.8), so clock skew between the controller and the node does not shorten or lengthen a lease.
- `Install-TenkoDhcpMirror.ps1`: registers the scheduled task (every minute, under the given account, "run whether the user is logged on or not", no highest privileges, a new instance is not started while one runs), stores the token with DPAPI under that account and the fingerprint beside it, and runs one `-Once` to show the result. `-Remove` unregisters the task and deletes the stored token.
- `README.md`: the account, the rights, the digest check, the two commands, what the log says.

`-Once` is the dry run: it reads, maps and prints the IR and the loss report as JSON on standard output and pushes nothing, so an operator can read exactly what would leave the controller. A normal run writes one line per run to a log file under the task account's profile (sequence, counts, answer, duration) and keeps the last seven days.

The mapping lives in the script because the exporter is the adapter (WT-Q2): the core receives only the IR and the loss report, as it would from any other source, and validates them. The cost is a mapping in PowerShell besides the Rust side of the other adapters; the Pester tests with recorded cmdlet output (section 3.4) hold it to the fixture IR.

### 2.3 What the mirror carries, and the loss report

Every 60 s (WT-Q2): the scopes with their pools, exclusions, lease time, state (active or inactive) and DNS settings; the options at server, scope and reservation level with the custom definitions; the reservations; the leases in the states active, active reservation and declined. Expired leases are left out. Policies and superscopes go to the loss report, as do failover relationships; the enabled filter lists are carried with their entries, as built (amended 2026-11-21), and an entry Tenko cannot match, or a reservation an enabled Allow list does not list, goes to the loss report; the server's DNS credential is never read (`Get-DhcpServerDnsCredential` is not called).

The loss report of the latest snapshot is shown on the mirror card. An entry is acknowledged per scope (`POST /migrate/mirrors/{id}/losses/ack` with the entries' keys, by an administrator's interactive session); an acknowledgment holds while the entry recurs unchanged and lapses when it changes. The prepare and the takeover refuse a scope with an unacknowledged entry (MIGRATION.md: nothing is dropped silently).

### 2.4 Storage and freshness

- `migrate.mirrors`: one row per source (section 2.1).
- `migrate.snapshots`: one row per mirror, an accepted envelope as CBOR with the hash of its configuration. What a push writes (the owner's decision of 2026-11-20; the earlier "one small write every ten minutes" did not hold, since leases change between most pushes):
  - The **configuration** (the scopes with their state, pools, exclusions and DDNS settings, the options at every level, the definitions, classes, policies, filters, superscopes, failover relationships, reservations, the source and every loss entry but those of leases) has its own hash. A push whose configuration changed is written at once while the reserve lasts: the snapshot, the mirror row and the audit record `migrate.mirror.push` (amended 2026-11-26, ADR 0033 decision 6: 30 changed configurations in a row, then one per ten minutes, `CHANGE_RESERVE` and `LEASES_WRITE_SECS`, counted from the mirror's `change_reserve_full_at`). A changed push past the reserve is held, and the first push after the refill whose configuration still differs is written, so the stored configuration may lag the newest push by ten minutes and one interval; the mirror shows `changes_left` and, on the controller that holds the change, `change_held` and `held_change_due`. The final pushes a takeover adopts from (section 2.7, step 2) may change only leases, so the takeover reads them as the newest envelopes in memory, written or not (below).
  - The **leases** and their loss entries have a hash of their own. Changed leases alone (a new lease, a lease gone, a state or an expiry moved) write the snapshot and the row at most every ten minutes per mirror (`LEASES_WRITE_SECS`), with no audit record. The mirror says which push the stored leases are from (`stored_sequence`, `stored_at`), so nobody takes a stored expiry time for a current one.
  - The controller that received a push holds its envelope in memory as the newest, stored or not.
  - Otherwise the push moves the freshness in memory, and the mirror row is written at most every half of the stale threshold (section 2.14).
  
  The lease path is never touched (ADR 0030 and 0031: no fact rows, nothing on the commit path).
- **For WP14.2:** the prepare and the takeover need the newest leases and take them from a push made for that moment (the newest envelope on the controller that received it, which for the takeover is the final push of section 2.7, step 2), never from the stored copy, whose leases may be ten minutes old.
- Freshness on the mirror card (on the connectors page, beside the plugin instances): the time since the last push, the time since the last change, the sequence, the counts of scopes, reservations and leases, the script's version and the server name it reports, and the losses. The mirror is **stale** after three missed intervals (180 s): the card says so and the system status carries the finding `migrate.mirror.stale` (a warning, and none once the mirror's servers were made silent by a takeover, when a stale mirror is the expected state; then a push accepted after the silence is the error, section 2.17).

### 2.5 The diff and the prepare

The **diff** compares a mirrored scope with Tenko's scope of the same network: the pool ranges, the exclusions, the lease time, the options at each level, the reservations (added, changed, removed, by MAC or client identifier and address), the DDNS settings mapped by the table of [active-directory.md](../active-directory.md) step 10, and whether the network is an IPAM prefix. Each row says what the prepare would do.

The **prepare** is a job (one per scope) that makes Tenko's scope equal to the mirror's while it serves nothing: it creates the IPAM prefix when missing, the scope with `enabled = false`, the pool as a range of role `dhcp_pool`, the exclusions, the option sets of the scope and of each reservation (server-level options become the server's set only where the server set has none of that code, otherwise a diff row the operator decides), the DDNS settings, and each reservation as an IPAM host of mode `reserved` named by section 2.9. A host that IPAM already holds with the reservation's MAC or client identifier, or with the reservation's address, is attached rather than duplicated; a disagreement between the two (the MAC on one host, the address on another) is a diff row that blocks the prepare until the operator resolves it. Reservations get no `dns_name` in IPAM, so their records stay DDNS records, as Windows DHCP writes them (section 2.9). The prepare runs again whenever the operator wants, and a run against an unchanged mirror changes nothing. Its reverse is the job's rollback or the ordinary deletion of the scope.

(Amended 2026-11-26.) The prepare is a request, not a job: each write is an inline job under the caller, so a run's writes carry the run's stamp, and `POST .../prepare` answers Tenko's scope with its prefix. The run's prepare writes, in the default VRF, the IPAM network with the scope's one pool range, then in one batch the scope, disabled and not authoritative, with the lease time, the DDNS flags (never the push's forward zone or TTL) and the distinct exclusions; options, reservations and filters stay rows of the diff, and no free text of the snapshot is written. Everything taken from the snapshot is checked before the first write: no open loss, no row to decide, exactly one range, a lease time and DDNS settings Tenko accepts. A prefix or scope at the network that the run did not create is refused, and IPAM refuses a network around or inside one. While the run's scope is disabled and untouched (its rows, the deleted ranges and the addresses of its prefix included, are as the run wrote them, with no option set, pool setting, policy or active lease; creating or deleting an exclusion changes the scope), the prepare of a later sitting rebuilds it to the newest snapshot, removed and then created; a scope a person or a takeover touched answers 409 and the person decides. A sitting never rebuilds or removes a scope it prepared itself (403 `condition`), so one approval allows one cycle of prepare and removal. The takeover phase calls the prepare of each plan scope before its window check, and the window binds what that left. `DELETE /migrate/runs/{id}/scopes/{cidr}` removes a run's disabled scope with its prefix: the run's session within five minutes of the approval of a later sitting and only while untouched, a person any disabled one. A refusal of IPAM names no object to the run's session.

### 2.6 The flip of a zone, and the origins it keeps

`POST /dns/zones/{id}/flip` with `{"to": "primary", "soa": {...}, "ns": [...]}` turns a secondary zone into a primary zone in place (ADR 0034, proposed): the kind changes, the transfer service stops refreshing it, the SOA `mname` and `rname` and the apex NS set become the operator's values (step 3 of today's runbook, done in the same commit), the serial continues from the copy's, and the records stay. The origins after the flip:

| The copy's RRset | Origin after the flip | Why |
|---|---|---|
| A, AAAA and DHCID at a name that holds a DHCID RRset, and a PTR whose target is such a name | `transfer` (frozen) | A name a DHCP server wrote; it waits for the takeover, and no writer touches it until then ([dns.md](../dns.md) section 10.7) |
| The apex SOA and NS | Replaced | The operator's values |
| Every other RRset (the controllers' SRV, CNAME and A records, static hosts, the `_msdcs` zone entire) | `ad` | Records of an AD zone without a known owner (identity plan section 3.6): an update from the access list may change them, as before; Slice 13's claim rule applies to them later (WT-Q9) |

The reverse zones are flipped after the forward zones are on Tenko, so that the PTR rule reads the forward names; a PTR whose target is in a zone Tenko does not hold becomes `ad`. The flip writes one change set per zone and the audit record `dns.zone.flip` with the counts by origin.

The reverse flip, `{"to": "secondary", "primaries": [...]}`, turns the primary back into a secondary of the named primaries; the next transfer replaces every record with the copy's, `transfer` again. It is step 2 of the DNS rollback (section 2.10); step 1 is on Windows.

`POST /dns/zones/{id}/release` turns every remaining `transfer` RRset of a primary zone into `manual`, or deletes them with `{"delete": true}`, and lists them first in a dry run. It is for the names that a takeover did not adopt because no mirrored lease or reservation stands behind them (stale names; Windows would have scavenged them, Tenko cannot until DNS-29). Catalog zones keep their own rule: `release` refuses a catalog zone.

Frozen names between the flip and the takeover: Windows DHCP's update of a frozen name is refused (audited as `dns.update.refuse`); a client renewing at Windows keeps its address and its frozen name, which is still right. A client new to Windows DHCP in that gap gets a `dynamic` name with Windows' DHCID, which the takeover adopts under WT-Q8. The runbook therefore does the flip and the takeover in one window (section 2.13).

### 2.7 The takeover of a scope

The takeover is a job per mirror pair (`POST /migrate/mirrors/{id}/scopes/{cidr}/takeover`, the UI button on the mirror's scope row, `tenko migrate takeover <mirror> <cidr>`). Since Windows is made silent per server, not per scope (section 2.17, amended 2026-11-21), the job takes over every scope its servers serve and refuses unless each is prepared and acknowledged. Its steps:

1. **Check.** The mirror is fresh (a push younger than 120 s), and so is its partner when it has one (section 2.15); the loss entries of the scopes are acknowledged on each; the prepare's diff holds no row of any kind, partner rows included (amended 2026-11-26: an option, reservation or filter row the prepare left also refuses); Tenko's scopes are disabled and not authoritative; the forward zone and the reverse zones are primary zones on Tenko that take DHCP updates under the profile (`update.dhcp`, [dhcp.md](../dhcp.md) section 13.1) and each scope's DDNS is enabled when the mirror's was. The diff and the loss entries are those of the stored configuration, and a held change is stored only by a later push (section 2.4): before it compares, the step needs, per mirror, the newest push on the controller that runs the job, accepted after the job's start, whose configuration hash equals the mirror's `last_hash`; while it differs, the job waits for the push that stores it (`change_held`, and `held_change_due` says when while the clock is trusted) or ends with its code. A failure ends the job with its code and changes nothing.
2. **The final pushes (a task).** A push of each mirror accepted after the job's start, by Tenko's order of events, requested at once (the takeover script starts the exporter's task on the mirror host; by hand, wait a minute). Windows still answers meanwhile; these pushes are the leases the job adopts.
3. **The records** (section 2.8), one change set per zone.
4. **The leases** (section 2.8), in batches of 1,000 rows, the scopes still disabled.
5. **Windows silent (a task).** Both servers are made silent by the method of section 2.17, and the task is completed with the method and the time; the takeover script does both, and checks the silence on each server itself. Nothing in Tenko writes to Windows (CONN-12 explicitly not).
6. **The scopes on.** `enabled = true`, not authoritative; from this commit the role answers for the network once the relay or the listener reaches it.
7. **The record.** A row in `migrate.takeovers` (the scopes, each final push's sequence and lease hash, the silencing method and time, the counts, the adopted addresses and names, the names left frozen, the skipped items with their reasons, the before-images of every RRset it changed) and the audit record `dhcp.scope.takeover` with the counts.

A failure in steps 3 and 4 rolls the job back from the before-images: the RRsets as they were, the adopted lease rows removed, the scopes disabled. From step 5 on the job never rolls back by itself, since that would leave both sides silent: a failure waits for the person, with the error finding `migrate.takeover.both_silent` and an alert at a deadline, and the person or the takeover script either completes step 6 or reverses the takeover, Tenko silent first, then Windows answering (section 2.17). The rollback is the job engine's, so it is visible and audited like every other. A relayed scope is refused at step 1 until Tenko has counted relayed packets from its relay address within the last ten minutes.

Between step 5 and step 6 nobody answers, for seconds. What a client experiences then and afterwards, and why no client loses its address, is section 2.17.

### 2.8 The adoption rule

**Leases.** Each mirrored lease of the scope (of both partners, merged by the rule of section 2.15) in the state active or active reservation becomes a `dhcp.leases` row: state `active`, the address, `ends` = `received` + (`expires` - `taken_at`) (amended 2026-11-21): the remaining time is the Windows server's own difference, its lease's `expires` minus the push's `taken_at`, both by that server's clock, applied to `received`, the moment Tenko accepted the push by its own clock, so that no offset between the two clocks enters the lease; the result is clamped to at most the Tenko scope's maximum lease time from `received` and to no earlier than `received`, `granted` = the adoption time (ADR 0031 point 3), the host name, and the cold field `adopted { mirror, sequence, guessed }`. A declined lease becomes an `abandoned` row with the hold of `[dhcp.decline]`. A lease is skipped and reported when its address is outside the Tenko pool and not a reservation, when it conflicts with a Tenko reservation of another client, or when Tenko holds an active row of another client at the address.

**The client's identity.** Tenko keys a lease by option 61 when the client sends one, else by `htype` and `chaddr`. Windows shows a client's identifier as six octets for both a client that sends option 61 of type 1 with its MAC and a client that sends none, so the mirror cannot always tell which key the client will present. The adoption decides it in this order: an identifier longer than six octets is the client's option 61 as it is; else, where a DHCID stands at the lease's name, Tenko computes the DHCID of both candidates (type 1 over `01` and the MAC, type 0 over `htype` 1 and the MAC) and takes the one that equals the record Windows wrote; else option 61 of type 1 with the MAC (proposed; most clients of a Windows network send it), and the row is marked `guessed`. Whether a candidate ever matches Windows' DHCID is what the rehearsal records (R137).

**The engine's rule for an adopted row.** When a REQUEST in RENEWING, REBINDING or INIT-REBOOT names an address whose active row is `adopted` and keyed by another identity, and the row's MAC equals the request's `chaddr` with `htype` 1, the row is the client's: the change rewrites it under the identity the client presented (a renewal, `granted` kept, `adopted` cleared) instead of refusing the address as another client's, and INIT-REBOOT counts the row as the client's record. A request from another MAC gets what it gets today: NAK on an authoritative scope, silence otherwise. The check reads fields the row already holds, so the path stays free of allocations (`tests/alloc.rs`). The first REQUEST of every adopted client clears `adopted`, whatever its key.

**Records.** For each adopted lease and each mirrored reservation with a lease, the name is the lease's host name under the name rule (section 2.9) and the zone is the scope's forward zone. At that name the takeover adopts:

| At the name | Condition | Written |
|---|---|---|
| A (or AAAA) and DHCID, origin `transfer` | The A RRset holds the lease's address and no other; a DHCID RRset stands beside it | A with the lease's address and DHCID computed by Tenko for the row's identity, origin `dhcp`, TTL by the scope's DDNS settings (a third of the lease time by default) |
| A and DHCID, origin `dynamic` | As above (WT-Q8, proposed: Windows DHCP rewrote the name after the flip or during a reverted takeover) | The same |
| PTR at the address's reverse name, origin `transfer` or `dynamic` | Its target is the name | PTR, origin `dhcp` |
| `manual`, `ipam`, `ad`, `dnssec`, a CNAME, an A RRset with other addresses, a name without a DHCID | Never adopted | Skipped and reported; Tenko's DDNS treats the name by its usual rules at the next renewal |

A name the takeover adopts loses its Kerberos owner (identity plan section 3.6; the zone's **Owners** tab) in the same change set: a `dynamic` name a Windows DHCP server created after the flip is owned by the principal that signed its update, and an adopted name belongs to the lease from then on (section 2.15).

The adopted lease row carries what a DDNS write would have left on it: the name as its option 81 name with the S flag (the server writes the A record), and the `ddns` block (`forward`, `reverse`, `dhcid`, `updated`). So the DDNS worker, which follows every committed row, finds the names to be the lease's own and writes nothing; at the client's first renewal the planner sees a `dhcp` name with the lease's DHCID and replaces it with what the client asks for. Where the engine rewrote a `guessed` row under another identity, the DHCID at the name is no longer the lease's: the worker replaces the A and DHCID of an adopted row's own name in one change set (the row's `ddns.dhcid` equals the record), and only then forgets the old identity. Names with a DHCID that no mirrored lease or reservation explains stay frozen and are listed in the takeover's record with the `release` action.

### 2.9 Names

The rule for every name the slice derives (WT-Q4), for a reservation's IPAM host and for the name at which records are adopted:

- A fully qualified name is kept (lowercased). When it is under a zone Tenko serves it is the record name; when it is not, it becomes the host's name and the reservation gets no adopted record, with a loss entry.
- A bare host name gets the zone: `nas01` becomes `nas01.corp.example.test` (the scope's forward zone, from its DDNS settings or option 15).
- A factory name is kept as it is (WT-Q10): the device's own default (`ESP_3A1F2B`, `android-5f2c9e01d4a6b7c8`) is not tidied into a name Tenko would have chosen. When it is a valid host-name label it gets the zone like any bare name; when it is not (an underscore, a space), it is kept as the host's name in IPAM, no record is derived from it, and a loss entry says so.

A reservation's IPAM address gets no `dns_name`, so the reservation's records stay DDNS records with the origin `dhcp`, written from the client's name as Windows DHCP wrote them (Windows registers reserved clients the same way as others). An operator who gives a reservation a `dns_name` later moves its records to IPAM by IPAM's existing take-over of `dhcp` records.

### 2.13 The runbook's shape, and the rehearsal

The rewritten runbook (WP14.3) is ordered so that every step before the window changes nothing a client uses. Since the amendment of section 2.16 the takeover script performs these steps in its phases (steps 1 to 5 in phase 2, step 6 in phases 4 and 5 after the person starts the window, step 8 in phase 6), and the runbook describes them for reading before a run and for the manual path:

0. **The rehearsal** (WT-Q6 as amended): the runbook from step 1 in the Windows lab's takeover line, below.
1. The starting state and the backups (today's step 1, with `Export-DhcpServer -Leases` on each DHCP server).
2. Tenko as secondary of every AD zone from one controller (section 2.15), the controllers allowing the transfer and notifying the node; one mirror per DHCP server, paired; the scope prepared from the mirrors; the losses acknowledged on both; the diff empty, the partner rows included. Coexistence mode secondary: no client points at Tenko.
3. The access list of the controllers and the zones' update policy (it applies from the flip); the profile confirmed (Home).
4. The lease times checked, not lowered (amended 2026-11-21, section 2.17): the remaining lease time is the margin within which a client keeps its address while nobody answers, and lowering it only shortens that margin; a scope with a lease time under an hour is warned about.
5. The registry value on each domain-joined Windows machine that is not a controller: `DisableDynamicUpdate` = 1 (`REG_DWORD`) under `HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters`, so that the member does not try to register its own name and the DHCP server writes it; checked with `reg query`. The controllers keep their registration.
6. **The window.** Directory replication forced (`repadmin /syncall /AdeP`) and a full transfer from the controller Tenko copies from, compared with every controller's records, so that the copy holds both controllers' latest registrations whatever their serials say; the flip of each zone, forward zones first (section 2.6); Tenko's `transfer.allow` and `notify` naming the controllers, then the controllers' copies converted to secondaries of Tenko in the order of R142; the controllers registering (today's step 5), with their DNS clients pointed at Tenko only if the rehearsal shows that their updates do not reach Tenko through their own secondary copy's `mname` (section 2.16.1); then the takeover of the servers' scopes (section 2.7), Windows made silent in it (section 2.17), and the relay or the listener; the check from a client.
7. **The parallel period**, a week: the exporter's tasks keep running and, with the service stopped, read nothing, so the mirrors are stale as expected, and a push after the silence is the alarm (section 2.17); Tenko's scopes not authoritative; the controllers serve their secondary copies as the second DNS server of the clients' option 6 list, behind Tenko.
8. After the parallel period, without ever starting the DHCP Server service (amended 2026-11-21 and 2026-11-24): the authorizations are already removed (section 2.17); the DHCP Server role stays installed on both servers with its database and its relationship, the service stopped and disabled, exactly as in the parallel period; each exporter's task and mirror removed, and the zones' objects in the directory partitions deleted (a DNS Server role installed later on a controller serves objects left there at once, as authoritative primaries with their old data, measured on 2026-11-20). This step is the point after which there is no scripted way back: the export of step 1 stays in the backup as a file, and going back is manual work (the takeover script's README). Removing the DHCP Server role is a manual step the operator takes when they choose, one server at a time: the uninstall, one restart, then the database directory moved or deleted. The script never takes it, since the lab measured that the removal needs a restart of the server, that a role installed again over a database left in place loads that database again, that `Import-DhcpServer` over an existing scope changes nothing, and that neither the export nor the relationship carries the DNS update credential ([ADR 0034](../adr/0034-zone-flip-and-adoption.md), amendment of 2026-11-24). The DNS Server role stays on the controllers as Tenko's secondaries until a second Tenko node exists (Phase 5, WT-Q12, R143).

Each phase up to the parallel period keeps its two-step rollback (section 2.10); step 8 has none. The INIT-REBOOT note: a client that boots with a lease Tenko holds no row for (one the mirror missed) gets silence, as RFC 2131 says, and falls back to DISCOVER after its timeout; it is offered its old address when the address is free, and the conflict probe ([dhcp.md](../dhcp.md) section 14) stands between it and a second client.

**The rehearsal** (WT-Q6 as amended on 2026-11-20): a second line of the Windows lab, the takeover line, beside the counted line of E44 (identity plan), whose entries it leaves untouched; the two lines never run at the same time. Its start state is Windows-first: both lab controllers with Windows DNS and Windows DHCP in a failover relationship in load balance, one scope over `192.0.2.0/24` with exclusions, reservations and options 3, 6 and 15, the lab's Windows client on a DHCP reservation, and the lab's Tenko node installed and serving nothing. Three actors run it: the **operator** builds the machines, takes and restores snapshots, and runs commands on the Tenko node and step scripts on the lab machines; the **inside observer**, a session on the admin workstation `adm1` (joined, with the Remote Server Administration Tools for Active Directory, DHCP, DNS and group policy), reads at once and changes something only after its own user approves that change, and never signs in to the Tenko node's API; the **lead** decides and reads the evidence. No secret travels on the channels between them: credentials live in files on the hosts that only root or SYSTEM reads. The line runs under Standard until its Hardened entry and under Hardened from the flip on, as the owner's cutover will (WT-Q5 as amended); the interactive actions under Hardened need an administrator's passkey session on the node. Nothing from the owner's own domain enters the lab (WT-Q14). The manifest, with the start state, every entry with its actor, action, check and evidence, what runs with the first package alone and what waits for which package, and the first basic set, is [`deploy/compose/lab-ad/windows/takeover/README.md`](../../deploy/compose/lab-ad/windows/takeover/README.md).

### 2.14 Single node first, cluster-aware

One node with the `controller`, `dns` and `dhcp` roles. Cluster-aware now: the mirror rows, the snapshots and the takeover records are in the replicated store; the push is accepted by any controller and written through the store; the freshness lives in the memory of the controller that took the push and is written to the mirror row at most every half of the stale threshold while pushes arrive (90 s at the default interval, `Mirror::freshness_write_secs`), so another controller or a restarted one reads a mirror that pushes as fresh, never falsely stale, with a sequence at most that far behind; the takeover's lease rows carry the node as every lease row does. ### 2.16 One script drives the takeover (amended 2026-11-20)

The owner graded the takeover of sections 2.1 to 2.15 by what the operator must do: a runbook open all the way, commands on two systems, values carried by hand. He decided on 2026-11-20 that **one script, run by the administrator on a domain-joined Windows machine, drives the takeover**: it asks for the domain's name, warns that it will act with administrator rights and lists exactly what it will change, asks for an account with enough rights through `Get-Credential`, and then does the Windows side with that account and the Tenko side through Tenko's API. Three conditions are fixed: (1) the script comes from the signed release, never from the node; (2) it never executes text that Tenko sends: it takes values, checks them against what Windows itself reports and uses them in fixed commands; (3) it signs in to Tenko through an approval a signed-in person gives in Tenko's UI, so the takeover stays the decision of an interactive session and is audited as such; the Windows credential lives only in that PowerShell session's memory, is never written and never sent to Tenko, and the Tenko server never holds a Windows right. The alternative set aside: the Windows credential entered into Tenko, with the server managing Windows remotely.

The Windows side run from the Tenko host instead (a remoting session Tenko opens, or PowerShell 7 on the Linux host) was set aside with it. On security it puts a domain administrator's credential on, or through, the host the threat model assumes can be compromised, where an attacker inside `tenko` or on the host takes it at its next use. On usability, remoting from Linux to Windows needs Kerberos or NTLM configured on the Linux host, its keytab or credential cache, and packages outside the release, where the script on Windows needs nothing but Windows; and the node would have to carry PowerShell and a WinRM client, widening what is installed and must be patched on every node, against ADR 0023's narrow footprint.

Everything the service does stays as sections 2.1 to 2.15 design it: the mirror and its push, the flip and its origins, the prepare, the adoption rule, the takeover job and its rollback, the reverse per phase. What changes is who performs the Windows half and the calls to Tenko, and how a script reaches operations that need an interactive session. [ADR 0038](../adr/0038-takeover-script-and-delegated-session.md) (Proposed) records the approval and the delegated session.

#### 2.16.1 The script

**Name and place.** `deploy/windows/takeover/Tenko-Takeover.ps1`, with its `README.md` and Pester suites; the three scripts are ASCII with CRLF line ends, which CI enforces, so that no editor, console or clipboard can change their bytes. The release carries, covered by `SHA256SUMS` and the release's provenance attestation, without an Authenticode signature (WT-Q15):

- **`Tenko-Takeover.ps1`, one file** with the exporter and the installer embedded as text in its data section, which the release run fills (a Pester test holds the embedded copies equal to the repository's files): the file the start line checks and starts, however it arrives.
- **The archive** `tenko-takeover-<version>.zip`: the same `Tenko-Takeover.ps1`, `Tenko-DhcpMirror.ps1`, `Install-TenkoDhcpMirror.ps1` and the README, each also a loose asset, so that one intake of the archive and `SHA256SUMS` brings everything a Windows takeover needs, including the separate files an organization signs. The script uses the exporter and the installer beside itself when they are there (an organization's signed copies), comparing each with the digest it carries, computed over the text before an Authenticode signature block so that the organization's signature does not change it; else its embedded copies. It copies exactly the bytes it hashed, so that nothing can swap a file between the check and its use.

The release run refuses to publish when any of these lacks its digest or its attestation, and writes the start forms below, filled with the tag and the digests, into the release notes. The script refuses a node whose version is not its own (the version `GET /health` names): a compatibility gate the node controls, never a check of origin.

**Its language.** The script needs PowerShell's Full Language: it builds the TLS chain, signs with the run's key and hashes through .NET types that Constrained Language refuses. It compiles nothing at run time: no `Add-Type` (an assembly compiled at run time is code that no signature on the file covers, and Constrained Language refuses `Add-Type` of C# outright), no script block made from text, no self-modification, so that the file as released is the whole code and an organization can sign it and have its application control policy allow it. Its HTTP helper is plain PowerShell over .NET types: a `TcpClient` and an `SslStream` whose certificate check is a synchronous callback run while `AuthenticateAsClient` returns, and HTTP/1.0 requests and answers read and bounded by the script itself. The exporter's certificate check, a C# class compiled with `Add-Type` today, moves to the same form (WP14.5; R225), since the exporter runs under the mirror host's policy too. At start the script reads `$ExecutionContext.SessionState.LanguageMode` and, when it is not `FullLanguage`, stops with exit 1 and says that the domain's AppLocker or App Control for Business policy must allow the file, by the organization's signature or its hash (Microsoft's pages: under such a policy PowerShell runs a script the policy does not allow in Constrained Language, and one it allows in Full Language). Where App Control for Business enforces on the controllers, a remote session there runs in Constrained Language whatever the script's own mode, so the script blocks it sends use cmdlets and core types only and return the cmdlets' output; the exporter's mapping, the configuration hash of the window's cross-check, the hashing and the HTTP helper all run on the script's own host, and a Pester suite runs every remote block in Constrained Language.

**The principle.** Text pasted into a console cannot be verified by Windows, by any signature or digest: its only protection is the place it was copied from and the machine it was copied on. Domains administered in tiers say the same in their own terms: a domain administrator's session runs no content from a lower tier, and a page of an application server is a lower tier. Therefore no page of Tenko shows the script, a command line or a digest to copy. The **Windows takeover** page says in plain words which release to take (the one whose version it shows, the node's own) and which file, and the release, brought in by the domain's own intake or opened on the release page, is the source. Whether the node should nevertheless show the script in a code box is WT-Q20.

**A copy on the node is not a source.** A file the account `tenko` can write, or that the web service serves, would hand a compromised service's file to a domain administrator. A copy owned by root and unwritable by the service, laid down by the installer from the release it verified and fetched by an administrator over SSH, was examined and is rejected: in-app updates move the node's version as the service account without root (ADR 0023, I3), so a root-owned copy lags the node's version until root runs the installer again, which I3 rules out as an update step; the installer verifies today only a digest fetched over TLS, the same footing as the domain's own intake; and in a tiered domain the copy still comes from a server the domain administrator does not run. It would hold only when root lays it down from a release whose signature root checks against a key compiled into the binary (API-19), refreshes it as part of every update by a root step the design then admits, and the node is administered as part of the domain's top tier, which as the authority of the AD zones it ought to be.

**The start.** The main case is a locked-down domain, the kind that runs the Hardened profile: nothing inside reaches the internet except update services that talk only to Microsoft, and neither the controllers nor the administrators' workstations can open the release page. Such a domain brought Tenko itself in through a controlled intake, fetched and verified on a connected machine and carried in. The takeover's files are part of the same release and come in by the same path at the same time: the archive `tenko-takeover-<version>.zip` and `SHA256SUMS`, beside the node's own release files.

**The start line.** One line, the same for every way the file arrives, with the tag and the verified digest built in:

```powershell
$f="$env:ProgramFiles\Tenko\takeover\Tenko-Takeover.ps1"; if ((Get-FileHash $f -Algorithm SHA256).Hash -eq '<sha256>') { Unblock-File $f; powershell.exe -NoProfile -ExecutionPolicy Bypass -File $f } else { Write-Error 'Tenko-Takeover.ps1 does not match the release digest; nothing was run.' }
```

It hashes the file on disk, compares the result with the digest in the line, and only then starts it; it replaces verify, unblock and run with one action. Since it hashes by path and then runs by path, the folder it reads from must be writable by Administrators only (the line reads `%ProgramFiles%\Tenko\takeover`, which only Administrators may write by default, where the person copies the file; the script warns when its folder is writable by others). The file is always on disk first, so that a resume and `-Reverse` have something to run. The scripts are ASCII with CRLF line ends, which CI enforces, so that a copy of the text pasted into Notepad and saved has the released file's bytes and the same digest; Notepad's save on Windows Server 2025 is checked in the rehearsal (T64), and the line's refusal names the digest it found, so that a save with a byte order mark shows as such. The release run writes the line and its fetching form into the release notes; the intake's check command prints the same line after its own checks. On an open network the line from the release notes is as strong as the account that publishes the releases, which the README states and the owner protects with a hardware security key. The facts the line rests on, from Microsoft's page on execution policies: the policy "isn't a security boundary"; `curl.exe` and `Invoke-WebRequest` "may not mark" a downloaded file as coming from the internet, and `Unblock-File` removes the mark when there is one (a file without one is left as it is), so the line does not depend on which it is; `-ExecutionPolicy` on `powershell.exe` sets the policy for that process only, where `Bypass` blocks nothing, whatever the machine's own policy (Windows clients default to `Restricted`, servers to `RemoteSigned`); and a policy set by group policy (**Turn on Script Execution**) overrides every scope, the command line included. Under such a policy the person sees PowerShell's refusal: with **Allow only signed scripts**, that the file "is not digitally signed"; with script execution turned off, that running scripts is disabled. **Allow local scripts and remote signed scripts** lets the unblocked file run. Under the other two the line cannot start the script on that host; the organization signs the archive's scripts (the intake table above), or the person runs it on a host where the domain's policy allows local scripts, or has the policy's owner allow them there, and the README says so (the scripts cannot be signed, WT-Q15).

**What the script cannot verify about itself.** Its own origin and integrity: a changed copy would change its own checks too. That check is the intake's verification or the line's comparison, made before the script starts, and it is as good as the release it verifies and, for a pasted line, the page the line and the text came from and the workstation they were copied on: a workstation that can change the clipboard can change the line's digest with it. An organization's own signature then proves that the file is the one the organization verified and approved. The release notes belong to a release whose files carry the release run's attestation; the README gives `gh attestation verify` for whoever wants the stronger check, on any machine. Once started, the script checks the payloads it carries against its own copy of their digests, which proves only that the file is whole, and nothing about where it came from.

**The host, the process and the credential.** The script runs only elevated, as an account of the domain's administrative tier, on a controller or on a dedicated administration workstation (a privileged access workstation), never on an everyday workstation or on a member server whose local administrators are of a lower tier: a Domain Admins credential must not sit in a process that a less privileged account could read or feed (ADR 0023's rule, turned the other way). It checks before anything else that its token is elevated and holds Domain Admins, refuses otherwise with exit 1, and sets its module path to the system's module directories only, so that no module from a user-writable path loads. It uses the logon it runs under for its Kerberos sessions and asks for no credential (WT-Q18, decided): the domain administrator's secret is never in the script's memory, never written, never sent to Tenko. The state file's access list (SYSTEM and Administrators) matches the elevated process.

**What it needs.** Windows PowerShell 5.1 with .NET Framework 4.7.2 or later (the exporter's minimum), WinRM to every controller and to the mirror host, and HTTPS to the node. The machine it runs on has no effective Name Resolution Policy Table rule that lists name servers for the domain or for its locator names: such a rule sends the query to its own servers whatever server `Resolve-DnsName` is given (measured on 2026-11-22, also with `-DnsOnly`, `-NoHostsFile` and `-TcpOnly`; a rule without name servers redirects nothing, and a more specific rule inherits the servers of a covering one), so the check after the DNS window that Tenko itself answers the locator records would prove nothing. The script reads the effective policy before any change and again before that check, and stops where such a rule exists or the policy cannot be read; a reverse is never stopped by it. Every CIM and remoting session uses `-Authentication Kerberos` and the host's FQDN as Active Directory reports it: never `Negotiate`, which falls back to NTLM, never an address, never a `TrustedHosts` entry, never CredSSP, never a session option that skips the certificate or name check. The script changes no WinRM, firewall or CredSSP setting on any machine, and it never makes a second hop: each server it acts on is reached by its own session from the script's host. It needs no module of its own: every Windows cmdlet runs in a session on a server that holds the module with its role (the controllers hold `ActiveDirectory`, `GroupPolicy`, `DnsServer` and `DhcpServer`).

Windows PowerShell 5.1 is the supported and lab-tested runtime. PowerShell 7 runs the script too, but hands its certificate check the chain the platform built, which may take an authority from the machine's own stores, so there the pin still binds a chain verified by its signatures to the approved root while the proof that the node itself presented that root holds on 5.1 only. In internal CA mode the API listener presents its root after the leaf, and the script's pin relies on exactly that: a chain the platform verified by signatures from the node's leaf to the root the person approved, built from what the node presented (amended 2026-11-21). When the node's name resolves to both address families the script tries IPv4 first, since the approval's bounds count an IPv6 /64 as one source (R233); it moves to the next address only when one takes no connection, never after a TLS refusal or any other failure.

**Parameters.** None is required. Started without one, the script runs or resumes the next phase, and when the state file shows a run it offers to reverse the latest phase instead; `-DryRun` discovers and prints the change list, changes nothing on Windows and contacts no Tenko; `-Reverse` undoes the latest phase done, both halves, and run again walks one more phase back. The script asks for the domain (the domain the machine is joined to is offered), for Tenko's address, given only as a host name under the domain whose first label is the node's name in the zones (`tenko.corp.example.test`; no literal address), a name no computer account or service principal name of the domain holds and that resolves to the node only, port 8443 unless written `host:port`, and for the mirror host, chosen from the list of the domain's reachable member servers. A resumed run reads the domain and the address from the state file and shows them.

**Two runs never interleave.** The script holds an exclusive lock on its state file while it runs, and writes a run marker (the run's id, the host, the time) under an administrators-only key on the PDC emulator through its session (`HKLM\SOFTWARE\Tenko\Takeover`); a second process or a second machine that finds a marker of another run stops with exit 1 and names it. The marker also records a pending barrier of the DHCP window (section 2.17), which a sitting without the state file reads from there and finishes. The marker goes with the run's end or its full reverse. The node's rule of one open run per domain is a second line, not the first.

**A zone that takes secure updates only.** Each zone keeps the update mode it had on Windows (WT-Q16), and there is no fallback to unsigned updates for a zone that took secure updates only. Until the Kerberos line of [identity-plan.md](identity-plan.md) (WP13.0 to WP13.4, with E44) is complete in the release the script comes from, phase 0 finds such a zone, changes nothing and stops with exit 1, printing: "The zone corp.example.test takes secure updates only. This release of Tenko cannot yet take over a zone that takes secure updates only without weakening it, because its secure updates (the Kerberos line of the identity plan) are not complete. Nothing was changed. Take over this domain with a release whose notes say the Kerberos line is complete." The script knows it from a constant of its own release, never from the node. Since secure-only is Windows' default for an AD-integrated zone, this holds most domains until then.

**When a step fails halfway.** The script stops at the step, records it as failed with its error, and prints two choices: run again, which resumes at the step after reading the actual state, or `-Reverse`, which undoes the phase's done steps in reverse order. A failed takeover job rolls itself back (section 2.7); the script then makes Windows answer again (section 2.17). When Tenko cannot be reached, `-Reverse` offers the Windows half alone: it warns that a node whose API is unreachable may still serve DHCP, so that a Windows server made to answer again would answer beside it (conflict detection, which the reverse turns on, limits the damage), and goes on only when the person confirms; Tenko's half is then recorded as pending, so that Windows can serve again without the node.

**The state file.** `%ProgramData%\Tenko\takeover\<domain>\state.json` on the machine that ran the script, beside the backups of phase 2. Every level of the state directory, and every work and backup directory the script uses on a remote host (under `%ProgramFiles%\Tenko\` there), is created closed: SYSTEM and Administrators only, set at creation, never afterwards; an existing level whose owner is not SYSTEM or Administrators, that grants write to anyone else, or that is a reparse point stops the script with exit 1. A file the script runs or dot-sources from such a directory is hashed again from its bytes just before it is used. It holds the run's id, the script's version, Tenko's address and the pinned fingerprint, the plan, each step with its state and time, phase 0's readings (the controllers and their addresses as Active Directory reports them, the locator's answer, the zones and their settings), and the record set of each zone read from Windows at the flip, the servers whose service this run stopped, and the values the reverse restores (the transfer and notify lists, the replication scopes, the lease times, conflict detection's value read in phase 0, the objectGUID or SID of every object the run created, the task names, the mirror ids, the group policy object's id). It holds the secret of the run's marks and no password, token, session or code. The reverse restores values only from this local file, and each only when it is of a class the sitting's own fresh discovery confirms: an address of a controller as Active Directory reports it now, or a value present at that discovery; anything else stops the reverse with exit 4. What the reverse writes to Windows from Tenko is bounded to two things: the lease values of section 2.17, and a zone's records after the person confirmed every difference from the record set read at the flip (phase 4). An object the run creates (Tenko's computer account, the exporter's account, the DHCP servers' DNS-update user, the group policy object) is recorded by its objectGUID or SID at creation, and carries the run's mark in its description: SHA-256 over a secret of the run and the object's name, so that a mark anyone can read fits no other name. The secret is recorded in the state file before the run creates its first object, so that a sitting that ended between a creation and the record of its SID knows the object as its own by its mark, but only while no one made it under the machine account quota, the domain's Domain Admins own it, and no principal outside the closed list of SIDs may write it (amended 2026-11-21). Any other object of the run's name is never adopted and never deleted: the step refuses with exit 1 and names it, and every removal is by the recorded objectGUID or SID. A run resumed on another machine discovers again and reverses a setting the first machine changed only when the person confirms the value shown, which must again be of phase 0's classes on that machine. Whether `Export-DhcpServer` writes a relationship's shared secret into the backup is read in the rehearsal (T10); the backup directory has the state file's access list either way.

**Exit states.** 0 the phase is done (for the DHCP window also when no client has been answered yet, with the warning of section 2.17); 1 refused before any change (a precondition, a right missing, the person declined); 2 stopped at a failed step (named in the state file); 3 waiting for the person's review or for the parallel period, or the DHCP window aborted at its choice (Abort, the default, changes nothing); 4 a value from Tenko disagreed with Windows, and nothing further was changed; 5 reversed.

**Rules for its code.** No `Invoke-Expression`, no script block made from text, no command line built from a value: every value is bound to a typed parameter (`[ipaddress]`, `[int]`, a string checked against its pattern). A remoting session runs script blocks written in the script, with values as arguments. Text from Tenko (an error's detail, a name) is printed only after control characters are removed and its length bounded, so that an answer cannot write escape sequences into the console. Every request to Tenko goes through the one HTTP helper of the script's language paragraph: it accepts only `application/json` answers and parses them itself into the fields the script reads (a Pester suite feeds it malformed, truncated, oversized and slow answers), follows no redirect, caps an answer's size and time, and holds the delegated session's secret and the one-time password of Tenko's computer account inside itself, taken from a `SecureString` and never passed as a parameter of a cmdlet or a function, so that module logging and transcription, which hardened domains turn on by group policy, record neither. `Invoke-WebRequest` and `Invoke-RestMethod` are not used at all (the first parses HTML with the Internet Explorer engine in Windows PowerShell 5.1 unless told otherwise; both follow redirects and pick a parser by the content type the node chooses). Groups and rights are compared by well-known SID, never by name, since names differ on a localized Windows: the remote blocks return each access entry's identity translated to a SID, and the checks hold a closed list (S-1-1-0 Everyone, S-1-5-11 Authenticated Users, S-1-5-18 SYSTEM, S-1-5-10 SELF, S-1-5-32-544 Administrators, and the domain's RIDs 512, 513, 515, 519, 526 and 527); Domain Admins is RID 512 of this domain's SID. A Pester test fails on any of these constructs, beside PSScriptAnalyzer's rule file of the exporter.

#### 2.16.2 The approval

The flow is the device-authorization pattern of RFC 8628 with the code computed on both sides instead of sent:

1. The script makes a P-256 key pair in memory (`ECDsaCng`, .NET Framework 4.7.2) and connects to the address. **The root it binds** is the self-signed end of a chain it builds from the leaf by signature verification, using only the certificates the server presented, with the host name matched against the leaf: the algorithm of the exporter's pin check (`Tenko.Mirror.Pin.Accepts` in `Tenko-DhcpMirror.ps1`), in the plain-PowerShell form both scripts then share. A partial chain is refused, and the last certificate the server lists is never taken as the root: an interceptor could append Tenko's real root to its own chain, and the code would then match. The script sends `POST /api/v1/auth/approvals` (no credential) with the purpose `windows-takeover`, the **plan** (the domain and forest root, the controllers, the zones, the forwarders, the DHCP servers, the relationship, the scopes, the mirror host, the node name, and the operations of section 2.16.1's phases), the public key as its uncompressed point, the script's version, the machine's name and the Windows user's name. Tenko validates the plan against its own rules (below) before it accepts the request, and answers with an approval id and a nonce; nothing else. The script refuses an answer that arrives more than 5 s after it sent the request, by its own stopwatch, or whose id is not of the exact form.
2. Both sides compute the **code**: the first 80 bits of SHA-256 over a fixed context string, the domain, the SHA-256 of the root, the SHA-256 of the plan as sent, the public key and the approval id, written as sixteen characters of Crockford's base32 in four groups (`K7QD-M2XR-9FHA-T4WB`). With the 5 s limit a search for an approval id whose code equals another approval's is beyond reach. The script shows the code with the address to open, `https://<address>/approve`.
3. The person signs in to the UI (under Hardened with a passkey) and types the code. Tenko compares it with the code it computes over its own root for each pending approval, in constant time, and refuses a code that matches two. A match shows the request: the plan in full (zones, controllers, servers, scopes, the mirror host, the node name, the forwarders, the operations); the machine and the Windows user, labeled as reported by the script and rendered as text; the source address and its reverse name. A code that matches nothing is refused; a script that reached Tenko through an interceptor computed its code over another root and cannot match, so the person's comparison of identities is the typing of the code itself. Approving is a second submit and needs a sign-in within the last five minutes (`require_fresh_person`).
4. The script collects with `POST /auth/approvals/{id}/collect`, signing the nonce with its private key (a 64-octet ECDSA signature); Tenko answers once, with the delegated session's secret, which the HTTP helper parses itself, never through `ConvertFrom-Json` or any other cmdlet, since module logging records what a cmdlet is given. The approval is consumed. An approval that is denied or withdrawn, or whose approving administrator signed out everywhere, was disabled or lost the administrator role before the script collected it, is never collected: the script says so and offers a new approval with a new code. The script pins the root as soon as the approval's answer is checked, before it shows the code, so that every collection poll and every later call must chain to the same root, and no call that carries or fetches a secret runs unpinned; it later hands the same fingerprint to the exporter's install, so no fingerprint is copied by hand.

**The run.** The first collect of a domain creates its run (`migrate.runs`, the plan in `migrate.run_plans`, the domain's one open run in `migrate.run_domains`), and every later sitting whose plan is equal joins it: its delegated session acts for the same run, so everything any sitting creates names the run. The lookup and the approval show the person the run an approval would join (its id, start, number of sittings and the newest sitting's source address); a plan that differs from the open run's is refused at the approval and at the collect (409 `migrate.run.plan`). A run keeps its newest 64 sittings and one mirror per DHCP server of the plan, and the next sitting gets a new mirror for a server only when the old one was deleted. Only a person ends a run: `POST /migrate/runs/{id}/close`, from a session that signed in within five minutes, after the run's mirrors are deleted and while none of the zones the run created is left unserved (amended 2026-11-26: the second condition; a zone of the run that a flip serves does not hold the close), deletes its rows and its sittings' sessions in one batch; a session the run no longer lists reaches nothing but its own sign-out.

The approval works only when the script and the browser reach Tenko's own TLS on the API port. Behind a reverse proxy that ends TLS, the script builds a chain to the proxy's root, the code never matches, and the run cannot start; it fails closed, and the script says why when the root it built is one the machine's own store trusts.

**Tenko's own limits on the plan.** The zones are the domain, `_msdcs.<forest root>` and the reverse zones covering the plan's scope networks, nothing else; at most 16 controllers, 32 DHCP servers and 256 scopes. Every body the run's session sends is checked against the plan in the route's handler: a zone is `kind` secondary, `catalog` false, scope `default` alone, no tenant, its primaries exactly the plan's PDC emulator, and it is created **not served**; a forwarding rule names a plan forwarder's zone and is created inactive, and a rule for `.` is never written by a run (it is a `decide` row of the window; amended 2026-11-26: a run writes no forwarding rule); the flip's SOA and NS name the plan's node name; `transfer.allow` and `notify` name the plan's controllers; the Kerberos adoption names the plan's account; a mirror names a plan DHCP server and the mirror host's address as a /32. Nothing a run creates answers or forwards before the window: the serving index leaves its zones out and its forwarding rules are off until the flip, so the window's decision covers everything that serves.

Bounds: at most two pending approvals per source (an IPv4 /32 or an IPv6 /64), 64 in all, ten minutes each by Tenko's own clock; one request per source every 10 s; one open run per domain; a body of at most 64 KiB parsed with strict types; the machine name a NetBIOS or DNS label and the user `DOMAIN\sAMAccountName`, ASCII only and bounded, so that no bidirectional control or look-alike character reaches the page; five wrong codes from one browser session within ten minutes lock its lookups for ten minutes. An administrator who signed in within five minutes denies the waiting approvals of one source or of all, also approved ones not yet collected, in one audited step, which is the answer to a host that fills the bounds (R233).

**The delegated session.** A session of the approving administrator (`Principal::User`, so that every rule that asks for an interactive session reads it as one), with one new field, `delegation: Option<DelegationId>`, on the session record and on the principal, so that every audit record names the run. It is presented as `Authorization: Bearer tnka_…`, never as a cookie, so no browser carries it and no cross-site rule applies, and it is accepted only from the source address of its approval request (another address is answered as an unknown session and audited); the HTTP helper binds its local endpoint to the local address of the approval's connection, so that a temporary IPv6 address or a second interface does not move it, which leaves a leak on the script's own host as the one case, the case for which a proof of the key on every request was left out. It is not a token: the token API neither creates, lists nor renews it, and a personal token never becomes one.

**It is never fresh.** `require_fresh` and `require_fresh_person` refuse every delegated session, so that no account self-service operation (a token, a passkey, TOTP, a password where none is stored, deleting a credential, revoking sessions) and no other operation behind a recent sign-in is ever reached through it. The one operation of the set that needs freshness, creating a mirror (which mints its token), is checked by an explicit rule of the delegation against the approval's time: within five minutes of it, in phase 2's first minutes; a later sitting needs a new approval. Pairing the run's two mirrors and deleting a run mirror are held to the same five minutes (amended 2026-11-26), and a sitting deletes only a mirror made before its own approval, so that it never deletes a mirror it made itself.

**Where it is enforced.** A default-deny allow-list of (method, route template), one condition per entry, and one check, `AuthService::admit_delegated`, which the authentication layer calls for every request of a delegated session before any handler runs (and the request context again where the layer did not run): a delegated session reaches no route that is not on the list, whatever the route itself checks, and the account routes, which call `AuthService::current` and never `authorize`, are therefore closed to it. In this order it refuses, with 403 `auth.delegation.refused` and `params.reason`, an unlisted route (`unlisted`), a listed one whose condition does not hold (`condition`), and every request of a session whose run (`migrate.runs`) is not open (`run`) but its own sign-out; then every object a listed route's path names, read from the path parameters as the router decoded them for the handler, must exist and be the run's, and a missing object and an object of another run answer the same 404 (`migrate.run.not_found` for a run), so the session never learns that objects outside its run exist; the audit says which. Each refusal is audited as `auth.delegation.refuse` at most once a minute per session and outcome, a pace in each controller's memory. Inside the list, `authorize` applies the approver's rights as for any session, and each handler on the list checks its body against the plan (above). The list (`delegation::TAKEOVER` in `tenko-auth`), by stage:

| Stage | Operations |
|---|---|
| Always | The reads of the run (`GET /migrate/runs/{id}`, its own run only), its zones, mirrors (snapshot, losses, diff), jobs and takeovers; `GET /system/ca-root`; the end of its own session (amended 2026-11-26: no phase reports) |
| Before the window | Create the plan's secondary zones, not served, and transfer them; the inactive forwarding rules of the plan's forwarders (amended 2026-11-26: none, and no transfer call: the secondaries are due at once); the plan's zones' update policy and Kerberos settings; `POST /dns/kerberos/adopt` for the plan's account; create the mirrors of the plan's DHCP servers bound to the mirror host's /32 (within five minutes of the approval, by Tenko's clock), pair them (amended 2026-11-26: within the same five minutes, each with the run's other mirror only, in a plan of two DHCP servers, and with no other change of a mirror); the prepare of the plan's scopes |

| Never | Every `/auth/*` route but its own end, users, tokens, sessions, settings, the profile, backups, secrets, approvals, starting the window, any object outside the plan, any body outside the plan (403 `auth.delegation.refused`) |

**Lifetime and revocation.** The shorter of eight hours and the profile's absolute session lifetime, with an idle limit of 15 minutes under every profile, both measured by Tenko on its own clock from the approval and from the session's last request, never against a time the script sends: the script reads its run while it waits, which records the request, so a killed script's session lapses within 15 minutes instead of the profile's idle limit. Every request records the session's activity before the check, so a refused request keeps it alive too; a client that neither signs out nor stops holds its run's domain until its lifetime ends, unless a person revokes it. It ends when the run is waiting for the parallel period, done, aborted or reversed; when the script ends (it revokes its own session); when a person closes the run (`POST /migrate/runs/{id}/close`); when the person presses **Revoke** on the run page or revokes it in the session list; and, as every session, when the approver is disabled or loses the administrator role.

**Audit.** `auth.approval.request` (at most once a minute per source), `.approve`, `.deny`, `.collect`, `.refuse` (a code matching nothing, once a minute); `auth.delegation.refuse` (a refused request of a delegated session, once a minute per session and outcome); `migrate.run.create`, `.join`, `.close`, `.phase`, `.window`, `.abort`; and every operation the script calls, with the approver as principal and the run in `delegation`. The run page lists them.

**The flip's interactive rule.** The flip refuses everything but `Principal::User` (`needs_a_session` on `feat/zone-flip`), and `interactive_only` refuses every token on the kinds `mirror` and `takeover`. A delegated session is a `Principal::User` created by a person's fresh interactive approval of one run; it reaches the flip and the takeover only for the plan's objects and only after the person started the window with a second fresh interactive action that a delegated session can never take. A token gains nothing: it stays `Principal::Token`, the rules refuse it as today, and nothing converts one into the other. The allow-list stands before every handler, so the flip's route needs no change, and no route outside the list (the account routes among them) is reachable at all.

#### 2.16.3 Trust

**The script is the released one.** The start forms of section 2.16.1 compare the file or its text with the digest the release notes print beside them, before anything runs; `gh attestation verify <file> --repo linkztream/tenko --signer-workflow linkztream/tenko/.github/workflows/release.yml` proves, on any machine, that the file came from the tagged commit's release run. Once API-19 delivers, the project's own release key signs `SHA256SUMS` ([upgrades.md](../upgrades.md)), and the README adds its check. Tenko never serves, generates or links a script, and no page of Tenko shows a script, a command line or a digest to copy: values only, as text (section 4.1 of [active-directory.md](../active-directory.md) already says so for its block).

**Tenko is the right Tenko.** The code binds the root the script built by signatures to the root the person's browser session reached (section 2.16.2, steps 1 and 3), and the plan to what the person read; the script pins the root for the run, compares `GET /system/ca-root` with it, and refuses a resumed run whose new approval binds another root. The exporter receives the same fingerprint. The anchor is the person's signed-in browser session on the node, as for every administrative action.

**A later sitting signs in only to the controllers it knew.** Once the node is the authority for `_msdcs`, it answers the DC locator and the `_kerberos` lookups of the script's host. Before a later sitting or a resume after phase 4 opens any session, the script compares the locator's answer (`nltest /dsgetdc:<domain> /force`) and the controllers' addresses with those phase 0 recorded in the local state file, and stops with exit 4 on any difference, so that a compromised node cannot steer the host's Kerberos exchange to a controller of its own.

**What a compromised Tenko node can still do to a takeover in progress:** lie about its own state (the script stops at the first check Windows or the node's DNS answers contradict, exit 4); refuse or stall (the script stops; `-Reverse` brings Windows back without the node); silence Windows early through the job's task, once the person confirmed the window at the console, which only advances what the person decided; read the plan, which the transfer gives it anyway. After the flip and the takeover it is an Active Directory-integrated DNS authority and DHCP server holding a domain computer account (WT-Q16), and a compromised one can do what such an authority can do in a typical domain: serve wrong records and leases and feed the controllers' secondary copies; steer names to hosts of its own and, with them, force a controller to authenticate to such a host (through the print spooler's or EFS's RPC interfaces) and relay that NTLM sign-in to certificate web enrollment without Extended Protection or to LDAP without signing and channel binding; request service tickets of accounts with a service principal name for an offline guess of their passwords; create computer accounts up to the domain's machine account quota (ten by default), which feed delegation attacks; and answer `wpad` and `isatap`, which clients look up to find a proxy or a router. In many domains that is a short path to Domain Admins. Phase 0 reads the settings these paths need and lists them as warnings (section 2.16.1, discovery); Tenko answers no query for `wpad` and `isatap` in a run's zones unless an administrator allows a name, matching Windows' global query block list; the node's name is deny-listed; Tenko's account has no delegation and sits in a container Windows names. The owner accepts the rest, or not, in WT-Q19. **What it cannot:** obtain the Windows credential; make the script run code; make it act on an object Windows did not report; start phases 4 and 5 without the person at the console; point a controller at an address other than the one the person typed and the pinned connection reached; supply a value the reverse restores; change the exporter or the group policy object; obtain a delegated session without a person typing the code of a script on that person's screen, for a plan that person read. The delegation guards against a stolen session, not against a compromised node, which enforces its own rules; the Windows side is guarded by the script's checks.

#### 2.16.4 The mirror

The scheduled exporter stays, and the script installs it in phase 2, one task per DHCP server, and removes it in phase 6. The parallel period needs fresh data (the error finding `migrate.mirror.scope_active` when a Windows scope turns active again, section 2.10), and the review needs a diff over pushes the person can read before the window. A script that pushed snapshots itself during its run would leave no token at rest but nobody watching during the week of the parallel period: two servers could answer one network unnoticed. By the priority order the installed exporter wins on security (the bounds ADR 0033 measured, and the watch) at equal performance, and with the install automatic, at equal usability.

Where it runs (WT-Q17; the one place that states both paths): the manual install of `deploy/windows/mirror/README.md` puts the exporter on the DHCP server itself, as built, and stays for a mirror set up by hand; the scripted path puts it by default on a member server that reads each DHCP server over RPC (`-ComputerName`, a new parameter of the exporter, reporting the server's FQDN as `source.server`), which a member of `DHCP Users` can do for all fourteen read cmdlets (measured). Nothing of Tenko then lands on a controller, and the controllers' Default Domain Controllers Policy needs no batch logon right for the task's account. The exporter is also the one Windows process that parses a compromised node's answers: on a member server a flaw there yields an account in `DHCP Users`, on a controller it would yield a foothold in the domain's top tier. The price is that the mirror host's local administrators could read the tokens and forge pushes, which the diff and the window's configuration binding guard, and which phase 0's warning about them names. The script installs with the built installer through a remoting session: the two files copied with `Copy-Item -ToSession` and checked by digest there, the token passed as a `SecureString` to `-Token` (encrypted in the Kerberos session), the account a group managed service account where the domain has a KDS root key (the script never creates one), else a user with a random password that exists only in memory and in the task's own store. The installer's own dry run is not used in the scripted path: inside the administrator's remote session it would read DHCP over RPC from the mirror host, a second hop that fails without delegation and that must never be mended with CredSSP. The first read is the task's own first run under its account, which also stores the token with DPAPI and deletes the installer's `token.pending`; the script waits for that run's push and checks that the plain file is gone. Phase 6 removes the batch logon right the installer granted on the mirror host with the task and the account. The scripted path needs three changes of the built installer, which the mirror's second package (WP14.1b) makes and on which phase 2 depends: `-ComputerName` for the server a task reads, `-SkipDryRun` so that no read runs in the administrator's session, and one task with its own data directory per DHCP server on one mirror host.

#### 2.16.5 Tenko's side

**What the measurements of 2026-11-20 settle, and the one that runs.** Each Windows DNS server keeps its own SOA serial and names itself as primary. Which of the two settings makes the difference, and whether `dc1` then sends a NOTIFY, was not observed. So the design depends on the source controller's copy having Tenko as secondary and notify target, which phase 2 sets and reads back before anything relies on the serial; it does not rely on NOTIFY arriving (Hardened refuses an unsigned one anyway): before the flip Tenko's secondaries refresh on the zone's SOA `refresh` (Windows' default 900 s, read in phase 0 and shown), so a write on the other controller is visible on the node within about three minutes plus that interval. The way back goes through a file-backed primary, restores the update setting explicitly, and lets every other controller load the directory copy by its own polling after its secondary is removed (about 145 s), one controller at a time while the PDC emulator answers. ### 2.17 Windows silent, never a deactivated scope (amended 2026-11-21)

**What was measured** (Windows Server 2025, the failover pair, a Windows 11 client, 2026-11-20). A deactivated scope answers the client's next renewal with a DHCPNAK, and the client drops its address and default route in the same second although its lease had minutes left; it then sends DISCOVERs, gets no offer and takes an APIPA address after eleven seconds. A silent server (its service stopped) does not: at the renewal the client sends two unicast REQUESTs, gets nothing, and about five seconds in sends one broadcast REQUEST, which another server holding the lease may ACK (the failover partner did, with no address change). Renewal REQUESTs carry no server identifier. The client does not switch its renewal target afterwards. Filter lists are per server and failover does not carry them. Deactivating the Windows scope, the first design's step, would therefore cut every client's connections at its next renewal. The takeover instead makes Windows silent while Tenko, already holding the adopted leases, answers the broadcast REQUEST.

**The ways to silence Windows**, in the priority order:

| | Security | Performance (the silent gap) | Usability (the reverse) | Fit |
|---|---|---|---|---|
| (a) The DHCP Server service stopped on both servers, its start type set to disabled | Nothing listens on port 67; the script reads the silence back (the service stopped, nothing bound to UDP 67) | Seconds: the final pushes are taken just before, so Tenko answers in the next step | The service started again, its start type restored | Independent of filter lists; the exporter reads nothing afterwards, so the final lease read is the push just before the stop, and a lease Windows changed in those seconds is taken back by the engine's rule for a free pool address (below) |
| (b) An enabled, empty Allow list on both servers, the service running | The service keeps listening and parsing | Seconds once a push after the switch arrives | One switch per server | The exporter keeps reading, so the final push is exact and the watch continues; not for a domain that already uses filter lists; a filtered REQUEST is dropped silently (measured, event 20097) |
| (c) The authorization removed from the directory | The service stops answering only when it next checks its authorization | Unknown, not immediate | `Add-DhcpServerInDC` | Every scope of the server; not a step of the window; removed right after the silence as the second barrier (below) |

The decision: (a) by default, security first; (b) offered where the measurement shows a silent drop and the domain uses no filter list; (c) never as the window's step, but as the second barrier below. The lab's fourth round (2026-11-21) measured all three toward a Windows 11 client: with an enabled, empty Allow list, with the service stopped on both servers, and with both servers not authorized, a renewal gets no answer and no NAK, and the client keeps its address until its lease ends (it retries in rounds, at the end of the lease sends one INIT-REBOOT request and only then removes its address). Under (b) each dropped packet is logged as event 20097 in the server's filter notifications log and nothing in the DHCP audit log. The design's dependency holds (R226, resolved).

**What the stop silences, and what phase 0 therefore reads.** The service is the DHCP Server service, `DHCPServer`, named exactly and never `Dhcp`, the DHCP client, which a controller needs for its own DNS registration. Stopping it also silences the server's DHCPv6 scopes, with the DNS options of stateless DHCPv6, and its multicast scopes: phase 0 reads `Get-DhcpServerv6Scope` and `Get-DhcpServerv4MulticastScope` on each server, and method (a) is refused while one exists that Tenko does not take over. Phase 0 also reads whether a group policy sets the start mode of `DHCPServer` (the System Services settings of the policies that apply to the controllers); such a policy would start the service again at its next application or a reboot, so the window is refused until the policy's owner changes it, and the change list names the policy.

**The second barrier.** Clients keep sending their renewals by unicast to their old Windows server through the parallel period and after (R227), so a Windows server that starts again would answer them at once. It would not refuse them: a Windows server answers a renewal for a lease it no longer holds with an ACK and a new lease of the relationship's MCLT, one hour (audit event 10, measured on 2026-11-21). The danger after a takeover is therefore re-capture, a restarted Windows server taking the clients back one renewal at a time, and two servers serving one network, not a loss of addresses; the second barrier, the finish and the alarm are judged by that. A stopped service can be started again by a group policy, Server Manager's offer, a monitoring tool, an administrator, or a step that needs the running service. So right after Tenko's silence task is completed, the script also removes the authorization of both servers from the directory (`Remove-DhcpServerInDC`), forces directory replication (`repadmin /syncall /AdeP`), and reads the removal back against each controller's own replica for a bounded time (below); only then does it count the barrier as in place. A server reads its authorization from the replica on its own controller when its service starts: a removal not yet replicated there is not seen (measured: a server started four seconds after the removal served for about a minute, logging event 1044). An unauthorized server logs system event 1046 within about four seconds of its start and serves nobody, while its scope still reads active and its failover relationship still reads normal (measured). The stopped service needs no restart for the removal to matter: it matters at the next start, by whoever starts it, and event 1046 is the check after any later start. The reverse adds the authorization back (`Add-DhcpServerInDC`) while the service runs unauthorized, forces replication, reads it back on each controller and only then restarts the service, since a server started before the replication logs 1046 and stays silent (measured). The alarm for a Windows server that answers again stays (below).

**The signal and the final lease read.** The takeover script drives both sides, so it tells Tenko directly instead of Tenko inferring a state from a push: it requests the final push of each mirror (the job's step 2), waits until Tenko has accepted a push of each mirror after the job's start, in Tenko's own order of events (a sequence above any accepted before the start), lets the job adopt the records and leases while Tenko's scopes stay disabled, and then, in this order (amended 2026-11-21):

1. The person's approval of the stop: in a single sitting, the DNS window's typed confirmation, which showed this warning, when the stop begins within 15 minutes of it by the process's monotonic stopwatch; otherwise, and in every resumed or split sitting, one choice at the console, Abort or Continue, with Abort the default, which changes nothing and ends the sitting with exit 3. The warning says what happens next (the DHCP Server service stopped and disabled on the named servers, Tenko answering their scopes at once, the authorizations removed right after) and how to go back (`-Reverse`).
2. The DHCP Server service stopped and disabled on both servers and the silence read back on each with its own session, as a hard condition: when it cannot be read back, both services are started again as they were and Tenko stays off.
3. The job's silence task completed at once (step 5), so that Tenko answers within seconds.
4. Then both authorizations removed, replication forced and the removal read back on each controller's replica, every 5 s for up to 300 s. A replica that has not caught up by then does not stop the run: the barrier is recorded as pending in the state file and beside the run's marker on the PDC emulator, a warning names the controllers, and the check step and every later sitting read it again until it holds, while the services stay stopped and disabled; a sitting without the state file finds the pending barrier beside the marker and offers to read the replicas again.

Whoever has chosen to migrate is committed at the Continue, and clients get no gap: Tenko answers as soon as Windows is silent, and the second barrier follows without holding them. The method of silencing is the script's own choice, recorded in its state file, never taken from the task. By hand, the operator does the same and completes the task.

**When Tenko's side fails after the silence.** The script tries the task's completion three times. When it still fails, or Tenko's job fails after it, the script reverts Tenko's takeovers first where any completed, then starts both Windows services again as they were, still authorized at that point, so that they answer at once with no wait for replicas, and its last lines say per scope who answers and what to run next. A reverse whose restart of a Windows service fails turns Tenko's scopes on again once every Windows server it started is stopped, disabled and read back, by the route that resumes a takeover (section 3.2), and that call is tried three times; a refusal by Tenko for the takeover itself stands, and the next reverse brings Windows back without asking Tenko again. A resume reads each Windows service again before it completes anything, stops one that answers again, and counts a completion already made as made.

**Before the stop, the console prints the lines that bring each Windows server back by hand** (fixed text in the script, the same in the README): `Add-DhcpServerInDC -DnsName <server> -IPAddress <address>`, `Set-Service DHCPServer -StartupType Automatic` and `Start-Service DHCPServer` on each server, with the names and addresses phase 0 read. A script killed between "Windows silent" and "Tenko on" leaves both sides silent; from step 5 on, the job never rolls back by itself into that state: it waits, shows the error "Windows silent since <time>, Tenko's scopes off", raises the error finding `migrate.takeover.both_silent` at once and alerts the person through the notification channels two minutes after the silence task's completion, by Tenko's clock. After step 6 the DHCP window's last step waits 300 s, by the script's stopwatch, for Tenko's first ACK in the taken-over scopes (Tenko's own counters, a gate), and when none comes it finishes with a warning instead of an error (amended 2026-11-22). A quiet network is the usual reason: a client that holds a lease asks its old server by unicast until T2, 87.5 percent of its lease time, and only a new, restarted or reconnecting client broadcasts, so minutes can pass with no request that Tenko could answer. The warning tells the person to prove the takeover with a renewal on any client (`ipconfig /renew`), and, if a client that asks gets no answer, to check the relay or the listener, or to reverse. The takeover then counts as done and unproven, the sitting ends as a proven one does (exit 3, the parallel period), and Tenko's dashboard shows "no client answered yet" for the takeover until its first ACK; that line belongs to the takeover job and is not yet built on the server. A failure of Tenko's side at the completion or in its job is the case above, in which the script brings Windows back itself.

**The order and the gap.** Tenko holds every adopted lease before Windows goes silent, and its scopes are enabled in the step after; until then they are not in the serving image and answer nothing (`crates/tenko-dhcp/src/config/image.rs` line 159; `Drop(NoScope)` in `v4/engine/mod.rs` lines 405 to 409), so at no moment do two servers offer different addresses. What a client experiences:

| The client | What happens |
|---|---|
| Bound, between renewals | Nothing |
| Renewing (T1) during the seconds of silence | Two unicast REQUESTs to its Windows server go unanswered; the broadcast one about five seconds in reaches Tenko once its scope is on, else the client retries later, keeping its lease |
| Renewing after the takeover | The same five seconds at every renewal, since the client keeps its Windows server as target, then Tenko's ACK; no address change (R227) |
| Rebinding (T2) | A broadcast REQUEST, answered by Tenko from the adopted row |
| A new client (DISCOVER) | No offer during the seconds of silence, then Tenko's offer at the client's next retry (4, 8, 17, 33 s) |
| A client restarting (INIT-REBOOT) | Tenko answers from the adopted row; a client Tenko holds no row for gets silence (RFC 2131), falls back to DISCOVER and is offered its old address when it is free |

The longest silence that costs nobody an address is the shortest remaining lease time among the clients. The script refuses the window when a scope's lease time is under an hour, and the silent gap of the window is seconds. Lowering the lease time no longer helps: it only shortens that margin and multiplies the renewals that pay the five seconds, so the script does not offer it (section 2.13, step 4). After the takeover every renewal ends in a broadcast that whoever answers first can take, which helps a rogue DHCP server: the README recommends DHCP snooping or a DHCP guard on the switches.

**What the built engine does, and what must be true of Tenko's scopes** (`crates/tenko-dhcp/src/v4/engine/mod.rs` on `75af2f27`):

- A broadcast REQUEST with `ciaddr` set, no server identifier and no relay is classified as renewing (lines 863 to 868; the engine does not see whether a packet was broadcast) and is ACKed when the client holds a bound row (lines 881 to 883, 994 to 997), by unicast to `ciaddr` (lines 1386 to 1393). An adopted row keyed by the client's own identity is renewed that way.
- An adopted row keyed by the other identity (section 2.8) is not the client's row for the engine, on four paths; nothing in `v4/` reads `adopted` yet, and WP14.2 content 3 builds the rekey rule on each before any window, with a row of E76 for each:
  - a local renewal or rebinding: the allocator finds the address held (`crates/tenko-dhcp/src/allocator.rs` lines 164 to 170) and `refuse` NAKs it on an authoritative scope (lines 873 to 879, 909 to 912); the rule: ACK;
  - a relayed renewal or rebinding: `if client.remote && bound.is_none()` returns `Ignore(NoRecord)` before any allocation (lines 887 to 888), so a relayed client would get no answer until its lease ends; the rule: ACK;
  - INIT-REBOOT: the `known` check reads only the leases by the client's own identity and the reservations (lines 895 to 906), so a restarting client is ignored, then DISCOVERs and is offered another address while the adopted row holds its old one; the rule: the row is the client's, ACK;
  - DISCOVER: `allocate` looks the client's lease up by its identity (`allocator.rs` line 245), does not find the adopted row, and offers past the adopted address (`mod.rs` lines 744 to 766), while `holds_lease` (lines 1034 to 1040) counts the client as new against its limits; the rule: offer the adopted address.

  A renewal answered from the renewal cache (lines 950 to 968) commits nothing; the first REQUEST of an adopted row must commit, so that `adopted` clears. A relayed scope also needs its gateway to forward to Tenko before the silence: the job's check refuses a relayed scope until Tenko has counted relayed packets from that scope's relay address within the last ten minutes of its own clock, which it drops while the scope is off but counts (WP14.2).
- `authoritative` is on by default (`crates/tenko-core/src/dhcp.rs` lines 624 to 627, per scope at 1044 to 1046): an authoritative scope NAKs a renewing client whose address another row holds (`crates/tenko-dhcp/tests/client_address.rs` lines 337 to 345) and an INIT-REBOOT for such an address, which would do to Windows' clients what the deactivated Windows scope did. The prepare therefore creates Tenko's scopes with `authoritative = false`, which answers those with silence (`crates/tenko-dhcp/tests/engine.rs` line 306); they stay so through the parallel period, and phase 6 returns them to the server's setting once Windows is gone.
- A renewing client Tenko holds no row for, on the listener's link, with a free pool address, is ACKed with a new binding (`crates/tenko-dhcp/tests/client_address.rs` lines 317 to 336): the take-back of a lease the final push missed. INIT-REBOOT without a row is silent (lines 893 to 906). A REQUEST that names another server is silent (lines 857 to 859).

**Two rules for every step and its reverse** (amended 2026-11-21). No step leaves both sides silent with no way forward: a step silences one side only when the other side serves or is ready to serve at the next step, and its failure path restores the side it silenced. No resume destroys what a later step needs: values read from Windows replace saved ones only once every read of the step succeeded, a resume never reads again what the state file already holds, and the discovery of a later sitting does not read a server whose service this run stopped, but takes what the state file recorded of it.

**The reverse.** The DHCP Server cmdlets talk to the running service, so the reverse first restores the service's start type and starts it on each server while the server is still unauthorized: it serves nobody (event 1046), while its cmdlets answer (measured on 2026-11-21 for the reads; R230 for the lease write). Then the leases are written into both Windows servers (`Add-DhcpServerv4Lease`, which Windows accepts and does not replicate, so on each server) and read back, so that Windows knows the leases granted while Tenko served; conflict detection on; the authorization added back, replication forced and the authorization read back on each server's own controller. Only then are Tenko's scopes made silent and the service restarted, so that it reads its authorization and serves (event 1044 read back), and only then is Tenko's revert recorded as final; a restart that fails turns Tenko's scopes on again. Under (b) the list is switched off instead of the restart. Tenko keeps answering until the restart, so the silent gap is the restart's seconds (R232). The write-back takes values from a node that may be lying at the moment a person reverses, so it is narrow: only an address and a client identifier and an end; never a host name, a DNS state, a description or a policy from Tenko, so that no name is planted that Windows would register or delete under the DHCP servers' DNS credential; the address state fixed to active; only addresses inside the pool and outside the exclusions that are no one else's reservation; the end bounded by the scope's lease time; the count bounded by the pool and checked against what the script itself read from Windows in phase 0. The pairs the script read before the stop, kept in its state file, are preferred; a lease new under Tenko is written without a name, and its client registers again at its renewal; an address Windows still lists is left as Windows has it. Windows answers a renewal for a lease it does not hold with an ACK and a new lease of one hour (measured, R228), so no client is refused either way; the write-back is there so that Windows does not offer a new client an address another client holds, with conflict detection as the second guard. Tenko never NAKs a client it adopted: a disabled scope answers nothing.

**The parallel period.** Under (a) the mirror goes stale at the takeover and stays stale: its task keeps running and fails to read, which is the expected state. Any push accepted after the completion of the silence task, in Tenko's own order of events, means a Windows server answers again, and that is the alarm, an error. Under (b) the pushes continue, and the alarm is a push after the silence whose filter list no longer silences the server. The findings follow (section 2.12). Nothing prepares a scope from a push accepted after the silence: such a push holds the configuration Windows has while silenced (under (b) the Allow list the script switched on), so the prepare and the diff of a taken-over scope read only pushes up to the sequence recorded at the silence.

**Clocks** (amended 2026-11-21). An adopted lease takes its remaining time from the Windows server's own clock and its end from Tenko's (section 2.8), so no offset between them enters a lease. The window still depends on the clocks agreeing, since the clients, the Windows servers and Tenko then share one lease space, so it measures them, and it is refused while the node's own clock guard holds the node's clock (the owner's decision of 2026-11-21 on the node's clock guard, a requirement of its own):

- **The offset.** The job measures each Windows server's offset as Tenko's reception time of the final push minus the push's `taken_at`, corrected for nothing else. It is measured where the difference is used, it needs no time from the script or from the node's answer, and its only bias is the exporter's read and transfer time, seconds and always in one direction. The window is refused above 60 seconds, with a message naming both clocks ("dc2.corp.example.test's clock is 74 s behind ns1's: its push says 11:58:46 UTC, ns1 received it at 12:00:00 UTC"). The job measures again from a fresh push just before the silence step and refuses there as well.
- **The Windows side's own time.** Phase 0 reads each controller's time service through its session (`w32tm /query /status` and `/query /source`, native commands that Constrained Language allows), and the domain's hierarchy, whose root is the PDC emulator. It warns when the PDC emulator takes its time from its own hardware clock or from no source, when another controller does not follow the domain hierarchy, or when a controller's last synchronization is old.
- **Every short timed rule runs on a monotonic stopwatch on the side that measures it,** never by comparing two machines' wall clocks:
  - the script: the 5 s limit on the approval's answer, the ten minutes for Tenko to change its computer account's password (judged by `pwdLastSet` against its value before, never against a time), the 15 minutes within which the DNS window's confirmation stands for the DHCP window, and the 300 s wait for Tenko's first ACK;
  - Tenko: the approval's ten minutes, the delegated session's five minutes of freshness for the mirrors, its idle cap and its deadline, the two minutes of the both-silent alert, the ten minutes of relayed packets, and the order of events that decides which pushes are final or after the silence (sequences, not times);
  - the lease-time margin of the window is a duration of each scope, compared with seconds of silence, and involves no clock.

**What changes in the follow-up package** (`feat/mirror-pair`, `0ceb1a21`, not merged). Before it merges: `migrate.mirror.stale_after_takeover` must not report the expected state of method (a) as an error (`crates/tenko-migrate/src/mirror/service.rs` lines 1375 to 1381); a stale mirror after a takeover is no finding, and the error is a push after the silence. And `migrate.mirror.scope_active` (lines 1396 to 1403), which reads the newest stored summary's `active` flag, would fire right after every takeover, since the Windows scopes now stay active: it must count only pushes accepted after the completion of the takeover's silence task, in Tenko's order of events (the sequence it recorded then), never by comparing a push's `taken_at` with a time of Tenko's, and under (a) any such push is the alarm, whatever the flag. What can follow: the condition for method (b), which needs the exporter to read the filter list's state (the follow-up's own item), and a severity on the status warning, which today has none (`crates/tenko-api/src/dto/system.rs` lines 641 to 649).

## 6. Owner decisions

Each question lists its options, the trade-offs and the recommendation. The owner decided WT-Q1 to WT-Q7 on 2026-11-01 and WT-Q8 to WT-Q12 on 2026-11-05; each ends with the decision. WT-Q13 and WT-Q14 were decided on 2026-11-20. WT-Q15 to WT-Q20 came with section 2.16 and were decided on 2026-11-20 as recommended.

**WT-Q1. How does the Windows DHCP data reach Tenko?**
- Options: (a) a scheduled PowerShell script on a controller pushes to Tenko's API over HTTPS with a token scoped to write one mirror; (b) Tenko pulls over WinRM with PowerShell remoting, as MIGRATION.md's design said; (c) a Tenko component installed on the controller that Tenko instructs; (d) a periodic `Export-DhcpServer` file copied to Tenko by hand.
- Trade-offs: (b) needs Kerberos or NTLM credentials with DHCP rights stored in Tenko, and a channel through which a compromised Tenko runs commands on a controller; (c) is the same channel with an installed foothold, which the privilege boundary of ADR 0023 forbids; (d) has no credentials but is not live and turns the cutover into a race with the copy; (a) holds no Windows credential in Tenko, keeps the controller's side static and read only, and is live within a minute. DNS needs none of these: the zone transfer with NOTIFY is live already.
- **Recommendation: (a); DNS by the existing transfer.**
- **Decided (2026-11-01): (a), the scheduled script pushes with a token scoped to one source; Tenko never holds a Windows credential and never connects to Windows; DNS data comes by AXFR and IXFR with NOTIFY.**

**WT-Q2. What does the mirror carry, how often, and where does the mapping live?**
- Options: (a) every 60 s: scopes, options at every level, reservations and active leases, with policies, filters and superscopes in the loss report, mapped by the script onto the IR; (b) the full `Export-DhcpServer -Leases` XML pushed raw, mapped by a Windows adapter inside Tenko; (c) configuration only, leases left to the renewals.
- Trade-offs: (b) puts a Windows-specific parser in the core and a large document on the wire every minute; (c) gives up the takeover's continuity (the address protection between the switch and each client's rebinding, the INIT-REBOOT answer, the record adoption); (a) keeps the core source-neutral, with the cost of a mapping written in PowerShell and held to the fixture by tests.
- **Recommendation: (a); the exporter is one adapter, Kea, BIND, dnsmasq and OPNsense adapters are its siblings, and nothing in the core assumes Windows.**
- **Decided (2026-11-01): (a).**
- **Amended (2026-11-21):** the exporter as built carries the enabled filter lists with their entries, since Tenko serves a restricted scope; an entry Tenko cannot match, and a reservation an enabled Allow list does not list, go to the loss report. Policies and superscopes stay in the loss report.

**WT-Q3. What does the takeover do?**
- Options: (a) per scope, in the UI and the CLI: convert the mirrored leases to Tenko leases with their remaining time, adopt the transferred A, DHCID and PTR records of mirrored leases and reservations as `dhcp` records with Tenko's DHCID (the proof is the mirrored lease or reservation), activate the scope, record it; the reverse deactivates the scope and leaves the records; (b) today's step 10: delete the Windows-written records and let the renewals write them anew; (c) adopt at the first renewal, when the client proves its identity.
- Trade-offs: (b) leaves every client without a name until it renews; (c) needs no mirror for the records but trusts a renewal from whoever asks first, and a client that never renews keeps a frozen name; (a) keeps every name served throughout, with the mirror as the proof and the engine's rule for the identity a client presents (section 2.8).
- **Recommendation: (a).**
- **Decided (2026-11-01): (a); it replaces step 10's deletion. Today `conflict = protect` refuses any `transfer` record, which is why the adoption is an explicit action.**

**WT-Q4. How are the reservations' names made?**
- Options: (a) a fully qualified name is kept, a bare host name gets the zone, a factory name is kept as it is; (b) every name made a bare label under the zone; (c) names left out, the operator names hosts later.
- Trade-offs: (b) rewrites names the operator chose; (c) loses thirty names the operator typed once; (a) keeps what is there and adds only the zone.
- **Recommendation: (a), with the reading of WT-Q10.**
- **Decided (2026-11-01): (a).**

**WT-Q5. Which profile?**
- Options: (a) Home now, with unsigned RFC 2136 updates from the controllers' addresses by access list, and Hardened after GSS-TSIG; (b) wait for Slice 13 and take over under Hardened at once; (c) Standard now.
- Trade-offs: (b) delays the takeover by Slice 13's 82 builder-days; (c) adds nothing the reference domain needs over Home except stricter defaults the runbook sets per zone anyway; (a) is the runbook's assumption and the footing whose limits section 4 of the runbook documents.
- **Recommendation: (a).**
- **Decided (2026-11-01): (a), Home now; Hardened after GSS-TSIG (Slice 13, WP13.0 to WP13.4 of identity-plan.md, which stays as planned and follows this slice).**
- **Amended (2026-11-05): the Home profile with the access list stays the path of the rehearsal and of a home user without a domain; the owner's own cutover waits for Slice 13's GSS-TSIG and runs under Hardened from the first day, so that secure updates are the integration test and no interim period takes unsigned updates.**

**WT-Q6. How is the takeover rehearsed?**

**WT-Q8. Does the takeover adopt `dynamic` names besides `transfer` ones?**
- Options: (a) `transfer` only, as WT-Q3's text says; (b) `transfer`, and `dynamic` names that carry a DHCID and the mirrored lease's address; (c) also `manual` names with a DHCID.
- Trade-offs: under (a), a name Windows DHCP wrote after the flip (a client new to Windows in the window) or during a reverted takeover is `dynamic` and is refused at the first renewal, which brings step 10's gap back for those names; (b) closes that with the same proof as WT-Q3 (a DHCID at the name means a DHCP server wrote it, and the controllers' access list means only the controllers' services write `dynamic` records); (c) would let a takeover change records an operator made.
- **Recommendation: (b).**
- **Decided (2026-11-05): (b), `transfer` names and `dynamic` names that carry a DHCID and the mirrored lease's address.**

**WT-Q9. What origin do the other transferred records get at the flip?**
- Options: (a) `ad`; (b) `manual`; (c) `transfer` kept on every RRset.
- Trade-offs: (c) refuses Netlogon's hourly registration of every locator record (event 5774 every hour, a changed controller address never registered); (b) is updatable but loses the mark that the record came from AD, which Slice 13's claim rule needs (identity plan section 3.6); (a) is updatable from the access list today and governed by the claim rule later.
- **Recommendation: (a).**
- **Decided (2026-11-05): (a), origin `ad`, updatable from the access list and governed by the claim rule later.**

**WT-Q10. What does "a factory name is kept as it is" mean for a name that is not a valid host name?**
- Options: (a) a valid label gets the zone like any bare name; an invalid one is kept as the IPAM host's name, with no record derived and a loss entry; (b) an invalid one is tidied (`ESP_3A1F2B` to `esp-3a1f2b`) and gets the zone; (c) a factory name is recognized by its pattern and never gets the zone.
- Trade-offs: (b) invents a name nobody chose, and the client keeps registering its own under DDNS anyway; (c) guesses at patterns that change by vendor; (a) is decidable by syntax alone and changes nothing the owner typed.
- **Recommendation: (a), the reading section 2.9 writes.**
- **Decided (2026-11-05): (a).**

**WT-Q11. How long does the mirror token live?**
- Options: (a) within TGL-05 (365 days under Home), with the finding `migrate.mirror.token_expiring` 14 days ahead and a replacement from the mirror card; (b) non-expiring for mirror tokens as an exception to TGL-05.
- Trade-offs: (b) avoids a yearly chore but makes one token class an exception to a never-relaxed rule; (a) keeps the rule and makes the chore visible in time.
- **Recommendation: (a).**
- **Decided (2026-11-05): (a), within TGL-05, with `migrate.mirror.token_expiring` 14 days ahead.**

**WT-Q12. What happens to the DNS Server role on the controllers after the flip?**
- Options: (a) it stays, the controllers holding secondary copies of Tenko's zones (the clients' second DNS server) until a second Tenko node exists; (b) it is removed after the parallel period, as today's runbook does; (c) the AD-integrated zones stay frozen as today's runbook does, without becoming secondaries.
- Trade-offs: (b) leaves one Tenko node as the only server of the AD zones until Phase 5; (c) keeps a stale copy that grows staler; (a) keeps a current copy that answers when the node is down and makes the DNS rollback a conversion with current data (section 2.10), at the cost of keeping the role and converting AD-integrated zones to secondaries (R142).
- **Recommendation: (a).**
- **Decided (2026-11-05): (a), the controllers keep the DNS Server role as secondaries of Tenko's zones until a second Tenko node exists.**

**WT-Q13. Under which identity do the two Windows DHCP servers register their clients' names, before and during the parallel period?**
- Options: (a) one dedicated user account, a member of no privileged group and not of DnsUpdateProxy, set as the DNS credential on both servers (`Set-DhcpServerDnsCredential`); (b) the same account, also a member of DnsUpdateProxy; (c) no credential: each server signs as its controller's computer account.
- Trade-offs: (c) is the default and breaks failover's updates (the partner cannot change a name the other owns on Windows) and, in Tenko's zones, signs as a privileged principal that may change any name, the controllers' locator records included: security last. (b) leaves every name it writes without an owner, so any computer of the realm can take one until the takeover adopts it. (a) gives each name one unprivileged owner that both servers share, and the takeover clears it (section 2.8); its cost is one account whose password lives in both servers, changed by hand. The rehearsal sets up whatever the owner's domain has, so that it rehearses the real state; the recommendation is what the cutover should start from.
- **Recommendation: (a), set on the owner's servers before the mirror is installed; security first, at no cost in performance or features.**
- **Decided (2026-11-20): (a), one dedicated unprivileged user account as the DNS credential on both DHCP servers, not a member of DnsUpdateProxy. The owner's domain already works this way and its scope uses DHCP name protection.**

**WT-Q14. Does the rehearsal still read the owner's own domain?**
- Options: (a) no: the takeover line uses only the lab domain, and the owner's real data is first read by the runbook's step 2 on his own node (secondaries and mirrors that serve nothing, the diff and the prepare), with the DHCID identifier type recorded there before the window; (b) yes: as E77 first had it, a read-only transfer and mirror of the real domain into the lab node for an afternoon.
- Trade-offs: (b) shows the real names and the real DHCID type earlier, at the price of a transfer permission and an exporter task on the real controllers pointed at a lab node, and of real names on a machine whose results are filed in a public repository; (a) touches nothing real until the owner's own node, which reads the same data under the same restrictions, and learns the real DHCID type one step later, still before any client is affected.
- **Recommendation: (a); security first, and step 2 of the runbook gives the same reading without a second copy.**
- **Decided (2026-11-20): (a), the rehearsal reads only the lab domain.**

**WT-Q15. How does an administrator know the scripts are the released ones?**
- The facts (2026-11-20): there is no budget for a code-signing certificate, and the providers' own pages offer no free publicly trusted route for this project: the free program for open source requires a license the OSI approved, and the project's is BUSL-1.1; Microsoft's signing service takes individual developers only in the United States and Canada; the low-cost certificate for open-source developers has no supported path from hosted CI and is revoked for software that is distributed commercially.
- Options: (a) the digest in `SHA256SUMS` and the release's provenance attestation, checked by one documented command (the start forms of section 2.16.1, or the intake's), the file always taken from the release and never from the node, and `SHA256SUMS` signed with the project's own release key once the node's release signatures exist (API-19, [upgrades.md](../upgrades.md)); (b) a certificate of the project's own that each administrator imports once as a trusted publisher; (c) a paid, publicly trusted certificate later, when a budget allows, signed in a release environment limited to tags with a required reviewer and timestamped, with the certificate holder's legal name, which every signature shows, disclosed to the owner first.
- Trade-offs: (b) puts a root the project made into every administration host's trust store, where it could sign any script those hosts then run without a prompt: a wider trust than the one file needs, security last. (c) lets Windows check a signature at every run, but costs money the project does not have, and in the locked-down domains this design is for, where application control enforces script rules, the signature that counts is the organization's own anyway (section 2.16.1). (a) costs nothing, proves through the attestation's signature which release run built the file, and the checks run before anything executes; what it cannot do is have Windows check the file again at each run, which the domain's own signature does where it matters.
- What the script can and cannot check about its own origin: nothing (section 2.16.1); it checks the exporter and the installer it brings along, and the node's version as a compatibility gate.
- **Recommendation: (a) now, by the priority order with the budget as a fact; (c) when a budget exists, as an addition; (b) not. The release refuses to publish the scripts without their digests and attestation. The owner's cutover does not wait for a certificate: his domain verifies at intake and, if it enforces script rules, signs with its own.**
- **Decided (2026-11-20): (a), the digest and the provenance attestation, no certificate and no project root. Without a certificate the chain is as strong as the account that publishes the releases, which gets a hardware security key before the first scripted takeover; the README states that residual.**

**WT-Q16. How do the zones take updates after a scripted flip?**
- Options: (a) secure updates with GSS-TSIG under every profile, the script creating Tenko's computer account of [active-directory.md](../active-directory.md) section 4.1 with a one-time password it generates; (b) by the profile: GSS-TSIG under Hardened, unsigned updates from the controllers' addresses (WT-Q5's footing) under the others; (c) the zone's own mode on Windows carried over: secure only becomes (a), nonsecure and secure becomes the access list.
- Trade-offs: (b) keeps Tenko out of the directory under Home and Standard, but takes updates whose source address can be forged over UDP (`ad.update_spoof`). (a) signs every update and gives each name an owner, at the price that Tenko holds a computer account of the domain, which reads the directory as any domain computer can and reaches further when compromised (WT-Q19; ADR 0026, accepted; WT-Q5 as amended already takes it for the owner's cutover); that account is Tenko's own identity, not a right of the operator's, which is how this plan reads condition 3. (c) asks the operator nothing and, for the reference domain and every domain left on Windows' default, is (a).
- **Recommendation: (c), which is (a) for the reference domain; security first, no new question for the operator.**
- **Decided (2026-11-20): (c), each zone's Windows update mode carried over, with no unsigned fallback for a zone that took secure updates only: such a domain gets no scripted flip until the Kerberos line of [identity-plan.md](identity-plan.md) is complete (section 2.16.1). Under Hardened, raising a zone that took unsigned updates on Windows to secure-only is offered in the change list, off by default, and applied in a later window, so that devices that register unsigned do not stop on the night of the window.**

**WT-Q17. Where does the exporter run during a scripted takeover?**
- Options: (a) one task per DHCP server on a member server, reading its server over RPC with `-ComputerName`, the tokens bound to that host; (b) on each DHCP server as built, with the batch logon right granted to the task's account in the Default Domain Controllers Policy by the script; (c) on the machine that runs the script, a workstation included.
- Trade-offs: (b) puts a task, an account with batch logon and a token on each controller and changes the controllers' policy. (c) stops pushing when the workstation sleeps, so the mirror turns stale in the parallel period, an error finding. (a) keeps the controllers free of anything of Tenko (a member of `DHCP Users` reads all fourteen cmdlets over RPC, measured), at the cost of a parameter in the exporter, a member server that stays on and the DHCP management tools on it. The exporter is also the one Windows process that parses a compromised node's answers: on a member server a flaw there yields an account in `DHCP Users`, on a controller a foothold in the domain's top tier. The mirror host's local administrators could then read the tokens and forge pushes, which the diff and the window's binding guard, and which phase 0 warns about.
- **Recommendation: (a), security first; (b) where the domain has no member server.**
- **Decided (2026-11-20): (a), the task run by a group managed service account where the domain has a KDS root key; (b) stays as the fallback where no member server exists, its batch logon right removed by `-Reverse` and read back. The owner's own domain has no member server today and will have one before his cutover.**

**WT-Q18. Does the script use the administrator's own logon or ask for a credential?** (It changes the owner's decision of 2026-11-20, which named `Get-Credential`.)
- Options: (a) the script runs only elevated, as an account of the domain's administrative tier, on a controller or a privileged access workstation, and uses that logon's Kerberos identity for its sessions: no prompt; (b) the same host and elevation rule, and `Get-Credential` kept for the domain rights.
- Trade-offs: a domain administrator's credential in a less privileged process is readable by malware of that session and fed by a module planted in a user-writable path, so both options require the elevated administrative process. Given that, (b) adds a second copy of the secret in the process's memory and a prompt that is not on the secure desktop, for no right the logon lacks; (a) removes both and one action per sitting. (b) still fits a domain whose administrators sign in to the administration host with an account other than the domain administrator.
- **Recommendation: (a), security first, and one action fewer per sitting.**
- **Decided (2026-11-20): (a); `Get-Credential` is dropped.**

**WT-Q19. Does the owner accept what a compromised node can do as the domain's DNS authority?**
- The residual, in the threat model's words: after the flip and the takeover, a compromised Tenko node is the authority of the AD zones and holds a domain computer account (WT-Q16), which in a typical domain is a short path toward Domain Admins: steering names, relaying a controller's forced NTLM sign-in to certificate web enrollment or to LDAP without signing, requesting service tickets for offline guessing, creating computer accounts up to the quota, answering `wpad` and `isatap` (section 2.16.3). It belongs to replacing AD DNS itself, not to the script.
- Options: (a) accept it, with phase 0's warnings, Tenko's block of `wpad` and `isatap`, and the owner hardening what the warnings name (LDAP signing and channel binding, Extended Protection on web enrollment, the machine account quota at 0, the print spooler off on the controllers, no RC4 for accounts with a service principal name, no certificate template that a domain computer may enroll in with a subject of its choosing, any purpose or write access, no `EDITF_ATTRIBUTESUBJECTALTNAME2` on a certificate authority, no Group Policy Preferences password in SYSVOL) before his cutover; (b) take over without a computer account (WT-Q16 (b)), which removes the account's paths but not the authority's; (c) move DHCP only and leave AD DNS on the controllers.
- **Recommendation: (a): the hardening the warnings name closes the account's paths at no cost to Tenko, and the authority is what the takeover is for; (c) keeps the controllers as DNS servers, the role the owner wants gone.**
- **Decided (2026-11-20): (a), the residual accepted with the countermeasures.**

**WT-Q20. Should the node show the script in a code box?**
- Options: (a) no: the release, by intake or by its page, is the only source, and the node's page names the release and the file in plain words; (b) yes, a code box with the script and its digest on the **Windows takeover** page.
- Trade-offs: (b) saves opening the release page, but a compromised node would serve a script that a domain administrator runs and the digest beside it, which breaks condition 1 and, in a tiered domain, runs content from a lower tier in a domain administrator's session; a root-owned copy on the node fetched over SSH fails for the reasons of section 2.16.1. (a) costs the person one page opened elsewhere.
- **Recommendation: (a), security first.**
- **Decided (2026-11-20): (a), no code, command or digest on any page of Tenko.**
